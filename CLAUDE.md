# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Unreal Engine 5.7 C++ game project (`CellularAutomata.uproject`) implementing a 3D cellular-automata simulation, rendered with `UHierarchicalInstancedStaticMeshComponent` cell instances (one cube mesh instanced per live cell). The gameplay module is `CellularAutomata` (Runtime, Default loading phase).

The project briefly depended on the third-party **VoxelFree** plugin (SDF/marching-cubes voxel terrain engine) but that was dropped and the plugin fully removed — it was built for volumetric terrain, not for placing discrete cell instances, and was unnecessary overhead for this project's needs. Do not reintroduce a `Voxel` module dependency without deliberate reconsideration.

## Build / run

No lint config — it's a standard UE C++ project built through the Unreal toolchain. There *is* a small automation test suite (`Source/CellularAutomata/Private/Tests/AutomataTests.cpp`, whole file under `#if WITH_DEV_AUTOMATION_TESTS`, no extra `Build.cs` dependency), run headless with:

`"C:\Program Files\Epic Games\UE_5.7\Engine\Binaries\Win64\UnrealEditor-Cmd.exe" "<repo>\CellularAutomata.uproject" -ExecCmds="Automation RunTests CellularAutomata" -testexit="Automation Test Queue Empty" -unattended -nopause -nosplash -abslog=<file>`

Four tests, chosen for the places where a bug is both likely and invisible: `Grid.NegativeCoords` (chunk math on negative coordinates — the floor-division trap flagged under `Automata/Grid/`, and generation is centred on the origin so negative coordinates are the norm, plus the "a re-created chunk must not inherit stale ages" guarantee), `Rules.RuleStringRoundTrip` (`Parse → Format → Parse`, range compression, and seven malformed strings that must each be rejected *whole* with a non-empty error), `Compute.CpuGpuParity` and `Compute.GpuBatchParity` (differential tests — they need no known-good answer, only that two implementations agree: CPU against GPU, and one batched dispatch against N single steps, comparing live cells, ages **and** decay stages). The last two are the automated form of the manual check the batching work was verified with, and they carry `EAutomationTestFlags::NonNullRHI` plus their own `GMaxRHIFeatureLevel` check so they report "skipped" rather than fail under `-nullrhi`. Note the whole run costs an editor startup (tens of seconds) — there is no fast inner loop for UE automation tests. Deliberately not covered: anything requiring an actor, a tick or a render — that is where UE tests get expensive and brittle, and it is checked by hand in PIE instead.

  `"C:\Program Files\Epic Games\UE_5.7\Engine\Build\BatchFiles\Build.bat" -projectfiles -project="<repo>\CellularAutomata.uproject" -game -rocket -progress`

## Architecture

Actor/controller composition, not a monolithic GameMode:

- **`AAGameMode`** (`Core/GameMode/AGameMode.*`) — minimal; only wires `PlayerControllerClass` to `AGamePlayerController`. Note the doubled `A` prefix: the UE Actor-class convention (`A`) plus the class's own name (`AGameMode`) yields `AAGameMode`. `DefaultEngine.ini`'s `GlobalDefaultGameMode` points at this class.
- **`AGamePlayerController`** (`Core/PlayerController/GamePlayerController.*`) — owns the camera. No spline-following camera anymore (removed — see below); just toggles between gameplay input (`FInputModeGameOnly`, pawn input enabled) and UI input (`FInputModeGameAndUI`, cursor shown, pawn input disabled) via `SetCameraControlEnabled()`, and on `BeginPlay` sets FOV (viewmode is no longer forced here — see hotkeys below). `SetupInputComponent()` binds the project's testing hotkeys, all resolving the `AAutomataOrchestrator` in the world via `UGameplayStatics::GetActorOfClass` (except the camera-only ones) — built with Enhanced Input (`UInputAction`/`UInputMappingContext` constructed at runtime via `NewObject`, not saved as `.uasset` content, since a handful of project-wide hotkeys doesn't need dedicated assets), all mapped on one shared `SimulationMappingContext` — all except **P**: **P** (`OnToggleSimulation()`) calls `Start()`/`Stop()` depending on `IsSimulationRunning()`, and is deliberately **not** routed through Enhanced Input at all — it's caught in an `InputKey()` override on the controller, which fires immediately per raw OS key message (`WM_KEYDOWN`, `IE_Pressed` only, so no repeat-on-hold). Enhanced Input evaluates its triggers once per `Tick` by sampling the key's current down/up *level*, so under heavy frame lag (large `AddInstances`/HISM cluster-tree rebuilds at high cell counts) a quick press-and-release of P could land entirely inside one long frame gap and never register as a transition — the pause got harder to catch the worse the lag became, which defeated the whole point of a pause key; `InputKey()` sees every press regardless of frame length. The other hotkeys stay on Enhanced Input — they're either less lag-critical or hold-style bindings that genuinely want per-tick evaluation; **F** (`OnFastStepPressed()`/`OnFastStepReleased()`, bound to `ETriggerEvent::Started`/`Completed`) — a bare press (no Shift) calls `Next()` once, which now advances **`StepsPerRender` generations per press** (the same value tuned via T/G), computed off the game thread, rendering only the final one (see `Next()` under the orchestrator bullet below); if Shift is down at the moment F is pressed (checked via `IsInputKeyDown(EKeys::LeftShift)`, not a separate Enhanced Input binding), it instead calls `AAutomataOrchestrator::StartFastStep()` — a **hold** mode, independent of `bSimulationRunning` and mutually exclusive with it (`Start()` refuses while `IsFastStepActive()`, and `StartFastStep()` refuses while Play is running), that paces steps by `Speed` exactly like continuous Play via the same `bFastStepActive` branch in `Tick()` (ahead of the `bSimulationRunning` branch, sharing `TimeSinceLastStep`/`StepAsync()`/chunked-render with zero duplicated logic) — and stops the instant F is released (`OnFastStepReleased()` calls `StopFastStep()` only if `IsFastStepActive()`). Bound to `Started`/`Completed` rather than `Triggered` specifically so a bare hold of F doesn't repeat `Next()` every frame (that was the pre-Shift-hold-mode behavior and confused continuous auto-stepping with a single step). **R** (`OnResetSimulation()`) calls `ResetToInitialState()` — rebuilds the grid from `InitialStateCells` (ages reset to 0), the shared "initial pattern" populated by whichever of `StartFromSelection()` (Enter), `LoadStateFromFile()` (Ctrl+O) or `GenerateRandom()` itself ran most recently (see the `InitialStateCells`/`ResetToInitialState()` paragraph below for the full picture), so an isolated glider/oscillator, a loaded save, or just the last random spawn can all be replayed from their exact starting shape. Deliberately *not* gated on `IsSimulationRunning()` since both paths guard their own race with `bStepInProgress`. **R is caught in the same raw `InputKey()` override as P, not through Enhanced Input** — for exactly the reason described there (a quick press-and-release landing inside one long frame gap is never seen by Enhanced Input's per-tick level sampling, and R is pressed precisely when the sim is lagging hardest), and it goes through a *deferred* path on top: when a background step is in flight, `ResetToInitialState()` sets `bResetToInitialStatePending` and returns instead of refusing, and `ApplyStepResult()`/`Next()`'s completion performs the reset once the `Grid` race is over. Those were two independent bugs with one shared symptom ("R doesn't always work") — the input-sampling one and the silently-dropped-during-a-step one — fixed separately; **1**/**2** (`OnSetLitMode()`/`OnSetUnlitMode()`) toggle `VIEWMODE LIT`/`VIEWMODE UNLIT` via console command — the game used to force Unlit unconditionally on `BeginPlay` (to skip lighting cost when rendering large numbers of instanced automaton cells), but now starts lit by default and Unlit is an opt-in hotkey instead; **Left Shift** (held) — `OnSpeedBoostStarted()`/`OnSpeedBoostEnded()` (bound to `Started`/`Completed`) scale the possessed `ADefaultPawn`'s `UFloatingPawnMovement::MaxSpeed` by `AAutomataOrchestrator::CameraSpeedMultiplier` for faster flying while held, restoring the original speed on release — `BaseFlySpeed` caches that original value on first press (guarded by `<= 0.0f` so a stray repeated `Started` can't cache an already-boosted speed). `CameraSpeedMultiplier` lives on the orchestrator rather than the controller/pawn so a designer tunes it from the same Details panel as the rest of the simulation; **Z** (`OnToggleChunkedRender()`) flips `AAutomataOrchestrator::bEnableChunkedRender` via `SetChunkedRenderEnabled()`/`IsChunkedRenderEnabled()` — there's no automatic cell-count threshold for chunked rendering (an earlier `ChunkedRenderCellThreshold` property was removed), it's purely a manual on/off toggle now; **X** (`OnCycleChunkedRenderOrder()`) advances `AAutomataOrchestrator::ChunkedRenderOrder` to the next `EChunkedRenderOrder` value by calling `CycleChunkedRenderOrder()` (wraps back to `Sequential` after the last value) — see `EChunkedRenderOrder` under Chunked rendering below for what each order looks like; **V** (`OnToggleWaitForChunkedRenderToFinish()`) flips `AAutomataOrchestrator::bWaitForChunkedRenderToFinish` via `SetWaitForChunkedRenderToFinish()`/`IsWaitingForChunkedRenderToFinish()` — see `bWaitForChunkedRenderToFinish` under Chunked rendering below for the two interrupt-vs-wait behaviors this switches between; **B** (`OnToggleCellCulling()`) flips `AAutomataOrchestrator::bEnableCellCulling` via `SetCellCullingEnabled()`/`IsCellCullingEnabled()` — see `bEnableCellCulling` under `CellCullStartDistance`/`CellCullEndDistance` below; **C** (`OnToggleRenderCullVolume()`) flips `bEnableRenderCullVolume` — see `ARenderCullVolume` under `Automata/Rendering/` below; **H** (`OnToggleGhostShape()`) flips `bEnableGhostShape` via `SetGhostShapeEnabled()`/`IsGhostShapeEnabled()` — see the Ghost Shape paragraph there too; **N** (`OnNewSeed()`) calls `AAutomataOrchestrator::NewSeed()` — re-rolls `Seed` and re-seeds the grid, i.e. the "show me a different one" counterpart to **R**, which replays the *same* `InitialStateCells` pattern. **Caught in the same raw `InputKey()` override as P and R, not through Enhanced Input, and deferred through `bNewSeedPending` the way R is through `bResetToInitialStatePending`** — it had exactly the same two independent sources of dropped presses as R did (per-tick Enhanced Input level sampling missing a short press inside one long lagged frame, plus a silent refusal while a background step holds `Grid`), and for the same reason: a re-roll is pressed precisely when the grid has grown big and ugly, i.e. when the lag is worst. The two pending flags are mutually exclusive (each clears the other), since N and R want incompatible things from the same `Grid` — last press wins rather than whichever flag happens to be checked first. `Seed` is deliberately re-rolled only at the moment the deferred re-seed actually runs, not when the flag is raised, so repeated presses during one long step burn one seed rather than several unseen ones; **K** (`OnMoveCullVolumeToSelection()`) teleports the cull volume onto the current selection (`MoveCullVolumeToSelection()`) and **L** (`OnSelectCellsInCullVolume()`) selects every alive cell inside it (`SelectCellsInCullVolume()`, with the same Shift/Ctrl combine modifiers as a marquee drag) — the two together make the cull box usable without the viewport gizmo: select a cell, K to bring the box there, L to grab everything it now contains; **=/NumPad+** and **-/NumPad-** (`OnIncreaseSpeed()`/`OnDecreaseSpeed()`, both bound to `Triggered`, so holding repeats) call `AAutomataOrchestrator::AdjustSpeed(±SpeedAdjustStep)` to nudge `Speed` up/down by a fixed `0.5` step, clamped to `[0.1, 100.0]` inside `AdjustSpeed()` itself — deliberately wider than `Speed`'s own `UIMax = "10.0"` metadata, since that only caps the Details-panel slider, not a hard `ClampMax`; **Home** (`OnFrameAllCells()`) resolves the orchestrator and delegates to the public `AGamePlayerController::FrameAllCells(AAutomataOrchestrator*)`. It is a public method rather than a private handler because `ResetToInitialState()` used to call it through `GamePC` at the end of every R press — that auto-framing was **removed** (R now only rebuilds the pattern and leaves the camera exactly where it was, since being yanked to a framing distance on every reset fought with flying around a structure), so today the only caller is the explicit Home press. `FrameAllCells()` moves the possessed pawn along its *current* view direction (viewing angle unchanged, only distance) so the whole live-cell set fits in frame — `AAutomataOrchestrator::ComputeAliveCellsBounds()` scans `GetAliveCells()` once for a world-space AABB (via `GridToWorld()` on the min/max cell coordinates, expanded by half a `CellSize` since `GridToWorld()` gives cell *centers*) and returns its center and bounding-sphere radius (`FrameAllCells()` itself returns `false` and does nothing if the grid is empty/uninitialized or the pawn/camera aren't ready yet); it then computes `Distance = Radius / sin(FOV/2)` (the exact distance at which a sphere of that radius exactly fills the frustum half-angle, using `PlayerCameraManager->GetFOVAngle()`), multiplies by a small `FramingPadding` (`1.1`) so cells don't touch the frame edge, and sets the pawn's location to `Center - CameraRotation.Vector() * Distance` via `PlayerCameraManager->GetCameraRotation()`; **T**/**G** (`OnIncreaseStepsPerRender()`/`OnDecreaseStepsPerRender()`, bound to `Triggered` like `+`/`-` for Speed, so holding repeats) call `AAutomataOrchestrator::AdjustStepsPerRender(±1)` to nudge `StepsPerRender` (see `StepsPerRender` under Chunked rendering below), clamped to a minimum of `1` inside `AdjustStepsPerRender()` itself (originally mapped to `[`/`]` but rebound by hand during testing — see `SetupInputComponent()` for the current mapping). **Tab** (`OnToggleSelectionMode()`, originally C but rebound by hand during testing) toggles **one shared mouse-interaction mode** covering both cell selection (see the dedicated section below, after `AgeMaterials`) and HUD interaction — a separate H hotkey for "show the cursor so I can click the HUD" existed briefly and was folded into Tab, since both wanted the exact same state (`SetCameraControlEnabled(false)`: camera stopped, cursor shown, controller input still live) and having two keys toggling one thing independently could leave it half-on. H was later reused for Ghost Shape. While active, **left mouse button** drag-selects a screen-space rectangle of cells (**Shift**+drag adds to the existing selection, **Ctrl**+drag removes from it — see `ESelectionCombineMode` in that section), **I** (`OnInvertSelection()`) inverts the selection against the alive-cell set, **Delete** (`OnDeleteSelectedCells()`) kills the selected cells in place without resetting the simulation, and **Enter** (`OnExtractSelection()`) launches the current selection as a fresh starting state; **M** (`OnBakeCellsToMesh()`) bakes the current state (or the selection, if one exists) into a single hollow mesh and unloads the cells from memory — see the Baking paragraph below; **S**/**O** (`OnSaveOrSaveAs()`/`OnLoadState()`) — Ctrl+S/Ctrl+Shift+S save/save-as, Ctrl+O loads, to/from a `.casave` file (see the `Automata/Persistence/` bullet below for the format and semantics) — mapped on the raw `S`/`O` keys *without* a modifier (Enhanced Input has no way to require Ctrl directly in a key mapping), so the handlers themselves check `IsInputKeyDown(EKeys::LeftControl/RightControl)` and silently return if Ctrl isn't held (bare `S` still drives `ADefaultPawn` camera movement, unaffected), then branch on Shift to pick `SaveState()` (Ctrl+S) vs `SaveStateAs()` (Ctrl+Shift+S). **Why hotkeys and not just the `CallInEditor` buttons**: clicking a `CallInEditor` button in the Details panel during PIE is unreliable — if the World Outliner still has the non-PIE (persistent-level) copy of the actor selected rather than its PIE-world duplicate, the click invokes the function on the frozen editor-world instance, whose `Tick()` never runs (`AActor::TickActor` early-returns when `TickType == LEVELTICK_ViewportsOnly`, which is how the engine ticks actors outside PIE) — so e.g. continuous Play silently never begins, with no error. Hotkeys sidestep this entirely since key input always arrives via the currently-possessing (PIE-world) `PlayerController`. Requires the `EnhancedInput` module (see below).
- **`AAutomataOrchestrator`** (`Orchestration/AutomataOrchestrator.*`) — the top-level conductor, placed in the level as an Actor. Root component is `CellsMeshHierarchical` (`UHierarchicalInstancedStaticMeshComponent`); `CellsMeshFlat` (`UInstancedStaticMeshComponent`) is attached as its child. Both are created unconditionally in the constructor and exist for the actor's whole life, though they no longer receive instances directly themselves — `CellMeshComponentType` (`ECellMeshComponentType::Instanced`/`HierarchicalInstanced`, default `HierarchicalInstanced`) now picks the class for the `AgeMeshComponents` pool instead (see `GetActiveCellsMeshComponent()` under `Automata/Rendering/` below, and `AgeMaterials` there for why); there is no separate scene-root or camera spline (that system was fully removed; `AGamePlayerController` no longer has `StartSplineMovement`/`StopSplineMovement`/spline-following `Tick`). Owns simulation parameters (`GridSize`, `ChunkSize`, `Amount`, `Seed`, `SpawnRadius`, `ClusterFactor`, `Speed`, `CameraSpeedMultiplier`, `CellMesh`/`AgeMaterials`/`CellSize`/`CellMeshComponentType`, `bEnableChunkedRender`/`ChunkedRenderCellsPerFrame`/`ChunkedRenderOrder`/`StepsPerRender`, `BirthCounts`, `SurvivalCounts`, `Neighborhood`) exposed as `CallInEditor` UFUNCTIONs (`Start/Pause/Resume/Stop/Next/Clear/GenerateRandom/NewSeed`) so designers can drive the sim from the Details panel. `BeginPlay` first wipes any instance state duplicated from the editor world (`ClearAllCellInstances()`/`ClearBakedMesh()`/`ClearGhostShape()` — PIE copies the placed actor *with* whatever instances a pre-PIE `GenerateRandom()`/`Next()` click left on its components, and the normal render path doesn't clear orphaned ones), then wires up the player controller, rebuilds the component pools, calls `GenerateRandom()`, and finally shows the HUD via `InitializeHUD()`. That last call moved here **from `PostActorCreated()`** deliberately: that callback fires on any actor creation, including merely placing the actor in the editor outside PIE, and the HUD widget must never pop up outside a real game session — `BeginPlay()` is guaranteed PIE/game only. `NewSeed()` re-rolls `Seed` via `FMath::Rand()` and calls `GenerateRandom()`. A private `CreateGrid()` helper (always builds an `FDenseCellGrid` from `CellSize`/`ChunkSize` — see `Automata/Grid/` below) is shared by `GenerateRandom()`/`ResetToInitialState()`/`StartFromSelection()` (fresh grid) and `StepAsync()` (next-generation buffer) — `Next()`'s background loop is the one exception: it builds its intermediate generation buffers inside the background lambda from game-thread-snapshotted `CellSize`/`ChunkSize` copies, since `CreateGrid()` reads live UPROPERTYs a background thread must not touch (see `Next()` below). `GenerateRandom()`/`Next()`/`StepAsync()`→`ApplyStepResult()` all log generation-or-step and render timing (`FPlatformTime::Seconds()`) as an ad-hoc profiling baseline ahead of scaling to much larger cell counts. `Next()` builds a fresh `FCellularAutomatonRule` from `BirthCounts`/`SurvivalCounts`/`Neighborhood` every call (so Details-panel edits take effect immediately, no caching) and advances **`StepsPerRender` generations per call** (the same value the T/G hotkeys tune; at `1` it's the original single step), rendering only the final generation in one immediate shot via `RenderGridImmediate()` — intermediate generations never hit the screen, mirroring how continuous Play skips renders under `StepsPerRender`. The whole multi-generation loop runs on the thread pool exactly like `StepAsync()` (it used to be fully synchronous on the game thread, which froze the screen for the entire computation once multiplied by `StepsPerRender`): rule/strategy/`CellSize`/`ChunkSize` are snapshotted on the game thread before dispatch (intermediate generation buffers are built *in* the background lambda from the snapshotted values, constructing `FDenseCellGrid` directly rather than via `CreateGrid()`, which reads live UPROPERTYs), `bStepInProgress` guards the whole flight, and the completion hands off to the game thread to swap `Grid` and render — so the only remaining hitch on F is the render itself, same as Play. **Still stub**: `Clear`. Cell storage/rendering/simulation is delegated to the `Automata/` subsystem (below), not implemented inline.

Continuous play/stop: `Start()` (also acts as the "Play" entry point) generates a grid if none exists yet, resets the tick accumulator, sets `bSimulationRunning = true`, and calls `SetActorTickEnabled(true)`. `PrimaryActorTick.bCanEverTick = true` but `bStartWithTickEnabled = false` in the constructor, so the actor doesn't tick at all until `Start()` explicitly enables it. `Tick()` accumulates `DeltaTime` and, once it crosses `1/Speed` seconds (recomputed each tick, not cached, so editing `Speed` in the Details panel takes effect immediately), calls `StepAsync()` — **not** `Next()` — provided no background step is already in flight (`!bStepInProgress`) and no render hand-off is pending (`!bRenderHandoffPending`, see `StepsPerRender` below); if either is true, that tick is skipped rather than queued. `Stop()` clears `bSimulationRunning`, calls `FinishChunkedRenderImmediately()` (see Chunked rendering below — snaps any in-progress reveal, including a pending hand-off, straight to its final state instead of leaving it frozen once ticking stops), then disables ticking; it does **not** reset the grid (that's `Clear()`'s job, still a stub).

**`StepAsync()` — off the game thread, so continuous Play doesn't stall the camera/UI**: `Next()` (the manual `CallInEditor` button) originally stayed fully synchronous, but during continuous Play, that same synchronous cost was landing straight in `Tick()`, blocking the game thread (and therefore camera movement/input) for as long as the step took, which got severe at scale (multi-second stalls once the grid grew past hundreds of thousands of cells) — `StepAsync()` was the fix for Play, and `Next()` itself later moved to the same background-dispatch pattern too once it started computing `StepsPerRender` generations per press (see the orchestrator bullet above; the freeze that was tolerable for one step wasn't for ten). `StepAsync()` fixes this: on the game thread it first builds `FCellularAutomatonRule` from `BirthCounts`/`SurvivalCounts`/`Neighborhood`, a compute strategy via `CreateComputeStrategy()` (picks `FCpuComputeStrategy`/`FGpuComputeStrategy` per `ComputeMethod` — see `Automata/Simulation/` below), and a fresh `NextGridBuffer` via `CreateGrid()` (all three read Details-panel `UPROPERTY`s, so this snapshot has to happen before handing off — a background thread must never race a Details-panel edit), sets `bStepInProgress = true`, then dispatches `ComputeStrategy->Step(*Grid, *NextGridBuffer, AutomatonRule)` onto `Async(EAsyncExecution::ThreadPool, ...)` (`ComputeStrategy`, a `TUniquePtr`, is captured by move into the lambda exactly like `NextGridBuffer`). The CPU strategy's internal `ParallelFor` (see `Automata/Simulation/` below) still runs fine nested inside this — the calling thread is now a thread-pool worker instead of the game thread, so the game thread is free the whole time. **One dispatch is not necessarily one generation**: `StepAsync()` asks the freshly built strategy `SupportsStepBatching(Rule)` and, when it says yes (GPU, non-Generations rule), computes `StepsPerRender` generations inside that single background dispatch via the `StepBatch()` loop — the same loop and the same skip-`ComputeAges()`-when-`> 1` rule as `Next()`, holding the previous generation alive in a local `TUniquePtr` while the next is computed into a fresh buffer (built in the background from game-thread-snapshotted `CellSize`/`ChunkSize`, same as `Next()`). When it says no — the CPU strategy — `BatchGenerations` stays 1 and the previous rhythm is preserved exactly, render-skipping counter and all; collecting generations into one long block there would be identical work with coarser pacing and a longer-held `bStepInProgress`, i.e. pure loss. **The loop also breaks out the moment `StepBatch()` reports it advanced only one generation**, for the same reason applied dynamically: `SupportsStepBatching()` is answered once per dispatch, but whether a batch actually fits is decided inside `StepBatch()` from the current AABB volume, which grows with the grid. Once that volume passes the batch ceiling the batch is trimmed to 1, and without the early break the loop would grind `StepsPerRender` single steps inside one dispatch — the same work as one multi-second block, holding `bStepInProgress` (which gates R and regeneration) throughout and interrupting the chunked reveal. Observed live at ~11M live cells: one such dispatch took 7.7 s. Correspondingly `LastDispatchGenerations` is written in `ApplyStepResult()` from what actually happened, not in `StepAsync()` from what was planned — otherwise a trimmed batch would make `Tick()` wait `StepsPerRender / Speed` for a single computed generation, slowing the simulation by exactly that factor. Correspondingly, `Tick()` paces dispatches at `LastDispatchGenerations / Speed` rather than `1 / Speed`, so `Speed` keeps meaning *generations* per second instead of silently becoming *dispatches* per second once batching engages.

When the background lambda finishes, it hands off to `AsyncTask(ENamedThreads::GameThread, ...)`, which calls `ApplyStepResult()` — swaps `Grid` and immediately clears `bStepInProgress` (deliberately at the *top* of the function, right after the swap, not at the end — its scope is narrowed to exactly "a background `Step()` is reading `*Grid`", nothing about rendering) before deciding whether/how to render (see `StepsPerRender` under Chunked rendering below); `Next()` and `GenerateRandom()` both check `bStepInProgress` and refuse (with a warning log) to run while a background step is outstanding — otherwise a manual click during Play could swap `Grid` out from under the background thread mid-read. The game-thread→background handoff captures `this` only as a `TWeakObjectPtr` for the completion callback (guards against the actor being destroyed — e.g. level unload — while a step is in flight; the background lambda itself never touches `this` at all, only the pre-snapshotted rule/grid pointers).

**Chunked rendering — spreads `AddInstances` across multiple frames for huge grids**: even with `StepAsync()` moving the simulation step off the game thread, `Renderer->Render()`'s own `AddInstances` call is still synchronous and still runs on the game thread — profiling showed it alone taking tens to hundreds of milliseconds once the grid grows past a few hundred thousand live cells, which is enough to stall the camera for a visible frame even though the step itself no longer does. `ApplyStepResult()` only takes this path for continuous Play (`StepAsync`'s completion), gated purely by `bEnableChunkedRender` — no automatic cell-count threshold; it's a manual on/off switch (Details panel or the **Z** hotkey, see `AGamePlayerController::OnToggleChunkedRender()` above) — `Next()`/`GenerateRandom()` always render the whole grid in one shot, since spreading a single deliberate manual action across frames would hurt responsiveness rather than help it. When chunking triggers, the shared `RenderCurrentGrid()` helper (used by both `ApplyStepResult()`'s normal path and the deferred hand-off below) calls `Renderer->BeginRender(*Grid, ChunkedRenderOrder, CameraLocation)` (builds the full `TArray<FTransform>` and clears the component once, but adds nothing yet) and sets `bChunkedRenderInProgress = true` — `bStepInProgress` is unaffected (already cleared, see `StepAsync()` above). `Tick()` then calls `AdvanceChunkedRender()` every frame — regardless of `bSimulationRunning`, so a reveal already in progress finishes even if `Stop()` is called mid-way — which calls `Renderer->AdvanceRenderChunk(ChunkedRenderCellsPerFrame)` to add the next slice of the pre-built transforms; once the whole array has been added, it clears `bChunkedRenderInProgress` and logs how many frames the reveal took. `FInstancedMeshCellGridRenderer::Render()` itself is implemented as `BeginRender(Grid, EChunkedRenderOrder::Sequential, FVector::ZeroVector)` (order is irrelevant for a one-shot render — everything lands in the same frame regardless) followed by one unbounded `AdvanceRenderChunk()` call, so the one-shot and chunked paths share the same transform-building code without duplication.

**`EChunkedRenderOrder` — which order live cells appear in across those frames** (`Automata/Rendering/ChunkedRenderOrder.h`, its own header like `ENeighborhood`): `AAutomataOrchestrator::ChunkedRenderOrder` picks it, rebuilt/read fresh on every `BeginRender()` call, no caching — same convention as `ComputeMethod`/`FCellularAutomatonRule`. `FInstancedMeshCellGridRenderer::BeginRender()` reorders the `TArray<FIntVector>` from `GetAliveCells()` (cheaper to permute than the built `FTransform`s) before building transforms, timed as `FRenderTimings::ReorderSeconds`: **`Sequential`** (default) — no-op, `GetAliveCells()`'s own order, which for `FDenseCellGrid` is chunk-by-chunk (`TMap<FIntVector, FChunk>` iteration order), so the reveal visibly fills one spatial blob at a time before moving to the next; **`SequentialReversed`** — `Algo::Reverse` of the same order; **`Shuffled`** — one `Algo::RandomShuffle` — each frame's slice becomes a uniform-random sample of the whole grid, so the overall silhouette is visible almost immediately and subsequent frames just increase density, rather than filling blob-by-blob; **`DistanceFromCameraNearFirst`**/**`DistanceFromCameraFarFirst`** — `Algo::Sort` by squared distance from `GamePC->PlayerCameraManager->GetCameraLocation()` (`FVector::ZeroVector` if `GamePC`/its camera manager isn't set yet), ascending or descending; **`FromCenterOutward`** — `Algo::Sort` by squared distance from the midpoint of the current alive-cell AABB (computed fresh from `AliveCells` each call, not from `FDenseCellGrid`'s internal chunk grid, so the renderer stays grid-agnostic) — reveal "grows" outward from the grid's own center regardless of camera position. Switchable live via the **X** hotkey (`AGamePlayerController::OnCycleChunkedRenderOrder()` → `CycleChunkedRenderOrder()`, cycles through the enum and wraps) or directly in the Details panel.

**`bWaitForChunkedRenderToFinish` — interrupt-and-restart vs. wait-for-completion when a new generation outruns the reveal**: by default (`false`), if a new generation finishes computing while the previous chunked reveal is still spreading across frames, `ApplyStepResult()` doesn't wait for it — it immediately calls `RenderCurrentGrid()` again, which rebuilds `PendingTransforms` from scratch via `BeginRender()` on the new `Grid`, so the undrawn tail of the previous reveal simply never reaches the screen (this is the **only** behavior that existed before this property was added, and remains the default). Setting it to `true` instead gates *stepping itself*, not rendering: in `Tick()`, `bBlockedByChunkedRender = bWaitForChunkedRenderToFinish && bChunkedRenderInProgress` is added to both the `bSimulationRunning` and `bFastStepActive` step-dispatch conditions, so the next `StepAsync()` (computing the next generation) simply doesn't fire while a reveal is still in progress — `TimeSinceLastStep` keeps accumulating meanwhile, so the step fires on the very next `Tick()` once `AdvanceChunkedRender()` (called unconditionally earlier in the same `Tick()`) finishes the reveal, no explicit hand-off flag needed. Because stepping is blocked at the source, `ApplyStepResult()`'s `if (bChunkedRenderInProgress)` interrupt branch is never actually reached in this mode — the reveal is always already finished by the time a new generation is ready to render. This deliberately gates *computing* the next generation, not just its render, matching "wait for the drawing to finish, then reset/draw the new state, and only then compute the next one." Switchable live via the **V** hotkey (`AGamePlayerController::OnToggleWaitForChunkedRenderToFinish()` → `SetWaitForChunkedRenderToFinish()`/`IsWaitingForChunkedRenderToFinish()`) or directly in the Details panel — unlike `ChunkedRenderCellsPerFrame`, not gated by `bEnableChunkedRender`'s `EditCondition`, so it stays visible as a pre-configurable default the same way `ChunkedRenderOrder` does.

**`StepsPerRender` — computing generations ahead of the display, without rendering every one**: at large cell counts, even chunked `AddInstances` costs real time, and showing every single generation isn't necessary — `StepsPerRender` (default `1` = render every generation, current behavior) lets `ApplyStepResult()` skip rendering for `StepsPerRender - 1` out of every `StepsPerRender` computed generations, only calling `RenderCurrentGrid()` once the counter (`StepsSinceLastRender`, reset in `GenerateRandom()`/`Start()`/`StartFastStep()` for a clean count on every fresh run) reaches the threshold. `ApplyStepResult()` takes how many generations its dispatch advanced and steps `StepsSinceLastRender` — as well as `GenerationCount` and the ghost-shape counter — **by that count rather than by one**, which is what makes the batched path (see `StepAsync()` above) need no special case at all: a dispatch that lands a full batch reaches the threshold through the very same condition and renders; skipped generations just log a "рендер пропущен (X/Y)" line and return immediately, so `Tick()` can dispatch the next `StepAsync()` right away (paced only by `Speed`, same as always) — this is exactly what narrowing `bStepInProgress`'s scope (see `StepAsync()` above) enables: computing ahead no longer waits on `bChunkedRenderInProgress`. This deliberately caps how far ahead the simulation can get to **at most one batch** past what's on screen: if the `StepsPerRender`-th generation finishes computing while the *previous* one's chunked reveal hasn't finished trickling in yet, `ApplyStepResult()` doesn't interrupt that reveal (which would abandon its progress and restart from scratch) — instead it sets `bRenderHandoffPending = true` and returns, and `Tick()`'s dispatch condition also checks `!bRenderHandoffPending`, so no further stepping happens until the hand-off completes. `AdvanceChunkedRender()` checks `bRenderHandoffPending` right after finishing a reveal and, if set, immediately calls `RenderCurrentGrid()` for the (by-then possibly even more current) `Grid` and clears the flag — at which point `Tick()` is free to start the next batch. `FinishChunkedRenderImmediately()` (`Stop()`'s helper, see above) does the same hand-off check before its own flush loop, so a pending generation is never left permanently unrendered just because Play was stopped mid-wait. `GenerateRandom()` ignores `StepsPerRender` entirely, and both it and `Next()` always render immediately and in full, ignoring `bEnableChunkedRender`'s spreading — but `Next()` *uses* `StepsPerRender` differently than Play does: rather than skipping renders between background steps, it computes all `StepsPerRender` generations in one background batch per press and renders only the last (see the orchestrator bullet above) — same net "generations per render" ratio, different mechanism.

**Correctness note on `GamePC`**: `AGamePlayerController* GamePC` is a `UPROPERTY(Transient)`, not a raw pointer — this matters specifically because of Live Coding. Reinstancing after a hot patch during an active PIE session only copies `UPROPERTY`-tagged fields from the old instance to the new one; a plain C++ member survives as uninitialized garbage (not `nullptr`), and `BeginPlay()` — the only place that populates `GamePC` — does not re-run on reinstancing. A raw-pointer `GamePC` therefore silently held garbage after any Live Coding patch made during PIE, and `Pause()`/`Resume()` dereferencing it segfaulted (`Access violation`) the next time either was called, crashing the whole Editor process. Fixed by making it a `UPROPERTY` (so reinstancing either preserves it correctly or resets it to `nullptr`) plus explicit null checks in `Pause()`/`Resume()` that log a warning and return instead of crashing when `GamePC` isn't set yet (e.g. before `BeginPlay`/outside PIE). Any other raw non-`UPROPERTY` `UObject*` member added to `AAutomataOrchestrator` (or any `UCLASS` in this project) in the future is a candidate for the same bug.
- **`Automata/Grid/`** — `FCellGrid` (`CellGrid.h`, abstract, plain C++ not `UObject`): stores live cells addressed by integer `FIntVector` coordinates, decoupled from rendering. `GetAliveCells`/`SetAlive`/`Clear`/`Num` are pure virtual; `GridToWorld(FIntVector)` is **virtual with a default cubic-lattice implementation** (`Cell * CellSize`) — deliberately virtual so a future non-cubic topology (e.g. hex) can override just the coordinate-to-world math without touching storage or rendering. `FDenseCellGrid` (`DenseCellGrid.*`, chunked: space is divided into fixed-size cubic chunks — default `ChunkSize=16`, i.e. 4096 cells — each a packed `TBitArray`; chunks live in a sparse `TMap<FIntVector, FChunk>` and are lazily created on first live cell / pruned when they empty out, so memory scales with occupied volume, not a fixed upper bound) is the sole concrete implementation, unconditionally constructed by `CreateGrid()` from `CellSize`/`ChunkSize`. An earlier `FSparseCellGrid` (`TSet<FIntVector>`-backed) existed alongside it, selectable via an `AAutomataOrchestrator::GridStorageStrategy` enum property — both were removed to simplify the storage layer down to one implementation; if a sparse/scatter-friendly storage is ever needed again, reintroducing it as a second `FCellGrid` subclass is straightforward since the interface is already storage-strategy-agnostic everywhere else (`FCpuComputeStrategy`/`FGpuComputeStrategy`/`FInstancedMeshCellGridRenderer` only ever go through `GetAliveCells()`/`SetAlive()`/`GridToWorld()`). **Correctness note if touching `FDenseCellGrid`**: chunk-coordinate math needs real floor-division/positive-modulo helpers (defined file-local in `DenseCellGrid.cpp`) because cell coordinates routinely go negative (sphere-centered generation) and `FMath::DivideAndRoundDown` is *not* floor division for integers (it truncates toward zero). Chunk granularity is intentionally the unit future CPU/GPU per-chunk dispatch would parallelize over — not implemented yet. `FCellGrid` also declares `GetAge(FIntVector)`/`SetAge(FIntVector, uint8)` — a per-cell saturating byte counting how many consecutive generations that cell has survived (`0` = just born), used by `AgeMaterials` rendering (see `Automata/Rendering/` below). `FDenseCellGrid::FChunk` stores this as a parallel `TArray<uint8> Ages` alongside `Bits`, indexed identically via `CellToLocalIndex()` — zero-initialized on lazy chunk creation and wiped wholesale (along with the rest of the chunk) when a chunk empties out and gets pruned, so a cell reborn later in a freshly-recreated chunk always starts at Age 0, never inheriting stale history. Age is deliberately **not** computed inside either compute strategy — `Automata/Simulation/CellAging.h/.cpp`'s `CellAging::ComputeAges(const FCellGrid* OldGrid, FCellGrid& NewGrid)` is a separate post-`Step()` pass, called from `Next()` and from `StepAsync()`'s background lambda right after `ComputeStrategy->Step(...)`, that diffs every alive cell in `NewGrid` against `OldGrid` (`Age = OldGrid->GetAge(Cell)+1` if it was already alive there, else `0`) purely through the public `FCellGrid` interface — this means `FCpuComputeStrategy`, `FGpuComputeStrategy`, and the `.usf` shader needed **zero changes** to support aging. `GenerateRandom()` needs no `ComputeAges()` call at all — a freshly created grid's chunks zero-init `Ages` on their own, so newly spawned cells are already Age 0 for free. Safe to fully parallelize (unlike the `SetAlive`/`WriteBack` sequential phase elsewhere) because `SetAge` only ever writes distinct bytes at distinct array indices, never touching the `TBitArray`/`AliveCount` that actually need serialized writes.
- **`Automata/Simulation/`** — `ENeighborhood` (`Neighborhood.h`, `UENUM`): `VonNeumann` (6 face neighbors) or `Moore` (26, full 3×3×3 cube minus center) — deliberately its own header rather than folded into `AutomataOrchestrator.h`, so the simulation subsystem owns its own type. `FCellularAutomatonRule` (`CellularAutomatonRule.*`, plain C++ not `UObject`) is a **pure parameter holder** — takes `BirthCounts`/`SurvivalCounts` (each a `TArray<int32>`, exposed as `AAutomataOrchestrator::BirthCounts`/`SurvivalCounts` UPROPERTYs so designers edit them as plain arrays in the Details panel) plus a neighborhood, stores them as `TSet<int32>`/`TArray<FIntVector>` (O(1) membership checks / precomputed offsets) behind `GetBirthCounts()`/`GetSurvivalCounts()`/`GetNeighborOffsets()` getters, and owns **no stepping logic at all** — that's delegated to a swappable `Automata/Simulation/ComputeStrategy/` implementation (below). **No *Conway* rule string** — an earlier version used classic notation (`"B3/S23"`) with a hybrid parser (digit-per-count vs. comma-separated) to handle 3D neighbor counts exceeding 9 (up to 26 for Moore); that ambiguity and parsing complexity is why the three explicit, independent, unambiguous parameters above are the actual source of truth. A *different*, unambiguous notation was added later on top of them — see `RuleStringParser` next.

**`RuleStringParser` (`Automata/Simulation/RuleStringParser.h/.cpp`, plain namespace like `CellAging`) — string notation as a convenience layer, not a replacement**: parses `"Survival/Birth/States/Neighborhood"` (e.g. `"0-6/1,3/2/VN"`, `"13-26/13-14,17-19/2/M"`) — the exact format used by williamyang98/3D-Cellular-Automata (itself following Softology): Survival/Birth are comma-separated lists whose elements are single counts or inclusive `x-y` ranges, States is the total cell-state count (`>= 2`), Neighborhood is `M`/`Moore` or `VN`/`VonNeumann`, case-insensitively. This is **not** a reversal of the "no rule string" decision above — that was specifically about Conway notation breaking on two-digit neighbor counts; explicit `,`/`-` separators are unambiguous at any digit count. `ParseRuleString()` fills a result struct or fails with a human-readable error and touches nothing (never applies a rule half-way); `FormatRuleString()` is the inverse, re-compressing count lists into ranges (`1,2,3,7` → `1-3,7`). `AAutomataOrchestrator::RuleString` (`UPROPERTY`) plus `ApplyRuleString()`/`TryApplyRuleString()` are the only consumers — they overwrite `BirthCounts`/`SurvivalCounts`/`States`/`Neighborhood` **by field name, never positionally** (the string's field order is Survival-then-Birth, the opposite of those properties' declaration order — blind positional assignment would silently swap them). `GetActiveRuleString()` reports the *effective* rule by formatting those four properties, rather than echoing `RuleString`, which may be empty (rule built from the arrays in the Details panel) or stale (arrays hand-edited afterwards).

**`States` / Generations — multi-state decay**: `States == 2` (default) is the classic binary automaton and behaves bit-identically to how the project worked before this existed. `States > 2` enables "Generations": a cell that stops surviving doesn't die outright but decays through states `2, 3, ..., (States-1)` on its way to 0 (fully dead), and while decaying it is **birth-immune** — it can be neither revived nor killed, it just walks down at a fixed rate. Only state 1 (fully alive) counts as a live neighbor. Decay state is a **separate storage channel from `Age`** (see `FCellGrid::IsDecaying()`/`GetDecayState()`/`SetDecayState()`): `Age` is cosmetic, monotonic, and meaningful only for live cells; decay state affects the rule itself and is meaningful only for non-live ones. `FDenseCellGrid::FChunk` holds it as a third parallel `TArray<uint8> DecayStates` next to `Bits`/`Ages`, allocated **only** when the grid was constructed with decay enabled (`CreateGrid()` passes `States > 2`) — at `States == 2` it stays a default-empty `TArray` with no heap allocation at all, so the feature costs literally nothing in the common case. `ClampMax = 255` on `States` is not decorative: the state is a `uint8`.

Advancing decay is `CellDecay::AdvanceDecayStates(OldGrid, NextGrid, MaxStates)` (`Automata/Simulation/CellDecay.h/.cpp`) — a post-`Step()` pass alongside `CellAging::ComputeAges()`, working purely through the public `FCellGrid` interface so it doesn't care whether the generation was computed on CPU or GPU. Unlike `ComputeAges()` it is **not** parallelized: `SetAge()` is safe to call concurrently because the cell is already alive in the new grid (its chunk was created by the sequential write-back phase), whereas a decaying cell is typically *not* alive there and needs a lazy chunk creation — and `TMap::Add()` is not thread-safe even for disjoint keys. Both compute strategies needed only a narrow change for birth-immunity: the CPU strategy gained one short-circuit branch, and the GPU shader a second input bit-plane (`InputDecayBits`, "is decaying") gated by a `bDecayActive` uniform, bound to the same buffer as `InputBits` when inactive so no second allocation happens at `States == 2`. Rendering reuses the `AgeMaterials` bucketing to colour decay stages rather than introducing a second component pool. `States` round-trips through `.casave` as its own header field.

**`Automata/Simulation/ComputeStrategy/` — pluggable compute strategy**: `FCellularAutomatonComputeStrategy` (`CellularAutomatonComputeStrategy.h`, abstract, plain C++ not `UObject`, non-copyable — same convention as `FCellGrid`/`FCellGridRenderer`) declares the one-generation contract `virtual void Step(const FCellGrid& CurrentGrid, FCellGrid& NextGrid, const FCellularAutomatonRule& Rule) const = 0`: for every alive cell and its neighbors (candidate set, so cells can only be born adjacent to something alive), counts alive neighbors in `CurrentGrid` and writes the next state into `NextGrid` — never mutates `CurrentGrid`, so callers must double-buffer (see `AAutomataOrchestrator::Next()`). This is a deliberately **synchronous/blocking** contract mirroring the original `FCellularAutomatonRule::Step()` it replaced — `Next()`/`StepAsync()` already wrap the call appropriately for their own needs (`StepAsync()` dispatches onto `Async(EAsyncExecution::ThreadPool, ...)`, see above), so a strategy with its own async backend (e.g. a GPU dispatch+readback) does that internally rather than changing this interface.

**`StepBatch()` / `SupportsStepBatching()` — several generations per strategy invocation**: `virtual int32 StepBatch(Current, Next, Rule, NumSteps)` advances *up to* `NumSteps` generations in one call, exposing only the last one in `NextGrid`, and returns how many it actually advanced (always `>= 1`, `<= NumSteps`). Callers loop `while (Done < NumSteps) Done += StepBatch(..., NumSteps - Done)` and never need to know whether a given strategy can batch. The default implementation is a single `Step()` returning 1, so `FCpuComputeStrategy` is untouched and that loop degenerates to the previous one-generation-per-iteration shape. It exists because the GPU strategy pays a full CPU→GPU→CPU cycle *per generation* (pack, upload, blocking readback, and an unpack that is linear in the AABB **volume**, not in live cells) — at `StepsPerRender > 1` that was being paid for generations nobody ever sees. Two obligations bind any implementation returning `> 1`: it must have **filled the ages itself** (`CellAging::ComputeAges()` can only diff two adjacent generations, and the intermediates no longer exist — the caller skips `ComputeAges()` exactly when it gets `> 1` back), and it must not do so for a Generations rule (`Rule.HasDecayStates()`), since `CellDecay::AdvanceDecayStates()` runs *between* generations on the CPU and a batch would jump over it.

`virtual bool SupportsStepBatching(const FCellularAutomatonRule&)` answers a different question — not *how* to call `StepBatch()` but whether the caller should **restructure around** batching, which has to be decided before the call. It matters only in continuous Play (see `StepAsync()` above): `true` makes one background dispatch compute the whole `StepsPerRender` run, `false` keeps the one-generation-per-dispatch rhythm with the render-skipping counter. Default `false`; `FGpuComputeStrategy` returns `!Rule.HasDecayStates()`. It deliberately does **not** check volume limits — those depend on the current grid state and change generation to generation, and `StepBatch()` handles them itself by trimming the batch; answering "unsupported" because of one momentarily inflated AABB would disable batching for the rest of the run. `AAutomataOrchestrator::ComputeMethod` (`EComputeMethod::Cpu`/`Gpu`) picks which concrete strategy `CreateComputeStrategy()` constructs — a private factory that switches on `ComputeMethod`, mirroring how `CreateGrid()` builds the grid from its own Details-panel properties; both `Next()` and `StepAsync()` call it fresh every invocation (same "rebuild from Details-panel UPROPERTYs every call" convention as `FCellularAutomatonRule` itself), so switching methods mid-session takes effect immediately with zero caching.

`FCpuComputeStrategy` (`CpuComputeStrategy.*`) is the **only currently-working implementation** — an exact relocation of the original `FCellularAutomatonRule::Step()` body, with `NeighborOffsets`/`BirthCounts`/`SurvivalCounts` member access rewritten to `Rule.GetNeighborOffsets()`/`Rule.GetBirthCounts()`/`Rule.GetSurvivalCounts()` and otherwise unchanged. **Parallelized across CPU threads**: the per-candidate neighbor-count-and-decide work only reads `CurrentGrid`, so it's embarrassingly parallel — it runs via `ParallelFor` over an indexed `TArray<FIntVector>` of deduplicated candidates, writing each candidate's next-alive state into an indexed `TArray<bool>` (not bit-packed in Unreal, unlike `std::vector<bool>`, so concurrent writes to distinct indices don't race). The actual `NextGrid.SetAlive(...)` calls happen afterward in a plain sequential loop over that result array — `TBitArray` inside `FDenseCellGrid` isn't thread-safe for concurrent writes, so it can't be called from inside the `ParallelFor` body. Verified via a temporary thread-ID-collecting diagnostic that this engages the real OS thread pool (~31 threads — 30 `FTaskGraphInterface` workers plus the calling thread — on a 16-core dev machine), not just nominal capacity.

**Candidate-set construction is itself parallelized (bucket-partitioned dedup)** — profiling at 1M+ live cells (added `FPlatformTime::Seconds()` breakdown logging inside `Step()`, still present) revealed that an earlier `TSet<FIntVector>`-based dedup (each alive cell's `Cell` + all `NeighborOffsets` inserted via `TSet::Add`, up to 27 hash-insertions per alive cell for Moore) consumed ~80% of total step wall-time on a single thread, even though the neighbor-count `ParallelFor` above genuinely engaged ~31 threads — the dedup itself was the actual bottleneck the whole time, not the per-candidate work. A first attempt at fixing this (fill a flat pre-sized array with duplicates via `ParallelFor`, then a single global `Algo::Sort`+`Algo::Unique` pass) measured *no real improvement*: `Algo::Sort` has no parallel variant in this engine, so sorting the entire un-deduplicated array (which is exactly as large as the old TSet's total insert count) is comparably expensive to hashing it — swapping one single-threaded bottleneck for another. The actual fix partitions candidates into `NumBuckets = 256` independent buckets by `GetTypeHash(Candidate) & BucketMask` (deterministic, so every duplicate of the same cell always lands in the same bucket regardless of which alive cell or thread produced it) via a classic counting-sort scatter: (1) a `ParallelForWithTaskContext` histogram pass gives each task a thread-local `TArray<int32>` bucket-count array (no synchronization), merged into one global histogram afterward (cheap — `NumTasks × NumBuckets` small ints); (2) a prefix sum over the histogram gives each bucket's offset into a flat `Scattered` array; (3) a second `ParallelFor` over alive cells scatters every raw candidate (duplicates included) into its bucket's slice, using `FPlatformAtomics::InterlockedIncrement` on a per-bucket cursor (`BucketCursors`, seeded from the offsets) since multiple threads write into the same bucket concurrently — but buckets themselves never overlap in memory; (4) a `ParallelFor(NumBuckets, ...)` sorts (`Algo::Sort`) and dedups (`Algo::Unique`) each bucket's slice independently, in parallel, with zero cross-thread synchronization since bucket memory ranges are disjoint; (5) a final `ParallelFor(NumBuckets, ...)` `FMemory::Memcpy`s each bucket's deduplicated slice into its final position in `Candidates` (offsets from a second prefix sum over post-dedup bucket sizes). Verified in PIE: at ~2.2M live cells this dropped `CandidateBuild`'s share of step time from ~80% to ~38% (675ms out of 1760ms total, vs. `ParallelFor`'s 865ms and `WriteBack`'s 213ms) — the dedup work itself is now genuinely spread across cores instead of the neighbor-count phase being the only real parallel section.

`FGpuComputeStrategy` (`GpuComputeStrategy.*`) is a **real RDG compute-shader implementation** — grid-storage-agnostic, like the CPU strategy (only touches `FCellGrid` through `GetAliveCells()`/`SetAlive()`, never `FDenseCellGrid` internals). `Step()` runs entirely on the calling thread plus one Render Thread round-trip: (1) `GetAliveCells()` then a plain sequential min/max scan gives an integer cell-space AABB (empty grid → return immediately, `NextGrid` stays empty); (2) the AABB is expanded by `Halo = 1` cell in every axis — safe in general because every `NeighborOffsets` entry (`CellularAutomatonRule.cpp::BuildNeighborOffsets`, both `VonNeumann` and `Moore`) has components only in `{-1,0,1}`; (3) **OOM guard**: if the resulting `VolumeDim.X*Y*Z` exceeds `AAutomataOrchestrator::GpuVolumeCellLimit` (`EditAnywhere`, default `512^3` ≈ 134M cells / ~16MB bit buffer — raised from an originally-hardcoded `256^3` once that turned out to be an arbitrary conservative choice rather than a real hardware limit; deliberately kept as a guard rather than removed outright, since the failure mode it prevents — two live cells ending up far apart in a sparse grid inflating the AABB to an unmanageable volume even with few live cells overall — is still possible at any cap) — it logs a warning and falls back to `FCpuComputeStrategy` for that step, the same "never silently do nothing" convention the old stub used; the limit is passed into `FGpuComputeStrategy`'s constructor by `CreateComputeStrategy()` (see `Automata/Simulation/ComputeStrategy/` below), rebuilt fresh every call like the rest of that factory's Details-panel-driven state — no caching, so raising it takes effect on the very next step; (4) alive cells are packed into a flat `TArray<uint32>` bit buffer (32 cells/word) in AABB-local coordinates, and the rule is packed into `BirthMask`/`SurvivalMask` `uint32` bitmasks (bit *i* = count *i* allowed — 0–26 fits easily) plus a fixed `int4[26]` neighbor-offset array (Moore's 26 is the max; `VonNeumann`'s 6 just leaves the tail unused, gated by an explicit `NeighborOffsetCount`). Cells outside the halo of any live cell are never dispatched-into as "alive" and, symmetrically, any out-of-buffer neighbor read the shader does is treated as dead — this exactly matches the CPU strategy's candidate-set semantics (a cell with 0 live neighbors is never evaluated as a birth candidate by either strategy, even if `BirthMask` technically allows it).

Dispatch happens inside `ENQUEUE_RENDER_COMMAND` (so RDG/RHI calls run on the Render Thread as required) which builds an `FRDGBuilder`, uploads the input buffer (`CreateStructuredBuffer`), clears a same-sized output buffer (`AddClearUAVPass`), runs `FCellularAutomatonStepCS` (a file-local `FGlobalShader` in `GpuComputeStrategy.cpp`, one `[numthreads(4,4,4)]` thread per cell in the volume, `Shaders/Private/CellularAutomatonStep.usf`) via `FComputeShaderUtils::AddPass`, then `AddReadbackBufferPass` enqueues a copy into an `FRHIGPUBufferReadback`. The shader writes results with `InterlockedOr` since up to 32 cells share a output word and can be written by different threads concurrently. After `GraphBuilder.Execute()`, the render command calls `RHICmdList.ImmediateFlush(EImmediateFlushType::FlushRHIThread)` — a **lightweight** flush that only pushes the recorded commands down to the RHI thread (and from there the GPU), without waiting for GPU completion. This is required: without it, the just-recorded commands sit unsubmitted in the `RHICmdList` while this same Render Thread immediately starts spin-polling `Readback->IsReady()` below — since nothing ever asks the GPU to actually run the work, the fence never signals and the poll loop hangs forever (observed directly: the whole editor froze on `Start()` with `ComputeMethod=Gpu`, no crash, just a dead viewport). An earlier version instead called `RHICmdList.SubmitCommandsAndFlushGPU()` (a deprecated forward to `SubmitAndBlockUntilGPUIdle()`) to solve the same submission problem, but that waits for the **entire GPU pipeline** to go fully idle, not just this pass — in PIE that fights the viewport's own rendering for the same thread and tripped the engine's hang detector, crashing the editor after a ~6s stall on a trivially small dispatch. `FlushRHIThread` submits without that blocking wait, avoiding both failure modes. **The `Readback->IsReady()`/`Lock()`/`Unlock()` poll loop itself also stays entirely inside the render command, on the Render Thread** — an earlier version polled `Readback->IsReady()` directly from the calling thread (game thread from `Next()`, or a `ThreadPool` worker from `StepAsync()`), which crashed (`Array index out of bounds: 0 into an array of size 0` inside `FRHIGPUFence::Poll()`) because `FRHIGPUBufferReadback` isn't designed to be polled from an arbitrary non-render thread. Instead, the calling thread only shares a raw `FEvent` (from `FPlatformProcess::GetSynchEventFromPool()`) and a `TSharedRef<TArray<uint32>>` result buffer with the render command: it calls `CompletionEvent->Wait()` and only reads the result buffer after `Wait()` returns, by which point the render command (which polls `Readback->IsReady()` in a spin loop, `Lock()`/`Memcpy()`/`Unlock()`s into that shared buffer, then `Trigger()`s the event) has fully finished — `Readback` itself never leaves the Render Thread. **`FRenderCommandFence` was tried first and also crashed** (`check(IsInGameThread() || IsInAsyncLoadingThread())` inside `FRenderCommandFence::IsFenceComplete()`) — its `Wait()` is only safe from the game thread, which breaks exactly the `StepAsync()` ThreadPool-worker call path this strategy needs to support; a raw pooled `FEvent` has no such restriction, since it's just an OS-level synchronization primitive. Once unblocked, `Step()` unpacks bits back into world/cell coordinates via a sequential `NextGrid.SetAlive(...)` loop, mirroring the CPU strategy's single-threaded `WriteBack` phase for the same thread-safety reason (`TBitArray` isn't safe for concurrent writes). This whole strategy is a single blocking call from the caller's point of view — it doesn't change `FCellularAutomatonComputeStrategy::Step()`'s synchronous contract, it just has its own internal async round-trip (RDG dispatch + GPU readback, blocking the Render Thread for its duration) instead of `FCpuComputeStrategy`'s CPU-side `ParallelFor`. `Step()` itself is now just `StepBatch(..., 1)`.

**Batched dispatch (`StepBatch()`) — one upload, N ping-ponged dispatches, one readback**: with `NumSteps > 1` and a non-Generations rule, the state is uploaded once, ping-ponged between two RDG buffers across N `AddPass` calls inside a single `FRDGBuilder` (each preceded by `AddClearUAVPass`, since the shader only ORs bits and never writes zeros), and read back once. Three consequences worth knowing before touching this code:

- **The halo must equal the batch size.** A pattern grows by at most one cell per axis per generation, so halo `K` makes a `K`-step batch *exact*; a smaller halo would silently lose border cells and diverge from the CPU strategy. When the resulting volume no longer fits the limits, the **batch is trimmed** to the largest `K` that does (monotonic, so the search converges) rather than abandoned — three steps instead of ten still removes two thirds of the round-trips. If even `K == 1` doesn't fit, the usual CPU fallback applies and 1 is returned.
- **Ages move into the shader** for the duration of a batch: a byte per cell packed four to a word, saturating at 255, mirroring `FCellGrid::GetAge()`/`SetAge()` semantics, written with `InterlockedOr` for the same reason as the alive bits (four cells share a word and are computed by different threads, but own distinct bytes of a zero-cleared word). The pre-batch ages are uploaded too, so a cell surviving the whole batch continues its count rather than restarting. Gated by a `bTrackAges` uniform; when off, the SRV slot is bound to the current input bit buffer and the UAV to a one-word dummy. **Unused SRV slots must be re-bound to the *current* `BitsIn` on every pass**, not captured once before the loop: the buffers swap roles each iteration, so a stale binding would name the very buffer that pass writes to — one resource as SRV and UAV simultaneously, which RDG validates regardless of whether the shader actually reads it.
- **Batching carries its own volume ceiling** at `GpuVolumeCellLimit / 8`, because the age plane costs a byte per cell against the bit-per-cell alive plane. Derived from the existing property rather than adding a second knob, so raising one raises both.

Measured on a 221³ volume with ~195k live cells and `StepsPerRender = 10` (RTX-class desktop GPU): 10 generations as one batch took **108.9 ms** against **278.5 ms** as ten separate round-trips, with bit-identical results (1 000 616 live cells either way). The win is entirely CPU-side — `Unpack` collapsed from 155.2 ms to 33.5 ms and `GetAliveCells` from 22.9 ms to 1.4 ms, while `GpuRoundTrip` actually *rose* (48.6 → 62.0 ms), since halo 10 inflates the dispatched volume by ~29% and the age plane adds work. After batching, the GPU dispatch itself is the dominant phase, i.e. the CPU-side overhead this was built to remove is largely gone.

**Per-phase timing log**: `StepBatch()` logs a `GpuStep:` line with a `GetAliveCells / Pack / GpuRoundTrip / Unpack` breakdown plus the volume and how many generations the round-trip covered — deliberately mirroring `FCpuComputeStrategy`'s `CandidateBuild/ParallelFor/WriteBack` line. The precedent for adding it before optimizing is that project's own history: the first attempt at fixing the CPU candidate-set bottleneck (global `Algo::Sort` instead of `TSet`) measured no improvement because the assumed bottleneck wasn't the real one.

Required new module dependencies: `RHI`/`RenderCore` (`CellularAutomata.Build.cs`, `PrivateDependencyModuleNames`) — not Live-Coding-safe, needs a cold rebuild. `AddShaderSourceDirectoryMapping(TEXT("/Project/CellularAutomata"), .../Source/CellularAutomata/Shaders)` is registered in `FCellularAutomataModule::StartupModule()` (`CellularAutomata.cpp`) — the module previously used the engine's default `FDefaultGameModuleImpl` with no custom startup logic; `CellularAutomata.h` now declares `FCellularAutomataModule : public FDefaultGameModuleImpl` for this purpose.
- **`Automata/Rendering/`** — `FCellGridRenderer` (`CellGridRenderer.h`, abstract, plain C++): `Render(const FCellGrid&)`, grid passed per-call rather than owned, so one renderer can redraw after each simulation step. `FInstancedMeshCellGridRenderer` (`InstancedMeshCellGridRenderer.*`) is the only concrete implementation: wraps a `UInstancedStaticMeshComponent*` (owned by the Actor, not this class), with `SetMesh`/`SetMaterial` setters called fresh before each `Render()` since those are designer-editable properties. Scales each instance so the mesh's actual bounding-box size matches `CellSize` (via `UStaticMesh::GetBounds()`), so grid cells tile evenly regardless of the assigned mesh's native dimensions. `AAutomataOrchestrator` holds one instance per `AgeMaterials` entry (`TArray<TUniquePtr<FInstancedMeshCellGridRenderer>> AgeRenderers` — see `AgeMaterials` below; there is no single/default renderer any more, since a bare `CellMaterial` no longer exists) via the **concrete** type, not the abstract base, since mesh/material setters aren't part of the abstract interface. **Perf-critical**: `Render()` builds a `TArray<FTransform>` for every alive cell and adds them in one batch via `UInstancedStaticMeshComponent::AddInstances(..., bUpdateNavigation=false)` rather than calling `AddInstance()` per cell — the per-call form rebuilds internal instance buffers on every invocation and showed catastrophic super-linear scaling under profiling (~1789x slower for only 54x more cells at ~45k cells). Both `CellsMeshFlat`/`CellsMeshHierarchical` also have collision disabled (`SetCollisionEnabled(ECollisionEnabled::NoCollision)` in the orchestrator's constructor) since automaton cells are purely visual — measured combined effect (batching + no collision) was a ~37x reduction in total render time at ~45k cells.

**`CellMeshComponentType` picks `UInstancedStaticMeshComponent` vs. `UHierarchicalInstancedStaticMeshComponent`/HISM for the `AgeMeshComponents` pool** (see `AgeMaterials` below) — `FInstancedMeshCellGridRenderer` itself needed zero code changes to support either, since `AddInstances`/`ClearInstances`/`SetStaticMesh` are all `virtual` overrides on HISM (it *is-a* `UInstancedStaticMeshComponent`), so calling them through the base-class pointer already dispatches correctly regardless of which concrete class it points at. `CellsMeshFlat`/`CellsMeshHierarchical` (`AAutomataOrchestrator`'s two permanent `CreateDefaultSubobject`-created components, `CellsMeshHierarchical` the actor's root) predate `AgeMaterials` becoming mandatory and no longer receive instances directly (the single-material render path that used to target one of them was removed along with `CellMaterial` — see `AgeMaterials` below) — they're kept only because `CellsMeshHierarchical` is still the attach-parent for the `AgeMeshComponents` pool, and `GetActiveCellsMeshComponent()` (returns whichever `CellMeshComponentType` selects) is still used for a cheap defensive `ClearInstances()` guard in `RenderCurrentGrid()`/`RenderGridImmediate()`. **Both components are created unconditionally in the constructor and live for the actor's whole lifetime** rather than being destroyed/recreated: dynamically swapping which `UClass` a `CreateDefaultSubobject`-created component is at runtime isn't something Live Coding can safely hot-patch for an already-placed level actor (confirmed directly — after changing `CreateDefaultSubobject<UInstancedStaticMeshComponent>` to `CreateDefaultSubobject<UHierarchicalInstancedStaticMeshComponent>` for what was originally a single `CellsMesh` field, the existing placed actor's component pointer silently reinstanced to `null` — no crash, just a dangling reference — because the old object couldn't be safely upcast to the new class; a genuine editor restart was needed to get a clean instance). This is *not* the same hazard `AgeMeshComponents` pool entries face — those are runtime `NewObject()`-created, not default subobjects, so creating/destroying them as `AgeMaterials`/`CellMeshComponentType` change is an ordinary, safe operation (see `RebuildAgeMeshComponents()` below).

HISM builds an internal LOD cluster tree over the instances (async rebuild after `AddInstances`/`ClearInstances`, tracked via `bIsOutOfDate`/`BuildTreeIfOutdated`) enabling per-cluster occlusion and distance culling — the payoff scales with cell count (relevant at the 700k+ live-cell sizes seen once the sim runs for a while), but each full-grid `ClearInstances()` + re-`AddInstances()` per generation also means HISM rebuilds that cluster tree from scratch every step, which is extra work the plain (non-hierarchical) `UInstancedStaticMeshComponent` doesn't do — worth comparing `AddInstances` timing (see `FRenderTimings`) between the two `CellMeshComponentType` settings if step time regresses at very large cell counts.

**`CellCullStartDistance`/`CellCullEndDistance` — per-instance distance culling, deliberately not HLOD**: HLOD (Hierarchical LOD) bakes simplified proxy meshes for groups of *static* actors via an explicit "Build HLODs" step in the editor, then swaps a whole cluster for its proxy past a distance — it has no way to react to a grid that's fully cleared and rebuilt every simulation step (there's no static state to bake), so it never engages here no matter how it's configured on the level; that's the "HLOD doesn't seem to work" outcome the property was added to replace. `CellCullStartDistance`/`CellCullEndDistance` (`AAutomataOrchestrator`, `Automata|Cells`, both default `0.0f` = disabled — same as engine default) instead drive `UInstancedStaticMeshComponent::SetCullDistances()` directly — genuine per-instance runtime distance culling computed every frame from the current view, needing no baking and updating automatically as instances get replaced generation-to-generation. Applying the distances is factored into its own private helper, `ApplyCellCullDistances()`, called from `RenderCurrentGrid()`/`RenderGridImmediate()` on every render and from `SetCellCullingEnabled()` directly (rounded to `int32` via `FMath::RoundToInt`, clamped to non-negative) — applied to `CellsMeshFlat`/`CellsMeshHierarchical` *and* every entry of `AgeMeshComponents`, regardless of which one `CellMeshComponentType` currently selects, so switching component types later doesn't leave a stale (or default/disabled) set of cull distances anywhere; `SetCullDistances()` itself is a no-op when values haven't changed, so the repeated call costs nothing once settled. `bEnableCellCulling` (default `true`) is a master on/off switch — while `false`, `ApplyCellCullDistances()` applies `(0, 0)` to all components instead of the configured distances, without touching `CellCullStartDistance`/`CellCullEndDistance` themselves, so toggling it for an A/B comparison never loses previously-tuned numbers; switchable live via the **B** hotkey (`AGamePlayerController::OnToggleCellCulling()` → `SetCellCullingEnabled()`/`IsCellCullingEnabled()`, no `CallInEditor` — same reasoning as `CycleChunkedRenderOrder()`/`SetWaitForChunkedRenderToFinish()` above, the checkbox is already directly editable) or the Details panel. **`SetCellCullingEnabled()` calls `ApplyCellCullDistances()` itself, immediately, rather than relying on the next render call** — an earlier version only applied cull distances as a side effect of rendering a newly-computed generation, so toggling `bEnableCellCulling` via the **B** hotkey while no generation was actively rendering (e.g. continuous Play paused, or between `Next()` calls) silently did nothing until the *next* render — `SetCullDistances()` itself updates the live `SceneProxy` on the Render Thread immediately and needs no `AddInstances()`/rebuild to take effect, so there was no actual reason to wait for a render; calling `ApplyCellCullDistances()` straight from the setter fixed the "have to regenerate a frame for the toggle to visibly take effect" symptom without needing to force any regeneration at all. **Two debugging aids added while chasing an initial "still doesn't cull no matter how far I fly" report**: (1) `ApplyCellCullDistances()` logs once whenever the applied `(Start, End)` actually changes (`"отсечение клеток по расстоянию включено/выключено"`), by comparing against `CellsMeshHierarchical->GetCullDistances()` before calling `SetCullDistances()` again; (2) while `CullEnd > 0`, a throttled (max once/second, via a local `static double LastCullDebugLogSeconds`) diagnostic line logs the camera location, the live-cell bounds center/radius (`ComputeAliveCellsBounds()`), the distance between them, the configured `(Start, End)`, and the *actual* `(Start, End)` read back from `CellsMeshHierarchical` right after `SetCullDistances()` — enough to directly compare "is the camera actually past the configured distance" against "did the value really stick on the component" without guessing. This diagnostic surfaced the actual root cause on this project: `r.ViewDistanceScale` (a Scalability-driven console variable, found via `r.ViewDistanceScale` with no argument to print its current value) was `10` instead of the expected default `1` — the engine multiplies `EndCullDistance` by this scale before comparing it to camera distance (`InstancedStaticMesh.cpp`'s `MaxDrawDistanceScale = GetCachedScalabilityCVars().ViewDistanceScale`), so a configured `20000` was actually enforcing a `200000`-unit (2 km) cutoff — nothing was broken, the fly-test distance just never reached the real threshold. Separately, disabling Nanite on the cell mesh (`NaniteSettings.bEnabled`) was tried and discarded — Nanite's renderer has no references to `EndCullDistance`/`InstanceCullDistance` at all (grepped `Renderer/Private/Nanite/`, zero hits) so it does bypass this legacy per-instance cull path, but turning Nanite off made rendering *worse* and introduced other bugs at this project's instance counts, so Nanite stayed enabled — the real fix was purely the `r.ViewDistanceScale` mismatch.

**`ARenderCullVolume` (`Automata/Rendering/RenderCullVolume.*`) — a placeable box that culls cells *before* they cost anything**: unlike `CellCullStartDistance`/`CellCullEndDistance`, which hide already-built instances after the fact and don't reduce the cost of building them, this cuts cells outside the box at the source — `BuildAgeBuckets()` calls `FCellGrid::GetAliveCellsInBounds()` instead of `GetAliveCells()`, so the transforms are never built and `AddInstances()` never sees them (and `FDenseCellGrid` overrides that method chunk-aware, rejecting whole chunks at a time). The orchestrator finds the actor itself via `UGameplayStatics::GetActorOfClass()` (the same idiom as everywhere else in the project) — no manual Details-panel reference. It is moved and resized with the ordinary actor gizmo: there are no `Size`/`Location` properties, since Location *is* the actor transform and Size is the `BoundsBox` `UBoxComponent`'s `BoxExtent`. Deliberately **axis-aligned only** — rotating the actor does not tilt the culling box, `GetWorldBounds()` always builds an AABB from location plus scaled extent, the same simplicity choice as the marquee selection's "no depth bound". Because a programmatic `SetActorLocation()` doesn't trigger it, `PostEditMove(bFinished)`/`PostEditChangeProperty()` (editor-only) explicitly ask the orchestrator to re-render so dragging or retyping the bounds updates the view immediately; `MoveCullVolumeToSelection()` (**K**) calls `RefreshRenderCullVolume()` itself for the same reason. Master switch `bEnableRenderCullVolume` (default `true`, hotkey **C**); `SelectCellsInCullVolume()` (**L**) selects everything inside it.

**Ghost Shape — a chunk-granular silhouette that coexists with the live simulation**: marked experimental alongside Baking. Instead of one cube of geometry per cell, it builds one per occupied **chunk** (via `CellMeshBuilder::BuildFromCells()` over an `FChunkGridView`, reusing the exact face-culling mesh builder the bake uses), which is orders of magnitude cheaper. Unlike `BakeCellsToMesh()` it is **not** a one-way snapshot: `Grid` is never freed, the simulation keeps running, and the silhouette is rebuilt every `GhostShapeRefreshInterval` generations (default `10`, its own counter — `CellMeshBuilder::BuildFromCells()` is synchronous and single-threaded, so rebuilding every generation would be felt on the game thread). Two modes depending on whether a cull volume is active: **(1)** cull box active — the silhouette is built only from chunks *outside* it while the detailed per-cell render keeps drawing everything inside, so the ghost is pure addition, showing where the structure continues beyond the box; **(2)** no cull box (or disabled) — "outside" means "everywhere", the silhouette covers the whole grid and **replaces** the detailed render entirely (`ShouldGhostShapeReplaceDetailedRender()`). Mode 2 is where the feature actually saves time: at high live-cell counts the detailed path (collect + `AddInstances` per cell) is the expensive part, and often all that's wanted is the overall shape of how the structure is evolving. Off by default; **H** toggles it; `GhostShapeMaterial` falls back to `AgeMaterials[0]` with a log line, exactly like `BakedMeshMaterial`.

**`AgeMaterials` — the sole source of cell materials, keyed by age, every render path**: `AAutomataOrchestrator::AgeMaterials` (`TArray<UMaterialInterface*>`) lets a designer assign cells different materials based on how many consecutive generations they've survived (`FCellGrid::GetAge()`, see `Automata/Grid/` above) — ordered oldest→youngest: the **last** element goes to Age-0 (just-born) cells, the **first** to cells that reached Age (N-1) or older, i.e. `MaterialIndex = N-1-min(Age, N-1)` where N = `AgeMaterials.Num()`. **Mandatory, not opt-in** — there used to be a separate `CellMaterial` (used whenever `AgeMaterials` was empty), removed once `AgeMaterials` became the only rendering path everywhere: keeping a fallback-to-single-material option would have kept alive exactly the "why is it showing the wrong thing" confusion the array-index-out-of-range/empty-slot bugs during testing already caused. `GenerateRandom()`/`Next()`/`StepAsync()` all now check `AgeMaterials.Num() == 0` up front and refuse (with a warning log) exactly like the pre-existing `!CellMesh` check — `RenderCurrentGrid()`/`RenderGridImmediate()` (see below) repeat the same guard defensively, since `AgeMaterials` could in principle be edited to empty in the Details panel between a background step's dispatch and its completion. At `N == 1` every cell renders with that one material regardless of age, exactly reproducing the old single-`CellMaterial` behavior. Unlike `bEnableChunkedRender`/`StepsPerRender`/`bWaitForChunkedRenderToFinish` (which only ever affect the continuous-Play pipeline), `AgeMaterials` applies identically in continuous Play (`StepAsync()` → `ApplyStepResult()` → `RenderCurrentGrid()`, chunked-render-aware) and in the manual step/spawn path (`Next()`/`GenerateRandom()` → `RenderGridImmediate()`, always one-shot) — "this cell is young" shouldn't depend on how it got drawn.

Since `UInstancedStaticMeshComponent`/HISM apply a material per **component** (`SetMaterial(0, ...)`), not per instance, N distinct materials need N separate mesh components — `AAutomataOrchestrator::AgeMeshComponents` (`UPROPERTY(Transient)`, one `UInstancedStaticMeshComponent`/`UHierarchicalInstancedStaticMeshComponent` — matching `CellMeshComponentType` — per `AgeMaterials` entry) plus a parallel plain `TArray<TUniquePtr<FInstancedMeshCellGridRenderer>> AgeRenderers`, both kept in sync by `RebuildAgeMeshComponents()` (called from `BeginPlay()`/`OnConstruction()`/`PostEditChangeProperty()` when `AgeMaterials` or `CellMeshComponentType` changes, and defensively from `RenderCurrentGrid()`/`RenderGridImmediate()` too). These pool components are created/destroyed at runtime via plain `NewObject<...>(this)` + `RegisterComponent()`/`DestroyComponent()` (see `CellMeshComponentType` above for why that's safe, unlike `CellsMeshFlat`/`CellsMeshHierarchical`). `AgeMeshComponents` is a `UPROPERTY` for the same reason as `GamePC` (see its correctness note above): it must survive Live Coding reinstancing during an edit to `AgeMaterials` itself (a reflection change). `AgeRenderers`, being a plain member, does *not* survive reinstancing — `RebuildAgeMeshComponents()` re-derives it from `AgeMeshComponents` whenever the two arrays' lengths disagree, before doing anything else, so a post-crash reconnect resyncs automatically rather than leaving `AgeRenderers` empty against a populated `AgeMeshComponents`.

`BuildAgeBuckets()` is the shared bucketing step (used by both render paths below): buckets `Grid->GetAliveCells()` by `MaterialIndex` into `AgeMaterials.Num()` arrays. `RenderCurrentGrid()` (continuous-Play path, chunked-render-aware) and `RenderGridImmediate()` (`Next()`/`GenerateRandom()`'s tail, always one-shot via `Render()` rather than `BeginRender()`/chunking — matching those two callers' existing "always render immediately and in full" semantics) both start by clearing `GetActiveCellsMeshComponent()` once (a cheap defensive `ClearInstances()` against any stale instances left on the now-otherwise-unused base component, e.g. from a level saved before `AgeMaterials` existed), then feed each bucket through a thin adapter, `FFilteredCellGridView` (`Automata/Rendering/FilteredCellGridView.h`) — a read-only `FCellGrid` wrapping the real grid that overrides only `GetAliveCells()` to return the pre-bucketed subset (forwarding `GetCellSize()`/`GridToWorld()`/`IsAlive()`/`GetAge()` to the wrapped grid; `SetAlive()`/`SetAge()`/`Clear()` are no-ops, since a render-only view is never meant to be mutated). This lets each `AgeRenderers[i]` call `BeginRender(FilteredView, ...)`/`Render(FilteredView)` completely unmodified — `FInstancedMeshCellGridRenderer` only ever touches `GetAliveCells()`/`GetCellSize()`/`GridToWorld()`, so `BeginRender()`/`AdvanceRenderChunk()` needed **zero code changes** to support multi-material rendering. `AdvanceChunkedRender()`/`FinishChunkedRenderImmediately()` (continuous-Play path only — `RenderGridImmediate()` never chunks) loop all N renderers: "reveal finished" means every one of them reports no remaining work in the same tick (`bMoreRemaining` ORed across all of them, evaluated unconditionally — not short-circuited — so every renderer gets ticked every frame), and `ChunkedRenderCellsPerFrame` is divided across the N buckets (`PerBucketBudget = max(1, ChunkedRenderCellsPerFrame / NumBuckets)`) rather than applied to each in full, so a larger `AgeMaterials` doesn't silently multiply the chunked-render frame budget by N.

Known cost characteristics (not yet profiled in this project at multi-million-cell scale, see the `CandidateBuild`/`ParallelFor`/`WriteBack` breakdown above for comparison): `CellAging::ComputeAges()` adds roughly one more full alive-cell pass per generation (order of a few percent of total step time, fully parallel, no serialized phase); each additional `AgeMeshComponents` entry adds its own fixed per-component overhead, and for HISM specifically its own LOD cluster-tree rebuild on every `ClearInstances()`+`AddInstances()` (see above) — the render-cost multiplier from N materials is expected to be sub-linear-ish but unmeasured; profile before committing to a large `AgeMaterials` count in production.

**Mouse cell-selection — isolate an interesting sub-pattern (glider/oscillator-hunting) and launch it as a fresh starting state**: a "selection mode" toggled by the **Tab** hotkey (`AGamePlayerController::OnToggleSelectionMode()` → `SetSelectionModeActive()`) that stops the camera and shows the cursor by calling the pre-existing `SetCameraControlEnabled(false)` (previously dead code outside `Pause()`/`Resume()`) — the controller's own `InputComponent` keeps receiving input throughout, since `DisableInput()`/`EnableInput()` only gate the *pawn's* input stack, not the controller's. While active, holding **left mouse button** and dragging draws a marquee rectangle (`OnSelectDragStarted()`/`OnSelectDragFinished()`, `Started`/`Completed` on a `SelectDragAction`) — a small native `AHUD` subclass, `AGameHud` (`Core/Hud/GameHud.*`, wired via `AAGameMode::HUDClass` in its constructor), overrides `DrawHUD()` to paint the live drag rectangle each frame by polling `AGamePlayerController::IsDraggingSelection()`/`GetSelectionDragStart()` plus a fresh `GetMousePosition()` call — no UMG widget needed, since `FUiController`'s widget system is unused for auto-show anyway (see below). On mouse-up, the controller computes the final screen rect, grabs a view-projection matrix **once** (not per cell) via `ULocalPlayer::GetProjectionData()` → `FSceneViewProjectionData::ComputeViewProjectionMatrix()` (the same API `UGameplayStatics::ProjectWorldToScreen` uses internally, but without its per-call overhead), and hands both off to `AAutomataOrchestrator::SelectCellsInScreenRect()` along with an `ESelectionCombineMode` (`Automata/Selection/SelectionCombineMode.h`, its own header per the `ENeighborhood`/`EChunkedRenderOrder` convention): the standard marquee-modifier pattern — plain drag **replaces** the selection, **Shift**+drag **adds** the rect's cells to it (set union, deduplicated via a `TSet` of the existing selection so it stays O(1) per cell at million-cell selection sizes), **Ctrl**+drag **subtracts** them (set difference via `TArray::RemoveAll` against a `TSet` of the rect hits). The modifier is sampled at drag *start* (`OnSelectDragStarted()`, stored in `PendingSelectionCombineMode`), not at release — like most editors, so the mode doesn't flip if the user lets go of the modifier slightly before the mouse button; Ctrl wins if both are held, and both left and right Shift/Ctrl work. **A click (mouse moved ≤ `ClickDragThresholdPixels` = 4px between press and release) picks a single cell instead of a rectangle**: the cursor is deprojected to a world ray (`DeprojectMousePositionToWorld`) and `CellSelection::PickCellAlongRay()` walks the cell lattice with Amanatides-Woo voxel DDA (exact boundary stepping — no cell on the ray is skipped), returning the *first* alive cell, i.e. exactly the cell whose face is visible under the cursor — engine line traces can't do this since all cell components have collision disabled; traversal is capped at the far side of the alive-cells bounding sphere (`ComputeAliveCellsBounds()`). The same combine modes apply (plain click replaces — clicking empty space clears the selection; Shift+click adds the cell, Ctrl+click removes it), sharing the combine logic with the marquee via the private `CombineWithSelection()` helper on the orchestrator.

Picking itself lives in `Automata/Selection/CellSelection.h/.cpp` — a plain namespace function (`CellSelection::SelectCellsInScreenRect()`), the same non-`UObject` idiom as `CellAging`: for every alive cell, `ViewProjectionMatrix.TransformFVector4(FVector4(WorldPos, 1))` projects it to clip space; cells behind the camera (`W <= KINDA_SMALL_NUMBER`) are dropped, the rest are perspective-divided into NDC and mapped to pixel coordinates, then tested against the drag rectangle. **Deliberately no depth/distance limiting** — the marquee selects every alive cell whose screen-space projection falls inside the rectangle regardless of how near or far it is, i.e. it behaves like an infinite frustum along the camera's view direction rather than a bounded 3D box (a conscious simplicity choice, not an oversight — see the plan this was built from, `snazzy-twirling-beacon.md`, for the considered-and-rejected depth-bounded alternative). Parallelized via `ParallelFor` into a same-size `TArray<bool>` followed by a sequential collect pass — the same two-phase "parallel flag, sequential gather" idiom as `CellAging::ComputeAges()` and the CPU compute strategy's candidate-set construction — since this runs as a one-shot action against potentially millions of alive cells on every mouse-release.

`AAutomataOrchestrator::SelectedCells` (`TArray<FIntVector>`, plain member, not a `UPROPERTY`) holds the current selection; `SelectCellsInScreenRect()` populates it and immediately calls `RenderSelectionOverlay()` so the highlight appears without waiting for the next simulation step. Rendering reuses the exact `FFilteredCellGridView` + `FInstancedMeshCellGridRenderer` pattern `AgeMaterials` established (see above) — one more pooled component, `SelectionMeshComponent` (`UPROPERTY(Transient)`, **always** a plain `UInstancedStaticMeshComponent` regardless of `CellMeshComponentType`, since a selection is always a small subset and gets nothing from HISM's cluster tree) plus its `TUniquePtr<FInstancedMeshCellGridRenderer> SelectionRenderer` (not a `UPROPERTY`, same Live-Coding-reinstancing rationale as `AgeRenderers` — `EnsureSelectionMeshComponent()` re-derives it from a surviving `SelectionMeshComponent` if the two ever disagree), painted with the designer-assigned `SelectionMaterial`. `RenderSelectionOverlay()` is called as an extra pass at the end of both `RenderGridImmediate()` and `RenderCurrentGrid()` (filtering `SelectedCells` down to currently-alive cells defensively, and always rendering in one shot — never chunked, since selections are always small) and clears the component whenever there's nothing to show. `ApplyCellCullDistances()` applies the same cull distances to `SelectionMeshComponent` as every other cell-rendering component.

`SelectedCells` is reset to empty at the top of `GenerateRandom()`, in `Next()`'s completion, and in `ApplyStepResult()` (right after the `Grid` swap) — any new generation invalidates a prior selection's coordinates, matching the intended workflow of "pause, fly around, select, extract" rather than selecting mid-Play. `AAutomataOrchestrator::StartFromSelection()` (`CallInEditor`, also bound to the **Enter** hotkey via `AGamePlayerController::OnExtractSelection()`) is the actual "launch as new state": guards on `bStepInProgress` (it swaps `Grid`, which a background `Next()`/`StepAsync()` may be reading at that moment — same refuse-with-warning as every other `Grid`-swapping path), an empty selection, or missing `AgeMaterials` the same way `GenerateRandom()`/`Next()` do, builds a fresh grid via the existing `CreateGrid()` helper, copies over only the selected (and still-alive) cells with `SetAge(..., 0)` (a fresh start, exactly like a newly-born cell), swaps it into `Grid`, clears `SelectedCells`, calls `GamePC->SetSelectionModeActive(false)` to hand camera control back, and finishes with `RenderGridImmediate()` — mirroring `GenerateRandom()`'s structure throughout. **Coordinates are deliberately left as-is, not translated to the origin** — the selected pattern stays exactly where it was picked, since the camera is already looking right at it and the automaton's rules are translation-invariant anyway, so there's nothing to gain from re-centering.

`AAutomataOrchestrator::DeleteSelectedCells()` (`CallInEditor`, category `Automata|Selection`, also bound to the **Delete** hotkey via `AGamePlayerController::OnDeleteSelectedCells()`) is the destructive counterpart to `StartFromSelection()`: instead of extracting the selection into a fresh grid, it kills the selected cells **in the current grid** (`Grid->SetAlive(Cell, false)`, counting only actually-alive ones for the log) — a manual state edit for cutting a piece out of a pattern and watching how the remainder evolves. The simulation is deliberately **not** reset: `Grid` stays the same object (no swap), ages of surviving cells are untouched, and P/F continue from the edited state. Guards mirror the other selection paths (`bStepInProgress` — a background step is *reading* `*Grid`, so mutating it mid-flight would race; no `Grid`; empty selection; empty `AgeMaterials`), then `SelectedCells.Reset()` + `RenderGridImmediate()` so the holes appear instantly.

**`InitialStateCells` / `ResetToInitialState()` — the "initial pattern": a persistent return point for R, and what `Automata/Persistence/` saves (see below)**: three equally-weighted sources overwrite `InitialStateCells` wholesale (plain member like `SelectedCells`, but with the opposite lifecycle — it survives simulation steps *and* new mouse selections) — `StartFromSelection()` (Enter, the extracted still-alive cells), `LoadStateFromFile()` (Ctrl+O, the file's own `InitialCells` section), and `GenerateRandom()` itself (the cells that actually landed in the grid after spawning, via `Grid->GetAliveCells()` — not the raw `Amount`, since reject-sampled spawns can collide onto the same cell). `ResetToInitialState()` (`CallInEditor`, what the **R** hotkey calls via `OnResetSimulation()`) replays whichever is current: rebuilds the grid from `InitialStateCells` with all ages back at 0, then calls `GamePC->FrameAllCells()` (see **Home** above) to re-frame the camera on the result — so after watching an extracted glider, a loaded save, or just a random spawn evolve (or explode), R snaps back to its exact starting shape and re-centers the view for another run. Because `GenerateRandom()` now also populates `InitialStateCells`, and `BeginPlay` always calls `GenerateRandom()` once, `InitialStateCells` is non-empty from the moment PIE starts — the `InitialStateCells.Num() == 0` fallback to `GenerateRandom()` inside `ResetToInitialState()` is a defensive path this project's normal usage doesn't actually reach, kept rather than removed.

**Baking — freeze the current state as one hollow mesh and free the cells (experimental, marked by the user as needing further iteration before it's genuinely useful)**: `AAutomataOrchestrator::BakeCellsToMesh()` (**M** hotkey / `CallInEditor`, category `Automata|Baking`) converts the current state into a single `UProceduralMeshComponent` section and *unloads* everything else: all instanced-mesh components are cleared **and `Grid` itself is freed** (`Grid.Reset()`), so the multi-million-cell chunk/instance memory is released and large areas can be inspected cheaply — a one-way snapshot "sculpture", not a render mode (the simulation cannot continue from it; Play/fast-step are force-stopped first, and `bChunkedRenderInProgress` is cleared so a mid-flight chunked reveal can't trickle instances back in after the wipe). If `SelectedCells` is non-empty, only the selection is baked (filtered to still-alive, like `StartFromSelection()`), else all alive cells. Geometry lives in `Automata/Meshing/CellMeshBuilder.h/.cpp` (plain namespace like `CellAging`/`CellSelection`): classic face culling — for each cell, each of the 6 cube faces is emitted only if the neighbor *in the baked set* (deliberately not `IsAlive()`, so baking a selection doesn't punch holes against unselected-but-alive neighbors) is absent; 4 verts per face (no sharing — crisp cube edges), winding/UV conventions match `KismetProceduralMeshLibrary::GenerateBoxMesh()` (see the `FFaceDef` comment in the .cpp), exact-count pre-pass for `Reserve`. `BakedMeshMaterial` (Details panel) paints it, falling back to `AgeMaterials[0]` with a log line; `BakedMeshComponent` is `UPROPERTY(Transient)`, lazily created (`EnsureBakedMeshComponent()`, mirrors `EnsureSelectionMeshComponent()`). `InitialStateCells` deliberately survives the bake, and `ClearBakedMesh()` is called from `GenerateRandom()`/`ResetToInitialState()`/`StartFromSelection()` — so **R** after inspecting a bake cleanly starts a new run (replaying the extracted pattern if one exists) with the snapshot removed. Requires the `ProceduralMeshComponent` module (`Build.cs`, `PrivateDependencyModuleNames`).

- **`Automata/Persistence/`** — save/load the automaton's rules + initial pattern to a `.casave` file, with a screenshot thumbnail. `AutomatonSaveHeader.h`'s `FAutomatonSaveHeader` (`USTRUCT`, not `UObject`) is a pure JSON-serializable parameter bag — rules (`BirthCounts`/`SurvivalCounts`/`Neighborhood`, the last written as a string via `FJsonObjectConverter`), geometry (`CellSize`/`ChunkSize`/`GridSize`), generation params (`Seed`/`Amount`/`SpawnRadius`/`ClusterFactor`), and three sanity counters (`CellCount`/`InitialCellCount`/`ThumbnailPngLength`) that `AutomatonStateSerializer::WriteSave()` fills in itself from the actual data being written, so a caller can never create a mismatch `ReadSave()` would then reject. Deliberately excludes viewing/render settings (`Speed`, `StepsPerRender`, materials, meshes) — those aren't automaton state. Adding a new saved parameter is one `UPROPERTY` here plus one line each in `AAutomataOrchestrator::BuildSaveHeader()`/`ApplySaveHeader()`.

`Automata/Persistence/AutomatonStateSerializer.h/.cpp` (plain namespace, same idiom as `CellAging`/`CellSelection`) owns the `.casave` binary container format (`ContainerVersion` currently `3`): `uint32 Magic("CASV")` + `uint32 ContainerVersion` + length-prefixed UTF-8 JSON header + `CellCount`-prefixed `{X,Y,Z,Age}` cell array + `InitialCellCount`-prefixed `{X,Y,Z}` array (no age — always replayed at Age 0) + `ThumbnailPngLength`-prefixed raw PNG bytes. Two independent version fields, two independent jobs: `ContainerVersion` bumps only when the byte *layout* changes (1→2 added the `InitialCells` section, 2→3 added the thumbnail section); `FormatVersion` (inside the JSON) bumps only on an incompatible change to the header's *semantics* — adding a JSON field bumps neither, so old files keep loading as new parameters get struct defaults. Written via `FMemoryWriter64` over a `TArray64<uint8>`; read via `FMemoryReaderView` (there's no `FMemoryReader64` in this engine version, despite `FMemoryWriter64` existing) wrapping `MakeMemoryView()`. `ReadSave()` validates every section's byte count against the file's actual remaining length *before* any `TArray::SetNumUninitialized()` call, so a corrupted/hand-edited length field can't trigger a runaway allocation; older files are still readable — a `Version < 2` file's `InitialCells` is derived from its main cell list (old files never separated "current state" from "return point"), and a `Version < 3` file's thumbnail section is simply empty (valid, not an error).

`AAutomataOrchestrator::SaveState()`/`SaveStateAs()`/`LoadStateFromFile()` (Ctrl+S/Ctrl+Shift+S/Ctrl+O — see the hotkey bullet above) fall back to `IDesktopPlatform` native Save/Open dialogs (`FDesktopPlatformModule::Get()`, default directory `Saved/AutomataSaves/` via `EnsureSaveDirectory()`) except when `SaveState()` already has a `LastSaveFilePath` from a prior save/load this session, in which case it silently overwrites that file with no dialog. **What gets saved is `InitialStateCells` — the same "initial pattern" `ResetToInitialState()`/R restores from (see that paragraph above) — never the current, possibly-evolved live `Grid`**, and saving doesn't touch `Grid`/camera/render at all: no reset, no re-frame, nothing rebuilt. This went through two earlier designs before landing here — first "save whatever's currently live," then "reset the grid to the initial pattern and re-frame the camera before saving" (both abandoned: the former lost the reproducible starting point on every save-after-some-evolution, the latter needlessly threw away in-progress simulation state for no real benefit, since the initial pattern was already sitting in `InitialStateCells` without any reset needed to read it) — the shipped version mutates nothing. Because of that, `SaveState()`/`SaveStateAs()` need **no** `bStepInProgress` guard (they only read `InitialStateCells`, a plain array only ever written on the game thread by `StartFromSelection()`/`LoadStateFromFile()`/`GenerateRandom()`); `LoadStateFromFile()` does need the guard, since it swaps `Grid` out from under a possible in-flight background step, same as every other `Grid`-swapping path.

The thumbnail (`AAutomataOrchestrator::CaptureThumbnailPng()`) is a screenshot of **whatever the camera currently sees** — the live, possibly-evolved simulation, not the saved initial pattern — taken via `GEngine->GameViewport->Viewport->ReadPixels()` (synchronous, game-thread-blocking, no extra render pass needed), center-cropped to a square (short side of the viewport kept whole, long side trimmed symmetrically off both edges via a manual row-by-row `FMemory::Memcpy` — no aspect distortion, just lost frame margin), unconditionally resized (`FImageUtils::ImageResize()`) to exactly `ThumbnailSizePixels` × `ThumbnailSizePixels` (default `768`) regardless of the actual viewport resolution/aspect ratio, and encoded with `FImageUtils::PNGCompressImageArray()`. This is a deliberately *inconsistent* pairing with the saved cell data (save a freshly-extracted glider, but the thumbnail can show a whole evolved swarm if the user let it run a while before hitting Ctrl+S) — intentional, since it's meant as a personal visual bookmark of the save *moment*, not a preview of what loading the file will produce. `FImageUtils`/`FViewport::ReadPixels()` are already reachable through this project's existing `Engine`/`RHI` dependencies — no new `Build.cs` entry was needed for the screenshot itself (only `DesktopPlatform`, for the dialogs — see Module dependencies below). Written twice with the same already-encoded bytes: embedded as the container's thumbnail section, and as a same-basename sibling `.png` next to the `.casave` (`FPaths::SetExtension()`) — the sibling is what actually shows a real thumbnail tile in Windows Explorer; a native `.casave`-specific Explorer icon would require registering a COM `IThumbnailProvider` shell extension (a separate, non-UE Win32/registry project) and was explicitly rejected as disproportionate for this project. Capture failure (no `GameViewport` — not PIE — zero viewport size, `ReadPixels()`/PNG-encode failure) is warn-and-continue at every step: a failed screenshot never blocks the actual save, and a `ThumbnailPngLength == 0` file loads back with an empty thumbnail (also valid, not an error).

- **`Ui/` — the HUD.** `FUiController` (`Ui/UiController.*`) is a plain (non-UObject) RAII-style helper, not an actor: it lazily creates a `UUserWidget` from a `TSubclassOf<UUserWidget>` set by the orchestrator (`HUDWidgetClass`) and exposes `ShowHUD/HideHUD/ToggleHUD`. Owned via `TUniquePtr` by `AAutomataOrchestrator`, driven from `BeginPlay()` (see that bullet for why not `PostActorCreated()`).

**Split of responsibilities — C++ supplies data and actions, the visuals are built by hand in UMG**: `UMainHudWidget` (`Ui/MainHudWidget.*`) is a thin native shell whose only job is `GetOrchestrator()` — a lazily resolved, `IsValid()`-revalidated `GetActorOfClass()` lookup (the same idiom as `EnsureRenderCullVolume()`), deliberately *not* an editor-assigned reference, since a widget asset cannot hold a pointer to a specific level actor. The layout lives in a Blueprint subclass (`Content/HUD/WBP_MainHud`) assembled in the UMG Designer. Everything the widget needs is therefore exposed as `BlueprintPure`/`BlueprintCallable`/`BlueprintType` on the orchestrator; when the HUD needs something new, the change belongs in C++ as API, not as widget-construction code.

**Data**: two `USTRUCT(BlueprintType)` summaries, both computed once and read by everyone rather than recomputed per consumer (so a log line and the on-screen number can never disagree). `FCellRenderStats` (`GetLastRenderStats()`) — `RenderedCellCount`/`TotalCellCount` ("drawn/total", i.e. how much the cull volume is removing), `EstimatedUploadMB` (sized from `RenderedCellCount`, a single figure like a file size, not a before/after pair) and `BytesPerInstance`, filled by `BuildAgeBuckets()`. `FHudStats` (`GetHudStats()`) — `bIsComputing`/`bIsRendering` (the `bStepInProgress`/`bChunkedRenderInProgress` phases, which can overlap), `CurrentFPS` (`GAverageFPS`, not recomputed), `GenerationCount`, `GenerationsPerSecond` (recomputed on a one-second window, not per frame — sub-second sampling is visibly noisy at low `Speed`), `EstimatedGpuComputeUploadMB` (read from whatever the GPU strategy already packed, never a separate grid scan), plus `AliveCellCount` (`Grid->Num()`, O(1) — the chunks keep the count) and `SelectedCellCount`. The last two refresh every tick, so a Delete or a new selection shows up immediately rather than at the next generation. `LastHudStats` is a `UPROPERTY` for the usual Live-Coding-reinstancing reason (see `GamePC`).

**Actions**: the simulation entry points were already `BlueprintCallable`; the HUD additions are `SetSpeed()`/`SetStepsPerRender()` (absolute setters for sliders, applying the same clamps as the `+`/`-` and T/G hotkeys rather than letting a slider write the `BlueprintReadWrite` property raw and reach 0), `TryApplyRuleString(In, out Error)` (same as `ApplyRuleString()` but takes the string as a parameter and hands the parse error *back* — a `UE_LOG` warning is invisible from UMG, and silently doing nothing on a button press is the worst option), and `GetActiveRuleString()`.

**`RulePresets` (`Automata/Simulation/RulePresets.h/.cpp`, plain namespace + `FRulePreset` `USTRUCT(BlueprintType)`)** — 13 ready-made rules transcribed verbatim from williamyang98/3D-Cellular-Automata's `system_entries.js`, in the source's own order and naming so a preset can be checked against the site one-to-one ("Builder 1"/"Builder 2" really are duplicates upstream; kept so the numbering matches). Each carries `Name`/`RuleString`/`SpawnRadius`/`Amount`; `GetRulePresets()` lists them and `ApplyRulePreset(Index, bApplySpawnSettings)` applies one **through `TryApplyRuleString()`**, so presets and hand-typed rules share exactly one application path instead of two that could drift. It deliberately does *not* regenerate the grid — applying a rule to an already-grown structure is sometimes exactly what's wanted, and "start fresh with this preset" is one more `GenerateRandom()` click. The upstream table specifies a fill *density*, which this project can't use directly (`Amount` is an absolute count and `GenerateRandom()` reject-samples **with collisions**, so `density × volume` systematically under-seeds); `Amount` is therefore derived with the coupon-collector estimate `N·ln(1/(1-p))`, `p` capped at 0.95 since full coverage by random draws is unreachable in principle. Two presets whose upstream radius is grid-relative get a concrete radius of 30, because `GridSize` doesn't affect generation in this project at all (it is saved and loaded, but `GenerateRandom()` seeds purely by `SpawnRadius`).

`AGameHud` (`Core/Hud/GameHud.*`, wired via `AAGameMode::HUDClass`) is separate and unrelated to UMG: a native `AHUD` subclass whose `DrawHUD()` paints the live marquee rectangle during a selection drag.

All of the plain-C++ helper classes above (`FUiController`, `FCellGrid`/`FDenseCellGrid`, `FCellGridRenderer`/`FInstancedMeshCellGridRenderer`, `FCellularAutomatonRule`) follow the same convention: non-copyable, owned via `TUniquePtr` (or, for `FCellularAutomatonRule`, constructed as a short-lived local) by whichever `UObject`/Actor uses them, `TWeakObjectPtr` (not raw pointers) for any `UObject` references they hold.

### Source layout convention

Code is being migrated from a flat `Orchestration/` and `Ui/` dump into a `Core/<Subsystem>/` layout (see the pending rename of `AGameMode`/`GamePlayerController` in git status). When adding new engine-level classes (game mode, controllers, pawns, etc.), place them under `Source/CellularAutomata/{Public,Private}/Core/<Subsystem>/`; higher-level gameplay/orchestration code stays under `Orchestration/`; widget/HUD glue stays under `Ui/`.

### Module dependencies

`CellularAutomata.Build.cs` pulls in `Core, CoreUObject, Engine, InputCore, Slate, SlateCore, UMG, WebBrowser, WebBrowserWidget, Json, JsonUtilities` as public dependencies, plus `EnhancedInput`, `RHI`, `RenderCore`, `ProceduralMeshComponent`, `DesktopPlatform` as private dependencies. `EnhancedInput` was added for `AGamePlayerController`'s Play/Stop hotkey — `EnhancedInput` is already the project's active input system per `Config/DefaultInput.ini`'s `DefaultPlayerInputClass`/`DefaultInputComponentClass`, so no plugin-enablement change was needed, just the module reference. `RHI`/`RenderCore` were added for `FGpuComputeStrategy`'s RDG compute-shader dispatch (see `Automata/Simulation/ComputeStrategy/`). `ProceduralMeshComponent` is for `BakeCellsToMesh()` (see the Baking paragraph above). `DesktopPlatform` is for the native Save/Open dialogs in `Automata/Persistence/` (see below) — a Developer module, unavailable in Shipping builds, which is fine since this project only runs in editor/PIE; the thumbnail screenshot itself (`FImageUtils`/`FViewport::ReadPixels()`) needed no separate module, already reachable through `Engine`/`RHI`. The `WebBrowser`/`WebBrowserWidget` dependency was for a `Ui/WebInterface` widget that has since been deleted — if reintroducing browser-based UI, that's the intended integration point. **Note**: adding a module to `Build.cs` isn't something Live Coding can hot-patch — it requires closing the Editor and a full cold rebuild (see Build/run section above).

`RemoteControlWebInterface` and `RiderLink` are both present but **disabled** (`"Enabled": false`) in the `.uproject` Plugins list — `RemoteControlWebInterface` tries to build a React web app on editor startup and fails in this environment (`Failed To Build WebApp`); `RiderLink`'s `RiderDebuggerSupport.dll` gets blocked by Windows Smart App Control (unsigned binary, `GetLastError=4551`). Don't re-enable either without addressing the underlying cause first.

### MCP / AI-editor integration

`Plugins/McpAutomationBridge` (from github.com/ChiR24/Unreal_mcp) is installed and gives Claude Code direct control of the running Editor over HTTP — spawning/inspecting actors, screenshots, console commands, asset ops, etc. Native MCP mode is enabled via `Config/DefaultGame.ini` (`[/Script/McpAutomationBridge.McpAutomationBridgeSettings]`, `bEnableNativeMCP=True`, port 3000) — no Node.js/bridge process needed. Registered in Claude Code at **user scope** (`claude mcp add unreal-engine --transport http --scope user http://localhost:3000/mcp`); MCP server tool lists only refresh when a Claude Code session (re)starts, not mid-session.

**Fast iteration loop while the Editor is already open**: after editing C++, trigger a hot patch instead of closing the editor for a full UBT rebuild — via the MCP `control_editor` tool's `console_command` action (or the in-editor Ctrl+Alt+F11 hotkey) running `LiveCoding.Compile`. This requires Live Coding to be enabled in the Editor already. A pure function-body edit (no new/changed `UPROPERTY`/`UFUNCTION`) patches in under a second; if unsure whether a patch actually landed, compare the edited `.cpp`'s mtime against `Intermediate/Build/Win64/x64/UnrealEditor/Development/CellularAutomata/<File>.cpp.obj` and `Binaries/Win64/UnrealEditor-CellularAutomata.dll`. A full cold UBT build still requires the Editor process to be closed first (it locks the DLL):
`"C:\Program Files\Epic Games\UE_5.7\Engine\Build\BatchFiles\Build.bat" CellularAutomataEditor Win64 Development -Project="<repo>\CellularAutomata.uproject" -WaitMutex`

**Known instability**: `LiveCoding.Compile` on an edit that changes reflection data (new/changed `UPROPERTY`/`UENUM`/`UFUNCTION` on a class with a live instance in the open level) has repeatedly crashed the Editor process during class reinstancing in this environment, restarting it silently with no crash dump (check `Saved/Logs/CellularAutomata.log`'s `Log file open` timestamp to detect this). Pure function-body edits have not shown this problem. After such a crash the patch is usually still applied (verify via MCP `inspect`/`get_property` once the Editor is back up) — no need to redo the edit, just reconnect.
