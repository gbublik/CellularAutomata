# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Unreal Engine 5.7 C++ game project (`CellularAutomata.uproject`) implementing a 3D cellular-automata simulation, rendered with `UHierarchicalInstancedStaticMeshComponent` cell instances (one cube mesh instanced per live cell). The gameplay module is `CellularAutomata` (Runtime, Default loading phase).

The project briefly depended on the third-party **VoxelFree** plugin (SDF/marching-cubes voxel terrain engine) but that was dropped and the plugin fully removed — it was built for volumetric terrain, not for placing discrete cell instances, and was unnecessary overhead for this project's needs. Do not reintroduce a `Voxel` module dependency without deliberate reconsideration.

## Architecture

Actor/controller composition, not a monolithic GameMode:

- **`AAGameMode`** (`Core/GameMode/AGameMode.*`) — minimal; only wires `PlayerControllerClass` to `AGamePlayerController`. Note the doubled `A` prefix: the UE Actor-class convention (`A`) plus the class's own name (`AGameMode`) yields `AAGameMode`. `DefaultEngine.ini`'s `GlobalDefaultGameMode` points at this class.
- **`AGamePlayerController`** (`Core/PlayerController/GamePlayerController.*`) — owns the camera. No spline-following camera anymore (removed — see below); just toggles between gameplay input (`FInputModeGameOnly`, pawn input enabled) and UI input (`FInputModeGameAndUI`, cursor shown, pawn input disabled) via `SetCameraControlEnabled()`, and on `BeginPlay` sets FOV (viewmode is no longer forced here — see hotkeys below). `SetupInputComponent()` binds thirteen testing hotkeys, all resolving the `AAutomataOrchestrator` in the world via `UGameplayStatics::GetActorOfClass` (except the camera-only ones) — built with Enhanced Input (`UInputAction`/`UInputMappingContext` constructed at runtime via `NewObject`, not saved as `.uasset` content, since a handful of project-wide hotkeys doesn't need dedicated assets), all mapped on one shared `SimulationMappingContext`: **P** (`OnToggleSimulation()`) calls `Start()`/`Stop()` depending on `IsSimulationRunning()`; **F** (`OnFastStepPressed()`/`OnFastStepReleased()`, bound to `ETriggerEvent::Started`/`Completed`) — a bare press (no Shift) just calls `Next()` once, same manual single-step as the original design; if Shift is down at the moment F is pressed (checked via `IsInputKeyDown(EKeys::LeftShift)`, not a separate Enhanced Input binding), it instead calls `AAutomataOrchestrator::StartFastStep()` — a **hold** mode, independent of `bSimulationRunning` and mutually exclusive with it (`Start()` refuses while `IsFastStepActive()`, and `StartFastStep()` refuses while Play is running), that paces steps by `Speed` exactly like continuous Play via the same `bFastStepActive` branch in `Tick()` (ahead of the `bSimulationRunning` branch, sharing `TimeSinceLastStep`/`StepAsync()`/chunked-render with zero duplicated logic) — and stops the instant F is released (`OnFastStepReleased()` calls `StopFastStep()` only if `IsFastStepActive()`). Bound to `Started`/`Completed` rather than `Triggered` specifically so a bare hold of F doesn't repeat `Next()` every frame (that was the pre-Shift-hold-mode behavior and confused continuous auto-stepping with a single step). **R** (`OnResetSimulation()`) calls `GenerateRandom()` to reset to a fresh random state with the same `Seed`, and is deliberately *not* gated on `IsSimulationRunning()` since `GenerateRandom()` already guards its own race with `bStepInProgress`; **1**/**2** (`OnSetLitMode()`/`OnSetUnlitMode()`) toggle `VIEWMODE LIT`/`VIEWMODE UNLIT` via console command — the game used to force Unlit unconditionally on `BeginPlay` (to skip lighting cost when rendering large numbers of instanced automaton cells), but now starts lit by default and Unlit is an opt-in hotkey instead; **Left Shift** (held) — `OnSpeedBoostStarted()`/`OnSpeedBoostEnded()` (bound to `Started`/`Completed`) scale the possessed `ADefaultPawn`'s `UFloatingPawnMovement::MaxSpeed` by `AAutomataOrchestrator::CameraSpeedMultiplier` for faster flying while held, restoring the original speed on release — `BaseFlySpeed` caches that original value on first press (guarded by `<= 0.0f` so a stray repeated `Started` can't cache an already-boosted speed). `CameraSpeedMultiplier` lives on the orchestrator rather than the controller/pawn so a designer tunes it from the same Details panel as the rest of the simulation; **Z** (`OnToggleChunkedRender()`) flips `AAutomataOrchestrator::bEnableChunkedRender` via `SetChunkedRenderEnabled()`/`IsChunkedRenderEnabled()` — there's no automatic cell-count threshold for chunked rendering (an earlier `ChunkedRenderCellThreshold` property was removed), it's purely a manual on/off toggle now; **=/NumPad+** and **-/NumPad-** (`OnIncreaseSpeed()`/`OnDecreaseSpeed()`, both bound to `Triggered` like `F`, so holding repeats) call `AAutomataOrchestrator::AdjustSpeed(±SpeedAdjustStep)` to nudge `Speed` up/down by a fixed `0.5` step, clamped to `[0.1, 100.0]` inside `AdjustSpeed()` itself — deliberately wider than `Speed`'s own `UIMax = "10.0"` metadata, since that only caps the Details-panel slider, not a hard `ClampMax`; **Home** (`OnFrameAllCells()`) moves the possessed pawn along its *current* view direction (viewing angle unchanged, only distance) so the whole live-cell set fits in frame — `AAutomataOrchestrator::ComputeAliveCellsBounds()` scans `GetAliveCells()` once for a world-space AABB (via `GridToWorld()` on the min/max cell coordinates, expanded by half a `CellSize` since `GridToWorld()` gives cell *centers*) and returns its center and bounding-sphere radius (false if the grid is empty/uninitialized); the controller then computes `Distance = Radius / sin(FOV/2)` (the exact distance at which a sphere of that radius exactly fills the frustum half-angle, using `PlayerCameraManager->GetFOVAngle()`), multiplies by a small `FramingPadding` (`1.1`) so cells don't touch the frame edge, and sets the pawn's location to `Center - CameraRotation.Vector() * Distance` via `PlayerCameraManager->GetCameraRotation()`; **T**/**G** (`OnIncreaseStepsPerRender()`/`OnDecreaseStepsPerRender()`, bound to `Triggered` like `+`/`-` for Speed, so holding repeats) call `AAutomataOrchestrator::AdjustStepsPerRender(±1)` to nudge `StepsPerRender` (see `StepsPerRender` under Chunked rendering below), clamped to a minimum of `1` inside `AdjustStepsPerRender()` itself (originally mapped to `[`/`]` but rebound by hand during testing — see `SetupInputComponent()` for the current mapping). **Why hotkeys and not just the `CallInEditor` buttons**: clicking a `CallInEditor` button in the Details panel during PIE is unreliable — if the World Outliner still has the non-PIE (persistent-level) copy of the actor selected rather than its PIE-world duplicate, the click invokes the function on the frozen editor-world instance, whose `Tick()` never runs (`AActor::TickActor` early-returns when `TickType == LEVELTICK_ViewportsOnly`, which is how the engine ticks actors outside PIE) — so e.g. continuous Play silently never begins, with no error. Hotkeys sidestep this entirely since key input always arrives via the currently-possessing (PIE-world) `PlayerController`. Requires the `EnhancedInput` module (see below).
- **`AAutomataOrchestrator`** (`Orchestration/AutomataOrchestrator.*`) — the top-level conductor, placed in the level as an Actor. Root component is `CellsMeshHierarchical` (`UHierarchicalInstancedStaticMeshComponent`); `CellsMeshFlat` (`UInstancedStaticMeshComponent`) is attached as its child. Both are created unconditionally in the constructor and exist for the actor's whole life — `CellMeshComponentType` (`ECellMeshComponentType::Instanced`/`HierarchicalInstanced`, default `HierarchicalInstanced`) just picks which one actually receives instances at render time (see `GetActiveCellsMeshComponent()`/`InitializeRenderer()` under `Automata/Rendering/` below); there is no separate scene-root or camera spline (that system was fully removed; `AGamePlayerController` no longer has `StartSplineMovement`/`StopSplineMovement`/spline-following `Tick`). Owns simulation parameters (`GridSize`, `GridStorageStrategy`, `ChunkSize`, `Amount`, `Seed`, `SpawnRadius`, `ClusterFactor`, `Speed`, `CameraSpeedMultiplier`, `CellMesh`/`CellMaterial`/`CellSize`/`CellMeshComponentType`, `bEnableChunkedRender`/`ChunkedRenderCellsPerFrame`/`StepsPerRender`, `BirthCounts`, `SurvivalCounts`, `Neighborhood`) exposed as `CallInEditor` UFUNCTIONs (`Start/Pause/Resume/Stop/Next/Clear/GenerateRandom/NewSeed`) so designers can drive the sim from the Details panel. `BeginPlay` wires up the player controller and immediately calls `GenerateRandom()` — the HUD is **not** shown automatically anymore (`InitializeHUD()`/`FUiController` still exist and are called from `PostActorCreated()` for editor-time HUD class validation, but no longer from `BeginPlay`). `NewSeed()` re-rolls `Seed` via `FMath::Rand()` and calls `GenerateRandom()`. A private `CreateGrid()` helper (switches on `GridStorageStrategy`) is shared by `GenerateRandom()` (fresh grid) and `Next()`/`StepAsync()` (next-generation buffer), so the three never duplicate the `Sparse`/`Dense` construction logic. `GenerateRandom()`/`Next()`/`StepAsync()`→`ApplyStepResult()` all log generation-or-step and render timing (`FPlatformTime::Seconds()`) as an ad-hoc profiling baseline ahead of scaling to much larger cell counts. `Next()` builds a fresh `FCellularAutomatonRule` from `BirthCounts`/`SurvivalCounts`/`Neighborhood` every call (so Details-panel edits take effect immediately, no caching), double-buffers into a new grid via `CreateGrid()`, then swaps it in and re-renders. **Still stub**: `Clear`. Cell storage/rendering/simulation is delegated to the `Automata/` subsystem (below), not implemented inline.

Continuous play/stop: `Start()` (also acts as the "Play" entry point) generates a grid if none exists yet, resets the tick accumulator, sets `bSimulationRunning = true`, and calls `SetActorTickEnabled(true)`. `PrimaryActorTick.bCanEverTick = true` but `bStartWithTickEnabled = false` in the constructor, so the actor doesn't tick at all until `Start()` explicitly enables it. `Tick()` accumulates `DeltaTime` and, once it crosses `1/Speed` seconds (recomputed each tick, not cached, so editing `Speed` in the Details panel takes effect immediately), calls `StepAsync()` — **not** `Next()` — provided no background step is already in flight (`!bStepInProgress`) and no render hand-off is pending (`!bRenderHandoffPending`, see `StepsPerRender` below); if either is true, that tick is skipped rather than queued. `Stop()` clears `bSimulationRunning`, calls `FinishChunkedRenderImmediately()` (see Chunked rendering below — snaps any in-progress reveal, including a pending hand-off, straight to its final state instead of leaving it frozen once ticking stops), then disables ticking; it does **not** reset the grid (that's `Clear()`'s job, still a stub).

**`StepAsync()` — off the game thread, so continuous Play doesn't stall the camera/UI**: `Next()` (the manual `CallInEditor` button) stayed fully synchronous — useful for immediate single-step feedback while designing a rule — but during continuous Play, the same synchronous cost was landing straight in `Tick()`, blocking the game thread (and therefore camera movement/input) for as long as the step took, which got severe at scale (multi-second stalls once the grid grew past hundreds of thousands of cells). `StepAsync()` fixes this: on the game thread it first builds `FCellularAutomatonRule` from `BirthCounts`/`SurvivalCounts`/`Neighborhood`, a compute strategy via `CreateComputeStrategy()` (picks `FCpuComputeStrategy`/`FGpuComputeStrategy` per `ComputeMethod` — see `Automata/Simulation/` below), and a fresh `NextGridBuffer` via `CreateGrid()` (all three read Details-panel `UPROPERTY`s, so this snapshot has to happen before handing off — a background thread must never race a Details-panel edit), sets `bStepInProgress = true`, then dispatches `ComputeStrategy->Step(*Grid, *NextGridBuffer, AutomatonRule)` onto `Async(EAsyncExecution::ThreadPool, ...)` (`ComputeStrategy`, a `TUniquePtr`, is captured by move into the lambda exactly like `NextGridBuffer`). The CPU strategy's internal `ParallelFor` (see `Automata/Simulation/` below) still runs fine nested inside this — the calling thread is now a thread-pool worker instead of the game thread, so the game thread is free the whole time. When the background lambda finishes, it hands off to `AsyncTask(ENamedThreads::GameThread, ...)`, which calls `ApplyStepResult()` — swaps `Grid` and immediately clears `bStepInProgress` (deliberately at the *top* of the function, right after the swap, not at the end — its scope is narrowed to exactly "a background `Step()` is reading `*Grid`", nothing about rendering) before deciding whether/how to render (see `StepsPerRender` under Chunked rendering below); `Next()` and `GenerateRandom()` both check `bStepInProgress` and refuse (with a warning log) to run while a background step is outstanding — otherwise a manual click during Play could swap `Grid` out from under the background thread mid-read. The game-thread→background handoff captures `this` only as a `TWeakObjectPtr` for the completion callback (guards against the actor being destroyed — e.g. level unload — while a step is in flight; the background lambda itself never touches `this` at all, only the pre-snapshotted rule/grid pointers).

**Chunked rendering — spreads `AddInstances` across multiple frames for huge grids**: even with `StepAsync()` moving the simulation step off the game thread, `Renderer->Render()`'s own `AddInstances` call is still synchronous and still runs on the game thread — profiling showed it alone taking tens to hundreds of milliseconds once the grid grows past a few hundred thousand live cells, which is enough to stall the camera for a visible frame even though the step itself no longer does. `ApplyStepResult()` only takes this path for continuous Play (`StepAsync`'s completion), gated purely by `bEnableChunkedRender` — no automatic cell-count threshold; it's a manual on/off switch (Details panel or the **Z** hotkey, see `AGamePlayerController::OnToggleChunkedRender()` above) — `Next()`/`GenerateRandom()` always render the whole grid in one shot, since spreading a single deliberate manual action across frames would hurt responsiveness rather than help it. When chunking triggers, the shared `RenderCurrentGrid()` helper (used by both `ApplyStepResult()`'s normal path and the deferred hand-off below) calls `Renderer->BeginRender(*Grid)` (builds the full `TArray<FTransform>` and clears the component once, but adds nothing yet) and sets `bChunkedRenderInProgress = true` — `bStepInProgress` is unaffected (already cleared, see `StepAsync()` above). `Tick()` then calls `AdvanceChunkedRender()` every frame — regardless of `bSimulationRunning`, so a reveal already in progress finishes even if `Stop()` is called mid-way — which calls `Renderer->AdvanceRenderChunk(ChunkedRenderCellsPerFrame)` to add the next slice of the pre-built transforms; once the whole array has been added, it clears `bChunkedRenderInProgress` and logs how many frames the reveal took. `FInstancedMeshCellGridRenderer::Render()` itself is implemented as `BeginRender()` followed by one unbounded `AdvanceRenderChunk()` call, so the one-shot and chunked paths share the same transform-building code without duplication.

**`StepsPerRender` — computing generations ahead of the display, without rendering every one**: at large cell counts, even chunked `AddInstances` costs real time, and showing every single generation isn't necessary — `StepsPerRender` (default `1` = render every generation, current behavior) lets `ApplyStepResult()` skip rendering for `StepsPerRender - 1` out of every `StepsPerRender` computed generations, only calling `RenderCurrentGrid()` once the counter (`StepsSinceLastRender`, reset in `GenerateRandom()`/`Start()`/`StartFastStep()` for a clean count on every fresh run) reaches the threshold; skipped generations just log a "рендер пропущен (X/Y)" line and return immediately, so `Tick()` can dispatch the next `StepAsync()` right away (paced only by `Speed`, same as always) — this is exactly what narrowing `bStepInProgress`'s scope (see `StepAsync()` above) enables: computing ahead no longer waits on `bChunkedRenderInProgress`. This deliberately caps how far ahead the simulation can get to **at most one batch** past what's on screen: if the `StepsPerRender`-th generation finishes computing while the *previous* one's chunked reveal hasn't finished trickling in yet, `ApplyStepResult()` doesn't interrupt that reveal (which would abandon its progress and restart from scratch) — instead it sets `bRenderHandoffPending = true` and returns, and `Tick()`'s dispatch condition also checks `!bRenderHandoffPending`, so no further stepping happens until the hand-off completes. `AdvanceChunkedRender()` checks `bRenderHandoffPending` right after finishing a reveal and, if set, immediately calls `RenderCurrentGrid()` for the (by-then possibly even more current) `Grid` and clears the flag — at which point `Tick()` is free to start the next batch. `FinishChunkedRenderImmediately()` (`Stop()`'s helper, see above) does the same hand-off check before its own flush loop, so a pending generation is never left permanently unrendered just because Play was stopped mid-wait. `Next()`/`GenerateRandom()` ignore `StepsPerRender` entirely — they always render synchronously and immediately, same as they always ignore `bEnableChunkedRender`'s spreading.

**Correctness note on `GamePC`**: `AGamePlayerController* GamePC` is a `UPROPERTY(Transient)`, not a raw pointer — this matters specifically because of Live Coding. Reinstancing after a hot patch during an active PIE session only copies `UPROPERTY`-tagged fields from the old instance to the new one; a plain C++ member survives as uninitialized garbage (not `nullptr`), and `BeginPlay()` — the only place that populates `GamePC` — does not re-run on reinstancing. A raw-pointer `GamePC` therefore silently held garbage after any Live Coding patch made during PIE, and `Pause()`/`Resume()` dereferencing it segfaulted (`Access violation`) the next time either was called, crashing the whole Editor process. Fixed by making it a `UPROPERTY` (so reinstancing either preserves it correctly or resets it to `nullptr`) plus explicit null checks in `Pause()`/`Resume()` that log a warning and return instead of crashing when `GamePC` isn't set yet (e.g. before `BeginPlay`/outside PIE). Any other raw non-`UPROPERTY` `UObject*` member added to `AAutomataOrchestrator` (or any `UCLASS` in this project) in the future is a candidate for the same bug.
- **`Automata/Grid/`** — `FCellGrid` (`CellGrid.h`, abstract, plain C++ not `UObject`): stores live cells addressed by integer `FIntVector` coordinates, decoupled from rendering. `GetAliveCells`/`SetAlive`/`Clear`/`Num` are pure virtual; `GridToWorld(FIntVector)` is **virtual with a default cubic-lattice implementation** (`Cell * CellSize`) — deliberately virtual so a future non-cubic topology (e.g. hex) can override just the coordinate-to-world math without touching storage or rendering. Two concrete implementations: `FSparseCellGrid` (`SparseCellGrid.*`, `TSet<FIntVector>`-backed, good for large mostly-empty grids) and `FDenseCellGrid` (`DenseCellGrid.*`, chunked: space is divided into fixed-size cubic chunks — default `ChunkSize=16`, i.e. 4096 cells — each a packed `TBitArray`; chunks live in a sparse `TMap<FIntVector, FChunk>` and are lazily created on first live cell / pruned when they empty out, so memory scales with occupied volume, not a fixed upper bound). `AAutomataOrchestrator::GridStorageStrategy` (`EGridStorageStrategy::Sparse`/`Dense`) picks which one `CreateGrid()` constructs. **Correctness note if touching `FDenseCellGrid`**: chunk-coordinate math needs real floor-division/positive-modulo helpers (defined file-local in `DenseCellGrid.cpp`) because cell coordinates routinely go negative (sphere-centered generation) and `FMath::DivideAndRoundDown` is *not* floor division for integers (it truncates toward zero). Chunk granularity is intentionally the unit future CPU/GPU per-chunk dispatch would parallelize over — not implemented yet.
- **`Automata/Simulation/`** — `ENeighborhood` (`Neighborhood.h`, `UENUM`): `VonNeumann` (6 face neighbors) or `Moore` (26, full 3×3×3 cube minus center) — deliberately its own header rather than folded into `AutomataOrchestrator.h`, so the simulation subsystem owns its own type. `FCellularAutomatonRule` (`CellularAutomatonRule.*`, plain C++ not `UObject`) is a **pure parameter holder** — takes `BirthCounts`/`SurvivalCounts` (each a `TArray<int32>`, exposed as `AAutomataOrchestrator::BirthCounts`/`SurvivalCounts` UPROPERTYs so designers edit them as plain arrays in the Details panel) plus a neighborhood, stores them as `TSet<int32>`/`TArray<FIntVector>` (O(1) membership checks / precomputed offsets) behind `GetBirthCounts()`/`GetSurvivalCounts()`/`GetNeighborOffsets()` getters, and owns **no stepping logic at all** — that's delegated to a swappable `Automata/Simulation/ComputeStrategy/` implementation (below). **Deliberately no rule string / parser** — an earlier version used classic Conway notation (`"B3/S23"`) with a hybrid parser (digit-per-count vs. comma-separated) to handle 3D neighbor counts exceeding 9 (up to 26 for Moore); that ambiguity and parsing complexity is why it was replaced with three explicit, independent, unambiguous parameters.

**`Automata/Simulation/ComputeStrategy/` — pluggable compute strategy**: `FCellularAutomatonComputeStrategy` (`CellularAutomatonComputeStrategy.h`, abstract, plain C++ not `UObject`, non-copyable — same convention as `FCellGrid`/`FCellGridRenderer`) declares the one-generation contract `virtual void Step(const FCellGrid& CurrentGrid, FCellGrid& NextGrid, const FCellularAutomatonRule& Rule) const = 0`: for every alive cell and its neighbors (candidate set, so cells can only be born adjacent to something alive), counts alive neighbors in `CurrentGrid` and writes the next state into `NextGrid` — never mutates `CurrentGrid`, so callers must double-buffer (see `AAutomataOrchestrator::Next()`). This is a deliberately **synchronous/blocking** contract mirroring the original `FCellularAutomatonRule::Step()` it replaced — `Next()`/`StepAsync()` already wrap the call appropriately for their own needs (`StepAsync()` dispatches onto `Async(EAsyncExecution::ThreadPool, ...)`, see above), so a strategy with its own async backend (e.g. a GPU dispatch+readback) does that internally rather than changing this interface. `AAutomataOrchestrator::ComputeMethod` (`EComputeMethod::Cpu`/`Gpu`) picks which concrete strategy `CreateComputeStrategy()` constructs — a private factory that switches on `ComputeMethod` exactly like `CreateGrid()` switches on `GridStorageStrategy`; both `Next()` and `StepAsync()` call it fresh every invocation (same "rebuild from Details-panel UPROPERTYs every call" convention as `FCellularAutomatonRule` itself), so switching methods mid-session takes effect immediately with zero caching.

`FCpuComputeStrategy` (`CpuComputeStrategy.*`) is the **only currently-working implementation** — an exact relocation of the original `FCellularAutomatonRule::Step()` body, with `NeighborOffsets`/`BirthCounts`/`SurvivalCounts` member access rewritten to `Rule.GetNeighborOffsets()`/`Rule.GetBirthCounts()`/`Rule.GetSurvivalCounts()` and otherwise unchanged. **Parallelized across CPU threads**: the per-candidate neighbor-count-and-decide work only reads `CurrentGrid`, so it's embarrassingly parallel — it runs via `ParallelFor` over an indexed `TArray<FIntVector>` of deduplicated candidates, writing each candidate's next-alive state into an indexed `TArray<bool>` (not bit-packed in Unreal, unlike `std::vector<bool>`, so concurrent writes to distinct indices don't race). The actual `NextGrid.SetAlive(...)` calls happen afterward in a plain sequential loop over that result array — `TSet`/`TBitArray` inside `FSparseCellGrid`/`FDenseCellGrid` aren't thread-safe for concurrent writes, so they can't be called from inside the `ParallelFor` body. Verified via a temporary thread-ID-collecting diagnostic that this engages the real OS thread pool (~31 threads — 30 `FTaskGraphInterface` workers plus the calling thread — on a 16-core dev machine), not just nominal capacity.

**Candidate-set construction is itself parallelized (bucket-partitioned dedup)** — profiling at 1M+ live cells (added `FPlatformTime::Seconds()` breakdown logging inside `Step()`, still present) revealed that an earlier `TSet<FIntVector>`-based dedup (each alive cell's `Cell` + all `NeighborOffsets` inserted via `TSet::Add`, up to 27 hash-insertions per alive cell for Moore) consumed ~80% of total step wall-time on a single thread, even though the neighbor-count `ParallelFor` above genuinely engaged ~31 threads — the dedup itself was the actual bottleneck the whole time, not the per-candidate work. A first attempt at fixing this (fill a flat pre-sized array with duplicates via `ParallelFor`, then a single global `Algo::Sort`+`Algo::Unique` pass) measured *no real improvement*: `Algo::Sort` has no parallel variant in this engine, so sorting the entire un-deduplicated array (which is exactly as large as the old TSet's total insert count) is comparably expensive to hashing it — swapping one single-threaded bottleneck for another. The actual fix partitions candidates into `NumBuckets = 256` independent buckets by `GetTypeHash(Candidate) & BucketMask` (deterministic, so every duplicate of the same cell always lands in the same bucket regardless of which alive cell or thread produced it) via a classic counting-sort scatter: (1) a `ParallelForWithTaskContext` histogram pass gives each task a thread-local `TArray<int32>` bucket-count array (no synchronization), merged into one global histogram afterward (cheap — `NumTasks × NumBuckets` small ints); (2) a prefix sum over the histogram gives each bucket's offset into a flat `Scattered` array; (3) a second `ParallelFor` over alive cells scatters every raw candidate (duplicates included) into its bucket's slice, using `FPlatformAtomics::InterlockedIncrement` on a per-bucket cursor (`BucketCursors`, seeded from the offsets) since multiple threads write into the same bucket concurrently — but buckets themselves never overlap in memory; (4) a `ParallelFor(NumBuckets, ...)` sorts (`Algo::Sort`) and dedups (`Algo::Unique`) each bucket's slice independently, in parallel, with zero cross-thread synchronization since bucket memory ranges are disjoint; (5) a final `ParallelFor(NumBuckets, ...)` `FMemory::Memcpy`s each bucket's deduplicated slice into its final position in `Candidates` (offsets from a second prefix sum over post-dedup bucket sizes). Verified in PIE: at ~2.2M live cells this dropped `CandidateBuild`'s share of step time from ~80% to ~38% (675ms out of 1760ms total, vs. `ParallelFor`'s 865ms and `WriteBack`'s 213ms) — the dedup work itself is now genuinely spread across cores instead of the neighbor-count phase being the only real parallel section.

`FGpuComputeStrategy` (`GpuComputeStrategy.*`) is a **real RDG compute-shader implementation** — grid-storage-agnostic, like the CPU strategy (only touches `FCellGrid` through `GetAliveCells()`/`SetAlive()`, never `FSparseCellGrid`/`FDenseCellGrid` internals). `Step()` runs entirely on the calling thread plus one Render Thread round-trip: (1) `GetAliveCells()` then a plain sequential min/max scan gives an integer cell-space AABB (empty grid → return immediately, `NextGrid` stays empty); (2) the AABB is expanded by `Halo = 1` cell in every axis — safe in general because every `NeighborOffsets` entry (`CellularAutomatonRule.cpp::BuildNeighborOffsets`, both `VonNeumann` and `Moore`) has components only in `{-1,0,1}`; (3) **OOM guard**: if the resulting `VolumeDim.X*Y*Z` exceeds `256^3` (~16.7M cells, a 2MB bit buffer) — which can happen if two live cells end up far apart in a sparse grid — it logs a warning and falls back to `FCpuComputeStrategy` for that step, the same "never silently do nothing" convention the old stub used; (4) alive cells are packed into a flat `TArray<uint32>` bit buffer (32 cells/word) in AABB-local coordinates, and the rule is packed into `BirthMask`/`SurvivalMask` `uint32` bitmasks (bit *i* = count *i* allowed — 0–26 fits easily) plus a fixed `int4[26]` neighbor-offset array (Moore's 26 is the max; `VonNeumann`'s 6 just leaves the tail unused, gated by an explicit `NeighborOffsetCount`). Cells outside the halo of any live cell are never dispatched-into as "alive" and, symmetrically, any out-of-buffer neighbor read the shader does is treated as dead — this exactly matches the CPU strategy's candidate-set semantics (a cell with 0 live neighbors is never evaluated as a birth candidate by either strategy, even if `BirthMask` technically allows it).

Dispatch happens inside `ENQUEUE_RENDER_COMMAND` (so RDG/RHI calls run on the Render Thread as required) which builds an `FRDGBuilder`, uploads the input buffer (`CreateStructuredBuffer`), clears a same-sized output buffer (`AddClearUAVPass`), runs `FCellularAutomatonStepCS` (a file-local `FGlobalShader` in `GpuComputeStrategy.cpp`, one `[numthreads(4,4,4)]` thread per cell in the volume, `Shaders/Private/CellularAutomatonStep.usf`) via `FComputeShaderUtils::AddPass`, then `AddReadbackBufferPass` enqueues a copy into an `FRHIGPUBufferReadback`. The shader writes results with `InterlockedOr` since up to 32 cells share a output word and can be written by different threads concurrently. After `GraphBuilder.Execute()`, the render command calls `RHICmdList.ImmediateFlush(EImmediateFlushType::FlushRHIThread)` — a **lightweight** flush that only pushes the recorded commands down to the RHI thread (and from there the GPU), without waiting for GPU completion. This is required: without it, the just-recorded commands sit unsubmitted in the `RHICmdList` while this same Render Thread immediately starts spin-polling `Readback->IsReady()` below — since nothing ever asks the GPU to actually run the work, the fence never signals and the poll loop hangs forever (observed directly: the whole editor froze on `Start()` with `ComputeMethod=Gpu`, no crash, just a dead viewport). An earlier version instead called `RHICmdList.SubmitCommandsAndFlushGPU()` (a deprecated forward to `SubmitAndBlockUntilGPUIdle()`) to solve the same submission problem, but that waits for the **entire GPU pipeline** to go fully idle, not just this pass — in PIE that fights the viewport's own rendering for the same thread and tripped the engine's hang detector, crashing the editor after a ~6s stall on a trivially small dispatch. `FlushRHIThread` submits without that blocking wait, avoiding both failure modes. **The `Readback->IsReady()`/`Lock()`/`Unlock()` poll loop itself also stays entirely inside the render command, on the Render Thread** — an earlier version polled `Readback->IsReady()` directly from the calling thread (game thread from `Next()`, or a `ThreadPool` worker from `StepAsync()`), which crashed (`Array index out of bounds: 0 into an array of size 0` inside `FRHIGPUFence::Poll()`) because `FRHIGPUBufferReadback` isn't designed to be polled from an arbitrary non-render thread. Instead, the calling thread only shares a raw `FEvent` (from `FPlatformProcess::GetSynchEventFromPool()`) and a `TSharedRef<TArray<uint32>>` result buffer with the render command: it calls `CompletionEvent->Wait()` and only reads the result buffer after `Wait()` returns, by which point the render command (which polls `Readback->IsReady()` in a spin loop, `Lock()`/`Memcpy()`/`Unlock()`s into that shared buffer, then `Trigger()`s the event) has fully finished — `Readback` itself never leaves the Render Thread. **`FRenderCommandFence` was tried first and also crashed** (`check(IsInGameThread() || IsInAsyncLoadingThread())` inside `FRenderCommandFence::IsFenceComplete()`) — its `Wait()` is only safe from the game thread, which breaks exactly the `StepAsync()` ThreadPool-worker call path this strategy needs to support; a raw pooled `FEvent` has no such restriction, since it's just an OS-level synchronization primitive. Once unblocked, `Step()` unpacks bits back into world/cell coordinates via a sequential `NextGrid.SetAlive(...)` loop, mirroring the CPU strategy's single-threaded `WriteBack` phase for the same thread-safety reason (`TSet`/`TBitArray` aren't safe for concurrent writes). This whole strategy is a single blocking call from the caller's point of view — it doesn't change `FCellularAutomatonComputeStrategy::Step()`'s synchronous contract, it just has its own internal async round-trip (RDG dispatch + GPU readback, blocking the Render Thread for its duration) instead of `FCpuComputeStrategy`'s CPU-side `ParallelFor`.

Required new module dependencies: `RHI`/`RenderCore` (`CellularAutomata.Build.cs`, `PrivateDependencyModuleNames`) — not Live-Coding-safe, needs a cold rebuild. `AddShaderSourceDirectoryMapping(TEXT("/Project/CellularAutomata"), .../Source/CellularAutomata/Shaders)` is registered in `FCellularAutomataModule::StartupModule()` (`CellularAutomata.cpp`) — the module previously used the engine's default `FDefaultGameModuleImpl` with no custom startup logic; `CellularAutomata.h` now declares `FCellularAutomataModule : public FDefaultGameModuleImpl` for this purpose.
- **`Automata/Rendering/`** — `FCellGridRenderer` (`CellGridRenderer.h`, abstract, plain C++): `Render(const FCellGrid&)`, grid passed per-call rather than owned, so one renderer can redraw after each simulation step. `FInstancedMeshCellGridRenderer` (`InstancedMeshCellGridRenderer.*`) is the only concrete implementation: wraps a `UInstancedStaticMeshComponent*` (owned by the Actor, not this class), with `SetMesh`/`SetMaterial` setters called fresh before each `Render()` since those are designer-editable properties. Scales each instance so the mesh's actual bounding-box size matches `CellSize` (via `UStaticMesh::GetBounds()`), so grid cells tile evenly regardless of the assigned mesh's native dimensions. `AAutomataOrchestrator` holds this via the **concrete** type `TUniquePtr<FInstancedMeshCellGridRenderer>` (not the abstract base) since it's the only renderer that exists and needs mesh/material setters the abstract interface deliberately doesn't expose. **Perf-critical**: `Render()` builds a `TArray<FTransform>` for every alive cell and adds them in one batch via `UInstancedStaticMeshComponent::AddInstances(..., bUpdateNavigation=false)` rather than calling `AddInstance()` per cell — the per-call form rebuilds internal instance buffers on every invocation and showed catastrophic super-linear scaling under profiling (~1789x slower for only 54x more cells at ~45k cells). Both `CellsMeshFlat`/`CellsMeshHierarchical` also have collision disabled (`SetCollisionEnabled(ECollisionEnabled::NoCollision)` in the orchestrator's constructor) since automaton cells are purely visual — measured combined effect (batching + no collision) was a ~37x reduction in total render time at ~45k cells.

**`CellMeshComponentType` picks `UInstancedStaticMeshComponent` (`CellsMeshFlat`) vs. `UHierarchicalInstancedStaticMeshComponent`/HISM (`CellsMeshHierarchical`)** — `AAutomataOrchestrator::GetActiveCellsMeshComponent()` returns whichever is selected; `FInstancedMeshCellGridRenderer` itself needed zero code changes to support either, since `AddInstances`/`ClearInstances`/`SetStaticMesh` are all `virtual` overrides on HISM (it *is-a* `UInstancedStaticMeshComponent`), so calling them through the base-class pointer already dispatches correctly regardless of which concrete class it points at. `InitializeRenderer()` compares `Renderer->GetComponent()` (added to `FInstancedMeshCellGridRenderer` specifically for this) against the currently-desired component every call; on a mismatch (i.e. `CellMeshComponentType` was just changed in the Details panel) it clears whichever component was previously active — so switching implementations doesn't leave two stale sets of cubes rendered simultaneously — and rebuilds `Renderer` around the new one. **Both components are created unconditionally in the constructor and live for the actor's whole lifetime** rather than being destroyed/recreated when the type is switched: dynamically swapping which `UClass` a `CreateDefaultSubobject`-created component is at runtime isn't something Live Coding can safely hot-patch for an already-placed level actor (confirmed directly — after changing `CreateDefaultSubobject<UInstancedStaticMeshComponent>` to `CreateDefaultSubobject<UHierarchicalInstancedStaticMeshComponent>` for what was originally a single `CellsMesh` field, the existing placed actor's component pointer silently reinstanced to `null` — no crash, just a dangling reference — because the old object couldn't be safely upcast to the new class; a genuine editor restart was needed to get a clean instance). Keeping both components permanently allocated (cheap while they hold 0 instances) sidesteps that failure mode entirely: after this point, switching `CellMeshComponentType` is a pure runtime choice that never again needs a C++ recompile or repatch.

HISM builds an internal LOD cluster tree over the instances (async rebuild after `AddInstances`/`ClearInstances`, tracked via `bIsOutOfDate`/`BuildTreeIfOutdated`) enabling per-cluster occlusion and distance culling — the payoff scales with cell count (relevant at the 700k+ live-cell sizes seen once the sim runs for a while), but each full-grid `ClearInstances()` + re-`AddInstances()` per generation also means HISM rebuilds that cluster tree from scratch every step, which is extra work the plain `CellsMeshFlat` doesn't do — worth comparing `AddInstances` timing (see `FRenderTimings`) between the two `CellMeshComponentType` settings if step time regresses at very large cell counts.
- **`FUiController`** (`Ui/UiController.*`) — plain (non-UObject) RAII-style helper, not an actor. Lazily creates a `UUserWidget` from a `TSubclassOf<UUserWidget>` set by the orchestrator, and exposes `ShowHUD/HideHUD/ToggleHUD`. Owned via `TUniquePtr` by `AAutomataOrchestrator`.

All of the plain-C++ helper classes above (`FUiController`, `FCellGrid`/`FSparseCellGrid`/`FDenseCellGrid`, `FCellGridRenderer`/`FInstancedMeshCellGridRenderer`, `FCellularAutomatonRule`) follow the same convention: non-copyable, owned via `TUniquePtr` (or, for `FCellularAutomatonRule`, constructed as a short-lived local) by whichever `UObject`/Actor uses them, `TWeakObjectPtr` (not raw pointers) for any `UObject` references they hold.

### Source layout convention

Code is being migrated from a flat `Orchestration/` and `Ui/` dump into a `Core/<Subsystem>/` layout (see the pending rename of `AGameMode`/`GamePlayerController` in git status). When adding new engine-level classes (game mode, controllers, pawns, etc.), place them under `Source/CellularAutomata/{Public,Private}/Core/<Subsystem>/`; higher-level gameplay/orchestration code stays under `Orchestration/`; widget/HUD glue stays under `Ui/`.

### Module dependencies

`CellularAutomata.Build.cs` pulls in `Core, CoreUObject, Engine, InputCore, Slate, SlateCore, UMG, WebBrowser, WebBrowserWidget, Json, JsonUtilities` as public dependencies, plus `EnhancedInput`, `RHI`, `RenderCore` as private dependencies. `EnhancedInput` was added for `AGamePlayerController`'s Play/Stop hotkey — `EnhancedInput` is already the project's active input system per `Config/DefaultInput.ini`'s `DefaultPlayerInputClass`/`DefaultInputComponentClass`, so no plugin-enablement change was needed, just the module reference. `RHI`/`RenderCore` were added for `FGpuComputeStrategy`'s RDG compute-shader dispatch (see `Automata/Simulation/ComputeStrategy/`). The `WebBrowser`/`WebBrowserWidget` dependency was for a `Ui/WebInterface` widget that has since been deleted — if reintroducing browser-based UI, that's the intended integration point. **Note**: adding a module to `Build.cs` isn't something Live Coding can hot-patch — it requires closing the Editor and a full cold rebuild (see Build/run section above).

`RemoteControlWebInterface` and `RiderLink` are both present but **disabled** (`"Enabled": false`) in the `.uproject` Plugins list — `RemoteControlWebInterface` tries to build a React web app on editor startup and fails in this environment (`Failed To Build WebApp`); `RiderLink`'s `RiderDebuggerSupport.dll` gets blocked by Windows Smart App Control (unsigned binary, `GetLastError=4551`). Don't re-enable either without addressing the underlying cause first.

### MCP / AI-editor integration

`Plugins/McpAutomationBridge` (from github.com/ChiR24/Unreal_mcp) is installed and gives Claude Code direct control of the running Editor over HTTP — spawning/inspecting actors, screenshots, console commands, asset ops, etc. Native MCP mode is enabled via `Config/DefaultGame.ini` (`[/Script/McpAutomationBridge.McpAutomationBridgeSettings]`, `bEnableNativeMCP=True`, port 3000) — no Node.js/bridge process needed. Registered in Claude Code at **user scope** (`claude mcp add unreal-engine --transport http --scope user http://localhost:3000/mcp`); MCP server tool lists only refresh when a Claude Code session (re)starts, not mid-session.

**Fast iteration loop while the Editor is already open**: after editing C++, trigger a hot patch instead of closing the editor for a full UBT rebuild — via the MCP `control_editor` tool's `console_command` action (or the in-editor Ctrl+Alt+F11 hotkey) running `LiveCoding.Compile`. This requires Live Coding to be enabled in the Editor already. A pure function-body edit (no new/changed `UPROPERTY`/`UFUNCTION`) patches in under a second; if unsure whether a patch actually landed, compare the edited `.cpp`'s mtime against `Intermediate/Build/Win64/x64/UnrealEditor/Development/CellularAutomata/<File>.cpp.obj` and `Binaries/Win64/UnrealEditor-CellularAutomata.dll`. A full cold UBT build still requires the Editor process to be closed first (it locks the DLL):
`"C:\Program Files\Epic Games\UE_5.7\Engine\Build\BatchFiles\Build.bat" CellularAutomataEditor Win64 Development -Project="<repo>\CellularAutomata.uproject" -WaitMutex`

**Known instability**: `LiveCoding.Compile` on an edit that changes reflection data (new/changed `UPROPERTY`/`UENUM`/`UFUNCTION` on a class with a live instance in the open level) has repeatedly crashed the Editor process during class reinstancing in this environment, restarting it silently with no crash dump (check `Saved/Logs/CellularAutomata.log`'s `Log file open` timestamp to detect this). Pure function-body edits have not shown this problem. After such a crash the patch is usually still applied (verify via MCP `inspect`/`get_property` once the Editor is back up) — no need to redo the edit, just reconnect.
