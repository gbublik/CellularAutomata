# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Unreal Engine 5.7 C++ game project (`CellularAutomata.uproject`) implementing a 3D cellular-automata simulation, rendered with `UHierarchicalInstancedStaticMeshComponent` cell instances (one cube mesh instanced per live cell). The gameplay module is `CellularAutomata` (Runtime, Default loading phase).

The project briefly depended on the third-party **VoxelFree** plugin (SDF/marching-cubes voxel terrain engine) but that was dropped and the plugin fully removed — it was built for volumetric terrain, not for placing discrete cell instances, and was unnecessary overhead for this project's needs. Do not reintroduce a `Voxel` module dependency without deliberate reconsideration.

## Build / run

No lint config — it's a standard UE C++ project built through the Unreal toolchain. There *is* a small automation test suite (`Source/CellularAutomata/Private/Tests/AutomataTests.cpp`, whole file under `#if WITH_DEV_AUTOMATION_TESTS`, no extra `Build.cs` dependency), run headless with:

`"C:\Program Files\Epic Games\UE_5.7\Engine\Binaries\Win64\UnrealEditor-Cmd.exe" "<repo>\CellularAutomata.uproject" -ExecCmds="Automation RunTests CellularAutomata" -testexit="Automation Test Queue Empty" -unattended -nopause -nosplash -abslog=<file>`

Twelve tests, chosen for the places where a bug is both likely and invisible. Two cover slice capture (`Slice.Orientation` — the asymmetric-figure guard against mirroring and transposition described under `Automata/Capture/`; `Slice.Raster` — nearest-wins independent of input order, exact N×N blocks under scaling, budget refusal leaving no half-result, and empty input failing honestly rather than emitting a 1×1 file). Three cover the generators (`Generation.Determinism` — same seed, same set, and a *different* seed giving a different one, since a generator that ignores the seed passes the first check perfectly; `Generation.RandomBallParity` — the golden test that `GenerateRandom()`'s refactor didn't silently shift every previously saved seed; `Generation.LatticeNeighborUniformity` — that the neighbour counts the presets promise are the counts the geometry actually has). The other four: `Grid.NegativeCoords` (chunk math on negative coordinates — the floor-division trap flagged under `Automata/Grid/`, and generation is centred on the origin so negative coordinates are the norm, plus the "a re-created chunk must not inherit stale ages" guarantee), `Rules.RuleStringRoundTrip` (`Parse → Format → Parse`, range compression, every one of the 14 neighbourhood tokens surviving print-then-parse back into itself (a gap in the token table would otherwise fall through to its `M` fallback silently), and twelve malformed strings that must each be rejected *whole* with a non-empty error — including `M2` and `E2`, rejected rather than coerced), `Compute.CpuGpuParity` and `Compute.GpuBatchParity` (differential tests — they need no known-good answer, only that two implementations agree: CPU against GPU, and one batched dispatch against N single steps, comparing live cells, ages **and** decay stages). The last two are the automated form of the manual check the batching work was verified with, and they carry `EAutomationTestFlags::NonNullRHI` plus their own `GMaxRHIFeatureLevel` check so they report "skipped" rather than fail under `-nullrhi`. `Rules.NeighborhoodShells` checks the shell model itself rather than the 14 values one by one: that each shell is exactly one `d²` class with no strays from the 5×5×5 cube it is scanned from (`(2,1,0)` at `d²=5` is the one waiting to leak in), that every value equals the union of its own shells (by set algebra, since `6+8` and `12+2` both give 14 and counting alone would not notice classes swapped), that every value stays under the 26-offset ceiling, that `Moore` still returns its original offsets in the original order, that the parity properties the face-less sets exist for still hold, and that reach is 2 exactly where far axes are present. The twelfth, `GenerationHistory`, covers the sliding window behind the HUD graph (see `Ui/` below) — and it is the reason that logic was extracted out of the orchestrator into free functions at all: the traps in it (the last sample being edited *in place* rather than appended, the rendered value being carried forward, X mapped by generation value rather than by array index) are exactly the kind that need no actor, tick or render to exercise. Note the whole run costs an editor startup (tens of seconds) — there is no fast inner loop for UE automation tests. Deliberately not covered: anything requiring an actor, a tick or a render — that is where UE tests get expensive and brittle, and it is checked by hand in PIE instead.

## Architecture

Actor/controller composition, not a monolithic GameMode:

- **`AAGameMode`** (`Core/GameMode/AGameMode.*`) — minimal; only wires `PlayerControllerClass` to `AGamePlayerController`. Note the doubled `A` prefix: the UE Actor-class convention (`A`) plus the class's own name (`AGameMode`) yields `AAGameMode`. `DefaultEngine.ini`'s `GlobalDefaultGameMode` points at this class.
- **`AGamePlayerController`** (`Core/PlayerController/GamePlayerController.*`) — owns the camera. No spline-following camera anymore (removed — see below); just toggles between gameplay input (`FInputModeGameOnly`, pawn input enabled) and UI input (`FInputModeGameAndUI`, cursor shown, pawn input disabled) via `SetCameraControlEnabled()`, and on `BeginPlay` sets FOV (viewmode is no longer forced here — see hotkeys below). `SetupInputComponent()` binds the project's testing hotkeys, all resolving the `AAutomataOrchestrator` in the world via `UGameplayStatics::GetActorOfClass` (except the camera-only ones) — built with Enhanced Input (`UInputAction`/`UInputMappingContext` constructed at runtime via `NewObject`, not saved as `.uasset` content, since a handful of project-wide hotkeys doesn't need dedicated assets), all mapped on one shared `SimulationMappingContext` — all except **P**: **P** (`OnToggleSimulation()`) calls `Start()`/`Stop()` depending on `IsSimulationRunning()`, and is deliberately **not** routed through Enhanced Input at all — it's caught in an `InputKey()` override on the controller, which fires immediately per raw OS key message (`WM_KEYDOWN`, `IE_Pressed` only, so no repeat-on-hold). Enhanced Input evaluates its triggers once per `Tick` by sampling the key's current down/up *level*, so under heavy frame lag (large `AddInstances`/HISM cluster-tree rebuilds at high cell counts) a quick press-and-release of P could land entirely inside one long frame gap and never register as a transition — the pause got harder to catch the worse the lag became, which defeated the whole point of a pause key; `InputKey()` sees every press regardless of frame length. The other hotkeys stay on Enhanced Input — they're either less lag-critical or hold-style bindings that genuinely want per-tick evaluation; **F** (`OnFastStepPressed()`/`OnFastStepReleased()`, bound to `ETriggerEvent::Started`/`Completed`) — a bare press (no Shift) calls `Next()` once, which now advances **`StepsPerRender` generations per press** (the same value tuned via T/G), computed off the game thread, rendering only the final one (see `Next()` under the orchestrator bullet below); if Shift is down at the moment F is pressed (checked via `IsInputKeyDown(EKeys::LeftShift)`, not a separate Enhanced Input binding), it instead calls `AAutomataOrchestrator::StartFastStep()` — a **hold** mode, independent of `bSimulationRunning` and mutually exclusive with it (`Start()` refuses while `IsFastStepActive()`, and `StartFastStep()` refuses while Play is running), that paces steps by `Speed` exactly like continuous Play via the same `bFastStepActive` branch in `Tick()` (ahead of the `bSimulationRunning` branch, sharing `TimeSinceLastStep`/`StepAsync()`/chunked-render with zero duplicated logic) — and stops the instant F is released (`OnFastStepReleased()` calls `StopFastStep()` only if `IsFastStepActive()`). Bound to `Started`/`Completed` rather than `Triggered` specifically so a bare hold of F doesn't repeat `Next()` every frame (that was the pre-Shift-hold-mode behavior and confused continuous auto-stepping with a single step). **R** (`OnResetSimulation()`) calls `ResetToInitialState()` — rebuilds the grid from `InitialStateCells` (ages reset to 0), the shared "initial pattern" populated by whichever of `StartFromSelection()` (Enter), `LoadStateFromFile()` (Ctrl+O) or `GenerateRandom()` itself ran most recently (see the `InitialStateCells`/`ResetToInitialState()` paragraph below for the full picture), so an isolated glider/oscillator, a loaded save, or just the last random spawn can all be replayed from their exact starting shape. Deliberately *not* gated on `IsSimulationRunning()` since both paths guard their own race with `bStepInProgress`. **R is caught in the same raw `InputKey()` override as P, not through Enhanced Input** — for exactly the reason described there (a quick press-and-release landing inside one long frame gap is never seen by Enhanced Input's per-tick level sampling, and R is pressed precisely when the sim is lagging hardest), and it goes through a *deferred* path on top: when a background step is in flight, `ResetToInitialState()` sets `bResetToInitialStatePending` and returns instead of refusing, and `ApplyStepResult()`/`Next()`'s completion performs the reset once the `Grid` race is over. Those were two independent bugs with one shared symptom ("R doesn't always work") — the input-sampling one and the silently-dropped-during-a-step one — fixed separately; **F1**–**F4** (`OnApplyRenderPreset0()`…`OnApplyRenderPreset3()`, each a thin wrapper over `OnApplyRenderPreset(int32)`) apply a whole **render preset** via `AAutomataOrchestrator::ApplyRenderPreset(Index)` — see `RenderPresets` under `Automata/Rendering/` below. These replaced a bare Lit/Unlit pair that sat on the same two keys: `VIEWMODE LIT`/`VIEWMODE UNLIT` are equivalent in cost here, so two keys were spent on a choice that changed nothing about speed. Viewmode is now one field of a preset alongside shadows, culling, background and a list of engine cvars. **U** (`OnToggleBackground()`) flips `SetBackgroundVisible()`/`IsBackgroundVisible()` — hide the sky/fog without losing the light (see that method below), and **Shift+U** (same handler, modifier checked in code) instead toggles the **headlight** — see `SetHeadlightEnabled()` under `Core/PlayerController/` below; separate from the presets because hiding the background is wanted on top of `Quality` too; **Vertical camera movement is rebound away from the engine defaults** (`RebindPawnVerticalMovement()`): stock `ADefaultPawn` binds its up/down axis to six keys, two of which are spoken for here — `LeftControl` fired on every Ctrl+S/Ctrl+Shift+S/Ctrl+O/Ctrl+C, and bare `C` on the cull toggle, so the camera sank at exactly the moment one looks at what changed. The two cannot be removed individually: they live in the private static `UPlayerInput::EngineDefinedAxisMappings`, which exposes only a const getter. So the engine binding is dropped from the pawn's `InputComponent` whole and replaced with an own axis on the same `ADefaultPawn::MoveUp_World`, leaving **Space/E up and Q down** — the engine set minus the two collisions. It runs from `Tick()`, once per pawn (compared against `VerticalMovementBoundPawn`), because the pawn's `InputComponent` is created later than both `SetupInputComponent()` and `AcknowledgePossession()` — see `ClientRestart_Implementation`, where acknowledge precedes `DispatchRestart()`. **Left Shift** (held) — `OnSpeedBoostStarted()`/`OnSpeedBoostEnded()` (bound to `Started`/`Completed`) scale the possessed `ADefaultPawn`'s `UFloatingPawnMovement::MaxSpeed` by `AAutomataOrchestrator::CameraSpeedMultiplier` for faster flying while held, restoring the original speed on release — `BaseFlySpeed` caches that original value on first press (guarded by `<= 0.0f` so a stray repeated `Started` can't cache an already-boosted speed). `CameraSpeedMultiplier` lives on the orchestrator rather than the controller/pawn so a designer tunes it from the same Details panel as the rest of the simulation; **Z** (`OnToggleChunkedRender()`) flips `AAutomataOrchestrator::bEnableChunkedRender` via `SetChunkedRenderEnabled()`/`IsChunkedRenderEnabled()` — there's no automatic cell-count threshold for chunked rendering (an earlier `ChunkedRenderCellThreshold` property was removed), it's purely a manual on/off toggle now; **X** (`OnCycleChunkedRenderOrder()`) advances `AAutomataOrchestrator::ChunkedRenderOrder` to the next `EChunkedRenderOrder` value by calling `CycleChunkedRenderOrder()` (wraps back to `Sequential` after the last value) — see `EChunkedRenderOrder` under Chunked rendering below for what each order looks like; **V** (`OnToggleWaitForChunkedRenderToFinish()`) flips `AAutomataOrchestrator::bWaitForChunkedRenderToFinish` via `SetWaitForChunkedRenderToFinish()`/`IsWaitingForChunkedRenderToFinish()` — see `bWaitForChunkedRenderToFinish` under Chunked rendering below for the two interrupt-vs-wait behaviors this switches between; **B** (`OnToggleCellCulling()`) flips `AAutomataOrchestrator::bEnableCellCulling` via `SetCellCullingEnabled()`/`IsCellCullingEnabled()` — see `bEnableCellCulling` under `CellCullStartDistance`/`CellCullEndDistance` below; **C** (`OnToggleRenderCullVolume()`) flips `bEnableRenderCullVolume`, and **Ctrl+C** (same handler, modifier checked in code) flips the box's own visibility instead via `OnToggleRenderCullVolumeVisibility()` — see `ARenderCullVolume` under `Automata/Rendering/` below; **H** (`OnToggleGhostShape()`) flips `bEnableGhostShape` via `SetGhostShapeEnabled()`/`IsGhostShapeEnabled()` — see the Ghost Shape paragraph there too; **N** (`OnNewSeed()`) calls `AAutomataOrchestrator::NewSeed()` — re-rolls `Seed` and re-seeds the grid, i.e. the "show me a different one" counterpart to **R**, which replays the *same* `InitialStateCells` pattern. **Caught in the same raw `InputKey()` override as P and R, not through Enhanced Input, and deferred through `bNewSeedPending` the way R is through `bResetToInitialStatePending`** — it had exactly the same two independent sources of dropped presses as R did (per-tick Enhanced Input level sampling missing a short press inside one long lagged frame, plus a silent refusal while a background step holds `Grid`), and for the same reason: a re-roll is pressed precisely when the grid has grown big and ugly, i.e. when the lag is worst. The two pending flags are mutually exclusive (each clears the other), since N and R want incompatible things from the same `Grid` — last press wins rather than whichever flag happens to be checked first. `Seed` is deliberately re-rolled only at the moment the deferred re-seed actually runs, not when the flag is raised, so repeated presses during one long step burn one seed rather than several unseen ones; **Y** (`OnGenerateState()`) builds the initial state with the currently selected geometric generator (`AAutomataOrchestrator::GenerateState()`), **Shift+Y** cycles to the next generator type without building (`CycleStateGeneratorType()` — see `Automata/Generation/` below), and **Ctrl+Y** logs a live-neighbour histogram of the *current* structure (`AnalyzeLiveStructure()`, same section) — the modifier is checked inside the handler, as with every other Ctrl combination here. Caught in the same raw `InputKey()` override as P/R/N for the same reason — the key is pressed exactly when the picture is disappointing and the grid has already grown, i.e. when the lag is worst — with Shift checked inside the handler, since Enhanced Input cannot require a modifier in a key mapping (the Ctrl+S/Ctrl+C idiom). Note **J** was the obvious letter and is already taken (`ToggleViewSliceAction`); `Y` was the only free letter left; **F6** (`OnCaptureTextureSlice()`) writes the current view out as a PNG slice, **Shift+F6** through a save dialog, and **F7** (`OnToggleSeriesCapture()`) records a whole series of frames as the simulation runs — see `Automata/Capture/` below; **F10** (`OnTakePhotoShot()`) takes the beauty shot instead — a real engine render at a resolution the window cannot hold, see "The photograph" under `Automata/Rendering/`. F10 specifically because the engine's own `DebugExecBindings` claim F1–F5, F9 and F11, F8 ejects from the pawn in PIE, and F6/F7 are already ours; **K** (`OnMoveCullVolumeToSelection()`) teleports the cull volume onto the current selection (`MoveCullVolumeToSelection()`) and **L** (`OnSelectCellsInCullVolume()`) selects every alive cell inside it (`SelectCellsInCullVolume()`, with the same Shift/Ctrl combine modifiers as a marquee drag) — the two together make the cull box usable without the viewport gizmo: select a cell, K to bring the box there, L to grab everything it now contains; **=/NumPad+** and **-/NumPad-** (`OnIncreaseSpeed()`/`OnDecreaseSpeed()`, both bound to `Triggered`, so holding repeats) call `AAutomataOrchestrator::AdjustSpeed(±SpeedAdjustStep)` to nudge `Speed` up/down by a fixed `0.5` step, clamped to `[0.1, 100.0]` inside `AdjustSpeed()` itself — deliberately wider than `Speed`'s own `UIMax = "10.0"` metadata, since that only caps the Details-panel slider, not a hard `ClampMax`; **Home** (`OnFrameAllCells()`) resolves the orchestrator and delegates to the public `AGamePlayerController::FrameAllCells(AAutomataOrchestrator*)`. It is a public method rather than a private handler because `ResetToInitialState()` used to call it through `GamePC` at the end of every R press — that auto-framing was **removed** (R now only rebuilds the pattern and leaves the camera exactly where it was, since being yanked to a framing distance on every reset fought with flying around a structure), so today the only caller is the explicit Home press. `FrameAllCells()` moves the possessed pawn along its *current* view direction (viewing angle unchanged, only distance) so the whole live-cell set fits in frame — `AAutomataOrchestrator::ComputeAliveCellsBounds()` scans `GetAliveCells()` once for a world-space AABB (via `GridToWorld()` on the min/max cell coordinates, expanded by half a `CellSize` since `GridToWorld()` gives cell *centers*) and returns its center and bounding-sphere radius (`FrameAllCells()` itself returns `false` and does nothing if the grid is empty/uninitialized or the pawn/camera aren't ready yet); it then computes `Distance = Radius / sin(FOV/2)` (the exact distance at which a sphere of that radius exactly fills the frustum half-angle, using `PlayerCameraManager->GetFOVAngle()`), multiplies by a small `FramingPadding` (`1.1`) so cells don't touch the frame edge, and sets the pawn's location to `Center - CameraRotation.Vector() * Distance` via `PlayerCameraManager->GetCameraRotation()`; **T**/**G** (`OnIncreaseStepsPerRender()`/`OnDecreaseStepsPerRender()`, bound to `Triggered` like `+`/`-` for Speed, so holding repeats) call `AAutomataOrchestrator::AdjustStepsPerRender(±1)` to nudge `StepsPerRender` (see `StepsPerRender` under Chunked rendering below), clamped to `[1, MaxStepsPerRender]` inside `SetStepsPerRender()`, which `AdjustStepsPerRender()` now routes through. **Shift+T/Shift+G** step to the next/previous **power of two** instead (`OnDoubleStepsPerRender()`/`OnHalveStepsPerRender()` → `ScaleStepsPerRender(bool)`): a step of one never reaches the interesting values, since typing 256 from the keyboard is either 255 presses or catching it on auto-repeat, where overshooting is easier than landing (observed — an intended 256 came out as 254). Powers of two are what matter here: the clean picture from fractal rules falls on 2^k, and the batching ceiling in `FGpuComputeStrategy` is governed by a halo equal to the batch size. It steps to the next *power*, not simply doubling, so that one press off an uneven value lands on 2^k rather than preserving the unevenness (254 → 256, not 508). These are bound to `Started` while the ±1 pair stays on `Triggered` — a doubling that repeated every frame of a hold would hit the ceiling in a fraction of a second — and each of the four handlers checks Shift itself, since Enhanced Input cannot require a modifier in a key mapping (same idiom as Shift+F, Ctrl+S, Ctrl+C). `MaxStepsPerRender` (4096) exists only because of that doubling: without a ceiling it would overflow `int32` within a dozen presses; batching is trimmed long before it (originally mapped to `[`/`]` but rebound by hand during testing — see `SetupInputComponent()` for the current mapping). **Digits 0–9** (`OnSetAgeFilter(int32)`) filter the view down to a single cell age, and **Shift+digit** adds that age to the ones already shown or removes it if it is already there — see `AgeFilterValues` under `Automata/Rendering/` below; the whole **NumPad** positions the camera (axial views, isometric, orthographic toggle, ortho zoom, framing) — see `AGameCameraManager` below; both are caught in the raw `InputKey()` override rather than Enhanced Input, for a reason unrelated to P/R/N's lag problem: ten-plus keys of one kind would be ten-plus `UInputAction`s for one lookup table. **Tab** (`OnToggleSelectionMode()`, originally C but rebound by hand during testing) toggles **one shared mouse-interaction mode** covering both cell selection (see the dedicated section below, after the cell-colour section) and HUD interaction — a separate H hotkey for "show the cursor so I can click the HUD" existed briefly and was folded into Tab, since both wanted the exact same state (`SetCameraControlEnabled(false)`: camera stopped, cursor shown, controller input still live) and having two keys toggling one thing independently could leave it half-on. H was later reused for Ghost Shape. While active, **left mouse button** drag-selects a screen-space rectangle of cells (**Shift**+drag adds to the existing selection, **Ctrl**+drag removes from it — see `ESelectionCombineMode` in that section), **I** (`OnInvertSelection()`) inverts the selection against the alive-cell set, **Delete** (`OnDeleteSelectedCells()`) kills the selected cells in place without resetting the simulation, and **Enter** (`OnExtractSelection()`) launches the current selection as a fresh starting state; **M** (`OnBakeCellsToMesh()`) bakes the current state (or the selection, if one exists) into a single hollow mesh and unloads the cells from memory — see the Baking paragraph below; **S**/**O** (`OnSaveOrSaveAs()`/`OnLoadState()`) — Ctrl+S/Ctrl+Shift+S save/save-as, Ctrl+O loads, to/from a `.casave` file (see the `Automata/Persistence/` bullet below for the format and semantics) — mapped on the raw `S`/`O` keys *without* a modifier (Enhanced Input has no way to require Ctrl directly in a key mapping), so the handlers themselves check `IsInputKeyDown(EKeys::LeftControl/RightControl)` and silently return if Ctrl isn't held (bare `S` still drives `ADefaultPawn` camera movement, unaffected), then branch on Shift to pick `SaveState()` (Ctrl+S) vs `SaveStateAs()` (Ctrl+Shift+S). **Why hotkeys and not just the `CallInEditor` buttons**: clicking a `CallInEditor` button in the Details panel during PIE is unreliable — if the World Outliner still has the non-PIE (persistent-level) copy of the actor selected rather than its PIE-world duplicate, the click invokes the function on the frozen editor-world instance, whose `Tick()` never runs (`AActor::TickActor` early-returns when `TickType == LEVELTICK_ViewportsOnly`, which is how the engine ticks actors outside PIE) — so e.g. continuous Play silently never begins, with no error. Hotkeys sidestep this entirely since key input always arrives via the currently-possessing (PIE-world) `PlayerController`. Requires the `EnhancedInput` module (see below).
- **`AGameCameraManager`** (`Core/CameraManager/GameCameraManager.*`) — everything it adds to `APlayerCameraManager` is a switchable **orthographic projection** (NumPad 5): without perspective distortion the structure reads like a drawing, and together with the axial numpad views that is exactly how a DCC viewport is used to examine a shape. `AGamePlayerController`'s constructor points `PlayerCameraManagerClass` at it — the constructor and not `BeginPlay()`, since `APlayerController` spawns the manager in `PostInitializeComponents()`, i.e. earlier. **Why a camera-manager subclass and not a `UCameraComponent` on the pawn**: the pawn is a stock `ADefaultPawn`, which has no camera component at all (the view comes from `GetActorEyesViewPoint()`), and the projection mode lives in an `FMinimalViewInfo` that the manager rebuilds *every frame* — writing `ProjectionMode` into `PlayerCameraManager->ViewTarget.POV` from outside is overwritten by the next `DoUpdateCamera()`. `UpdateViewTarget()` is the one virtual hook where the view is already computed but not yet submitted to the renderer, and it runs for both the current and the incoming (blending) view target, so the projection doesn't flicker when the target changes. Two properties of the ortho view are deliberate: `bAutoCalculateOrthoPlanes` is turned **off** (it derives the clip planes from a view-target distance this project never sets, which would make the clipping unpredictable), and the visible slab is **symmetric around the camera** — `OrthoNearClipPlane` is *negative* — because ortho gets switched on while the camera is often *inside* the structure, and with a near plane of 0 everything behind the camera would simply vanish, which reads as a bug rather than as a change of projection (DCC ortho views behave the same way). The depth range is a finite `1000000` units rather than `UE_OLD_WORLD_MAX`: linear ortho depth over that range still resolves ~0.1 units in a float, a thousandth of a cell, so cube faces don't z-fight. `OrthoWidth` is stored here but *fitted* by the controller — the radius of the live cells is the orchestrator's knowledge, not the camera's. State fields are `UPROPERTY(Transient)` for the usual Live-Coding-reinstancing reason (see `GamePC` below), so a hot patch mid-PIE doesn't silently drop back to perspective.

**NumPad — camera positioning.** Home frames along the current angle; this is the same thing from a chosen side. **4**/**6** — left/right, **8**/**2** — top/bottom, **1**/**3** — front/back (project axes are X forward, Y right, Z up, so "left view" is a gaze along +Y; the layout is geometric, like a DCC viewport), **7** — isometric, the only angle that shows three axes at once, i.e. the volume the axial views specifically hide, **9** — the same angle from the opposite side (the current view direction negated, not another fixed axis, since the angle may well have been set with the mouse), **0** — the same framing as Home (on the numpad because the hand is already there), **5** — ortho on/off, ***** / **/** — ortho zoom, **.** — frame the current *selection* instead of the whole grid (the pair to K/L: select an interesting piece, then fly to it without hunting for it by eye). **Requires NumLock on**: without it Windows sends `Left`/`Up`/`Home`/`Delete` from these keys — the very codes that move the cull volume. Not a conflict (they are different `FKey`s), but it is exactly why the numpad looks dead without NumLock.

All framing goes through one `AGamePlayerController::FrameBounds(Center, Radius, ViewDirection, bApplyRotation)` — Home keeps the current angle (`bApplyRotation = false`), the axial views also set the control rotation. Pitch is clamped to the camera manager's own `ViewPitchMin`/`ViewPitchMax` **before** the position is computed, and the position then uses the *clamped* direction: a top view is exactly -90°, which the manager trims to -89.9 on the first mouse move anyway, and standing the camera straight overhead while aiming 0.1° off walks the frame centre further off the bigger the structure gets. In orthographic mode the same call fits `OrthoWidth` instead of leaning on distance (distance does not affect an ortho picture at all), via `ComputeOrthoWidthForRadius()` — which fits the **smaller** side of the frame, since `OrthoWidth` is a *width* and the height follows from the aspect ratio, so on a wide screen (and it practically always is) the diameter has to be laid into the height or the grid gets cut off top and bottom. Toggling ortho on fits the width immediately, for the same reason: at the default width (or one left over from a differently-sized structure) the first press would show either one cell filling the screen or nothing at all, and that reads as a broken feature.

**A hand-picked ortho zoom survives a change of view.** `ScaleOrthoWidth()` (the `*` / `/` keys) marks the width as user-chosen (`HasUserOrthoWidth()`), and framing skips its own fit while that mark is set. Without it, switching to an axial view threw the zoom away — the numpad views go through the same framing code as Home, and that code *has* to set the ortho width or it would do nothing whatsoever in ortho, so picking a scale and walking around the structure by axis were mutually exclusive. Only explicit "fit this in frame" requests clear the mark: Home/Shift+Home, NumPad 0, NumPad . and enabling ortho; a change of view is not a request to fit, it is a request to look from elsewhere. The mark is raised in `ScaleOrthoWidth()` rather than in `SetOrthoWidth()` because automatic fitting goes through the setter too — counting that as "the user chose this" would let the first framing block every later one. Enabling ortho deliberately drops a zoom left from a previous session: the structure may have grown by an order of magnitude since, and the stale width would show exactly the emptiness that the initial fit exists to prevent.

**Shift+Home / Shift+\<numpad view\> frame only what is currently visible** — `AAutomataOrchestrator::ComputeVisibleCellsBounds()`, which mirrors the same three filters `BuildCellRenderData()` applies to alive cells: the cull volume (`GetActiveCullVolume()`), the age filter (`AgeFilter`/`bAgeFilterIncludesOlder`), the view slice (`bEnableViewSlice`). Plain Home still frames the whole structure, and the two are genuinely different requests: with the cull box cutting most of the grid away, framing the entire (mostly invisible) structure left the visible fragment tiny in the middle of an otherwise empty shot. The filtering is **duplicated** rather than calling `BuildCellRenderData()` — that one also colours cells and updates the view-slice refresh bookkeeping (`LastViewSliceCameraLocation`/...), none of which framing needs — so a change to one of the three filters has to be made in *both* places. It is not `const` (unlike `ComputeAliveCellsBounds()`) because `GetActiveCullVolume()` lazily caches the actor, the same reason `BuildCellRenderData()` isn't. Decaying cells are deliberately left out of the count: a framing sphere needs no per-decaying-cell accuracy and its radius already carries slack. `ComputeSelectedCellsBounds()` (NumPad .) is the third caller of the shared `ComputeCellsBounds(Cells, ...)` that the Ritter-sphere body was extracted into, and it filters the selection down to still-alive cells first (a selection outlives simulation steps).

`FHudStats::bOrthographicCamera` mirrors the projection off the controller (`IsOrthographicCamera()`), exactly like `bSelectionModeActive` — projection is camera state, not automaton state. And `AAutomataOrchestrator::ShowStatusMessage()`/`EStatusMessageKey` moved from private to **public** with a `StatusKey_Camera` added: the camera hotkeys live on the controller but have to report into the same on-screen channel, and a second `AddOnScreenDebugMessage()` call site would fork the convention — the engine's message keys are global, so lifetime, colour and key numbering must stay in one place or messages start overwriting each other.

**Status messages now go into the HUD, not over it.** The engine's on-screen channel draws its lines from a hardcoded 45 pixels down (`UnrealEngine.cpp`, `MessageStartY` — neither a setting nor a cvar), i.e. straight across the HUD's own top bar, and the bar cannot simply move down because several messages stack (45 plus 20 per line). `ShowStatusMessage()` therefore offers the message to `UMainHudWidget::OnStatusMessage(FText, int32 Key)` — a `BlueprintImplementableEvent`, same bridge shape as F5's `OnToggleInfoPanel()` — and only falls back to `AddOnScreenDebugMessage()` when the HUD cannot take it. Position, styling and lifetime become layout, which is where they belong; the three hardcoded seconds were presentation all along. That this was a one-place change is exactly the property described above: that call was the only `AddOnScreenDebugMessage()` in the project. The fallback checks whether the event is **implemented**, not merely whether a widget exists — an unimplemented `BlueprintImplementableEvent` is a silent no-op, so without the check the messages would have vanished outright the moment this shipped; a stub with no Blueprint implementation still has the native class as its `UFunction` owner, so a non-native owner is the signal that the graph has taken over.

**The headlight (Shift+U) — a lamp carried by the camera**, `AGamePlayerController::SetHeadlightEnabled()`/`IsHeadlightEnabled()`, off by default. It exists for one case the level's lighting cannot serve: flying *inside* the structure. From outside, the directional light shapes the figure; inside a dense lattice only the faces it happened to reach through are visible, and the rest is a dark cave. A lamp at the camera lights whatever you are actually next to.

**The light hangs on the possessed pawn, not on the controller, and that is load-bearing rather than stylistic.** `AController` marks itself hidden in its constructor (`SetHidden(true)`), and `ULightComponent::CreateRenderState_Concurrent()` only adds a light to the scene when `ShouldRender()` — which folds in the owner's hidden flag — is true. Parented to the controller it would silently never light anything, with nothing in the log: exactly the failure mode `CellMaterial`'s missing `PerInstanceCustomData3Vector` node has. On the pawn it also follows the camera for free, so there is no per-frame position update. `EnsureHeadlight()` creates it lazily on the first switch-on (the default session never pays for it) and re-creates it if the pawn changes; switching off only calls `SetVisibility(false)`, since the lamp is flicked back and forth and re-registering a light in the scene is not free.

Three deliberate settings at creation. **Inverse-squared falloff is off** (`LightFalloffExponent = 4`, unitless intensity) so that `HeadlightIntensity` and `HeadlightRadius` are independent knobs — with inverse-squared, changing how far the light reaches also changes how bright it is, and inside a structure both get retuned constantly. **`SourceRadius = 0`**, since the source sits exactly at the eye. And **shadows default off** (`bHeadlightCastsShadows`): a shadow-casting point light is a cubemap, i.e. six more passes over the same millions of instances — the same cost argument that gave `bCellsCastShadows` its own switch. All four settings live on `AAutomataOrchestrator` (`Automata|Camera`, next to `CameraSpeedMultiplier`, for the reason recorded there) and are re-read every frame while the lamp burns, so a slider drag is visible immediately; that per-frame read is also the only reason the controller caches the orchestrator (`FindOrchestrator()`, the `FindCullVolume()` idiom) instead of resolving it per press like every hotkey does.

**Shift+U rather than its own key, because there is no own key left** — every letter of the alphabet is spoken for (see the hotkey list above). Of the taken ones U is the only one about light and background, which makes the pair read as one thought: *U* removes the scene's light, *Shift+U* brings your own. The modifier is checked inside `OnToggleBackground()`, the usual "Enhanced Input cannot require a modifier in a key mapping" idiom. Note the lamp is invisible under **F2 (Unlit)** — that viewmode ignores lighting entirely — and `FHudStats::bHeadlightEnabled` mirrors the state off the controller, exactly like `bSelectionModeActive`/`bOrthographicCamera`.

- **`AAutomataOrchestrator`** (`Orchestration/AutomataOrchestrator.*`) — the top-level conductor, placed in the level as an Actor. Root component is `CellsMeshHierarchical` (`UHierarchicalInstancedStaticMeshComponent`); `CellsMeshFlat` (`UInstancedStaticMeshComponent`) is attached as its child. Both are created unconditionally in the constructor and exist for the actor's whole life, though they no longer receive instances directly themselves — `CellMeshComponentType` (`ECellMeshComponentType::Instanced`/`HierarchicalInstanced`, default `HierarchicalInstanced`) now picks which of them actually receives instances (see `GetActiveCellsMeshComponent()` under `Automata/Rendering/` below); there is no separate scene-root or camera spline (that system was fully removed; `AGamePlayerController` no longer has `StartSplineMovement`/`StopSplineMovement`/spline-following `Tick`). Owns simulation parameters (`GridSize`, `ChunkSize`, `Amount`, `Seed`, `SpawnRadius`, `ClusterFactor`, `Speed`, `CameraSpeedMultiplier`, `CellMesh`/`CellMaterial`/`AgeColors`/`AgeColorMaxAge`/`DecayColors`/`CellSize`/`CellMeshComponentType`, `bEnableChunkedRender`/`ChunkedRenderCellsPerFrame`/`ChunkedRenderOrder`/`StepsPerRender`, `BirthCounts`, `SurvivalCounts`, `Neighborhood`) exposed as `CallInEditor` UFUNCTIONs (`Start/Pause/Resume/Stop/Next/Clear/GenerateRandom/NewSeed`) so designers can drive the sim from the Details panel. `BeginPlay` first wipes any instance state duplicated from the editor world (`ClearAllCellInstances()`/`ClearBakedMesh()`/`ClearGhostShape()` — PIE copies the placed actor *with* whatever instances a pre-PIE `GenerateRandom()`/`Next()` click left on its components, and the normal render path doesn't clear orphaned ones), then wires up the player controller, binds the cell renderer, calls `GenerateRandom()`, and finally shows the HUD via `InitializeHUD()`. That last call moved here **from `PostActorCreated()`** deliberately: that callback fires on any actor creation, including merely placing the actor in the editor outside PIE, and the HUD widget must never pop up outside a real game session — `BeginPlay()` is guaranteed PIE/game only. `NewSeed()` re-rolls `Seed` via `FMath::Rand()` and calls `GenerateRandom()`. A private `CreateGrid()` helper (always builds an `FDenseCellGrid` from `CellSize`/`ChunkSize` — see `Automata/Grid/` below) is shared by `GenerateRandom()`/`ResetToInitialState()`/`StartFromSelection()` (fresh grid) and `StepAsync()` (next-generation buffer) — `Next()`'s background loop is the one exception: it builds its intermediate generation buffers inside the background lambda from game-thread-snapshotted `CellSize`/`ChunkSize` copies, since `CreateGrid()` reads live UPROPERTYs a background thread must not touch (see `Next()` below). `GenerateRandom()`/`Next()`/`StepAsync()`→`ApplyStepResult()` all log generation-or-step and render timing (`FPlatformTime::Seconds()`) as an ad-hoc profiling baseline ahead of scaling to much larger cell counts. `Next()` builds a fresh `FCellularAutomatonRule` from `BirthCounts`/`SurvivalCounts`/`Neighborhood` every call (so Details-panel edits take effect immediately, no caching) and advances **`StepsPerRender` generations per call** (the same value the T/G hotkeys tune; at `1` it's the original single step), rendering only the final generation in one immediate shot via `RenderGridImmediate()` — intermediate generations never hit the screen, mirroring how continuous Play skips renders under `StepsPerRender`. The whole multi-generation loop runs on the thread pool exactly like `StepAsync()` (it used to be fully synchronous on the game thread, which froze the screen for the entire computation once multiplied by `StepsPerRender`): rule/strategy/`CellSize`/`ChunkSize` are snapshotted on the game thread before dispatch (intermediate generation buffers are built *in* the background lambda from the snapshotted values, constructing `FDenseCellGrid` directly rather than via `CreateGrid()`, which reads live UPROPERTYs), `bStepInProgress` guards the whole flight, and the completion hands off to the game thread to swap `Grid` and render — so the only remaining hitch on F is the render itself, same as Play. **Still stub**: `Clear`. Cell storage/rendering/simulation is delegated to the `Automata/` subsystem (below), not implemented inline.

Continuous play/stop: `Start()` (also acts as the "Play" entry point) generates a grid if none exists yet, resets the tick accumulator, sets `bSimulationRunning = true`, and calls `SetActorTickEnabled(true)`. `PrimaryActorTick.bCanEverTick = true` but `bStartWithTickEnabled = false` in the constructor, so the actor doesn't tick at all until `Start()` explicitly enables it. `Tick()` accumulates `DeltaTime` and, once it crosses `1/Speed` seconds (recomputed each tick, not cached, so editing `Speed` in the Details panel takes effect immediately), calls `StepAsync()` — **not** `Next()` — provided no background step is already in flight (`!bStepInProgress`) and no render hand-off is pending (`!bRenderHandoffPending`, see `StepsPerRender` below); if either is true, that tick is skipped rather than queued. `Stop()` clears `bSimulationRunning`, calls `FinishChunkedRenderImmediately()` (see Chunked rendering below — snaps any in-progress reveal, including a pending hand-off, straight to its final state instead of leaving it frozen once ticking stops), then disables ticking; it does **not** reset the grid (that's `Clear()`'s job, still a stub).

**`StepAsync()` — off the game thread, so continuous Play doesn't stall the camera/UI**: `Next()` (the manual `CallInEditor` button) originally stayed fully synchronous, but during continuous Play, that same synchronous cost was landing straight in `Tick()`, blocking the game thread (and therefore camera movement/input) for as long as the step took, which got severe at scale (multi-second stalls once the grid grew past hundreds of thousands of cells) — `StepAsync()` was the fix for Play, and `Next()` itself later moved to the same background-dispatch pattern too once it started computing `StepsPerRender` generations per press (see the orchestrator bullet above; the freeze that was tolerable for one step wasn't for ten). `StepAsync()` fixes this: on the game thread it first builds `FCellularAutomatonRule` from `BirthCounts`/`SurvivalCounts`/`Neighborhood`, a compute strategy via `CreateComputeStrategy()` (picks `FCpuComputeStrategy`/`FGpuComputeStrategy` per `ComputeMethod` — see `Automata/Simulation/` below), and a fresh `NextGridBuffer` via `CreateGrid()` (all three read Details-panel `UPROPERTY`s, so this snapshot has to happen before handing off — a background thread must never race a Details-panel edit), sets `bStepInProgress = true`, then dispatches `ComputeStrategy->Step(*Grid, *NextGridBuffer, AutomatonRule)` onto `Async(EAsyncExecution::ThreadPool, ...)` (`ComputeStrategy`, a `TUniquePtr`, is captured by move into the lambda exactly like `NextGridBuffer`). The CPU strategy's internal `ParallelFor` (see `Automata/Simulation/` below) still runs fine nested inside this — the calling thread is now a thread-pool worker instead of the game thread, so the game thread is free the whole time. **One dispatch is not necessarily one generation**: `StepAsync()` asks the freshly built strategy `SupportsStepBatching(Rule)` and, when it says yes (GPU, non-Generations rule), computes `StepsPerRender` generations inside that single background dispatch via the `StepBatch()` loop — the same loop and the same skip-`ComputeAges()`-when-`> 1` rule as `Next()`, holding the previous generation alive in a local `TUniquePtr` while the next is computed into a fresh buffer (built in the background from game-thread-snapshotted `CellSize`/`ChunkSize`, same as `Next()`). When it says no — the CPU strategy — `BatchGenerations` stays 1 and the previous rhythm is preserved exactly, render-skipping counter and all; collecting generations into one long block there would be identical work with coarser pacing and a longer-held `bStepInProgress`, i.e. pure loss. **The loop also breaks out the moment `StepBatch()` reports it advanced only one generation**, for the same reason applied dynamically: `SupportsStepBatching()` is answered once per dispatch, but whether a batch actually fits is decided inside `StepBatch()` from the current AABB volume, which grows with the grid. Once that volume passes the batch ceiling the batch is trimmed to 1, and without the early break the loop would grind `StepsPerRender` single steps inside one dispatch — the same work as one multi-second block, holding `bStepInProgress` (which gates R and regeneration) throughout and interrupting the chunked reveal. Observed live at ~11M live cells: one such dispatch took 7.7 s. Correspondingly `LastDispatchGenerations` is written in `ApplyStepResult()` from what actually happened, not in `StepAsync()` from what was planned — otherwise a trimmed batch would make `Tick()` wait `StepsPerRender / Speed` for a single computed generation, slowing the simulation by exactly that factor. Correspondingly, `Tick()` paces dispatches at `LastDispatchGenerations / Speed` rather than `1 / Speed`, so `Speed` keeps meaning *generations* per second instead of silently becoming *dispatches* per second once batching engages.

When the background lambda finishes, it hands off to `AsyncTask(ENamedThreads::GameThread, ...)`, which calls `ApplyStepResult()` — swaps `Grid` and immediately clears `bStepInProgress` (deliberately at the *top* of the function, right after the swap, not at the end — its scope is narrowed to exactly "a background `Step()` is reading `*Grid`", nothing about rendering) before deciding whether/how to render (see `StepsPerRender` under Chunked rendering below); `Next()` and `GenerateRandom()` both check `bStepInProgress` and refuse (with a warning log) to run while a background step is outstanding — otherwise a manual click during Play could swap `Grid` out from under the background thread mid-read. The game-thread→background handoff captures `this` only as a `TWeakObjectPtr` for the completion callback (guards against the actor being destroyed — e.g. level unload — while a step is in flight; the background lambda itself never touches `this` at all, only the pre-snapshotted rule/grid pointers).

**Chunked rendering — spreads `AddInstances` across multiple frames for huge grids**: even with `StepAsync()` moving the simulation step off the game thread, `Renderer->Render()`'s own `AddInstances` call is still synchronous and still runs on the game thread — profiling showed it alone taking tens to hundreds of milliseconds once the grid grows past a few hundred thousand live cells, which is enough to stall the camera for a visible frame even though the step itself no longer does. `ApplyStepResult()` only takes this path for continuous Play (`StepAsync`'s completion), gated purely by `bEnableChunkedRender` — no automatic cell-count threshold; it's a manual on/off switch (Details panel or the **Z** hotkey, see `AGamePlayerController::OnToggleChunkedRender()` above) — `Next()`/`GenerateRandom()` always render the whole grid in one shot, since spreading a single deliberate manual action across frames would hurt responsiveness rather than help it. When chunking triggers, the shared `RenderCurrentGrid()` helper (used by both `ApplyStepResult()`'s normal path and the deferred hand-off below) calls `Renderer->BeginRender(*Grid, ChunkedRenderOrder, CameraLocation)` (builds the full `TArray<FTransform>` and clears the component once, but adds nothing yet) and sets `bChunkedRenderInProgress = true` — `bStepInProgress` is unaffected (already cleared, see `StepAsync()` above). `Tick()` then calls `AdvanceChunkedRender()` every frame — regardless of `bSimulationRunning`, so a reveal already in progress finishes even if `Stop()` is called mid-way — which calls `Renderer->AdvanceRenderChunk(ChunkedRenderCellsPerFrame)` to add the next slice of the pre-built transforms; once the whole array has been added, it clears `bChunkedRenderInProgress` and logs how many frames the reveal took. `FInstancedMeshCellGridRenderer::Render()` itself is implemented as `BeginRender(Grid, EChunkedRenderOrder::Sequential, FVector::ZeroVector)` (order is irrelevant for a one-shot render — everything lands in the same frame regardless) followed by one unbounded `AdvanceRenderChunk()` call, so the one-shot and chunked paths share the same transform-building code without duplication.

**`EChunkedRenderOrder` — which order live cells appear in across those frames** (`Automata/Rendering/ChunkedRenderOrder.h`, its own header like `ENeighborhood`): `AAutomataOrchestrator::ChunkedRenderOrder` picks it, rebuilt/read fresh on every `BeginRender()` call, no caching — same convention as `ComputeMethod`/`FCellularAutomatonRule`. `FInstancedMeshCellGridRenderer::BeginRender()` reorders the `TArray<FIntVector>` from `GetAliveCells()` (cheaper to permute than the built `FTransform`s) before building transforms, timed as `FRenderTimings::ReorderSeconds`: **`Sequential`** (default) — no-op, `GetAliveCells()`'s own order, which for `FDenseCellGrid` is chunk-by-chunk (`TMap<FIntVector, FChunk>` iteration order), so the reveal visibly fills one spatial blob at a time before moving to the next; **`SequentialReversed`** — `Algo::Reverse` of the same order; **`Shuffled`** — one `Algo::RandomShuffle` — each frame's slice becomes a uniform-random sample of the whole grid, so the overall silhouette is visible almost immediately and subsequent frames just increase density, rather than filling blob-by-blob; **`DistanceFromCameraNearFirst`**/**`DistanceFromCameraFarFirst`** — `Algo::Sort` by squared distance from `GamePC->PlayerCameraManager->GetCameraLocation()` (`FVector::ZeroVector` if `GamePC`/its camera manager isn't set yet), ascending or descending; **`FromCenterOutward`** — `Algo::Sort` by squared distance from the midpoint of the current alive-cell AABB (computed fresh from `AliveCells` each call, not from `FDenseCellGrid`'s internal chunk grid, so the renderer stays grid-agnostic) — reveal "grows" outward from the grid's own center regardless of camera position. Switchable live via the **X** hotkey (`AGamePlayerController::OnCycleChunkedRenderOrder()` → `CycleChunkedRenderOrder()`, cycles through the enum and wraps) or directly in the Details panel.

**`bWaitForChunkedRenderToFinish` — interrupt-and-restart vs. wait-for-completion when a new generation outruns the reveal**: by default (`false`), if a new generation finishes computing while the previous chunked reveal is still spreading across frames, `ApplyStepResult()` doesn't wait for it — it immediately calls `RenderCurrentGrid()` again, which rebuilds `PendingTransforms` from scratch via `BeginRender()` on the new `Grid`, so the undrawn tail of the previous reveal simply never reaches the screen (this is the **only** behavior that existed before this property was added, and remains the default). Setting it to `true` instead gates *stepping itself*, not rendering: in `Tick()`, `bBlockedByChunkedRender = bWaitForChunkedRenderToFinish && bChunkedRenderInProgress` is added to both the `bSimulationRunning` and `bFastStepActive` step-dispatch conditions, so the next `StepAsync()` (computing the next generation) simply doesn't fire while a reveal is still in progress — `TimeSinceLastStep` keeps accumulating meanwhile, so the step fires on the very next `Tick()` once `AdvanceChunkedRender()` (called unconditionally earlier in the same `Tick()`) finishes the reveal, no explicit hand-off flag needed. Because stepping is blocked at the source, `ApplyStepResult()`'s `if (bChunkedRenderInProgress)` interrupt branch is never actually reached in this mode — the reveal is always already finished by the time a new generation is ready to render. This deliberately gates *computing* the next generation, not just its render, matching "wait for the drawing to finish, then reset/draw the new state, and only then compute the next one." Switchable live via the **V** hotkey (`AGamePlayerController::OnToggleWaitForChunkedRenderToFinish()` → `SetWaitForChunkedRenderToFinish()`/`IsWaitingForChunkedRenderToFinish()`) or directly in the Details panel — unlike `ChunkedRenderCellsPerFrame`, not gated by `bEnableChunkedRender`'s `EditCondition`, so it stays visible as a pre-configurable default the same way `ChunkedRenderOrder` does.

**`StepsPerRender` — computing generations ahead of the display, without rendering every one**: at large cell counts, even chunked `AddInstances` costs real time, and showing every single generation isn't necessary — `StepsPerRender` (default `1` = render every generation, current behavior) lets `ApplyStepResult()` skip rendering for `StepsPerRender - 1` out of every `StepsPerRender` computed generations, only calling `RenderCurrentGrid()` once the counter (`StepsSinceLastRender`, reset in `GenerateRandom()`/`Start()`/`StartFastStep()` for a clean count on every fresh run) reaches the threshold. `ApplyStepResult()` takes how many generations its dispatch advanced and steps `StepsSinceLastRender` — as well as `GenerationCount` and the ghost-shape counter — **by that count rather than by one**, which is what makes the batched path (see `StepAsync()` above) need no special case at all: a dispatch that lands a full batch reaches the threshold through the very same condition and renders; skipped generations just log a "рендер пропущен (X/Y)" line and return immediately, so `Tick()` can dispatch the next `StepAsync()` right away (paced only by `Speed`, same as always) — this is exactly what narrowing `bStepInProgress`'s scope (see `StepAsync()` above) enables: computing ahead no longer waits on `bChunkedRenderInProgress`. This deliberately caps how far ahead the simulation can get to **at most one batch** past what's on screen: if the `StepsPerRender`-th generation finishes computing while the *previous* one's chunked reveal hasn't finished trickling in yet, `ApplyStepResult()` doesn't interrupt that reveal (which would abandon its progress and restart from scratch) — instead it sets `bRenderHandoffPending = true` and returns, and `Tick()`'s dispatch condition also checks `!bRenderHandoffPending`, so no further stepping happens until the hand-off completes. `AdvanceChunkedRender()` checks `bRenderHandoffPending` right after finishing a reveal and, if set, immediately calls `RenderCurrentGrid()` for the (by-then possibly even more current) `Grid` and clears the flag — at which point `Tick()` is free to start the next batch. `FinishChunkedRenderImmediately()` (`Stop()`'s helper, see above) does the same hand-off check before its own flush loop, so a pending generation is never left permanently unrendered just because Play was stopped mid-wait. `GenerateRandom()` ignores `StepsPerRender` entirely, and both it and `Next()` always render immediately and in full, ignoring `bEnableChunkedRender`'s spreading — but `Next()` *uses* `StepsPerRender` differently than Play does: rather than skipping renders between background steps, it computes all `StepsPerRender` generations in one background batch per press and renders only the last (see the orchestrator bullet above) — same net "generations per render" ratio, different mechanism.

**Correctness note on `GamePC`**: `AGamePlayerController* GamePC` is a `UPROPERTY(Transient)`, not a raw pointer — this matters specifically because of Live Coding. Reinstancing after a hot patch during an active PIE session only copies `UPROPERTY`-tagged fields from the old instance to the new one; a plain C++ member survives as uninitialized garbage (not `nullptr`), and `BeginPlay()` — the only place that populates `GamePC` — does not re-run on reinstancing. A raw-pointer `GamePC` therefore silently held garbage after any Live Coding patch made during PIE, and `Pause()`/`Resume()` dereferencing it segfaulted (`Access violation`) the next time either was called, crashing the whole Editor process. Fixed by making it a `UPROPERTY` (so reinstancing either preserves it correctly or resets it to `nullptr`) plus explicit null checks in `Pause()`/`Resume()` that log a warning and return instead of crashing when `GamePC` isn't set yet (e.g. before `BeginPlay`/outside PIE). Any other raw non-`UPROPERTY` `UObject*` member added to `AAutomataOrchestrator` (or any `UCLASS` in this project) in the future is a candidate for the same bug.
- **`Automata/Grid/`** — `FCellGrid` (`CellGrid.h`, abstract, plain C++ not `UObject`): stores live cells addressed by integer `FIntVector` coordinates, decoupled from rendering. `GetAliveCells`/`SetAlive`/`Clear`/`Num` are pure virtual; `GridToWorld(FIntVector)` is **virtual with a default cubic-lattice implementation** (`Cell * CellSize`) — deliberately virtual so a future non-cubic topology (e.g. hex) can override just the coordinate-to-world math without touching storage or rendering. `FDenseCellGrid` (`DenseCellGrid.*`, chunked: space is divided into fixed-size cubic chunks — default `ChunkSize=16`, i.e. 4096 cells — each a packed `TBitArray`; chunks live in a sparse `TMap<FIntVector, FChunk>` and are lazily created on first live cell / pruned when they empty out, so memory scales with occupied volume, not a fixed upper bound) is the sole concrete implementation, unconditionally constructed by `CreateGrid()` from `CellSize`/`ChunkSize`. An earlier `FSparseCellGrid` (`TSet<FIntVector>`-backed) existed alongside it, selectable via an `AAutomataOrchestrator::GridStorageStrategy` enum property — both were removed to simplify the storage layer down to one implementation; if a sparse/scatter-friendly storage is ever needed again, reintroducing it as a second `FCellGrid` subclass is straightforward since the interface is already storage-strategy-agnostic everywhere else (`FCpuComputeStrategy`/`FGpuComputeStrategy`/`FInstancedMeshCellGridRenderer` only ever go through `GetAliveCells()`/`SetAlive()`/`GridToWorld()`). **Correctness note if touching `FDenseCellGrid`**: chunk-coordinate math needs real floor-division/positive-modulo helpers (defined file-local in `DenseCellGrid.cpp`) because cell coordinates routinely go negative (sphere-centered generation) and `FMath::DivideAndRoundDown` is *not* floor division for integers (it truncates toward zero). Chunk granularity is intentionally the unit future CPU/GPU per-chunk dispatch would parallelize over — not implemented yet. `FCellGrid` also declares `GetAge(FIntVector)`/`SetAge(FIntVector, uint8)` — a per-cell saturating byte counting how many consecutive generations that cell has survived (`0` = just born), used by the `AgeColors` ramp when colouring instances (see `Automata/Rendering/` below). `FDenseCellGrid::FChunk` stores this as a parallel `TArray<uint8> Ages` alongside `Bits`, indexed identically via `CellToLocalIndex()` — zero-initialized on lazy chunk creation and wiped wholesale (along with the rest of the chunk) when a chunk empties out and gets pruned, so a cell reborn later in a freshly-recreated chunk always starts at Age 0, never inheriting stale history. Age is deliberately **not** computed inside either compute strategy — `Automata/Simulation/CellAging.h/.cpp`'s `CellAging::ComputeAges(const FCellGrid* OldGrid, FCellGrid& NewGrid)` is a separate post-`Step()` pass, called from `Next()` and from `StepAsync()`'s background lambda right after `ComputeStrategy->Step(...)`, that diffs every alive cell in `NewGrid` against `OldGrid` (`Age = OldGrid->GetAge(Cell)+1` if it was already alive there, else `0`) purely through the public `FCellGrid` interface — this means `FCpuComputeStrategy`, `FGpuComputeStrategy`, and the `.usf` shader needed **zero changes** to support aging. `GenerateRandom()` needs no `ComputeAges()` call at all — a freshly created grid's chunks zero-init `Ages` on their own, so newly spawned cells are already Age 0 for free. Safe to fully parallelize (unlike the `SetAlive`/`WriteBack` sequential phase elsewhere) because `SetAge` only ever writes distinct bytes at distinct array indices, never touching the `TBitArray`/`AliveCount` that actually need serialized writes.

- **`Automata/Simulation/`** — `ENeighborhood` (`Neighborhood.h`, `UENUM`) — deliberately its own header rather than folded into `AutomataOrchestrator.h`, so the simulation subsystem owns its own type. It is **one concept, with no separate radius**: each of its 14 values names a set of *shells*, and the set fixes both which cells count as neighbours and how far the rule reaches.

**Four shells are the entire design space, and knowing that is what keeps a fifteenth value from being invented.** Every offset worth having falls into one of four classes, told apart by squared length: faces `d²=1` (6, ±1 on one axis), edges `d²=2` (12), corners `d²=3` (8), far axes `d²=4` (6, ±2 on one axis — "skip a cell"). Of the 15 non-empty subsets, **14 are enum values** — `VonNeumann` is faces, `Moore` is faces+edges+corners, `VonNeumann2` is faces+edges+far axes, and the rest are named for their contents. The one missing subset is all four at once: they total **32** against a shader array of **26**, and — the fact that settles it — *no subset sums to anything between 27 and 31*, so raising that array short of the mask rework would buy literally nothing. Everything at 32 or beyond (all four shells, the Euclidean radius-2 ball which is also exactly 32, Moore r=2 at 124, von Neumann r=3 at 62) hits the 32-bit `BirthMask`/`SurvivalMask` and needs them reworked first. The geometry itself lives in exactly one place, `GetNeighborhoodShellMask()`, which `BuildNeighborOffsets()` merely expands — so a new neighbourhood is one line there plus one row in the parser's token table.

**There used to be a separate `NeighborhoodRadius`, and removing it was a simplification, not a feature cut.** Radius > 1 only ever worked for von Neumann, and von Neumann radius 2 is *precisely* faces+edges+far axes — i.e. the whole mechanism served one set that the shells already express. Moore r=2 was expressible by radius but never fit, so it never worked either way. The removal also deleted a constraint the parser had been carrying: trailing digits were stripped as a radius, which forbade any token ending in a digit. Now names are compared whole, so `VN2` is simply a name. Saved files are migrated on load — a `.casave` written with `VonNeumann` + `NeighborhoodRadius=2` maps to `VonNeumann2`, since otherwise it would silently reload as plain von Neumann with 6 neighbours instead of 24; `FAutomatonSaveHeader::NeighborhoodRadius` survives as a read-only legacy field for exactly that.

**What the shapes are for.** `FacesEdges` is the geometric prize: `d² ≤ 2` is the exact midpoint between von Neumann's `d² ≤ 1` and Moore's `d² ≤ 3`, and it grows a **rhombic dodecahedral** front — the third classic polyhedron, which neither of the familiar two produces. The shell sets that omit faces earn their place structurally instead: `Edges` preserves the parity of `x+y+z`, so the lattice splits into **two** mutually invisible sublattices (these are the FCC nearest neighbours); `Corners` flips every coordinate's parity each step, splitting it into **four**; `FarAxes` preserves the parity of *each* coordinate, splitting it into **eight** — inside any one of them it is literally von Neumann on a lattice of twice the spacing. All of these render as sparse crystal rather than solid. Two identities are worth remembering because they orient the whole table: `EdgesFarAxes` is exactly the Manhattan shell `|d| = 2`, i.e. **`VonNeumann2` with its interior removed**, and `EdgesCornersFarAxes` has the same 26 offsets as `Moore` built from entirely different shells — a direct "26 against 26" comparison at equal cost.

**Reach comes from the offsets, never from a stored number — `GetNeighborExtent()`.** Sets containing far axes reach *two* cells while everything else reaches one, and the GPU batch halo is sized from reach: `StepBatch()` uses `Extent × NumSteps`. `FCellularAutomatonRule` therefore computes the extent as the largest component magnitude over the actual offset list. Deriving it from the geometry rather than storing it alongside is what makes any future neighbourhood correct for free, and the failure mode it guards is invisible — too small a halo silently drops border cells, with no crash and no log line. `Compute.GpuBatchParity`'s `FarAxes` case exists solely for this: it is the one case where reach (2) exceeds what a naive "one cell per generation" assumption would give.

**Cost is linear in the offset count and nothing else.** `Pack`/`Unpack`/`GetAliveCells` do not change with the neighbourhood at all (they are per live cell), and the CPU candidate buffer is `alive × (offsets+1) × 12` bytes, so a 24-offset set is *cheaper* than the 26-offset Moore this project runs by default. The only thing reach costs is batch length: at extent 2 the halo doubles, so `StepsPerRender` starts getting trimmed roughly twice as early. Not one line of the `.usf` has changed across any of this work.

**`RuleStringParser` (`Automata/Simulation/RuleStringParser.h/.cpp`, plain namespace like `CellAging`) — string notation as a convenience layer, not a replacement**: parses `"Survival/Birth/States/Neighborhood"` (e.g. `"0-6/1,3/2/VN"`, `"13-26/13-14,17-19/2/M"`) — the exact format used by williamyang98/3D-Cellular-Automata (itself following Softology): Survival/Birth are comma-separated lists whose elements are single counts or inclusive `x-y` ranges, States is the total cell-state count (`>= 2`), Neighborhood is a short or long name from the `NeighborhoodTokens` table (`VN`/`VonNeumann`, `M`/`Moore`, `VN2`/`VonNeumann2`, `E`/`Edges`, `C`/`Corners`, `FA`/`FarAxes`, `FE`/`FacesEdges`, `FC`, `FFA`, `EC`, `EFA`, `CFA`, `FCFA`, `ECFA`), case-insensitively. That one table serves parsing, printing *and* the error message, so the three cannot drift apart when a neighbourhood is added. Names are compared whole — `VN2` is a name, not "VN with a digit" — which is only possible because the separate radius is gone. The digit is taken by stripping trailing digits off the token rather than by a separator, so `VonNeumann` parses through the same code as `VN`; its absence means radius 1, and `FormatRuleString()` symmetrically omits the digit at radius 1 — that pairing is what keeps every previously written rule string, and all 14 `RulePresets` entries, parsing *and* printing byte-identically to before radius existed. This is **not** a reversal of the "no rule string" decision above — that was specifically about Conway notation breaking on two-digit neighbor counts; explicit `,`/`-` separators are unambiguous at any digit count. `ParseRuleString()` fills a result struct or fails with a human-readable error and touches nothing (never applies a rule half-way); `FormatRuleString()` is the inverse, re-compressing count lists into ranges (`1,2,3,7` → `1-3,7`). `AAutomataOrchestrator::RuleString` (`UPROPERTY`) plus `ApplyRuleString()`/`TryApplyRuleString()` are the only consumers — they overwrite `BirthCounts`/`SurvivalCounts`/`States`/`Neighborhood` **by field name, never positionally** (the string's field order is Survival-then-Birth, the opposite of those properties' declaration order — blind positional assignment would silently swap them). `GetActiveRuleString()` reports the *effective* rule by formatting those four properties, rather than echoing `RuleString`, which may be empty (rule built from the arrays in the Details panel) or stale (arrays hand-edited afterwards).

**`States` / Generations — multi-state decay**: `States == 2` (default) is the classic binary automaton and behaves bit-identically to how the project worked before this existed. `States > 2` enables "Generations": a cell that stops surviving doesn't die outright but decays through states `2, 3, ..., (States-1)` on its way to 0 (fully dead), and while decaying it is **birth-immune** — it can be neither revived nor killed, it just walks down at a fixed rate. Only state 1 (fully alive) counts as a live neighbor. Decay state is a **separate storage channel from `Age`** (see `FCellGrid::IsDecaying()`/`GetDecayState()`/`SetDecayState()`): `Age` is cosmetic, monotonic, and meaningful only for live cells; decay state affects the rule itself and is meaningful only for non-live ones. `FDenseCellGrid::FChunk` holds it as a third parallel `TArray<uint8> DecayStates` next to `Bits`/`Ages`, allocated **only** when the grid was constructed with decay enabled (`CreateGrid()` passes `States > 2`) — at `States == 2` it stays a default-empty `TArray` with no heap allocation at all, so the feature costs literally nothing in the common case. `ClampMax = 255` on `States` is not decorative: the state is a `uint8`.

Advancing decay is `CellDecay::AdvanceDecayStates(OldGrid, NextGrid, MaxStates)` (`Automata/Simulation/CellDecay.h/.cpp`) — a post-`Step()` pass alongside `CellAging::ComputeAges()`, working purely through the public `FCellGrid` interface so it doesn't care whether the generation was computed on CPU or GPU. Unlike `ComputeAges()` it is **not** parallelized: `SetAge()` is safe to call concurrently because the cell is already alive in the new grid (its chunk was created by the sequential write-back phase), whereas a decaying cell is typically *not* alive there and needs a lazy chunk creation — and `TMap::Add()` is not thread-safe even for disjoint keys. Both compute strategies needed only a narrow change for birth-immunity: the CPU strategy gained one short-circuit branch, and the GPU shader a second input bit-plane (`InputDecayBits`, "is decaying") gated by a `bDecayActive` uniform, bound to the same buffer as `InputBits` when inactive so no second allocation happens at `States == 2`. Rendering colours decay stages from their own `DecayColors` ramp (see `Automata/Rendering/` below). `States` round-trips through `.casave` as its own header field.

**`Automata/Simulation/ComputeStrategy/` — pluggable compute strategy**: `FCellularAutomatonComputeStrategy` (`CellularAutomatonComputeStrategy.h`, abstract, plain C++ not `UObject`, non-copyable — same convention as `FCellGrid`/`FCellGridRenderer`) declares the one-generation contract `virtual void Step(const FCellGrid& CurrentGrid, FCellGrid& NextGrid, const FCellularAutomatonRule& Rule) const = 0`: for every alive cell and its neighbors (candidate set, so cells can only be born adjacent to something alive), counts alive neighbors in `CurrentGrid` and writes the next state into `NextGrid` — never mutates `CurrentGrid`, so callers must double-buffer (see `AAutomataOrchestrator::Next()`). This is a deliberately **synchronous/blocking** contract mirroring the original `FCellularAutomatonRule::Step()` it replaced — `Next()`/`StepAsync()` already wrap the call appropriately for their own needs (`StepAsync()` dispatches onto `Async(EAsyncExecution::ThreadPool, ...)`, see above), so a strategy with its own async backend (e.g. a GPU dispatch+readback) does that internally rather than changing this interface.

**`StepBatch()` / `SupportsStepBatching()` — several generations per strategy invocation**: `virtual int32 StepBatch(Current, Next, Rule, NumSteps)` advances *up to* `NumSteps` generations in one call, exposing only the last one in `NextGrid`, and returns how many it actually advanced (always `>= 1`, `<= NumSteps`). Callers loop `while (Done < NumSteps) Done += StepBatch(..., NumSteps - Done)` and never need to know whether a given strategy can batch. The default implementation is a single `Step()` returning 1, so `FCpuComputeStrategy` is untouched and that loop degenerates to the previous one-generation-per-iteration shape. It exists because the GPU strategy pays a full CPU→GPU→CPU cycle *per generation* (pack, upload, blocking readback, and an unpack that is linear in the AABB **volume**, not in live cells) — at `StepsPerRender > 1` that was being paid for generations nobody ever sees. Two obligations bind any implementation returning `> 1`: it must have **filled the ages itself** (`CellAging::ComputeAges()` can only diff two adjacent generations, and the intermediates no longer exist — the caller skips `ComputeAges()` exactly when it gets `> 1` back), and it must not do so for a Generations rule (`Rule.HasDecayStates()`), since `CellDecay::AdvanceDecayStates()` runs *between* generations on the CPU and a batch would jump over it.

`virtual bool SupportsStepBatching(const FCellularAutomatonRule&)` answers a different question — not *how* to call `StepBatch()` but whether the caller should **restructure around** batching, which has to be decided before the call. It matters only in continuous Play (see `StepAsync()` above): `true` makes one background dispatch compute the whole `StepsPerRender` run, `false` keeps the one-generation-per-dispatch rhythm with the render-skipping counter. Default `false`; `FGpuComputeStrategy` returns `!Rule.HasDecayStates()`. It deliberately does **not** check volume limits — those depend on the current grid state and change generation to generation, and `StepBatch()` handles them itself by trimming the batch; answering "unsupported" because of one momentarily inflated AABB would disable batching for the rest of the run. `AAutomataOrchestrator::ComputeMethod` (`EComputeMethod::Cpu`/`Gpu`) picks which concrete strategy `CreateComputeStrategy()` constructs — a private factory that switches on `ComputeMethod`, mirroring how `CreateGrid()` builds the grid from its own Details-panel properties; both `Next()` and `StepAsync()` call it fresh every invocation (same "rebuild from Details-panel UPROPERTYs every call" convention as `FCellularAutomatonRule` itself), so switching methods mid-session takes effect immediately with zero caching.

`FCpuComputeStrategy` (`CpuComputeStrategy.*`) is the **only currently-working implementation** — an exact relocation of the original `FCellularAutomatonRule::Step()` body, with `NeighborOffsets`/`BirthCounts`/`SurvivalCounts` member access rewritten to `Rule.GetNeighborOffsets()`/`Rule.GetBirthCounts()`/`Rule.GetSurvivalCounts()` and otherwise unchanged. **Parallelized across CPU threads**: the per-candidate neighbor-count-and-decide work only reads `CurrentGrid`, so it's embarrassingly parallel — it runs via `ParallelFor` over an indexed `TArray<FIntVector>` of deduplicated candidates, writing each candidate's next-alive state into an indexed `TArray<bool>` (not bit-packed in Unreal, unlike `std::vector<bool>`, so concurrent writes to distinct indices don't race). The actual `NextGrid.SetAlive(...)` calls happen afterward in a plain sequential loop over that result array — `TBitArray` inside `FDenseCellGrid` isn't thread-safe for concurrent writes, so it can't be called from inside the `ParallelFor` body. Verified via a temporary thread-ID-collecting diagnostic that this engages the real OS thread pool (~31 threads — 30 `FTaskGraphInterface` workers plus the calling thread — on a 16-core dev machine), not just nominal capacity.

**Candidate-set construction is itself parallelized (bucket-partitioned dedup)** — profiling at 1M+ live cells (added `FPlatformTime::Seconds()` breakdown logging inside `Step()`, still present) revealed that an earlier `TSet<FIntVector>`-based dedup (each alive cell's `Cell` + all `NeighborOffsets` inserted via `TSet::Add`, up to 27 hash-insertions per alive cell for Moore) consumed ~80% of total step wall-time on a single thread, even though the neighbor-count `ParallelFor` above genuinely engaged ~31 threads — the dedup itself was the actual bottleneck the whole time, not the per-candidate work. A first attempt at fixing this (fill a flat pre-sized array with duplicates via `ParallelFor`, then a single global `Algo::Sort`+`Algo::Unique` pass) measured *no real improvement*: `Algo::Sort` has no parallel variant in this engine, so sorting the entire un-deduplicated array (which is exactly as large as the old TSet's total insert count) is comparably expensive to hashing it — swapping one single-threaded bottleneck for another. The actual fix partitions candidates into `NumBuckets = 256` independent buckets by `GetTypeHash(Candidate) & BucketMask` (deterministic, so every duplicate of the same cell always lands in the same bucket regardless of which alive cell or thread produced it) via a classic counting-sort scatter: (1) a `ParallelForWithTaskContext` histogram pass gives each task a thread-local `TArray<int32>` bucket-count array (no synchronization), merged into one global histogram afterward (cheap — `NumTasks × NumBuckets` small ints); (2) a prefix sum over the histogram gives each bucket's offset into a flat `Scattered` array; (3) a second `ParallelFor` over alive cells scatters every raw candidate (duplicates included) into its bucket's slice, using `FPlatformAtomics::InterlockedIncrement` on a per-bucket cursor (`BucketCursors`, seeded from the offsets) since multiple threads write into the same bucket concurrently — but buckets themselves never overlap in memory; (4) a `ParallelFor(NumBuckets, ...)` sorts (`Algo::Sort`) and dedups (`Algo::Unique`) each bucket's slice independently, in parallel, with zero cross-thread synchronization since bucket memory ranges are disjoint; (5) a final `ParallelFor(NumBuckets, ...)` `FMemory::Memcpy`s each bucket's deduplicated slice into its final position in `Candidates` (offsets from a second prefix sum over post-dedup bucket sizes). Verified in PIE: at ~2.2M live cells this dropped `CandidateBuild`'s share of step time from ~80% to ~38% (675ms out of 1760ms total, vs. `ParallelFor`'s 865ms and `WriteBack`'s 213ms) — the dedup work itself is now genuinely spread across cores instead of the neighbor-count phase being the only real parallel section.

`FGpuComputeStrategy` (`GpuComputeStrategy.*`) is a **real RDG compute-shader implementation** — grid-storage-agnostic, like the CPU strategy (only touches `FCellGrid` through `GetAliveCells()`/`SetAlive()`, never `FDenseCellGrid` internals). `Step()` runs entirely on the calling thread plus one Render Thread round-trip: (1) `GetAliveCells()` then a plain sequential min/max scan gives an integer cell-space AABB (empty grid → return immediately, `NextGrid` stays empty); (2) the AABB is expanded by `Halo = 1` cell in every axis — safe in general because every `NeighborOffsets` entry (`CellularAutomatonRule.cpp::BuildNeighborOffsets`, both `VonNeumann` and `Moore`) has components only in `{-1,0,1}`; (3) **OOM guard**: if the resulting `VolumeDim.X*Y*Z` exceeds `AAutomataOrchestrator::GpuVolumeCellLimit` (`EditAnywhere`, default `512^3` ≈ 134M cells / ~16MB bit buffer — raised from an originally-hardcoded `256^3` once that turned out to be an arbitrary conservative choice rather than a real hardware limit; deliberately kept as a guard rather than removed outright, since the failure mode it prevents — two live cells ending up far apart in a sparse grid inflating the AABB to an unmanageable volume even with few live cells overall — is still possible at any cap) — it logs a warning and falls back to `FCpuComputeStrategy` for that step, the same "never silently do nothing" convention the old stub used; the limit is passed into `FGpuComputeStrategy`'s constructor by `CreateComputeStrategy()` (see `Automata/Simulation/ComputeStrategy/` below), rebuilt fresh every call like the rest of that factory's Details-panel-driven state — no caching, so raising it takes effect on the very next step; (4) alive cells are packed into a flat `TArray<uint32>` bit buffer (32 cells/word) in AABB-local coordinates, and the rule is packed into `BirthMask`/`SurvivalMask` `uint32` bitmasks (bit *i* = count *i* allowed — 0–26 fits easily) plus a fixed `int4[26]` neighbor-offset array (Moore's 26 is the max; `VonNeumann`'s 6 just leaves the tail unused, gated by an explicit `NeighborOffsetCount`). Cells outside the halo of any live cell are never dispatched-into as "alive" and, symmetrically, any out-of-buffer neighbor read the shader does is treated as dead — this exactly matches the CPU strategy's candidate-set semantics (a cell with 0 live neighbors is never evaluated as a birth candidate by either strategy, even if `BirthMask` technically allows it).

Dispatch happens inside `ENQUEUE_RENDER_COMMAND` (so RDG/RHI calls run on the Render Thread as required) which builds an `FRDGBuilder`, uploads the input buffer (`CreateStructuredBuffer`), clears a same-sized output buffer (`AddClearUAVPass`), runs `FCellularAutomatonStepCS` (a file-local `FGlobalShader` in `GpuComputeStrategy.cpp`, one `[numthreads(4,4,4)]` thread per cell in the volume, `Shaders/Private/CellularAutomatonStep.usf`) via `FComputeShaderUtils::AddPass`, then `AddReadbackBufferPass` enqueues a copy into an `FRHIGPUBufferReadback`. The shader writes results with `InterlockedOr` since up to 32 cells share a output word and can be written by different threads concurrently. After `GraphBuilder.Execute()`, the render command calls `RHICmdList.ImmediateFlush(EImmediateFlushType::FlushRHIThread)` — a **lightweight** flush that only pushes the recorded commands down to the RHI thread (and from there the GPU), without waiting for GPU completion. This is required: without it, the just-recorded commands sit unsubmitted in the `RHICmdList` while this same Render Thread immediately starts spin-polling `Readback->IsReady()` below — since nothing ever asks the GPU to actually run the work, the fence never signals and the poll loop hangs forever (observed directly: the whole editor froze on `Start()` with `ComputeMethod=Gpu`, no crash, just a dead viewport). An earlier version instead called `RHICmdList.SubmitCommandsAndFlushGPU()` (a deprecated forward to `SubmitAndBlockUntilGPUIdle()`) to solve the same submission problem, but that waits for the **entire GPU pipeline** to go fully idle, not just this pass — in PIE that fights the viewport's own rendering for the same thread and tripped the engine's hang detector, crashing the editor after a ~6s stall on a trivially small dispatch. `FlushRHIThread` submits without that blocking wait, avoiding both failure modes. **The `Readback->IsReady()`/`Lock()`/`Unlock()` poll loop itself also stays entirely inside the render command, on the Render Thread** — an earlier version polled `Readback->IsReady()` directly from the calling thread (game thread from `Next()`, or a `ThreadPool` worker from `StepAsync()`), which crashed (`Array index out of bounds: 0 into an array of size 0` inside `FRHIGPUFence::Poll()`) because `FRHIGPUBufferReadback` isn't designed to be polled from an arbitrary non-render thread. Instead, the calling thread only shares a raw `FEvent` (from `FPlatformProcess::GetSynchEventFromPool()`) and a `TSharedRef<TArray<uint32>>` result buffer with the render command: it calls `CompletionEvent->Wait()` and only reads the result buffer after `Wait()` returns, by which point the render command (which polls `Readback->IsReady()` in a spin loop, `Lock()`/`Memcpy()`/`Unlock()`s into that shared buffer, then `Trigger()`s the event) has fully finished — `Readback` itself never leaves the Render Thread. **`FRenderCommandFence` was tried first and also crashed** (`check(IsInGameThread() || IsInAsyncLoadingThread())` inside `FRenderCommandFence::IsFenceComplete()`) — its `Wait()` is only safe from the game thread, which breaks exactly the `StepAsync()` ThreadPool-worker call path this strategy needs to support; a raw pooled `FEvent` has no such restriction, since it's just an OS-level synchronization primitive. Once unblocked, `Step()` unpacks bits back into world/cell coordinates via a sequential `NextGrid.SetAlive(...)` loop, mirroring the CPU strategy's single-threaded `WriteBack` phase for the same thread-safety reason (`TBitArray` isn't safe for concurrent writes). This whole strategy is a single blocking call from the caller's point of view — it doesn't change `FCellularAutomatonComputeStrategy::Step()`'s synchronous contract, it just has its own internal async round-trip (RDG dispatch + GPU readback, blocking the Render Thread for its duration) instead of `FCpuComputeStrategy`'s CPU-side `ParallelFor`. `Step()` itself is now just `StepBatch(..., 1)`.

**Batched dispatch (`StepBatch()`) — one upload, N ping-ponged dispatches, one readback**: with `NumSteps > 1` and a non-Generations rule, the state is uploaded once, ping-ponged between two RDG buffers across N `AddPass` calls inside a single `FRDGBuilder` (each preceded by `AddClearUAVPass`, since the shader only ORs bits and never writes zeros), and read back once. Three consequences worth knowing before touching this code:

- **The halo must equal the batch size.** A pattern grows by at most one cell per axis per generation, so halo `K` makes a `K`-step batch *exact*; a smaller halo would silently lose border cells and diverge from the CPU strategy. When the resulting volume no longer fits the limits, the **batch is trimmed** to the largest `K` that does (monotonic, so the search converges) rather than abandoned — three steps instead of ten still removes two thirds of the round-trips. If even `K == 1` doesn't fit, the usual CPU fallback applies and 1 is returned.
- **Ages move into the shader** for the duration of a batch: a byte per cell packed four to a word, saturating at 255, mirroring `FCellGrid::GetAge()`/`SetAge()` semantics, written with `InterlockedOr` for the same reason as the alive bits (four cells share a word and are computed by different threads, but own distinct bytes of a zero-cleared word). The pre-batch ages are uploaded too, so a cell surviving the whole batch continues its count rather than restarting. Gated by a `bTrackAges` uniform; when off, the SRV slot is bound to the current input bit buffer and the UAV to a one-word dummy. **Unused SRV slots must be re-bound to the *current* `BitsIn` on every pass**, not captured once before the loop: the buffers swap roles each iteration, so a stale binding would name the very buffer that pass writes to — one resource as SRV and UAV simultaneously, which RDG validates regardless of whether the shader actually reads it.
- **Batching carries its own volume ceiling** at `GpuVolumeCellLimit / 8`, because the age plane costs a byte per cell against the bit-per-cell alive plane. Derived from the existing property rather than adding a second knob, so raising one raises both.

Measured on a 221³ volume with ~195k live cells and `StepsPerRender = 10` (RTX-class desktop GPU): 10 generations as one batch took **108.9 ms** against **278.5 ms** as ten separate round-trips, with bit-identical results (1 000 616 live cells either way). The win is entirely CPU-side — `Unpack` collapsed from 155.2 ms to 33.5 ms and `GetAliveCells` from 22.9 ms to 1.4 ms, while `GpuRoundTrip` actually *rose* (48.6 → 62.0 ms), since halo 10 inflates the dispatched volume by ~29% and the age plane adds work. After batching, the GPU dispatch itself is the dominant phase, i.e. the CPU-side overhead this was built to remove is largely gone.

**Per-phase timing log**: `StepBatch()` logs a `GpuStep:` line with a `GetAliveCells / Pack / GpuRoundTrip / Unpack` breakdown plus the volume and how many generations the round-trip covered — deliberately mirroring `FCpuComputeStrategy`'s `CandidateBuild/ParallelFor/WriteBack` line. The precedent for adding it before optimizing is that project's own history: the first attempt at fixing the CPU candidate-set bottleneck (global `Algo::Sort` instead of `TSet`) measured no improvement because the assumed bottleneck wasn't the real one.

**`Unpack` was the project's single largest cost, and what fixed it was not what looked obvious.** At 35M live cells a generation took 1111 ms, of which `Unpack` was 806 and the GPU dispatch itself only 25 — the "GPU" strategy spent 98% of its time on single-threaded CPU marshalling, which is why the machine looks idle (one thread of 32) while a step runs. Three changes took `Unpack` from 23.2 to 7.0 ns per live cell (**−70%**; at 8M cells 184.5 → 53.8 ms, a generation at 11M cells 287 → 213 ms), and the order in which they were tried matters more than the changes themselves:

- **Cache the last written chunk** (`FDenseCellGrid::FindChunkForWrite()`) — −24%. `SetAlive()`'s `TMap<FIntVector, FChunk>` lookup is ~11 ns, and both `Unpack` and the CPU strategy's `WriteBack` are built out of it. Write-path only: the cache is unsynchronised shared state, and `IsAlive()`/`SetAge()` are called from `ParallelFor`.
- **Power-of-two `ChunkSize`** — a further −12%, less than hoped. Nine integer divisions per `SetAlive()` turned out to be worth only ~2 ns, since independent divisions pipeline and hide behind the lookup's memory stalls.
- **Bit-scan the readback with `CountTrailingZeros`** — **−55%**, the real fix. The old loop asked every volume cell for its alive bit and paid a branch misprediction on most of them; jumping straight to set bits branches once per *live* cell instead of once per *volume* cell.
- **`FCellGrid::SetAliveWithAge()`** — a further **−50%, but only on the batched path**. With `NumSteps > 1` the shader fills the ages, so unpacking called `SetAlive()` then `SetAge()` for the same cell — and `SetAge()` is deliberately outside the chunk cache (it is called from `ParallelFor` in `CellAging::ComputeAges()`), so it re-found the chunk from scratch. That showed up as batched unpacking costing 16.3 ns per live cell against the ordinary path's 7.0; one lookup for both fields brought it to 8.2, i.e. the anomaly was entirely this. The virtual's default implementation just calls both, so the interface stays storage-agnostic.

After these, a 254-generation batch at 19M live cells costs 946 ms of which **`GpuRoundTrip` is 778 — 82%**. The CPU-side marshalling that started out as 98% of a step is now the minor term, and further work belongs on the GPU side (or on `GetAliveCells`, the largest remaining CPU phase and still single-threaded).

Two dead ends worth not repeating. **Chunk-aligned traversal** (to make the chunk cache hit ~100% instead of ~50%) was implemented, verified to actually run via a diagnostic field in the log, and bought *exactly zero* — which is what ruled out the remaining lookups and pointed at the scan instead; it was reverted. And the reason the real cost stayed hidden so long is **collinearity**: this project's rules hold volume/live-cell ratio near 7.5, so "cost per live cell" and "cost per volume cell" both looked constant, and no regression over 695 samples could separate "the writes are expensive" from "the scan is expensive". What finally separated them was a *different* measurement — the CPU strategy's `WriteBack`, which does the same writes while scanning no empty volume at all, costing the same ~20 ns per written cell.

Required new module dependencies: `RHI`/`RenderCore` (`CellularAutomata.Build.cs`, `PrivateDependencyModuleNames`) — not Live-Coding-safe, needs a cold rebuild. `AddShaderSourceDirectoryMapping(TEXT("/Project/CellularAutomata"), .../Source/CellularAutomata/Shaders)` is registered in `FCellularAutomataModule::StartupModule()` (`CellularAutomata.cpp`) — the module previously used the engine's default `FDefaultGameModuleImpl` with no custom startup logic; `CellularAutomata.h` now declares `FCellularAutomataModule : public FDefaultGameModuleImpl` for this purpose.
- **`Automata/Rendering/`** — `FCellGridRenderer` (`CellGridRenderer.h`, abstract, plain C++): `Render(const FCellGrid&, TArray<FCellRenderInstance>&&)` — *what* to draw is an explicit list of position+colour, not the grid itself (colour depends on age/decay, which is the orchestrator's policy, and an explicit list also covers drawing a subset without wrapping the grid); the grid stays in the signature only for `GetCellSize()`, still passed per-call rather than owned. `FInstancedMeshCellGridRenderer` (`InstancedMeshCellGridRenderer.*`) is the only concrete implementation: wraps a `UInstancedStaticMeshComponent*` (owned by the Actor, not this class), with `SetMesh`/`SetMaterial` setters called fresh before each `Render()` since those are designer-editable properties. Scales each instance so the mesh's actual bounding-box size matches `CellSize` (via `UStaticMesh::GetBounds()`), so grid cells tile evenly regardless of the assigned mesh's native dimensions. `AAutomataOrchestrator` holds exactly one (`CellsRenderer`) plus one for the selection overlay, via the **concrete** type, not the abstract base, since mesh/material setters aren't part of the abstract interface. **Perf-critical**: `Render()` builds a `TArray<FTransform>` for every alive cell and adds them in one batch via `UInstancedStaticMeshComponent::AddInstances(..., bUpdateNavigation=false)` rather than calling `AddInstance()` per cell — the per-call form rebuilds internal instance buffers on every invocation and showed catastrophic super-linear scaling under profiling (~1789x slower for only 54x more cells at ~45k cells). Both `CellsMeshFlat`/`CellsMeshHierarchical` also have collision disabled (`SetCollisionEnabled(ECollisionEnabled::NoCollision)` in the orchestrator's constructor) since automaton cells are purely visual — measured combined effect (batching + no collision) was a ~37x reduction in total render time at ~45k cells.

**`CellMeshComponentType` picks which of `CellsMeshFlat` (`UInstancedStaticMeshComponent`) and `CellsMeshHierarchical` (HISM) actually receives instances** — `FInstancedMeshCellGridRenderer` itself needed zero code changes to support either, since `AddInstances`/`ClearInstances`/`SetStaticMesh` are all `virtual` overrides on HISM (it *is-a* `UInstancedStaticMeshComponent`), so calling them through the base-class pointer already dispatches correctly regardless of which concrete class it points at. Both are `AAutomataOrchestrator`'s permanent `CreateDefaultSubobject`-created components (`CellsMeshHierarchical` the actor's root); `GetActiveCellsMeshComponent()` is the single place that decides which is active, and it is what `CellsRenderer` binds to (see below). The *other* one gets a cheap defensive `ClearInstances()` each render (`ClearInactiveCellsMeshComponent()`) — the active one is cleared by `BeginRender()` anyway, so clearing it there would wipe the render being drawn, whereas stale instances genuinely can survive on the inactive one after a type switch. **Both components are created unconditionally in the constructor and live for the actor's whole lifetime** rather than being destroyed/recreated: dynamically swapping which `UClass` a `CreateDefaultSubobject`-created component is at runtime isn't something Live Coding can safely hot-patch for an already-placed level actor (confirmed directly — after changing `CreateDefaultSubobject<UInstancedStaticMeshComponent>` to `CreateDefaultSubobject<UHierarchicalInstancedStaticMeshComponent>` for what was originally a single `CellsMesh` field, the existing placed actor's component pointer silently reinstanced to `null` — no crash, just a dangling reference — because the old object couldn't be safely upcast to the new class; a genuine editor restart was needed to get a clean instance). Runtime `NewObject()`-created components (`SelectionMeshComponent`, and the age-material pool that used to exist) never faced this hazard — they aren't default subobjects, so creating/destroying them at runtime is an ordinary, safe operation.

HISM builds an internal LOD cluster tree over the instances (async rebuild after `AddInstances`/`ClearInstances`, tracked via `bIsOutOfDate`/`BuildTreeIfOutdated`) enabling per-cluster occlusion and distance culling — the payoff scales with cell count (relevant at the 700k+ live-cell sizes seen once the sim runs for a while), but each full-grid `ClearInstances()` + re-`AddInstances()` per generation also means HISM rebuilds that cluster tree from scratch every step, which is extra work the plain (non-hierarchical) `UInstancedStaticMeshComponent` doesn't do — that comparison has now been run, and **the flat `Instanced` component wins outright — which is why it, not HISM, is `CellMeshComponentType`'s default**. Both settings were measured on the identical grid (same `Seed`, so the structure is bit-for-bit the same), rule `0-6/1,3/2/VN`, cull volume and distance culling both off:

| cells | FPS: ISM → HISM | `AddInstances`: ISM → HISM |
|---|---|---|
| 100,881 | 76.0 → 84.0 | 4.6 → 10.2 ms |
| 508,281 | 10.1 → 8.9 | 25.3 → 37.9 ms |
| 990,055 | 4.8 → 4.5 | 49.5 → 76.0 ms |

Insertion costs HISM 1.5–2.3× more at every size, far outside noise, and there is no FPS gain to pay for it (the 10–25% spread is within what camera placement alone could explain, so HISM cannot be said to *hurt* drawing — only to buy nothing). The cluster tree never gets a chance to help: the render does `ClearInstances()`+`AddInstances()` *every generation*, so the tree is rebuilt from scratch asynchronously and is usually still out of date when the next generation wipes it, meaning cluster culling never engages — and the structures these rules produce are dense and convex, with little inter-cluster occlusion to exploit anyway. HISM would become worth revisiting only if a mode appears where the grid stays unchanged for a long time (paused inspection, examining a bake), giving the tree time to finish. `FRenderTimings` now logs `GAverageFPS` alongside the phase breakdown precisely so this trade — insertion cost against draw cost — can be judged from one line instead of by feel.

**`CellCullStartDistance`/`CellCullEndDistance` — per-instance distance culling, deliberately not HLOD**: HLOD (Hierarchical LOD) bakes simplified proxy meshes for groups of *static* actors via an explicit "Build HLODs" step in the editor, then swaps a whole cluster for its proxy past a distance — it has no way to react to a grid that's fully cleared and rebuilt every simulation step (there's no static state to bake), so it never engages here no matter how it's configured on the level; that's the "HLOD doesn't seem to work" outcome the property was added to replace. `CellCullStartDistance`/`CellCullEndDistance` (`AAutomataOrchestrator`, `Automata|Cells`, both default `0.0f` = disabled — same as engine default) instead drive `UInstancedStaticMeshComponent::SetCullDistances()` directly — genuine per-instance runtime distance culling computed every frame from the current view, needing no baking and updating automatically as instances get replaced generation-to-generation. Applying the distances is factored into its own private helper, `ApplyCellCullDistances()`, called from `RenderCurrentGrid()`/`RenderGridImmediate()` on every render and from `SetCellCullingEnabled()` directly (rounded to `int32` via `FMath::RoundToInt`, clamped to non-negative) — applied to `CellsMeshFlat`/`CellsMeshHierarchical` *and* `SelectionMeshComponent`, regardless of which one `CellMeshComponentType` currently selects, so switching component types later doesn't leave a stale (or default/disabled) set of cull distances anywhere; `SetCullDistances()` itself is a no-op when values haven't changed, so the repeated call costs nothing once settled. `bEnableCellCulling` (default `true`) is a master on/off switch — while `false`, `ApplyCellCullDistances()` applies `(0, 0)` to all components instead of the configured distances, without touching `CellCullStartDistance`/`CellCullEndDistance` themselves, so toggling it for an A/B comparison never loses previously-tuned numbers; switchable live via the **B** hotkey (`AGamePlayerController::OnToggleCellCulling()` → `SetCellCullingEnabled()`/`IsCellCullingEnabled()`, no `CallInEditor` — same reasoning as `CycleChunkedRenderOrder()`/`SetWaitForChunkedRenderToFinish()` above, the checkbox is already directly editable) or the Details panel. **`SetCellCullingEnabled()` calls `ApplyCellCullDistances()` itself, immediately, rather than relying on the next render call** — an earlier version only applied cull distances as a side effect of rendering a newly-computed generation, so toggling `bEnableCellCulling` via the **B** hotkey while no generation was actively rendering (e.g. continuous Play paused, or between `Next()` calls) silently did nothing until the *next* render — `SetCullDistances()` itself updates the live `SceneProxy` on the Render Thread immediately and needs no `AddInstances()`/rebuild to take effect, so there was no actual reason to wait for a render; calling `ApplyCellCullDistances()` straight from the setter fixed the "have to regenerate a frame for the toggle to visibly take effect" symptom without needing to force any regeneration at all. **Two debugging aids added while chasing an initial "still doesn't cull no matter how far I fly" report**: (1) `ApplyCellCullDistances()` logs once whenever the applied `(Start, End)` actually changes (`"отсечение клеток по расстоянию включено/выключено"`), by comparing against `CellsMeshHierarchical->GetCullDistances()` before calling `SetCullDistances()` again; (2) while `CullEnd > 0`, a throttled (max once/second, via a local `static double LastCullDebugLogSeconds`) diagnostic line logs the camera location, the live-cell bounds center/radius (`ComputeAliveCellsBounds()`), the distance between them, the configured `(Start, End)`, and the *actual* `(Start, End)` read back from `CellsMeshHierarchical` right after `SetCullDistances()` — enough to directly compare "is the camera actually past the configured distance" against "did the value really stick on the component" without guessing. This diagnostic surfaced the actual root cause on this project: `r.ViewDistanceScale` (a Scalability-driven console variable, found via `r.ViewDistanceScale` with no argument to print its current value) was `10` instead of the expected default `1` — the engine multiplies `EndCullDistance` by this scale before comparing it to camera distance (`InstancedStaticMesh.cpp`'s `MaxDrawDistanceScale = GetCachedScalabilityCVars().ViewDistanceScale`), so a configured `20000` was actually enforcing a `200000`-unit (2 km) cutoff — nothing was broken, the fly-test distance just never reached the real threshold. Separately, disabling Nanite on the cell mesh (`NaniteSettings.bEnabled`) was tried and discarded — Nanite's renderer has no references to `EndCullDistance`/`InstanceCullDistance` at all (grepped `Renderer/Private/Nanite/`, zero hits) so it does bypass this legacy per-instance cull path, but turning Nanite off made rendering *worse* and introduced other bugs at this project's instance counts, so Nanite stayed enabled — the real fix was purely the `r.ViewDistanceScale` mismatch.

**`ARenderCullVolume` (`Automata/Rendering/RenderCullVolume.*`) — a placeable box that culls cells *before* they cost anything**: unlike `CellCullStartDistance`/`CellCullEndDistance`, which hide already-built instances after the fact and don't reduce the cost of building them, this cuts cells outside the box at the source — `BuildCellRenderData()` calls `FCellGrid::GetAliveCellsInBounds()` instead of `GetAliveCells()`, so the transforms are never built and `AddInstances()` never sees them (and `FDenseCellGrid` overrides that method chunk-aware, rejecting whole chunks at a time). The orchestrator finds the actor itself via `UGameplayStatics::GetActorOfClass()` (the same idiom as everywhere else in the project) — no manual Details-panel reference. It is moved and resized with the ordinary actor gizmo: there are no `Size`/`Location` properties, since Location *is* the actor transform and Size is the `BoundsBox` `UBoxComponent`'s `BoxExtent`. Deliberately **axis-aligned only** — rotating the actor does not tilt the culling box, `GetWorldBounds()` always builds an AABB from location plus scaled extent, the same simplicity choice as the marquee selection's "no depth bound". Because a programmatic `SetActorLocation()` doesn't trigger it, `PostEditMove(bFinished)`/`PostEditChangeProperty()` (editor-only) explicitly ask the orchestrator to re-render so dragging or retyping the bounds updates the view immediately; `MoveCullVolumeToSelection()` (**K**) calls `RefreshRenderCullVolume()` itself for the same reason. Master switch `bEnableRenderCullVolume` (default `true`, hotkey **C**); `SelectCellsInCullVolume()` (**L**) selects everything inside it.

**A hidden box does not cull** — `SetVolumeVisible()`/`IsVolumeVisible()` (hotkey **Ctrl+C**, `AGamePlayerController::OnToggleRenderCullVolumeVisibility()`) toggle the box's own geometry, and culling follows. Visibility and culling started out fully independent, which read badly on screen: an invisible crate that keeps cutting makes cells stop in mid-air for no visible reason. The invariant is enforced in exactly one place — `AAutomataOrchestrator::GetActiveCullVolume()`, which answers "is culling active right now" (actor present ∧ `bEnableRenderCullVolume` ∧ visible) and replaced the hand-written `bEnableRenderCullVolume ? EnsureRenderCullVolume() : nullptr` at all five of its call sites. **No second state is introduced**: `bEnableRenderCullVolume` is never overwritten, so showing the box again restores whatever **C** last set rather than force-enabling. Paths that want the box as a *spatial region* rather than as render culling (`SelectCellsInCullVolume()` on **L**, `MoveCullVolumeToSelection()` on **K**) deliberately keep calling `EnsureRenderCullVolume()` directly — the region exists whether or not it is currently cutting. Because visibility now changes what gets drawn, `SetVolumeVisible()` calls `NotifyOrchestratorToRefresh()` itself, same as `EndGizmoDrag()` — otherwise culled cells would return only at the next generation, and never while paused.

Ctrl is checked inside `OnToggleRenderCullVolume()` rather than mapped, since Enhanced Input can't require a modifier in a key mapping — the same idiom as Ctrl+S/Ctrl+O. Gizmo-handle visibility is the **conjunction** of selection mode and volume visibility: both `SetSelectionModeActive()` (Tab) and the Ctrl+C handler compose the two, so Tab can't pull handles out of a hidden box, and hiding mid-drag ends the drag first (same guard as leaving selection mode).

**`VolumeMaterial` — painting the box.** `UBoxComponent` draws wireframe edges only and takes no material at all, so a *filled* cube is a second component: `VolumeMesh` (`/Engine/BasicShapes/Cube`, a default subobject next to `BoundsBox`, collision and shadows off like every other purely visual component here), rescaled from `GetUnscaledBoxExtent() / 50` since the engine cube is 100 units. It stays hidden entirely while `VolumeMaterial` is unset — falling back to the default material would be worse than nothing, since an opaque cube would hide exactly the cells the culling exists to expose (the same conclusion `GhostShapeMaterial`/`BakedMeshMaterial` reached when their own fallback was dropped; a translucent material is what is expected). `ApplyVolumeVisuals()` is the single place that reconciles material, scale and visibility, called from `BeginPlay()` (the constructor is too early — `VolumeMaterial` isn't deserialized yet), from `PostEditChangeProperty()` (so typing a `BoxExtent` or assigning the material repaints immediately in-editor), and from `UpdateGizmoDrag()`'s scale branch every drag frame so the filled cube tracks the wireframe rather than lagging at its pre-drag size — which is why it compares the material before `SetMaterial()`, that call dirties the component's render state even when nothing changed.

**`RenderPresets` (`Automata/Rendering/RenderPresets.h/.cpp`, plain namespace + `FRenderPreset` `USTRUCT(BlueprintType)`) — whole quality profiles on F1–F4**, following `RulePresets` exactly (code-constant table, `BlueprintReadOnly` fields, `namespace RenderPresets { const TArray<FRenderPreset>& GetAll(); }`, plus `GetRenderPresets()`/`ApplyRenderPreset(int32)` on the orchestrator). Six profiles, of which four sit on F1–F4 and two belong to the F10 shot (see "The photograph" below — they have no key of their own, since outside a capture they are only slower): **Quality** (nothing disabled — also the way back), **Unlit** (differs from Quality in *exactly* the viewmode, so the two are comparable), **Balanced** (no Lumen, no shadows — neither from lights nor from the cells — no post-processing, no background, but full resolution and every cell still drawn), **Performance** (all of that plus 70% screen percentage and Ghost Shape, which without a cull volume replaces the per-cell render entirely — that, not the cvars, is where the time actually goes).

Two structural decisions carry the design. **Every preset sets every field and every cvar**: switching profiles can then never leave a tail from the previous one, so nothing has to be restored and no profile's result depends on which profile preceded it. That is why `FRenderCvars` (anonymous namespace in the .cpp) is a struct of named fields whose defaults *are* the Quality profile — the other three are written as differences from it, and the "same cvar names everywhere" invariant holds constructively instead of by eyeballing four lists. And **the whole preset is applied inside the orchestrator, including `VIEWMODE`** (routed through `RunRenderConsoleCommand()` → `GamePC->ConsoleCommand()`, since viewmode commands address a specific local player's viewport; `GEngine->Exec()` is the pre-`BeginPlay` fallback) — the controller's handler holds no console command of its own, so adding a fifth profile is a one-place change. `ApplyRenderPreset()` writes the cell fields directly rather than through their setters (each setter re-renders, and going through four of them would cost three or four full `RenderGridImmediate()` calls per keypress), then applies each thing once; `SetGhostShapeEnabled()` is the exception, called last through its setter because it is the one that changes *what* is drawn and its setter already does exactly the needed refresh. Deliberately **not** in any preset: `r.Nanite` (turning Nanite off on the cell mesh was already measured on this project and made rendering *worse* — see `CellCullStartDistance` above) and `bEnableChunkedRender` (Z stays independent; all four profiles would set it off anyway, so a field that never varies would be noise).

`ActiveRenderPresetIndex`/`bRenderPresetModified` (both `UPROPERTY(Transient)`, the usual Live-Coding-reinstancing reason) feed `FHudStats::RenderPresetName`/`RenderPresetIndex`/`bRenderPresetModified`. The modified flag is raised inside the setters the preset owns (`SetCellCullingEnabled()`, `SetGhostShapeEnabled()`, `SetCellShadowsEnabled()`, `SetBackgroundVisible()`) and cleared at the *end* of `ApplyRenderPreset()` — otherwise the HUD would keep naming a profile the screen no longer matches after one press of B or H.

**`bCellsCastShadows` / `SetCellShadowsEnabled()`** is its own switch rather than part of "shadow quality" in general: the shadow pass runs the same millions of instances again per cascade, so on this project it costs incomparably more than on an ordinary scene. `ApplyCellShadowSettings()` mirrors `ApplyCellCullDistances()` exactly — applied to *both* cell components plus `SelectionMeshComponent` (so a later `CellMeshComponentType` switch can't leave the other one stale), called from both render paths and immediately from the setter, since `SetCastShadow()` updates the scene proxy without needing a re-`AddInstances()`.

**`bShowBackground` / `SetBackgroundVisible()` — hide the sky, keep the light.** The naive version (hide `ASkyAtmosphere`) also kills the lighting, and that is a direct consequence of the level's setup rather than a bug: this level's `ASkyLight` has `bRealTimeCapture == true`, i.e. it rebuilds its ambient cubemap *from the sky* every frame. Remove the sky and there is nothing to rebuild from, so the ambient collapses along with the background — measured in PIE from a fixed camera, the blue and green cells disappeared entirely and the whole image fell back to the one warm directional light.

The fix is `USkyAtmosphereComponent::SetRenderInMainPass(false)`: it drops the sky from the basepass/transparency only, leaving the component in the scene for everything else — including the real-time sky capture. The camera stops seeing it; the capture keeps seeing it. Lights (`ASkyLight`/`ADirectionalLight`) are never touched at all. `AVolumetricCloud` gets the same treatment (via `FindComponentByClass`, since unlike `ASkyAtmosphere::GetComponent()` it exposes no public getter), while `AExponentialHeightFog` has no such flag and is simply hidden — verified in the same measurement to cost no light, the fog not being what feeds the capture.

**Rejected, and worth not retrying: freezing the capture** (`SetRealTimeCaptureEnabled(false)`) before hiding the sky. It reads like the obvious fix and it does not work, including with the hide deferred a frame via `SetTimerForNextTick`: that call does not rebuild the cubemap in place, it queues a recapture (`SetCaptureIsDirty()`) which still runs against the by-then-empty sky and freezes a *black* cubemap — i.e. exactly the lost light it was supposed to prevent. This was implemented, measured against `bRenderInMainPass` from an identical camera position, and removed.

**Ghost Shape — a chunk-granular silhouette that coexists with the live simulation**: marked experimental alongside Baking. Instead of one cube of geometry per cell, it builds one per occupied **chunk** (via `CellMeshBuilder::BuildFromCells()` over an `FChunkGridView`, reusing the exact face-culling mesh builder the bake uses), which is orders of magnitude cheaper. Unlike `BakeCellsToMesh()` it is **not** a one-way snapshot: `Grid` is never freed, the simulation keeps running, and the silhouette is rebuilt every `GhostShapeRefreshInterval` generations (default `10`, its own counter — `CellMeshBuilder::BuildFromCells()` is synchronous and single-threaded, so rebuilding every generation would be felt on the game thread). Two modes depending on whether a cull volume is active: **(1)** cull box active — the silhouette is built only from chunks *outside* it while the detailed per-cell render keeps drawing everything inside, so the ghost is pure addition, showing where the structure continues beyond the box; **(2)** no cull box (or disabled) — "outside" means "everywhere", the silhouette covers the whole grid and **replaces** the detailed render entirely (`ShouldGhostShapeReplaceDetailedRender()`). Mode 2 is where the feature actually saves time: at high live-cell counts the detailed path (collect + `AddInstances` per cell) is the expensive part, and often all that's wanted is the overall shape of how the structure is evolving. Off by default; **H** toggles it; `GhostShapeMaterial` has no fallback — unset means a warning plus the engine default material, exactly like `BakedMeshMaterial`.

**The photograph — `TakePhotoShot()` on F10, and the two profiles without an F-key**: F6/F7 rasterise the grid directly, bypassing the GPU, and give a flat image with no light or shadow — right for a mask, useless as a portrait. F10 is the other half: an ordinary engine render with all the lighting, at a resolution the window cannot hold. It stops the simulation (the frame has to hold still), applies a capture profile, redraws the grid whole, and issues `HighResShot`.

**`HighResShot` does not render in tiles.** It allocates a *single* render target of the requested size (`UnrealClient.cpp`: `DummyViewport->SizeX = GScreenshotResolutionX`), checked only against the RHI 2D texture limit. Video memory therefore grows with the **area** of the frame — 4K is ~8 Mpx, 8K ~33 — while the grid size barely matters. This contradicts the July high-quality-render research, which states the opposite and reasons from it about tile seams; that claim was taken on trust and cost a crash. The first Photo profile set `ScreenPercentage 200` to fight seams that cannot exist, turning 7680×4320 into 15360×8640 — 133 Mpx of GBuffer — and killed the editor on a scene of **82 thousand** live cells. `ValidatePhotoShotResolution()` now refuses past the texture limit and warns past 40 Mpx, and it runs **before any side effect**, so a refusal leaves simulation, cuts and profile untouched. The default is 4K, not 8K; raise it once 4K is proven on the card at hand.

**`PhotoShotDelayFrames` is not a pause either.** `r.HighResScreenshotDelay` makes the engine render the frame *at shot resolution* that many times over and keep the last, so the number is a direct multiplier on capture cost. It defaulted to 30 here — 7.5× the engine's own default of 4 — for no gain whatsoever. Now 4, which is also the threshold below which `TemporalAA` is force-disabled (`ShowFlags.cpp`). The loop is synchronous (`FlushRenderingCommands()` per iteration), so the window is frozen throughout; there is no progress to show and none is attempted.

**Two capture profiles, neither with an F-key** — `RenderPresets::GetPhotoPresetIndex(bLeanMemory)` looks them up **by name**, since positional arithmetic would break on any insertion. `Photo` differs from `Quality` in no cvar at all (with no tiles, TSR is safe and the shutter delay gives it still frames to converge on); it exists as its own entry because it also clears Ghost Shape and culling, and because the shot owns it and can tune it without disturbing the working profile. `Photo Lean` drops everything sized by the frame — Lumen, VSM, TSR history, bloom/DOF/SSAO/fog — but **keeps shadow quality high on purpose**: without VSM, shadows come from a fixed-size atlas that does not scale with the frame, and shadows are half the point of a portrait.

**What the shot does and does not touch.** It leaves alone everything set up for *looking* — cull volume (C), view slice (J), age filter (digits), hidden sky (U). The first version cleared the slice and the filter "so everything fits in frame", quietly discarding the setting the frame had been composed around. The profile owns quality plus the two accelerators that spoil a photograph; what is *in* the frame is the photographer's business. The background has to be saved and restored by hand around `ApplyRenderPreset()`, because a profile is required to set every field it owns and the table has no notion of an exception. Conversely the *tools* are hidden for the shot and restored after, unconditionally: the cull box, its gizmo handles and the selection highlight (`HideEditingVisualsForPhoto()`/`RestoreEditingVisualsAfterPhoto()`, the latter also on a failed shot — the screen must come back as it was found). That this is possible at all is the payoff from splitting the box's visibility from its culling: cells stay cut exactly as configured while the crate is out of frame.

**Completion is detected by frame counter, and that detail is load-bearing.** `HighResShot` returns *immediately* — it only raises a flag; the frame is drawn later, inside the viewport draw, blocking the game thread. There is no usable delegate: `UGameViewportClient::OnScreenshotCaptured()` looks right but subscribing to it **cancels writing the file** (`GameViewportClient.cpp`: *"If delegate subscribed, fire it instead of writing out a file to disk"*). So the hook is `Tick()` — but the tick of the *same* frame runs **before** the draw (order within a frame: input → actor tick → draw), so reporting from there put the gizmo handles back a moment before the shutter and they photographed faithfully. Waiting for `GFrameCounter` to move fixes both that and the duration, which was being measured a frame short. The completion line looks for the file **on disk** rather than assuming it appeared, since a shot that does not fit in memory fails silently.

**A photograph can only show what can be displayed** — the shot goes through the same `RenderGridImmediate()` and the same instances. A "fast-forward N generations before the shot" parameter was built and then removed for exactly this reason: a state too big for the screen is too big for the frame. Texture memory is logged at every shot (`RHIGetTextureMemoryStats()`), so `Photo` against `Photo Lean` is a comparison of numbers rather than impressions. The genuinely seam-free route to larger frames is Movie Render Queue, which tiles *with overlap* — blocked by MRQ rendering in the editor world while the structure lives in PIE.

**Cell color is per-instance data, not a material — one `CellMaterial`, a keyframe ramp, and `PerInstanceCustomData`**: cells used to be coloured by an `AgeMaterials` array (`TArray<UMaterialInterface*>`, ordered oldest→youngest, `MaterialIndex = N-1-min(Age, N-1)`). Because ISM/HISM applies a material per **component**, N materials meant N runtime components, a bucketing pass per generation, N `AddInstances` calls and N HISM cluster-tree rebuilds. That whole structure is gone. Now:

- **`CellMaterial`** (`UMaterialInterface*`) — the single base material for every cell of every age, and the only mandatory one (`GenerateRandom()`/`Next()`/`StepAsync()` refuse with a warning if it's unset, exactly like the pre-existing `!CellMesh` check; the render paths repeat the guard defensively, since it could be cleared in the Details panel between a background step's dispatch and its completion). It **must** contain a `PerInstanceCustomData3Vector` node (`DataIndex = 0`) feeding Base Color/Emissive. This is the one hard failure mode worth knowing: the engine derives `bHasPerInstanceCustomData` from the material itself (`MakeInstanceDataFlags(...)`, `InstancedStaticMesh.cpp:309`) and binds `GDummyFloatBuffer` when it's false (`:457`) — a material without that node renders every cell one flat colour with **nothing in the log**. Giving the node a loud `ConstDefaultValue` (magenta) makes "custom data never arrived" distinguishable from "the colour really is black".
- **`AgeColors`** (`TArray<FLinearColor>`) — keyframes **smoothly interpolated**, not bucketed. Ordered `[0]` = age 0 (just born) → `[Last]` = oldest: the **reverse** of `AgeMaterials`. Empty is deliberately *not* an error (unlike a missing `CellMaterial`) — it yields white, i.e. "whatever the material looks like on its own", which is the normal state right after assigning a material and before authoring a ramp; refusing to render there would recreate exactly the "why is nothing showing" confusion. One element = flat colour.
- **`AgeColorMaxAge`** (default 32) — the age at which the last keyframe is reached (`t = clamp(Age / AgeColorMaxAge, 0, 1)`). Deliberately decoupled from `AgeColors.Num()`: keyframe count is the ramp's *resolution*, this is its *duration*. Under `AgeMaterials` these were the same number, so "a smooth gradient, but over 4 generations" was unexpressible.
- **`DecayColors`** — a separate ramp for Generations decay states (`2 .. States-1`), empty = fall back to `AgeColors`. Previously decaying cells shared the age buckets and were pixel-identical to live ones, which hid the most interesting part of Generations rules. Note the fallback is *approximately*, not bit-identically, the old look: the old formula reused the age bucket index, the new one stretches the decay range across the whole ramp.
- **`SelectionColor`** replaces the former `SelectionMaterial` — the highlight now draws with the same `CellMaterial` and differs only in its custom-data colour (`SelectionScaleMultiplier = 1.1` and the dedicated `SelectionMeshComponent` are unchanged).

Colours are `FColor` (not `FLinearColor`) inside `FCellRenderInstance` for size, and the conversion is **`ToFColor(bSRGB=false)`** — `PerInstanceCustomData` is a raw float the material never sRGB-decodes, so the quantisation must be linear; `bSRGB=true` silently washes the whole ramp out with nothing in the log. HDR brightness belongs on a scalar `Intensity` parameter on a Material Instance, not in the byte. As with `AgeMaterials` before it, the ramp applies identically in continuous Play (`StepAsync()` → `ApplyStepResult()` → `RenderCurrentGrid()`, chunked-render-aware) and in the manual step/spawn path (`Next()`/`GenerateRandom()` → `RenderGridImmediate()`, one-shot) — "this cell is young" shouldn't depend on how it got drawn.

**One renderer, not a pool.** `AgeMeshComponents`/`AgeRenderers`/`RebuildAgeMeshComponents()` are deleted; there is a single `TUniquePtr<FInstancedMeshCellGridRenderer> CellsRenderer` bound to `GetActiveCellsMeshComponent()`. `CellsMeshFlat`/`CellsMeshHierarchical` — the two permanent `CreateDefaultSubobject` components that had been reduced to attach-parents — receive instances again, which is what they existed for. `EnsureCellsRenderer()` replaces all three phases of the old rebuild with one condition (`!CellsRenderer || CellsRenderer->GetComponent() != Target`), covering first call, a `CellMeshComponentType` switch, and a Live-Coding-nulled `TUniquePtr` alike; on a rebind it clears the *previous* component so a type switch doesn't leave two overlapping grids. The old `AgeMeshComponents`-is-a-`UPROPERTY` dance is unnecessary now: the components are default subobjects that always survive reinstancing, and the plain `TUniquePtr` being nulled is exactly what the first half of that condition catches.

Two consequences at the call sites: `ApplyCellCullDistances()` no longer loops a pool (both permanent components plus `SelectionMeshComponent` already cover everything), and the defensive `ClearInstances()` in the render paths flipped from the **active** component to the **inactive** one (`ClearInactiveCellsMeshComponent()`) — the active one is now the render target and `BeginRender()` clears it every frame, so clearing it there would have the render wipe itself, while stale instances can only survive on the component `CellMeshComponentType` no longer selects. `ClearAllCellInstances()`'s orphan sweep needed no logic change and now doubles as the migration cleanup: with the legitimate set down to three components, every leftover runtime-created age component is an orphan it destroys on the first `BeginPlay`.

**`BuildCellRenderData()`** (replacing `BuildAgeBuckets()`) is the shared collection step for both render paths: one pass producing a single `TArray<FCellRenderInstance>` — live cells coloured from a 256-entry age LUT, plus (when `States > 2`) decaying cells from their own LUT. The LUTs are built once per render rather than per cell: at millions of cells a lerp per cell is millions of wasted lerps, while the table is 1 KB. Cull-volume filtering (`GetAliveCellsInBounds()`/`GetDecayingCellsInBounds()`) is unchanged and still happens before anything is built. It also fixes a long-standing undercount: `LastRenderStats.RenderedCellCount` used to be `AliveCells.Num()` written *after* decaying cells had been added to the buckets, so under Generations both it and `EstimatedUploadMB` were low by exactly the decaying-cell count. It now counts the array actually handed to the renderer — which means it can legitimately exceed `TotalCellCount` (`Grid->Num()` counts only live cells).

**`AgeFilterValues` — the view cut down to chosen age layers (digit keys)**: an **empty list** (the default) draws everything, and each entry keeps cells of exactly that age. A bare digit **0–9** selects that one age (the same digit again clears the filter); **Shift+digit** *adds* an age to what is already shown, or removes it if it is already there — remove the last one and the filter switches itself off, since "nothing selected" and "show everything" are one state, not two. Age is how many consecutive generations a cell has survived, so under rules where nothing ever dies (`0-6/1,3/2`) "age N" is precisely the concentric layer born N generations ago — an octahedron face under von Neumann, a cube face under Moore. That makes this layer-by-layer dissection, concentric, complementing the flat view slice.

**A set rather than a single age, because the interesting thing is the *combination* of layers**: where the growth front (age 0) sits relative to the old core is only visible with both on screen at once, and one-layer-at-a-time cannot show it. It started as a single `int32 AgeFilter` with `-1` for "off"; the list replaced it, and `TArray<int32>` edited in the Details panel is the same idiom as `BirthCounts`/`SurvivalCounts`. Order and duplicates carry no meaning — `ApplyAgeFilterChange()` canonicalises the list (sorted, deduplicated, clamped) so that a hand-typed panel entry behaves like a keypress and so that Shift+digit reliably finds an age already in the set. `GetAgeFilter()` survives for callers that want a single layer, but now answers only when exactly one is selected; `GetAgeFilterValues()`/`IsAgeFilterActive()` are the full picture.

**Off is the empty list, not age `0`** (as it was `-1`, not `0`, before). Age 0 is the just-born cells — the first colour of the ramp and the growth front, the single most interesting layer. The first version used zero as "off", which made that layer unreachable altogether and left the digits looking shifted by one against the colours; that was noticed immediately.

**The last digit is the deliberate exception: 9 means "age 9 and older"** (`bAgeFilterIncludesOlder`). There are ten digits and 256 ages, so without it every cell older than nine generations — the tail of the ramp, usually the largest part of the structure — was reachable by no digit at all. It is its own flag rather than a special case for 9 inside the comparison, because `AgeFilterValues` is also edited from the Details panel, where 9 is an age like 42 and has to mean exactly itself; and there is deliberately **no** "is anything older?" condition, since when nothing is, `>= 9` equals `== 9` and the flag changes nothing. **The flag belongs to the digit that raised it and leaves with it**: `ToggleAgeFilterValue()` clears it when Shift+9 removes the nine, so the tail can never stay switched on by itself — which would read as "the key did nothing".

The filter is expanded into a **256-entry mask** (`BuildAgeFilterMask()`) **before** the render loop, so the per-cell cost is one table read with no scan of the selected list across millions of cells. It was an `[AgeFilterMin, AgeFilterMax]` range while the filter was a single age; a range cannot express an arbitrary set of layers, and the mask is no more expensive per cell than the two comparisons it replaced. `SetAgeFilter(NewAgeFilter, bIncludeOlder)` (single age, `-1` clears) and `ToggleAgeFilterValue(Age, bIncludeOlder)` (add/remove) both set age and flag in one call — two calls would mean an intermediate state (right age, stale flag), each re-rendering the grid, i.e. a double render per keypress — and both clear the flag whenever the filter itself goes off, since it is meaningless there.

Decaying cells (Generations) are hidden **entirely** while any age filter is active: their age is undefined — decay is a separate state channel, not an age (`FCellGrid::IsDecaying()`) — and assigning them one would be a lie.

One UE 5.7 trap this ran into, worth knowing before touching any log line here: `ApplyAgeFilterChange()` (the shared tail of both setters) builds its log and on-screen strings with `if`/`else` *before* calling `Printf`, rather than picking a format string with a ternary. The format string is `consteval`-checked (`TCheckedFormatString`) and must be a literal, so `Printf(bFlag ? TEXT("a %d") : TEXT("b %d"), X)` does not compile at all.

`FCellRenderInstance` (`Automata/Rendering/CellRenderInstance.h`) is `{ FVector3f Position; FColor Color; }`, exactly 16 bytes. **`Position` is already world-space**, and that is load-bearing twice over: `AdvanceRenderChunk()` spans frames while `ApplyStepResult()` swaps `Grid` underneath it, so no grid reference may be held between `BeginRender()` and the last chunk — and it let `PendingTransforms` be **deleted outright**. `BeginRender()` used to materialise one `FTransform` per live cell up front and hold them for the whole reveal; `sizeof(FTransform)` is 80 bytes under LWC, i.e. ~560 MB at 7M cells against 112 MB now, with the transform construction moved into `AdvanceRenderChunk()` where it spreads across the reveal instead of spiking on one frame. Secondary win: the `DistanceFromCamera*`/`FromCenterOutward` comparators stop calling the **virtual** `GridToWorld()` twice per comparison.

Per chunk, `AdvanceRenderChunk()` builds that slice's transforms and a flat `TArray<float>` of RGB, calls `AddInstances()`, then one range `SetCustomData(First, First + Count - 1, Data, bMarkRenderStateDirty=false)`. **`MarkRenderStateDirty()` is deliberately never called**: `SetCustomData` already marks the changed instances through `PrimitiveInstanceDataManager` (`CustomDataChanged` → `MarkComponentRenderInstancesDirty()` → `MarkRenderInstancesDirty()`, latched by `bComponentMarkedDirty`), which is the cheap incremental path, whereas `MarkRenderStateDirty()` destroys and recreates the whole scene proxy — once per chunk slice that would be catastrophic. There is no visible zero-colour frame either, since `AddInstances` and `SetCustomData` land in the same game-thread call and the gather is deferred to end-of-frame. Passing `bMarkRenderStateDirty=true` would additionally call `Modify()` (an undo-transaction write, per generation, at millions of instances). `SetNumCustomDataFloats(3)` is called **after** `ClearInstances()`, not before — it sizes and zeroes the buffer from the *current* instance count, so calling it on a still-full component allocates a large array `ClearInstances()` immediately discards; it early-outs when unchanged, so it's free after the first call.

`FFilteredCellGridView` survives but is no longer part of the render path — its only remaining consumer is the DDA ray-pick in `CellSelection::PickCellAlongRay()`. `AdvanceChunkedRender()`/`FinishChunkedRenderImmediately()` now drive one renderer, and `PerBucketBudget = max(1, ChunkedRenderCellsPerFrame / NumBuckets)` is gone: the full `ChunkedRenderCellsPerFrame` goes to it.

**Chunked rendering multiplies total render cost — it does not merely spread a fixed amount of work.** This was measured, not reasoned: `FRenderTimings` collected six per-phase timers that nothing ever printed (`GetLastRenderTimings()` had no callers), so the parameter had only ever been tuned by watching for stutter. With the breakdown logged (`RenderTimings[chunked|oneshot|immediate]`, see `LogRenderTimings()` in `AutomataOrchestrator.cpp`), the same ~622k live cells on the flat `Instanced` component cost **35.97 ms in one `AddInstances` call, 78.63 ms across 7 (budget 100k), and 179.23 ms across 31 (budget 20k)** — a 5× penalty for the finest slicing. Each `AddInstances()` call evidently does work proportional to the instances already present, so N calls of B instances lose badly to one call of N·B. Two consequences worth keeping straight:

- **The apparent superlinearity in render cost is an artifact of chunking, not of instance count.** Cost per cell in the one-shot path is a flat ~0.058 µs and scales linearly; under chunking it climbed 0.169 → 0.440 µs/cell between 168k and 990k purely because a fixed budget means more calls as the grid grows. An earlier reading of that curve blamed HISM's LOD cluster-tree rebuild — wrong twice over, since the run was on `Instanced`, which builds no tree at all.
- **Chunking still does what it claims** (it caps the per-frame spike), but on large grids the trade is bad: one 36 ms hitch beats forty 5 ms frames totalling 200 ms. Hence `ChunkedRenderCellsPerFrame`'s default was raised 20000 → 100000 — not to encourage chunking, but so that pressing **Z** costs 2× instead of 5×. `AddInstances` is ~97% of render time either way; `CustomData` (per-instance colour) is ~1% and `Reorder` is exactly 0 under `Sequential`, so neither is worth optimizing.

Known cost characteristics (not yet profiled in this project at multi-million-cell scale, see the `CandidateBuild`/`ParallelFor`/`WriteBack` breakdown above for comparison): `CellAging::ComputeAges()` adds roughly one more full alive-cell pass per generation (order of a few percent of total step time, fully parallel, no serialized phase); the render side now has a single cell component, so the former per-material overhead (one component each, and for HISM one LOD cluster-tree rebuild each) is gone — what remains is one cluster-tree rebuild on every `ClearInstances()`+`AddInstances()` (see above) — plus 12 bytes/instance of per-instance colour upload and an O(N) `CustomDataChanged` marking loop per chunk slice (timed separately as `FRenderTimings::CustomDataSeconds`). That last one has since been measured and is a non-issue: **per-instance colour is ~1% of render time** (4.77 ms of 435 ms at 990k cells), against `AddInstances`'s ~97%. Unmeasured at multi-million-cell scale — profile before assuming.

**Mouse cell-selection — isolate an interesting sub-pattern (glider/oscillator-hunting) and launch it as a fresh starting state**: a "selection mode" toggled by the **Tab** hotkey (`AGamePlayerController::OnToggleSelectionMode()` → `SetSelectionModeActive()`) that stops the camera and shows the cursor by calling the pre-existing `SetCameraControlEnabled(false)` (previously dead code outside `Pause()`/`Resume()`) — the controller's own `InputComponent` keeps receiving input throughout, since `DisableInput()`/`EnableInput()` only gate the *pawn's* input stack, not the controller's. While active, holding **left mouse button** and dragging draws a marquee rectangle (`OnSelectDragStarted()`/`OnSelectDragFinished()`, `Started`/`Completed` on a `SelectDragAction`) — a small native `AHUD` subclass, `AGameHud` (`Core/Hud/GameHud.*`, wired via `AAGameMode::HUDClass` in its constructor), overrides `DrawHUD()` to paint the live drag rectangle each frame by polling `AGamePlayerController::IsDraggingSelection()`/`GetSelectionDragStart()` plus a fresh `GetMousePosition()` call — no UMG widget needed, since `FUiController`'s widget system is unused for auto-show anyway (see below). On mouse-up, the controller computes the final screen rect, grabs a view-projection matrix **once** (not per cell) via `ULocalPlayer::GetProjectionData()` → `FSceneViewProjectionData::ComputeViewProjectionMatrix()` (the same API `UGameplayStatics::ProjectWorldToScreen` uses internally, but without its per-call overhead), and hands both off to `AAutomataOrchestrator::SelectCellsInScreenRect()` along with an `ESelectionCombineMode` (`Automata/Selection/SelectionCombineMode.h`, its own header per the `ENeighborhood`/`EChunkedRenderOrder` convention): the standard marquee-modifier pattern — plain drag **replaces** the selection, **Shift**+drag **adds** the rect's cells to it (set union, deduplicated via a `TSet` of the existing selection so it stays O(1) per cell at million-cell selection sizes), **Ctrl**+drag **subtracts** them (set difference via `TArray::RemoveAll` against a `TSet` of the rect hits). The modifier is sampled at drag *start* (`OnSelectDragStarted()`, stored in `PendingSelectionCombineMode`), not at release — like most editors, so the mode doesn't flip if the user lets go of the modifier slightly before the mouse button; Ctrl wins if both are held, and both left and right Shift/Ctrl work. **A click (mouse moved ≤ `ClickDragThresholdPixels` = 4px between press and release) picks a single cell instead of a rectangle**: the cursor is deprojected to a world ray (`DeprojectMousePositionToWorld`) and `CellSelection::PickCellAlongRay()` walks the cell lattice with Amanatides-Woo voxel DDA (exact boundary stepping — no cell on the ray is skipped), returning the *first* alive cell, i.e. exactly the cell whose face is visible under the cursor — engine line traces can't do this since all cell components have collision disabled; traversal is capped at the far side of the alive-cells bounding sphere (`ComputeAliveCellsBounds()`). The same combine modes apply (plain click replaces — clicking empty space clears the selection; Shift+click adds the cell, Ctrl+click removes it), sharing the combine logic with the marquee via the private `CombineWithSelection()` helper on the orchestrator.

Picking itself lives in `Automata/Selection/CellSelection.h/.cpp` — a plain namespace function (`CellSelection::SelectCellsInScreenRect()`), the same non-`UObject` idiom as `CellAging`: for every alive cell, `ViewProjectionMatrix.TransformFVector4(FVector4(WorldPos, 1))` projects it to clip space; cells behind the camera (`W <= KINDA_SMALL_NUMBER`) are dropped, the rest are perspective-divided into NDC and mapped to pixel coordinates, then tested against the drag rectangle. **Deliberately no depth/distance limiting** — the marquee selects every alive cell whose screen-space projection falls inside the rectangle regardless of how near or far it is, i.e. it behaves like an infinite frustum along the camera's view direction rather than a bounded 3D box (a conscious simplicity choice, not an oversight — see the plan this was built from, `snazzy-twirling-beacon.md`, for the considered-and-rejected depth-bounded alternative). Parallelized via `ParallelFor` into a same-size `TArray<bool>` followed by a sequential collect pass — the same two-phase "parallel flag, sequential gather" idiom as `CellAging::ComputeAges()` and the CPU compute strategy's candidate-set construction — since this runs as a one-shot action against potentially millions of alive cells on every mouse-release.

`AAutomataOrchestrator::SelectedCells` (`TArray<FIntVector>`, plain member, not a `UPROPERTY`) holds the current selection; `SelectCellsInScreenRect()` populates it and immediately calls `RenderSelectionOverlay()` so the highlight appears without waiting for the next simulation step. Rendering reuses `FInstancedMeshCellGridRenderer` (see above) — one more component, `SelectionMeshComponent` (`UPROPERTY(Transient)`, **always** a plain `UInstancedStaticMeshComponent` regardless of `CellMeshComponentType`, since a selection is always a small subset and gets nothing from HISM's cluster tree) plus its `TUniquePtr<FInstancedMeshCellGridRenderer> SelectionRenderer` (not a `UPROPERTY`, same Live-Coding-reinstancing rationale as `CellsRenderer` — `EnsureSelectionMeshComponent()` re-derives it from a surviving `SelectionMeshComponent` if the two ever disagree), painted with the same `CellMaterial` as ordinary cells and the designer-assigned `SelectionColor` in its per-instance custom data. `RenderSelectionOverlay()` is called as an extra pass at the end of both `RenderGridImmediate()` and `RenderCurrentGrid()` (filtering `SelectedCells` down to currently-alive cells defensively, and always rendering in one shot — never chunked, since selections are always small) and clears the component whenever there's nothing to show. `ApplyCellCullDistances()` applies the same cull distances to `SelectionMeshComponent` as every other cell-rendering component.

`SelectedCells` is reset to empty at the top of `GenerateRandom()`, in `Next()`'s completion, and in `ApplyStepResult()` (right after the `Grid` swap) — any new generation invalidates a prior selection's coordinates, matching the intended workflow of "pause, fly around, select, extract" rather than selecting mid-Play. `AAutomataOrchestrator::StartFromSelection()` (`CallInEditor`, also bound to the **Enter** hotkey via `AGamePlayerController::OnExtractSelection()`) is the actual "launch as new state": guards on `bStepInProgress` (it swaps `Grid`, which a background `Next()`/`StepAsync()` may be reading at that moment — same refuse-with-warning as every other `Grid`-swapping path), an empty selection, or a missing `CellMaterial` the same way `GenerateRandom()`/`Next()` do, builds a fresh grid via the existing `CreateGrid()` helper, copies over only the selected (and still-alive) cells with `SetAge(..., 0)` (a fresh start, exactly like a newly-born cell), swaps it into `Grid`, clears `SelectedCells`, calls `GamePC->SetSelectionModeActive(false)` to hand camera control back, and finishes with `RenderGridImmediate()` — mirroring `GenerateRandom()`'s structure throughout. **Coordinates are deliberately left as-is, not translated to the origin** — the selected pattern stays exactly where it was picked, since the camera is already looking right at it and the automaton's rules are translation-invariant anyway, so there's nothing to gain from re-centering.

`AAutomataOrchestrator::DeleteSelectedCells()` (`CallInEditor`, category `Automata|Selection`, also bound to the **Delete** hotkey via `AGamePlayerController::OnDeleteSelectedCells()`) is the destructive counterpart to `StartFromSelection()`: instead of extracting the selection into a fresh grid, it kills the selected cells **in the current grid** (`Grid->SetAlive(Cell, false)`, counting only actually-alive ones for the log) — a manual state edit for cutting a piece out of a pattern and watching how the remainder evolves. The simulation is deliberately **not** reset: `Grid` stays the same object (no swap), ages of surviving cells are untouched, and P/F continue from the edited state. Guards mirror the other selection paths (`bStepInProgress` — a background step is *reading* `*Grid`, so mutating it mid-flight would race; no `Grid`; empty selection; missing `CellMaterial`), then `SelectedCells.Reset()` + `RenderGridImmediate()` so the holes appear instantly.

**`InitialStateCells` / `ResetToInitialState()` — the "initial pattern": a persistent return point for R, and what `Automata/Persistence/` saves (see below)**: three equally-weighted sources overwrite `InitialStateCells` wholesale (plain member like `SelectedCells`, but with the opposite lifecycle — it survives simulation steps *and* new mouse selections) — `StartFromSelection()` (Enter, the extracted still-alive cells), `LoadStateFromFile()` (Ctrl+O, the file's own `InitialCells` section), and `GenerateRandom()` itself (the cells that actually landed in the grid after spawning, via `Grid->GetAliveCells()` — not the raw `Amount`, since reject-sampled spawns can collide onto the same cell). `ResetToInitialState()` (`CallInEditor`, what the **R** hotkey calls via `OnResetSimulation()`) replays whichever is current: rebuilds the grid from `InitialStateCells` with all ages back at 0, then calls `GamePC->FrameAllCells()` (see **Home** above) to re-frame the camera on the result — so after watching an extracted glider, a loaded save, or just a random spawn evolve (or explode), R snaps back to its exact starting shape and re-centers the view for another run. Because `GenerateRandom()` now also populates `InitialStateCells`, and `BeginPlay` always calls `GenerateRandom()` once, `InitialStateCells` is non-empty from the moment PIE starts — the `InitialStateCells.Num() == 0` fallback to `GenerateRandom()` inside `ResetToInitialState()` is a defensive path this project's normal usage doesn't actually reach, kept rather than removed.

**Baking — freeze the current state as one hollow mesh and free the cells (experimental, marked by the user as needing further iteration before it's genuinely useful)**: `AAutomataOrchestrator::BakeCellsToMesh()` (**M** hotkey / `CallInEditor`, category `Automata|Baking`) converts the current state into a single `UProceduralMeshComponent` section and *unloads* everything else: all instanced-mesh components are cleared **and `Grid` itself is freed** (`Grid.Reset()`), so the multi-million-cell chunk/instance memory is released and large areas can be inspected cheaply — a one-way snapshot "sculpture", not a render mode (the simulation cannot continue from it; Play/fast-step are force-stopped first, and `bChunkedRenderInProgress` is cleared so a mid-flight chunked reveal can't trickle instances back in after the wipe). If `SelectedCells` is non-empty, only the selection is baked (filtered to still-alive, like `StartFromSelection()`), else all alive cells. Geometry lives in `Automata/Meshing/CellMeshBuilder.h/.cpp` (plain namespace like `CellAging`/`CellSelection`): classic face culling — for each cell, each of the 6 cube faces is emitted only if the neighbor *in the baked set* (deliberately not `IsAlive()`, so baking a selection doesn't punch holes against unselected-but-alive neighbors) is absent; 4 verts per face (no sharing — crisp cube edges), winding/UV conventions match `KismetProceduralMeshLibrary::GenerateBoxMesh()` (see the `FFaceDef` comment in the .cpp), exact-count pre-pass for `Reserve`. `BakedMeshMaterial` (Details panel) paints it — no fallback: unset means a warning plus the engine default material, since a `CellMaterial` driven by per-instance custom data would render a procedural mesh black; `BakedMeshComponent` is `UPROPERTY(Transient)`, lazily created (`EnsureBakedMeshComponent()`, mirrors `EnsureSelectionMeshComponent()`). `InitialStateCells` deliberately survives the bake, and `ClearBakedMesh()` is called from `GenerateRandom()`/`ResetToInitialState()`/`StartFromSelection()` — so **R** after inspecting a bake cleanly starts a new run (replaying the extracted pattern if one exists) with the snapshot removed. Requires the `ProceduralMeshComponent` module (`Build.cs`, `PrivateDependencyModuleNames`).

- **`Automata/Generation/`** — geometric generators of the *initial* state: lattices, solids, noise, symmetric seeds. Built for one specific effect the random-ball spawn cannot produce in principle — a large **metastable** structure that stands still under the current rule until one cell is knocked out of it, at which point a chain reaction spreads from that point. (The "knock a cell out" half needed no new code: Tab → click picks a single cell via `CellSelection::PickCellAlongRay()`, Delete kills it in place without resetting, R restores the structure for the next attempt.)

**Generators are deliberately *pure geometry*** — they never read `BirthCounts`/`SurvivalCounts` and never run trial steps. Whether a given structure is stable under a given rule is a question about the rule, and matching the two stays manual. What makes that matching arithmetic rather than guesswork is `FStateGeneratorParams::bAnalyzeNeighborCounts` (on by default): after generating, `StateGenerators::AnalyzeNeighborCounts()` logs a histogram of live-neighbor counts, **separately for live cells and for the empty cells adjacent to them** — still a property of the point set, not of the rule.

**`AAutomataOrchestrator::AnalyzeLiveStructure()` (Ctrl+Y) is the same measurement taken mid-run**, on `Grid`'s live cells instead of a generator's output — because the original only ever fires from `GenerateState()` (Y), so it describes the *generated* lattice and says nothing about what that lattice evolved into. It answers the question the generator version cannot: where the rule's thresholds fall relative to the distribution that actually exists right now. Under `0-6/1,3/2/ECFA`, for instance, survival ends at 6 of 26 neighbours, so the share of cells already past 7 is the share about to die — which is exactly the overcrowding collapse those rules cycle through. It needs no `bStepInProgress` guard: a background step only *reads* `*Grid`, this only reads, and the sole writer (`ApplyStepResult()`) is the same game thread that runs this.

The sample is a central sub-cube, `LiveAnalysisSampleExtent` (default 24), and that bound is **load-bearing for time, not memory**: cost grows as sample × offsets², since every sampled cell walks its neighbours and every empty neighbour then walks its own. At 24 that is ~117k cells and about a second; at 48 it is nearly a million and over ten. The `Occupied` set is built over *all* live cells either way, so the extent buys nothing on memory. Since an evolved structure is neither periodic nor necessarily centred, the sub-cube describes its **core rather than its growth front**, and the two genuinely differ — so the log always prints how many cells landed in the sample and what share of the total that is, rather than leaving the coverage implied. Measured (and locked down by `Generation.LatticeNeighborUniformity`): `LatticePlanes` with `Thickness=1` on a single axis gives **every** live cell exactly 8 Moore neighbours and **every** adjacent empty cell exactly 9 — so a rule with `8 ∈ S` and `9 ∉ B` holds it forever, and one missing cell drops its eight neighbours to 7 while raising the two empties above and below the hole to 8. `LatticeBlocks` 2×2×2 is the other good candidate (7 for live, 1/2/4 for empty — a much wider margin); `LatticeCheckerboard` is degenerate (12 both ways, and 0 under von Neumann), and `LatticeFrame` is the only lattice with a *non*-uniform count, which is exactly why it's worth measuring before use.

**Generators return `TArray<FIntVector>`, they never touch `FCellGrid`.** That's load-bearing: `SetAlive()` caches the last chunk and is not thread-safe, so filling must stay sequential and in one place (`RebuildGridFromCells()`), while the generators themselves are free to parallelize, the cell count can be estimated up front, and the whole module is unit-testable without the engine (the header doesn't even forward-declare the grid). Files follow the established conventions exactly: `EStateGeneratorType`/`ESeedSymmetry` in their own headers (per `ENeighborhood`/`ESelectionCombineMode`), `StateGeneratorPresets.h/.cpp` mirroring `RulePresets`, and `StateGenerators.h/.cpp` as a flat namespace like `CellAging`/`CellMeshBuilder`.

`EStateGeneratorType` is **flat**, not "family + subtype": Shift+Y is then exactly `(uint8 + 1) % Num` (the `CycleChunkedRenderOrder()` idiom), `EditCondition` needs one comparison instead of two, and the HUD gets one dropdown. Family survives only as `FStateGeneratorPreset::FamilyName` — data for grouping, not a type. Likewise **all parameters live in one `FStateGeneratorParams`**, not four per-family structs, and the decisive reason is technical: `EditCondition` inside a USTRUCT resolves in *that struct's* scope, so `Type` must live inside it, and once it does, separate structs would each need their own copy of `Type`. `EditConditionHides` is mandatory rather than decorative — there are ~15 fields and only 3–5 are relevant at once.

**`GenerateRandom()` is now a thin wrapper over the `RandomBall` generator, but on *local* parameters, never `GenerationParams`** — it's what `BeginPlay()`, N (`NewSeed()`) and `ResetToInitialState()`'s fallback all go through, and a lattice configured in the panel must not silently redefine what those three mean. Its random loop was copied *verbatim* (same order of `FRandRange` calls, same reject-sampling, same rounding) so a given `Seed` still produces the picture it did before; `Generation.RandomBallParity` is the golden test guarding exactly that, comparing against the pre-existing `AutomataTestUtils::SeedSphere()`.

**Overload guard**: `GenerateState()` checks `StateGenerators::EstimateCellCount()` against `MaxGeneratedCells` (24M) **before touching the grid at all**, so a refusal leaves the current state intact — the bake-budget idiom, but deliberately **without** auto-coarsening (coarsening a lattice changes the geometry, and the geometry is the whole point). The limit isn't a low ceiling — the project's working scale is millions of live cells and this sits ~3× above it; it exists to catch the cases where one slider drag multiplies the volume by orders of magnitude (a solid box at `Extent=200` is 64M). Noise generators' estimates are *expected*, not upper bounds, so `FCellEmitter` re-checks the ceiling by fact as it goes. **Lattice-point counts for spheres are computed exactly**, in O(R²), not from `4/3πR³`: the continuous volume is not an upper bound on lattice points, and on a hollow sphere the two approximations' errors compound until the estimate falls *below* the truth and stops guarding anything (caught by `Generation.Determinism`, 708 vs 744). Because that's O(R²), the HUD's copy of the estimate refreshes on a 0.25 s timer rather than every tick.

Two traps worth not re-discovering: **negative modulo** (`-3 % 8` is `-3` in C++, so lattices need `WrapMod`/floor-division — the symptom is a pattern that looks right in the positive octant and tears exactly at zero, i.e. dead centre of the frame), and **`FMath::PerlinNoise3D` returning exactly 0 at integer points** — with a "round" `NoiseScale` (1.0/0.5/0.25) the field degenerates and the result comes out empty or solid, hence the default `0.08` and the warning in `SetStateGeneratorParams()`. Perlin takes no seed at all, so "different seeds" are different sampling offsets (±512, with a fractional part).

- **`Automata/Capture/`** — export an orthogonal slice as a PNG, for use as a texture: masks, ornaments, overlays. **F6** writes to `Saved/AutomataSlices/`, **Shift+F6** opens a save dialog.

**This is not a screenshot, and that is the whole point.** The image is rasterised straight out of `FCellGrid`; no GPU, no `SceneCapture`, no tiled assembly. Under a strictly axis-aligned orthogonal projection a cell lands exactly on a cell of a 2D grid, so: there is no antialiasing *by construction* (a pixel is a cell — intermediate values have nowhere to come from), the size is bounded by neither the window nor the 16384 render-target limit, and the result is reproducible regardless of where the camera sits or how it is zoomed. Measured against the screenshot it replaces: **120 KB at 512² versus 1.5 MB**, and sharper — few distinct colours compress well precisely because nothing is smoothed. What is lost is bloom, shadows and highlights: the image is flat, the cell's own ramp colour. For a mask that is the point; it will not look like a beauty shot.

**The camera only chooses a side.** Its own basis is snapped to the nearest world axes, and what lands in frame is decided by the active filters — cull volume, age filter, view slice — not by the screen rectangle. Cut with the box and the slice contains exactly the box's contents. That falls out for free because the cells come from `BuildCellRenderData()`, the very same collection that feeds the on-screen render: there is nowhere for a second set of "what to show" rules to appear, let alone drift. (The plan called for factoring that collection into a shared helper; it wasn't needed — `BuildCellRenderData()` already returns `{world position, colour}` with every filter applied, which is exactly the rasteriser's input, and refactoring the hot render path for it would have been risk without gain.)

**Orientation is where this goes wrong, so it is worth stating.** `BuildAxes()` snaps forward and up, but **derives the horizontal as a cross product** rather than snapping it too — snapping all three independently lets a diagonal view (NumPad7 isometric) collapse two of them onto the same axis, and lets rounding noise produce a mirrored image, which is invisible on a symmetric pattern. The axis of sight is also excluded from the "up" candidates for the same reason. `Slice.Orientation` guards this with a deliberately **asymmetric** figure (a "Г"), because a symmetric one passes while transposed *and* while mirrored.

**Gamma is the trap that leaves no trace.** `BuildAgeColorLut()` produces *linear* bytes — that is what the material needs (`PerInstanceCustomData` is a raw float, see `FCellRenderInstance`) — but every image viewer reads a PNG as sRGB, so writing those bytes straight out yields a picture visibly darker than the screen, with nothing in the log. Both LUT builders therefore take a `bSRGB` parameter (default off, so the render path is unchanged) and the capture passes `true`, controlled by `FSliceCaptureParams::bEncodeSRGB`. Turn it off only when the slice goes back into the engine as a mask with sRGB disabled on the texture.

**Series capture (F7, again to abort)** turns this from "a screenshot tool" into a way to watch an evolution frame by frame: frames land in their own `Series_<date>/` subfolder as `Frame_0000.png`… ready to be assembled into an animation or spread out as variants of one ornament. The step is counted in **generations**, not screen frames or seconds — the pattern changes by generation, and only that makes the series evenly spaced regardless of simulation speed or of how many generations one background dispatch happened to compute. The first frame is the current state, the one the user was looking at when they decided to record.

It rides the ordinary simulation rather than spinning its own loop: a loop would freeze the editor for minutes on a large grid, whereas this shows progress and can be interrupted. If Play was stopped, the series starts it and stops it again at the end; if Play was already running, it leaves it alone — the series is an observer, not an owner.

**`bSeriesFastMode` (default on) skips the on-screen render entirely while recording** — the capture rasterises from the grid, so a generation does not need to reach the screen to reach a file, and `AddInstances` is ~97% of a frame's cost. The inter-step delay is dropped too: `Speed` paces *viewing*, and identical files would just take proportionally longer to produce. The picture therefore sits still during a series (progress goes to the status line) — **and stays on the state F7 was pressed from after it ends too: `StopSeriesCapture()` deliberately does no catch-up render.** The final generation is already in the last PNG, and rendering a multi-million-cell grid is the single most expensive operation there is, so paying for it to show a frame that is being looked at in the files anyway is pure loss. The screen refreshes on the next render of its own accord (P, F, R, N). **The ordering in `ApplyStepResult()` is load-bearing**: the last frame's `CaptureSeriesFrame()` ends the series by calling `StopSeriesCapture()`, which clears `bSeriesCaptureActive` — so the skip-render decision is snapshotted into a local (`bSeriesSkipsRender`) *before* the capture block rather than read at the `return` below it. Read it after, and the final generation — alone out of all of them — still reaches `AddInstances`.

**Tiling (`ESliceTileMode`) is mirror-based, and that is a deliberate ceiling.** Reflection seams up unconditionally — pixels along the mirror line coincide by construction — so any slice becomes a seamless tile, at the cost of the result always being symmetric. A pattern that tiles *without* symmetry would require the automaton to be computed on a torus, which is a property of the simulation rather than of the capture, and would touch `FCellGrid`, both compute strategies and the `.usf` shader; that was considered and deliberately not done.

The one thing worth doing in code rather than by hand in an editor: **the edge row is not duplicated**. The tile is `[0..W-1][W-2..1]`, width `2W-2` — not `[0..W-1][W-1..0]`. Duplicating the edge puts a double line on every seam, exactly the artifact the whole per-pixel approach exists to avoid. It also leaves the tile closed on itself: the column after the last one is column 0 of the next copy, and that pair is as symmetric as any pair inside. `Slice.Tile` pins this down with a four-colour strip (on a uniform image a wrong mirror looks right) and checks that a one-pixel axis is left alone rather than collapsing to `2*1-2 == 0`.

Note the budget is checked on the image *before* mirroring, so a tile can come out nearly four times `MaxCapturePixels` in area.

Four depth modes (`ECellRasterMode`): `NearestToCamera` (what the screen shows), `Silhouette` (two-colour stencil — the cheapest mode and the most direct answer to "I need a mask"), `Thickness` (cells along the ray, normalised to greys — a thickness map that is not visible on screen at all). Every mode must be **order-independent**: `GetAliveCells()` iterates a `TMap` and its order changes between generations, so a mode that depended on it would produce different pixels for the same state. `PixelsPerCell` scales by block copy, never interpolation. `MaxCapturePixels` (8192², about half the peak — pixel buffer plus PNG buffer) is checked *before* any allocation, the `MaxGeneratedCells` idiom.

**`CapturePresets` (`Automata/Capture/CapturePresets.h/.cpp`, plain namespace + `FCapturePreset` `USTRUCT(BlueprintType)`) — whole capture setups, cycled with Shift+F7**, following `RulePresets`/`RenderPresets` exactly (code-constant table, `BlueprintReadOnly` fields, `namespace CapturePresets { const TArray<FCapturePreset>& GetAll(); }`, plus `GetCapturePresets()`/`ApplyCapturePreset(int32)`/`CycleCapturePreset()` on the orchestrator). Shift+F7 is to F7 what Shift+Y is to Y — the modifier picks *what to shoot with*, the bare key shoots — and it is checked inside `OnToggleSeriesCapture()` rather than mapped, the usual Enhanced-Input-can't-require-a-modifier idiom.

A preset stores a whole `FSliceCaptureParams` and is applied by assigning the struct, so switching presets can never leave a tail from the previous one — the same determinism argument as `FRenderPreset`, and the reason there is no "leave this field alone". Index 0 (`Обычная съёмка`) is default-constructed rather than hand-written, so it cannot drift from `FSliceCaptureParams`'s own defaults. `ApplyCapturePreset()` does not touch a running series: its length and step are fixed at start, and changing the frame size mid-series would produce a series of mismatched frames.

The other three are the **logo hunt**, and they are three different questions rather than three tastes: `Лого: силуэт` (does the *shape* read at all — `Silhouette`, 1 px/cell, 60 frames × 10 generations), `Лого: орнамент` (the same mirrored into a symmetric mark), `Лого: финал` (the winner in full colour at 8 px/cell on a transparent background, one frame). **Colour is deliberately absent from the hunt**: the mark is the cell arrangement, and the ramp is a swappable test palette — a knowingly late, free decision, since the capture rasterises from the grid, so the same seed and the same generation re-shoot bit-identically under any `AgeColors`. The series step is coarse because adjacent generations are near-identical: a fine step yields the same candidates several times over, not more of them.

**Every series folder gets a passport** — `WriteSeriesManifest()`, called from `StartSeriesCapture()` before the first frame (so even a series aborted immediately leaves a folder that explains itself). `Series.casave` goes through `WriteStateToFile()`, the exact Ctrl+S path down to the thumbnail — a near-identical "almost a save" format would drift from the real one at the first header change — and `Series.txt` says the same in words plus how to re-shoot a given frame. **A PNG carries no rule, seed or generation**, so a candidate carried off into another folder cannot be re-shot larger, recoloured or mirrored a month later, which is precisely what is wanted once one is chosen; frame `N` is generation `StartGeneration + N × SeriesGenerationsPerFrame`, and that offset is the one coordinate the image itself cannot hold. `WriteStateToFile()` therefore takes `bUpdateLastSavePath` — the passport must not become the target of the next silent Ctrl+S, or saving state would quietly relocate into a slices folder. Failure is warn-and-continue throughout: frames matter more than the passport. Note `FFileHelper::EEncodingOptions::ForceUTF8` already means *with* BOM (`ForceUTF8WithoutBOM` is the other one), and the BOM is required or Notepad renders the Cyrillic as garbage.

- **`Automata/Persistence/`** — save/load the automaton's rules + initial pattern to a `.casave` file, with a screenshot thumbnail. `AutomatonSaveHeader.h`'s `FAutomatonSaveHeader` (`USTRUCT`, not `UObject`) is a pure JSON-serializable parameter bag — rules (`BirthCounts`/`SurvivalCounts`/`Neighborhood`, the last written as a string via `FJsonObjectConverter`), geometry (`CellSize`/`ChunkSize`/`GridSize`), generation params (`Seed`/`Amount`/`SpawnRadius`/`ClusterFactor`), and three sanity counters (`CellCount`/`InitialCellCount`/`ThumbnailPngLength`) that `AutomatonStateSerializer::WriteSave()` fills in itself from the actual data being written, so a caller can never create a mismatch `ReadSave()` would then reject. Deliberately excludes viewing/render settings (`Speed`, `StepsPerRender`, materials, meshes) — those aren't automaton state. Adding a new saved parameter is one `UPROPERTY` here plus one line each in `AAutomataOrchestrator::BuildSaveHeader()`/`ApplySaveHeader()`.

`Automata/Persistence/AutomatonStateSerializer.h/.cpp` (plain namespace, same idiom as `CellAging`/`CellSelection`) owns the `.casave` binary container format (`ContainerVersion` currently `3`): `uint32 Magic("CASV")` + `uint32 ContainerVersion` + length-prefixed UTF-8 JSON header + `CellCount`-prefixed `{X,Y,Z,Age}` cell array + `InitialCellCount`-prefixed `{X,Y,Z}` array (no age — always replayed at Age 0) + `ThumbnailPngLength`-prefixed raw PNG bytes. Two independent version fields, two independent jobs: `ContainerVersion` bumps only when the byte *layout* changes (1→2 added the `InitialCells` section, 2→3 added the thumbnail section); `FormatVersion` (inside the JSON) bumps only on an incompatible change to the header's *semantics* — adding a JSON field bumps neither, so old files keep loading as new parameters get struct defaults. Written via `FMemoryWriter64` over a `TArray64<uint8>`; read via `FMemoryReaderView` (there's no `FMemoryReader64` in this engine version, despite `FMemoryWriter64` existing) wrapping `MakeMemoryView()`. `ReadSave()` validates every section's byte count against the file's actual remaining length *before* any `TArray::SetNumUninitialized()` call, so a corrupted/hand-edited length field can't trigger a runaway allocation; older files are still readable — a `Version < 2` file's `InitialCells` is derived from its main cell list (old files never separated "current state" from "return point"), and a `Version < 3` file's thumbnail section is simply empty (valid, not an error).

`AAutomataOrchestrator::SaveState()`/`SaveStateAs()`/`LoadStateFromFile()` (Ctrl+S/Ctrl+Shift+S/Ctrl+O — see the hotkey bullet above) fall back to `IDesktopPlatform` native Save/Open dialogs (`FDesktopPlatformModule::Get()`, default directory `Saved/AutomataSaves/` via `EnsureSaveDirectory()`) except when `SaveState()` already has a `LastSaveFilePath` from a prior save/load this session, in which case it silently overwrites that file with no dialog. **What gets saved is `InitialStateCells` — the same "initial pattern" `ResetToInitialState()`/R restores from (see that paragraph above) — never the current, possibly-evolved live `Grid`**, and saving doesn't touch `Grid`/camera/render at all: no reset, no re-frame, nothing rebuilt. This went through two earlier designs before landing here — first "save whatever's currently live," then "reset the grid to the initial pattern and re-frame the camera before saving" (both abandoned: the former lost the reproducible starting point on every save-after-some-evolution, the latter needlessly threw away in-progress simulation state for no real benefit, since the initial pattern was already sitting in `InitialStateCells` without any reset needed to read it) — the shipped version mutates nothing. Because of that, `SaveState()`/`SaveStateAs()` need **no** `bStepInProgress` guard (they only read `InitialStateCells`, a plain array only ever written on the game thread by `StartFromSelection()`/`LoadStateFromFile()`/`GenerateRandom()`); `LoadStateFromFile()` does need the guard, since it swaps `Grid` out from under a possible in-flight background step, same as every other `Grid`-swapping path.

The thumbnail (`AAutomataOrchestrator::CaptureThumbnailPng()`) is a screenshot of **whatever the camera currently sees** — the live, possibly-evolved simulation, not the saved initial pattern — taken via `GEngine->GameViewport->Viewport->ReadPixels()` (synchronous, game-thread-blocking, no extra render pass needed), center-cropped to a square (short side of the viewport kept whole, long side trimmed symmetrically off both edges via a manual row-by-row `FMemory::Memcpy` — no aspect distortion, just lost frame margin), unconditionally resized (`FImageUtils::ImageResize()`) to exactly `ThumbnailSizePixels` × `ThumbnailSizePixels` (default `768`) regardless of the actual viewport resolution/aspect ratio, and encoded with `FImageUtils::PNGCompressImageArray()`. This is a deliberately *inconsistent* pairing with the saved cell data (save a freshly-extracted glider, but the thumbnail can show a whole evolved swarm if the user let it run a while before hitting Ctrl+S) — intentional, since it's meant as a personal visual bookmark of the save *moment*, not a preview of what loading the file will produce. `FImageUtils`/`FViewport::ReadPixels()` are already reachable through this project's existing `Engine`/`RHI` dependencies — no new `Build.cs` entry was needed for the screenshot itself (only `DesktopPlatform`, for the dialogs — see Module dependencies below). Written twice with the same already-encoded bytes: embedded as the container's thumbnail section, and as a same-basename sibling `.png` next to the `.casave` (`FPaths::SetExtension()`) — the sibling is what actually shows a real thumbnail tile in Windows Explorer; a native `.casave`-specific Explorer icon would require registering a COM `IThumbnailProvider` shell extension (a separate, non-UE Win32/registry project) and was explicitly rejected as disproportionate for this project. Capture failure (no `GameViewport` — not PIE — zero viewport size, `ReadPixels()`/PNG-encode failure) is warn-and-continue at every step: a failed screenshot never blocks the actual save, and a `ThumbnailPngLength == 0` file loads back with an empty thumbnail (also valid, not an error).

- **`Ui/` — the HUD.** `FUiController` (`Ui/UiController.*`) is a plain (non-UObject) RAII-style helper, not an actor: it lazily creates a `UUserWidget` from a `TSubclassOf<UUserWidget>` set by the orchestrator (`HUDWidgetClass`) and exposes `ShowHUD/HideHUD/ToggleHUD`. Owned via `TUniquePtr` by `AAutomataOrchestrator`, driven from `BeginPlay()` (see that bullet for why not `PostActorCreated()`).

**A UMG widget never sees a keypress** — input arrives at `AGamePlayerController`, so anything the HUD should react to needs a bridge. **F5** (`OnToggleHudInfoPanel()` → `AAutomataOrchestrator::ToggleHudInfoPanel()`) is that bridge for hiding the info panel: it forwards to `UMainHudWidget::OnToggleInfoPanel()`, a `BlueprintImplementableEvent`. C++ deliberately does not know *what* gets hidden — one panel, several, or a cycle of "everything → compact → nothing" — because that is layout, and layout lives in UMG. The same shape is the right one for any future HUD key. `GetHudWidget()` (via the new `FUiController::GetWidget()`, a weak reference rather than the raw public `NewWidget` field) reaches the widget, and `ToggleHud()`/`IsHudVisible()` finally expose `FUiController::ToggleHUD()` — written long ago and, until now, called from nowhere at all.

**Split of responsibilities — C++ supplies data and actions, the visuals are built by hand in UMG**: `UMainHudWidget` (`Ui/MainHudWidget.*`) is a thin native shell whose only job is `GetOrchestrator()` — a lazily resolved, `IsValid()`-revalidated `GetActorOfClass()` lookup (the same idiom as `EnsureRenderCullVolume()`), deliberately *not* an editor-assigned reference, since a widget asset cannot hold a pointer to a specific level actor. The layout lives in a Blueprint subclass (`Content/HUD/WBP_MainHud`) assembled in the UMG Designer. Everything the widget needs is therefore exposed as `BlueprintPure`/`BlueprintCallable`/`BlueprintType` on the orchestrator; when the HUD needs something new, the change belongs in C++ as API, not as widget-construction code.

**Data**: two `USTRUCT(BlueprintType)` summaries, both computed once and read by everyone rather than recomputed per consumer (so a log line and the on-screen number can never disagree). `FCellRenderStats` (`GetLastRenderStats()`) — `RenderedCellCount`/`TotalCellCount` ("drawn/total", i.e. how much the cull volume is removing), `EstimatedUploadMB` (sized from `RenderedCellCount`, a single figure like a file size, not a before/after pair) and `BytesPerInstance`, filled by `BuildCellRenderData()`. `FHudStats` (`GetHudStats()`) — `bIsComputing`/`bIsRendering` (the `bStepInProgress`/`bChunkedRenderInProgress` phases, which can overlap), `CurrentFPS` (`GAverageFPS`, not recomputed), `GenerationCount`, `GenerationsPerSecond` (recomputed on a one-second window, not per frame — sub-second sampling is visibly noisy at low `Speed`), `EstimatedGpuComputeUploadMB` (read from whatever the GPU strategy already packed, never a separate grid scan), plus `AliveCellCount` (`Grid->Num()`, O(1) — the chunks keep the count) and `SelectedCellCount`. The last two refresh every tick, so a Delete or a new selection shows up immediately rather than at the next generation. Three more mirror the live *settings* rather than measurements, so the HUD reads exactly what the hotkeys change instead of keeping its own copy: `SimulationSpeed` (`Speed`, +/-) and `StepsPerRender` (T/G), and `CameraSpeed` — read straight off the possessed pawn's `UFloatingPawnMovement::MaxSpeed` rather than derived from `CameraSpeedMultiplier`, since the controller has already multiplied it while Left Shift is held and the HUD should show the boosted figure. Note `SimulationSpeed` vs `GenerationsPerSecond` is target vs. actual: the gap between them is the readable sign that the sim is compute-bound rather than throttled by its setting. A **mode block** follows the same mirror rule, one field per hotkey — `bSimulationRunning`/`bFastStepActive` (P, Shift+F), `bSelectionModeActive` (Tab, read off the controller), `ComputeMethod`, `bChunkedRenderEnabled`/`ChunkedRenderOrder`/`bWaitForChunkedRenderToFinish` (Z/X/V), `bCellCullingEnabled` (B), `bRenderCullVolumeEnabled`/`bRenderCullVolumeVisible` (C, Ctrl+C) and `bGhostShapeEnabled` (H), plus `bCellsCastShadows` and `bBackgroundVisible` (U) and the render-profile trio `RenderPresetName`/`RenderPresetIndex`/`bRenderPresetModified` (F1–F4 — see `RenderPresets` above; the last one is what lets the widget draw a "Performance\*" once a hotkey has changed something the profile owns). Four of them are *effective* states rather than switches, and exist precisely because they can't be derived from the switches in the widget: `bCullVolumeActive` comes straight from `GetActiveCullVolume()` (which also requires the actor to be present in the level), and `bGhostShapeReplacesDetailedRender` from `ShouldGhostShapeReplaceDetailedRender()` — the mode that actually buys the speed. Reading them from the same functions the renderer uses is the point; a widget-side copy of those conditions could drift.

The other two, `bCellCullingActive` and `bViewSliceActive`, complete the trio of "is this actually cutting right now" flags behind the HUD's three cut indicators — **Culling** (B, distance), **Volume** (C, the box) and **Slab** (J, the view slice), i.e. the terminology split described under `Automata/Rendering/`: culling is what the renderer skips *after* the instances are built, the other two remove cells in `BuildCellRenderData()` before anything is built at all. All three lamps are wired to "cutting", never to "switched on", and `bCellCullingActive` is why: `bEnableCellCulling` defaults to **true** while both cull distances default to **0** (the engine's own "off"), so an indicator bound to that switch would be lit from the first second of every session while nothing whatsoever was being culled. `bViewSliceActive` adds the camera-availability half of the condition `BuildCellRenderData()` itself checks — the slice plane is defined by the camera, so without one there is nothing to cut with. The plain switches (`bCellCullingEnabled`/`bRenderCullVolumeEnabled`/`bViewSliceEnabled`) all survive alongside, so a widget wanting a third, dimmed "armed but inert" state can build it from a pair of fields with no C++ change. `LastHudStats` is a `UPROPERTY` for the usual Live-Coding-reinstancing reason (see `GamePC`).

**Actions**: the simulation entry points were already `BlueprintCallable`; the HUD additions are `SetSpeed()`/`SetStepsPerRender()` (absolute setters for sliders, applying the same clamps as the `+`/`-` and T/G hotkeys rather than letting a slider write the `BlueprintReadWrite` property raw and reach 0), `TryApplyRuleString(In, out Error)` (same as `ApplyRuleString()` but takes the string as a parameter and hands the parse error *back* — a `UE_LOG` warning is invisible from UMG, and silently doing nothing on a button press is the worst option), and `GetActiveRuleString()`.

**`RulePresets` (`Automata/Simulation/RulePresets.h/.cpp`, plain namespace + `FRulePreset` `USTRUCT(BlueprintType)`)** — 13 ready-made rules transcribed verbatim from williamyang98/3D-Cellular-Automata's `system_entries.js`, in the source's own order and naming so a preset can be checked against the site one-to-one (this project's own finds are appended **after** that whole block, never inserted into it, precisely so that one-to-one numbering survives — currently one: **`Crystal Growth 1 (Moore)`**, `0-6/1,3/2/M`, which differs from the catalogued `Crystal Growth 1` in a single letter, the neighbourhood, and that is enough to change the growth geometry — under Moore the diagonals advance as fast as the axes, so the front is cubic and throws straight rays, where von Neumann's Manhattan metric gives an octahedral front with faces instead. Its core reads as a symmetric cross and is the strongest logo candidate so far) ("Builder 1"/"Builder 2" really are duplicates upstream; kept so the numbering matches). Each carries `Name`/`RuleString`/`SpawnRadius`/`Amount`; `GetRulePresets()` lists them and `ApplyRulePreset(Index, bApplySpawnSettings)` applies one **through `TryApplyRuleString()`**, so presets and hand-typed rules share exactly one application path instead of two that could drift. It deliberately does *not* regenerate the grid — applying a rule to an already-grown structure is sometimes exactly what's wanted, and "start fresh with this preset" is one more `GenerateRandom()` click. The upstream table specifies a fill *density*, which this project can't use directly (`Amount` is an absolute count and `GenerateRandom()` reject-samples **with collisions**, so `density × volume` systematically under-seeds); `Amount` is therefore derived with the coupon-collector estimate `N·ln(1/(1-p))`, `p` capped at 0.95 since full coverage by random draws is unreachable in principle. Two presets whose upstream radius is grid-relative get a concrete radius of 30, because `GridSize` doesn't affect generation in this project at all (it is saved and loaded, but `GenerateRandom()` seeds purely by `SpawnRadius`).

**The generation graph — two lines over generation number, and the first time-series storage in the project**: everything else HUD-facing (`FRenderTimings`, `FCellRenderStats`, `FHudStats`) is a snapshot of the last moment. A single instantaneous number cannot show what a run is actually judged by — where the rule accelerates, where it plateaus, where it collapses, and how much the cull volume is really taking off the renderer's plate — so `UGenerationGraphWidget` plots **total alive cells** against **rendered ("visible") cells**.

The two numbers arrive from different places at different rates, and that asymmetry is the whole design. Alive exists for every generation that reaches the game thread (`ApplyStepResult()`, right after `GenerationCount += Generations`); rendered exists only where `BuildCellRenderData()` actually ran. Four independent mechanisms punch holes in the second series — `StepsPerRender`, GPU batching (intermediate generations never exist on the game thread at all, and the batch is trimmed at runtime), series fast mode, and Ghost Shape replacing the detailed render — so the stride is not constant. Two consequences: samples are stored as **`(generation, value)` pairs** and X is mapped **by generation value, not by array index** (index mapping would compress and stretch the curve every time the batch size changed); and nothing may assume `rendered ≤ alive`, since under `States > 2` decaying cells are drawn but not counted alive.

`Automata`-style free functions in `Orchestration/GenerationHistory.h/.cpp` (namespace `GenerationHistory`, the `CellAging`/`CellSelection` idiom) own the window; `AAutomataOrchestrator` owns only the `UPROPERTY(Transient) TArray<FGenerationSample> GenerationSamples` (Transient for the `LastHudStats` reason — history cannot be recomputed on the next render, so Live-Coding reinstancing must not wipe it) and `GenerationHistoryCapacity` (512 **samples**, not generations). The member is named `Samples`, not `History`, because inside the class the latter would shadow the namespace.

Two write paths, deliberately asymmetric. `AppendGenerationSample()` sits beside the two `GenerationCount` increments (`ApplyStepResult()` and `Next()`'s completion) and **above** both render-skip returns, next to the series-capture and Ghost-Shape hooks and for the same reason: the alive line describes the simulation, not the screen. It carries the previous sample's rendered value forward, which is what makes the rendered line hold its last value as a step instead of dropping to zero. `NoteRenderedCells(int32)` is called from the four render points and **takes the count as a parameter rather than reading `LastRenderStats`** — `BuildCellRenderData()` has four callers, two of which (`BuildSliceCapture()`/`EstimateSliceCaptureSize()`) save and restore those stats, so "only the callers that leave fresh stats call me" is an unwritten contract a fifth caller would break silently. The parameter also lets the two Ghost-Shape branches record an honest **0**: zero detailed instances really do reach `AddInstances()` there, and watching the rendered line drop to the floor when Ghost Shape takes over is precisely the diagnostic the graph exists for. When the last sample is already about the current generation it is edited **in place** — load-bearing, not an optimisation: `RefreshRenderCullVolume()` fires from `Tick()` on every camera move while the view slice is on, and without in-place editing one flight of the camera would smear a single generation across hundreds of X positions. History is cleared in `ResetGenerationCounter()`, the one funnel for all five "start a run over" paths; `BakeCellsToMesh()` deliberately does **not** clear it, since a bake is "freeze and inspect" and the run that produced the sculpture is exactly what you want beside it (the visible consequence: `AliveCellCount` on the HUD drops to 0 while the graph keeps the curve).

**The widget is `UWidget` + `SLeafWidget`, not `UUserWidget` + `NativePaint`** — that was the first design and it is wrong for a reason worth recording: `SObjectWidget::OnPaint` paints **all** children first and only then calls `NativePaint` with a raised `LayerId`, so axis labels placed inside such a widget would sit *under* the graph and an opaque background would erase them outright, forcing axis text to be drawn from C++ via `MakeText` — which defeats the entire "layout lives in UMG" split. As a leaf widget it is an ordinary node of the tree: drop it in an `Overlay`, stack `TextBlock`s on top, and it appears directly in the palette (`GetPaletteCategory()` → "Automata", which **must** be `#if WITH_EDITOR` or non-editor builds fail to link) with no intermediate Widget Blueprint. Three more obligations that bite only later: `ComputeVolatility()` must return `true` (the data changes with no Slate invalidation whatsoever, so under `RetainerBox`/`InvalidationBox` or `Slate.EnableGlobalInvalidation 1` the graph would freeze on a cached image), `ReleaseSlateResources()` must reset the shared pointer, and colours must be multiplied by `InWidgetStyle.GetColorAndOpacityTint()` or the graph stays opaque while its parent panel fades. `MakeLines` takes its point array **by value** and in **local** coordinates. Y is scaled by the max of *both* series, pinned at 0, rounded to a nice 1/2/5×10^k ceiling with hysteresis (a raw per-frame max makes the whole curve breathe), and `bLogScaleY` exists mainly for the cull volume: with it on, rendered runs two or three orders of magnitude below alive and a linear axis lays that line flat on the floor.

`AGameHud` (`Core/Hud/GameHud.*`, wired via `AAGameMode::HUDClass`) is separate and unrelated to UMG: a native `AHUD` subclass whose `DrawHUD()` paints the live marquee rectangle during a selection drag.

All of the plain-C++ helper classes above (`FUiController`, `FCellGrid`/`FDenseCellGrid`, `FCellGridRenderer`/`FInstancedMeshCellGridRenderer`, `FCellularAutomatonRule`) follow the same convention: non-copyable, owned via `TUniquePtr` (or, for `FCellularAutomatonRule`, constructed as a short-lived local) by whichever `UObject`/Actor uses them, `TWeakObjectPtr` (not raw pointers) for any `UObject` references they hold.

### Source layout convention

Code is being migrated from a flat `Orchestration/` and `Ui/` dump into a `Core/<Subsystem>/` layout (see the pending rename of `AGameMode`/`GamePlayerController` in git status). When adding new engine-level classes (game mode, controllers, pawns, etc.), place them under `Source/CellularAutomata/{Public,Private}/Core/<Subsystem>/`; higher-level gameplay/orchestration code stays under `Orchestration/`; widget/HUD glue stays under `Ui/`.

### Module dependencies

`CellularAutomata.Build.cs` pulls in `Core, CoreUObject, Engine, InputCore, Slate, SlateCore, UMG, WebBrowser, WebBrowserWidget, Json, JsonUtilities` as public dependencies, plus `EnhancedInput`, `RHI`, `RenderCore`, `ProceduralMeshComponent`, `DesktopPlatform` as private dependencies. `EnhancedInput` was added for `AGamePlayerController`'s Play/Stop hotkey — `EnhancedInput` is already the project's active input system per `Config/DefaultInput.ini`'s `DefaultPlayerInputClass`/`DefaultInputComponentClass`, so no plugin-enablement change was needed, just the module reference. `RHI`/`RenderCore` were added for `FGpuComputeStrategy`'s RDG compute-shader dispatch (see `Automata/Simulation/ComputeStrategy/`). `ProceduralMeshComponent` is for `BakeCellsToMesh()` (see the Baking paragraph above). `DesktopPlatform` is for the native Save/Open dialogs in `Automata/Persistence/` (see below) — a Developer module, unavailable in Shipping builds, which is fine since this project only runs in editor/PIE; the thumbnail screenshot itself (`FImageUtils`/`FViewport::ReadPixels()`) needed no separate module, already reachable through `Engine`/`RHI`. The `WebBrowser`/`WebBrowserWidget` dependency was for a `Ui/WebInterface` widget that has since been deleted — if reintroducing browser-based UI, that's the intended integration point. **Note**: adding a module to `Build.cs` isn't something Live Coding can hot-patch — it requires closing the Editor and a full cold rebuild (see Build/run section above).

`RemoteControlWebInterface` and `RiderLink` are both present but **disabled** (`"Enabled": false`) in the `.uproject` Plugins list — `RemoteControlWebInterface` tries to build a React web app on editor startup and fails in this environment (`Failed To Build WebApp`); `RiderLink`'s `RiderDebuggerSupport.dll` gets blocked by Windows Smart App Control (unsigned binary, `GetLastError=4551`). Don't re-enable either without addressing the underlying cause first.

### MCP / AI-editor integration

`Plugins/McpAutomationBridge` (from github.com/ChiR24/Unreal_mcp) is installed and gives Claude Code direct control of the running Editor over HTTP — spawning/inspecting actors, screenshots, console commands, asset ops, etc. Native MCP mode is enabled via `Config/DefaultGame.ini` (`[/Script/McpAutomationBridge.McpAutomationBridgeSettings]`, `bEnableNativeMCP=True`, port 3000) — no Node.js/bridge process needed. Registered in Claude Code at **user scope** (`claude mcp add unreal-engine --transport http --scope user http://localhost:3000/mcp`); MCP server tool lists only refresh when a Claude Code session (re)starts, not mid-session.

**Fast iteration loop while the Editor is already open**: after editing C++, trigger a hot patch instead of closing the editor for a full UBT rebuild — via the MCP `control_editor` tool's `console_command` action (or the in-editor Ctrl+Alt+F11 hotkey) running `LiveCoding.Compile`. This requires Live Coding to be enabled in the Editor already. A pure function-body edit (no new/changed `UPROPERTY`/`UFUNCTION`) patches in under a second; if unsure whether a patch actually landed, compare the edited `.cpp`'s mtime against `Intermediate/Build/Win64/x64/UnrealEditor/Development/CellularAutomata/<File>.cpp.obj` and `Binaries/Win64/UnrealEditor-CellularAutomata.dll`. A full cold UBT build still requires the Editor process to be closed first (it locks the DLL):
`"C:\Program Files\Epic Games\UE_5.7\Engine\Build\BatchFiles\Build.bat" CellularAutomataEditor Win64 Development -Project="<repo>\CellularAutomata.uproject" -WaitMutex`

**Known instability**: `LiveCoding.Compile` on an edit that changes reflection data (new/changed `UPROPERTY`/`UENUM`/`UFUNCTION` on a class with a live instance in the open level) has repeatedly crashed the Editor process during class reinstancing in this environment, restarting it silently with no crash dump (check `Saved/Logs/CellularAutomata.log`'s `Log file open` timestamp to detect this). After such a crash the patch is usually still applied (verify via MCP `inspect`/`get_property` once the Editor is back up) — no need to redo the edit, just reconnect.

**A pure function-body edit is *not* safe either, and the earlier claim here that it was is wrong** — measured: a comments-and-bodies-only change to `AutomataOrchestrator.cpp`/`GamePlayerController.cpp`/`RenderCullVolume.cpp` (verified by `git diff` to touch no `UPROPERTY`/`UFUNCTION`/`UCLASS` at all) compiled cleanly, produced `patch_0`, and then killed the process outright — no silent restart, the process was simply gone. The log's last lines are a full run of `LogClass: Function <every UFUNCTION of the class> is new or belongs to a modified class`, which is the point: **Live Coding reinstances the whole class whenever its `.cpp` is patched**, regardless of whether reflection data actually changed, so a class with a live instance in the open level is exposed to the reinstancing crash on *any* edit. Treat "cold rebuild with the Editor closed" as the default for this project's orchestrator/controller classes, and hot-patching as a gamble worth taking only with unsaved work already saved.

### Config

- `Config/DefaultEngine.ini`: `GameDefaultMap=/Game/levels/NewMap.NewMap`, `GlobalDefaultGameMode=/Script/CellularAutomata.AGameMode` (i.e. `AAGameMode`).
- `Config/DefaultInput.ini`: input action/axis bindings consumed by `AGamePlayerController`, plus a `[/Script/Engine.PlayerInput]` block that **removes five engine `DebugExecBindings`**. `Engine/Config/BaseInput.ini` binds F1–F5 to viewmode commands, and this project owns all five: F1–F4 are render profiles, F5 the HUD info panel. F5 was the visible one — `viewmode shadercomplexity` floods the screen with colour — while F1–F4 collided quietly, both the preset and the engine setting a viewmode with the winner decided by ordering. Removed by exact match rather than clearing the array, so F11 fullscreen, the shader-recompile and profile chords and the debug camera survive; **the strings must match `BaseInput.ini` to the character** (including the space after the comma on F1), because ini array removal compares text rather than the parsed struct and a stray space makes it silently do nothing. Left in place: `LeftShift`/`RightShift` → `DebugManager` column cycling, which overlaps this project's speed boost and every Shift modifier but has not misbehaved.
