# Selection, initial state and baking

Mouse marquee/ray-pick selection, `InitialStateCells`/`ResetToInitialState()`, and baking cells to one mesh. Read before changing selection or the R-key return point.

**Mouse cell-selection — isolate an interesting sub-pattern (glider/oscillator-hunting) and launch it as a fresh starting state**: a "selection mode" toggled by the **Tab** hotkey (`AGamePlayerController::OnToggleSelectionMode()` → `SetSelectionModeActive()`) that stops the camera and shows the cursor by calling the pre-existing `SetCameraControlEnabled(false)` (previously dead code outside `Pause()`/`Resume()`) — the controller's own `InputComponent` keeps receiving input throughout, since `DisableInput()`/`EnableInput()` only gate the *pawn's* input stack, not the controller's. While active, holding **left mouse button** and dragging draws a marquee rectangle (`OnSelectDragStarted()`/`OnSelectDragFinished()`, `Started`/`Completed` on a `SelectDragAction`) — a small native `AHUD` subclass, `AGameHud` (`Core/Hud/GameHud.*`, wired via `AAGameMode::HUDClass` in its constructor), overrides `DrawHUD()` to paint the live drag rectangle each frame by polling `AGamePlayerController::IsDraggingSelection()`/`GetSelectionDragStart()` plus a fresh `GetMousePosition()` call — no UMG widget needed, since `FUiController`'s widget system is unused for auto-show anyway (see below). On mouse-up, the controller computes the final screen rect, grabs a view-projection matrix **once** (not per cell) via `ULocalPlayer::GetProjectionData()` → `FSceneViewProjectionData::ComputeViewProjectionMatrix()` (the same API `UGameplayStatics::ProjectWorldToScreen` uses internally, but without its per-call overhead), and hands both off to `AAutomataOrchestrator::SelectCellsInScreenRect()` along with an `ESelectionCombineMode` (`Automata/Selection/SelectionCombineMode.h`, its own header per the `ENeighborhood`/`EChunkedRenderOrder` convention): the standard marquee-modifier pattern — plain drag **replaces** the selection, **Shift**+drag **adds** the rect's cells to it (set union, deduplicated via a `TSet` of the existing selection so it stays O(1) per cell at million-cell selection sizes), **Ctrl**+drag **subtracts** them (set difference via `TArray::RemoveAll` against a `TSet` of the rect hits). The modifier is sampled at drag *start* (`OnSelectDragStarted()`, stored in `PendingSelectionCombineMode`), not at release — like most editors, so the mode doesn't flip if the user lets go of the modifier slightly before the mouse button; Ctrl wins if both are held, and both left and right Shift/Ctrl work. **A click (mouse moved ≤ `ClickDragThresholdPixels` = 4px between press and release) picks a single cell instead of a rectangle**: the cursor is deprojected to a world ray (`DeprojectMousePositionToWorld`) and `CellSelection::PickCellAlongRay()` walks the cell lattice with Amanatides-Woo voxel DDA (exact boundary stepping — no cell on the ray is skipped), returning the *first* alive cell, i.e. exactly the cell whose face is visible under the cursor — engine line traces can't do this since all cell components have collision disabled; traversal is capped at the far side of the alive-cells bounding sphere (`ComputeAliveCellsBounds()`). The same combine modes apply (plain click replaces — clicking empty space clears the selection; Shift+click adds the cell, Ctrl+click removes it), sharing the combine logic with the marquee via the private `CombineWithSelection()` helper on the orchestrator.

Picking itself lives in `Automata/Selection/CellSelection.h/.cpp` — a plain namespace function (`CellSelection::SelectCellsInScreenRect()`), the same non-`UObject` idiom as `CellAging`: for every alive cell, `ViewProjectionMatrix.TransformFVector4(FVector4(WorldPos, 1))` projects it to clip space; cells behind the camera (`W <= KINDA_SMALL_NUMBER`) are dropped, the rest are perspective-divided into NDC and mapped to pixel coordinates, then tested against the drag rectangle. **Deliberately no depth/distance limiting** — the marquee selects every alive cell whose screen-space projection falls inside the rectangle regardless of how near or far it is, i.e. it behaves like an infinite frustum along the camera's view direction rather than a bounded 3D box (a conscious simplicity choice, not an oversight — see the plan this was built from, `snazzy-twirling-beacon.md`, for the considered-and-rejected depth-bounded alternative). Parallelized via `ParallelFor` into a same-size `TArray<bool>` followed by a sequential collect pass — the same two-phase "parallel flag, sequential gather" idiom as `CellAging::ComputeAges()` and the CPU compute strategy's candidate-set construction — since this runs as a one-shot action against potentially millions of alive cells on every mouse-release.

`AAutomataOrchestrator::SelectedCells` (`TArray<FIntVector>`, plain member, not a `UPROPERTY`) holds the current selection; `SelectCellsInScreenRect()` populates it and immediately calls `RenderSelectionOverlay()` so the highlight appears without waiting for the next simulation step. Rendering reuses `FInstancedMeshCellGridRenderer` (see above) — one more component, `SelectionMeshComponent` (`UPROPERTY(Transient)`, **always** a plain `UInstancedStaticMeshComponent` regardless of `CellMeshComponentType`, since a selection is always a small subset and gets nothing from HISM's cluster tree) plus its `TUniquePtr<FInstancedMeshCellGridRenderer> SelectionRenderer` (not a `UPROPERTY`, same Live-Coding-reinstancing rationale as `CellsRenderer` — `EnsureSelectionMeshComponent()` re-derives it from a surviving `SelectionMeshComponent` if the two ever disagree), painted with the same `CellMaterial` as ordinary cells and the designer-assigned `SelectionColor` in its per-instance custom data. `RenderSelectionOverlay()` is called as an extra pass at the end of both `RenderGridImmediate()` and `RenderCurrentGrid()` (filtering `SelectedCells` down to currently-alive cells defensively, and always rendering in one shot — never chunked, since selections are always small) and clears the component whenever there's nothing to show. `ApplyCellCullDistances()` applies the same cull distances to `SelectionMeshComponent` as every other cell-rendering component.

`SelectedCells` is reset to empty at the top of `GenerateState()`, in `Next()`'s completion, and in `ApplyStepResult()` (right after the `Grid` swap) — any new generation invalidates a prior selection's coordinates, matching the intended workflow of "pause, fly around, select, extract" rather than selecting mid-Play. `AAutomataOrchestrator::StartFromSelection()` (`CallInEditor`, also bound to the **Enter** hotkey via `AGamePlayerController::OnExtractSelection()`) is the actual "launch as new state": guards on `bStepInProgress` (it swaps `Grid`, which a background `Next()`/`StepAsync()` may be reading at that moment — same refuse-with-warning as every other `Grid`-swapping path), an empty selection, or a missing `CellMaterial` the same way `GenerateState()`/`Next()` do, builds a fresh grid via the existing `CreateGrid()` helper, copies over only the selected (and still-alive) cells with `SetAge(..., 0)` (a fresh start, exactly like a newly-born cell), swaps it into `Grid`, clears `SelectedCells`, calls `GamePC->SetSelectionModeActive(false)` to hand camera control back, and finishes with `RenderGridImmediate()` — mirroring `GenerateState()`'s structure throughout. **Coordinates are deliberately left as-is, not translated to the origin** — the selected pattern stays exactly where it was picked, since the camera is already looking right at it and the automaton's rules are translation-invariant anyway, so there's nothing to gain from re-centering.

`AAutomataOrchestrator::DeleteSelectedCells()` (`CallInEditor`, category `Automata|Selection`, also bound to the **Delete** hotkey via `AGamePlayerController::OnDeleteSelectedCells()`) is the destructive counterpart to `StartFromSelection()`: instead of extracting the selection into a fresh grid, it kills the selected cells **in the current grid** (`Grid->SetAlive(Cell, false)`, counting only actually-alive ones for the log) — a manual state edit for cutting a piece out of a pattern and watching how the remainder evolves. The simulation is deliberately **not** reset: `Grid` stays the same object (no swap), ages of surviving cells are untouched, and P/F continue from the edited state. Guards mirror the other selection paths (`bStepInProgress` — a background step is *reading* `*Grid`, so mutating it mid-flight would race; no `Grid`; empty selection; missing `CellMaterial`), then `SelectedCells.Reset()` + `RenderGridImmediate()` so the holes appear instantly.

**`InitialStateCells` / `ResetToInitialState()` — the "initial pattern": a persistent return point for R, and what `Automata/Persistence/` saves (see below)**: three equally-weighted sources overwrite `InitialStateCells` wholesale (plain member like `SelectedCells`, but with the opposite lifecycle — it survives simulation steps *and* new mouse selections) — `StartFromSelection()` (Enter, the extracted still-alive cells), `LoadStateFromFile()` (Ctrl+O, the file's own `InitialCells` section), and `GenerateState()` itself (the cells that actually landed in the grid after spawning, via `Grid->GetAliveCells()` — not the raw `Amount`, since reject-sampled spawns can collide onto the same cell). `ResetToInitialState()` (`CallInEditor`, what the **R** hotkey calls via `OnResetSimulation()`) replays whichever is current: rebuilds the grid from `InitialStateCells` with all ages back at 0, then calls `GamePC->FrameAllCells()` (see **Home** above) to re-frame the camera on the result — so after watching an extracted glider, a loaded save, or just a random spawn evolve (or explode), R snaps back to its exact starting shape and re-centers the view for another run. Because `GenerateState()` now also populates `InitialStateCells`, and `BeginPlay` always calls `GenerateState()` once, `InitialStateCells` is non-empty from the moment PIE starts — the `InitialStateCells.Num() == 0` fallback to `GenerateState()` inside `ResetToInitialState()` is a defensive path this project's normal usage doesn't actually reach, kept rather than removed.

**Baking — freeze the current state as one hollow mesh and free the cells (experimental, marked by the user as needing further iteration before it's genuinely useful)**: `AAutomataOrchestrator::BakeCellsToMesh()` (**M** hotkey / `CallInEditor`, category `Automata|Baking`) converts the current state into a single `UProceduralMeshComponent` section and *unloads* everything else: all instanced-mesh components are cleared **and `Grid` itself is freed** (`Grid.Reset()`), so the multi-million-cell chunk/instance memory is released and large areas can be inspected cheaply — a one-way snapshot "sculpture", not a render mode (the simulation cannot continue from it; Play/fast-step are force-stopped first, and `bChunkedRenderInProgress` is cleared so a mid-flight chunked reveal can't trickle instances back in after the wipe). If `SelectedCells` is non-empty, only the selection is baked (filtered to still-alive, like `StartFromSelection()`), else all alive cells. Geometry lives in `Automata/Meshing/CellMeshBuilder.h/.cpp` (plain namespace like `CellAging`/`CellSelection`): classic face culling — for each cell, each of the 6 cube faces is emitted only if the neighbor *in the baked set* (deliberately not `IsAlive()`, so baking a selection doesn't punch holes against unselected-but-alive neighbors) is absent; 4 verts per face (no sharing — crisp cube edges), winding/UV conventions match `KismetProceduralMeshLibrary::GenerateBoxMesh()` (see the `FFaceDef` comment in the .cpp), exact-count pre-pass for `Reserve`. `BakedMeshMaterial` (Details panel) paints it — no fallback: unset means a warning plus the engine default material, since a `CellMaterial` driven by per-instance custom data would render a procedural mesh black; `BakedMeshComponent` is `UPROPERTY(Transient)`, lazily created (`EnsureBakedMeshComponent()`, mirrors `EnsureSelectionMeshComponent()`). `InitialStateCells` deliberately survives the bake, and `ClearBakedMesh()` is called from `GenerateState()`/`ResetToInitialState()`/`StartFromSelection()` — so **R** after inspecting a bake cleanly starts a new run (replaying the extracted pattern if one exists) with the snapshot removed. Requires the `ProceduralMeshComponent` module (`Build.cs`, `PrivateDependencyModuleNames`).
