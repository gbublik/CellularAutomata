# Orchestrator — `Orchestration/AutomataOrchestrator.*`

Continuous play, the off-thread step, chunked rendering and `StepsPerRender`. Read before touching stepping, render pacing or anything that swaps `Grid`.

## Where the code lives — one class, eighteen translation units

`AAutomataOrchestrator` is **one `UCLASS` declared in one header**, but its implementation is split across eighteen `.cpp` files in `Private/Orchestration/`. The split is by responsibility, and it is purely physical: no reflection, no Blueprint binding and no `.umap` property override is affected by which file a method sits in, because UHT reads the *header*. The header stays whole on purpose — roughly two thirds of it is doc-comments, and splitting it would scatter the documentation that makes the class readable at all.

Two things this does **not** buy, and both are worth not rediscovering. It does **not** make Live Coding safe: `LiveCoding.Compile` reinstances the whole class whenever any of its `.cpp` files is patched, and there is still exactly one class — a cold rebuild with the Editor closed remains the default. And it does **not** decouple anything: `Grid` is read or written from nearly every file (it has no cluster boundary at all), and `bStepInProgress`, `SelectedCells` and `GenerationCount` are each touched from seven or eight of them. The split makes the code navigable and cuts merge conflicts on what used to be a single six-thousand-line file that 73% of the project's commits touched; it does not change the coupling, and a later move to `UActorComponent`s would have to face that coupling unchanged.

`Photo`, `Baking` and `GhostShape` were the three clusters looked at for becoming `UActorComponent`s, against `UAutomataSonifierComponent`'s own two-part test: an independent tick, and owning `UObject` sub-state with its own lifecycle. **Only `Photo` moved** (`Automata/Photo/`, see `docs/rendering.md`) — and the other two were tried and put back, which is worth recording so the same road is not walked twice.

The test separates them cleanly once you check rather than assume. Photo genuinely needed its own tick: it polls for a file across frames while the actor's tick is off, because photographs are taken on pause. Baking and Ghost Shape need no tick at all — a bake is a one-shot action, and the ghost counter is advanced from the step path (`AdvanceGhostShape()`). What is left of the case for them is "owns a `UProceduralMeshComponent`", which is not much of a case: the orchestrator already owns three components (`CellsMeshFlat`, `CellsMeshHierarchical`, `SelectionMeshComponent`) without difficulty.

The cost, measured rather than guessed: Photo has a single entry point and owes nothing outward, whereas these two are *called into* from about a dozen places — `ClearBakedMesh()`/`ClearGhostShape()` from six files including `BeginPlay`, `RefreshGhostShape()` from two, `ShouldGhostShapeReplaceDetailedRender()` from three plus `AGamePlayerController`. Keeping those call sites unchanged means leaving ten forwarders on the actor, so the header barely shrinks. And the `friend` surface would have to grow well past Photo's: Ghost Shape wants `Grid`, `GetActiveCullVolume()`, `RenderGridImmediate()`, `CellsMeshHierarchical` and `bRenderPresetModified`; baking adds `bStepInProgress`, `SelectedCells` and `InitialStateCells`. Roughly 350 lines out, 30 lines of forwarders back, a wider `friend`, and no behavioural change whatsoever — the same "risk without gain" test that declined a shared helper in `docs/capture.md`. They stay as their own `.cpp` files, which is what actually made them navigable.

Note what the sonifier did **not** do when it became a component, and what Photo copied: it left its `UPROPERTY`s on the orchestrator and reads them through the owner. That is not an accident — a config `UPROPERTY` that moves to a component silently loses its baked override in `NewMap.umap`, with no compile error and nothing in the log. `Develope.umap` still carries `RenderCaptureResolution` and `bUseRenderLODMeshes`, properties deleted from the code long ago, as standing proof of how quiet that failure is.

Types that are not the actor's own live outside the header, per the project convention that a `UENUM` gets its own file: `EComputeMethod` (`Automata/Simulation/ComputeMethod.h`), `ECellMeshComponentType` (`Automata/Rendering/CellMeshComponentType.h`), `FCellRenderStats` (`Automata/Rendering/CellRenderStats.h`) and the HUD summaries (`Ui/HudStats.h`). Moving them changed no reflection path — those are module-scoped, not file-scoped — so `WBP_MainHud`'s bindings to `FHudStats` and its 43 fields were untouched. (That single struct has since been split into seven per-subsystem ones — see `docs/hud.md`; the split *does* touch the widget graphs, which is why the old struct stays alive and deprecated until they are re-wired.)

- **`AAutomataOrchestrator`** (`Orchestration/AutomataOrchestrator.*`) — the top-level conductor, placed in the level as an Actor. Root component is `CellsMeshHierarchical` (`UHierarchicalInstancedStaticMeshComponent`); `CellsMeshFlat` (`UInstancedStaticMeshComponent`) is attached as its child. Both are created unconditionally in the constructor and exist for the actor's whole life, though they no longer receive instances directly themselves — `CellMeshComponentType` (`ECellMeshComponentType::Instanced`/`HierarchicalInstanced`, default `HierarchicalInstanced`) now picks which of them actually receives instances (see `GetActiveCellsMeshComponent()` under `Automata/Rendering/` below); there is no separate scene-root or camera spline (that system was fully removed; `AGamePlayerController` no longer has `StartSplineMovement`/`StopSplineMovement`/spline-following `Tick`). Owns simulation parameters (`GridSize`, `ChunkSize`, `Seed`, `Speed`, `CameraSpeedMultiplier`, `CellMesh`/`CellMaterial`/`AgeColors`/`AgeColorMaxAge`/`DecayColors`/`CellSize`/`CellMeshComponentType`, `bEnableChunkedRender`/`ChunkedRenderCellsPerFrame`/`ChunkedRenderOrder`/`StepsPerRender`, `BirthCounts`, `SurvivalCounts`, `Neighborhood`) exposed as `CallInEditor` UFUNCTIONs (`Start/Pause/Resume/Stop/Next/GenerateState/NewSeed`) so designers can drive the sim from the Details panel. `BeginPlay` first wipes any instance state duplicated from the editor world (`ClearAllCellInstances()`/`ClearBakedMesh()`/`ClearGhostShape()` — PIE copies the placed actor *with* whatever instances a pre-PIE `GenerateState()`/`Next()` click left on its components, and the normal render path doesn't clear orphaned ones), then wires up the player controller, binds the cell renderer, calls `GenerateState()`, and finally shows the HUD via `InitializeHUD()`. That last call moved here **from `PostActorCreated()`** deliberately: that callback fires on any actor creation, including merely placing the actor in the editor outside PIE, and the HUD widget must never pop up outside a real game session — `BeginPlay()` is guaranteed PIE/game only. `NewSeed()` re-rolls `Seed` via `FMath::Rand()` and calls `GenerateState()`. A private `CreateGrid()` helper (always builds an `FDenseCellGrid` from `CellSize`/`ChunkSize` — see `Automata/Grid/` below) is shared by `GenerateState()`/`ResetToInitialState()`/`StartFromSelection()` (fresh grid) and `StepAsync()` (next-generation buffer) — `Next()`'s background loop is the one exception: it builds its intermediate generation buffers inside the background lambda from game-thread-snapshotted `CellSize`/`ChunkSize` copies, since `CreateGrid()` reads live UPROPERTYs a background thread must not touch (see `Next()` below). `GenerateState()`/`Next()`/`StepAsync()`→`ApplyStepResult()` all log generation-or-step and render timing (`FPlatformTime::Seconds()`) as an ad-hoc profiling baseline ahead of scaling to much larger cell counts. `Next()` builds a fresh `FCellularAutomatonRule` from `BirthCounts`/`SurvivalCounts`/`Neighborhood` every call (so Details-panel edits take effect immediately, no caching) and advances **`StepsPerRender` generations per call** (the same value the T/G hotkeys tune; at `1` it's the original single step), rendering only the final generation in one immediate shot via `RenderGridImmediate()` — intermediate generations never hit the screen, mirroring how continuous Play skips renders under `StepsPerRender`. The whole multi-generation loop runs on the thread pool exactly like `StepAsync()` (it used to be fully synchronous on the game thread, which froze the screen for the entire computation once multiplied by `StepsPerRender`): rule/strategy/`CellSize`/`ChunkSize` are snapshotted on the game thread before dispatch (intermediate generation buffers are built *in* the background lambda from the snapshotted values, constructing `FDenseCellGrid` directly rather than via `CreateGrid()`, which reads live UPROPERTYs), `bStepInProgress` guards the whole flight, and the completion hands off to the game thread to swap `Grid` and render — so the only remaining hitch on F is the render itself, same as Play. Cell storage/rendering/simulation is delegated to the `Automata/` subsystem (below), not implemented inline.

Continuous play/stop: `Start()` (also acts as the "Play" entry point) generates a grid if none exists yet, resets the tick accumulator, sets `bSimulationRunning = true`, and calls `SetActorTickEnabled(true)`. `PrimaryActorTick.bCanEverTick = true` but `bStartWithTickEnabled = false` in the constructor, so the actor doesn't tick at all until `Start()` explicitly enables it. `Tick()` accumulates `DeltaTime` and, once it crosses `1/Speed` seconds (recomputed each tick, not cached, so editing `Speed` in the Details panel takes effect immediately), calls `StepAsync()` — **not** `Next()` — provided no background step is already in flight (`!bStepInProgress`) and no render hand-off is pending (`!bRenderHandoffPending`, see `StepsPerRender` below); if either is true, that tick is skipped rather than queued. `Stop()` clears `bSimulationRunning`, calls `FinishChunkedRenderImmediately()` (see Chunked rendering below — snaps any in-progress reveal, including a pending hand-off, straight to its final state instead of leaving it frozen once ticking stops), then disables ticking; it does **not** reset the grid — stopping is not clearing, and returning to a known state is what **R** (`ResetToInitialState()`) and **N** (`NewSeed()`) already do. There used to be an empty `Clear()` next to them, a `CallInEditor` button that had never been written; it was removed rather than implemented, since nothing called it and neither hotkeys nor any Blueprint referenced it.

**`StepAsync()` — off the game thread, so continuous Play doesn't stall the camera/UI**: `Next()` (the manual `CallInEditor` button) originally stayed fully synchronous, but during continuous Play, that same synchronous cost was landing straight in `Tick()`, blocking the game thread (and therefore camera movement/input) for as long as the step took, which got severe at scale (multi-second stalls once the grid grew past hundreds of thousands of cells) — `StepAsync()` was the fix for Play, and `Next()` itself later moved to the same background-dispatch pattern too once it started computing `StepsPerRender` generations per press (see the orchestrator bullet above; the freeze that was tolerable for one step wasn't for ten). `StepAsync()` fixes this: on the game thread it first builds `FCellularAutomatonRule` from `BirthCounts`/`SurvivalCounts`/`Neighborhood`, a compute strategy via `CreateComputeStrategy()` (picks `FCpuComputeStrategy`/`FGpuComputeStrategy` per `ComputeMethod` — see `Automata/Simulation/` below), and a fresh `NextGridBuffer` via `CreateGrid()` (all three read Details-panel `UPROPERTY`s, so this snapshot has to happen before handing off — a background thread must never race a Details-panel edit), sets `bStepInProgress = true`, then dispatches `ComputeStrategy->Step(*Grid, *NextGridBuffer, AutomatonRule)` onto `Async(EAsyncExecution::ThreadPool, ...)` (`ComputeStrategy`, a `TUniquePtr`, is captured by move into the lambda exactly like `NextGridBuffer`). The CPU strategy's internal `ParallelFor` (see `Automata/Simulation/` below) still runs fine nested inside this — the calling thread is now a thread-pool worker instead of the game thread, so the game thread is free the whole time. **One dispatch is not necessarily one generation**: `StepAsync()` asks the freshly built strategy `SupportsStepBatching(Rule)` and, when it says yes (GPU, non-Generations rule), computes `StepsPerRender` generations inside that single background dispatch via the `StepBatch()` loop — the same loop and the same skip-`ComputeAges()`-when-`> 1` rule as `Next()`, holding the previous generation alive in a local `TUniquePtr` while the next is computed into a fresh buffer (built in the background from game-thread-snapshotted `CellSize`/`ChunkSize`, same as `Next()`). When it says no — the CPU strategy — `BatchGenerations` stays 1 and the previous rhythm is preserved exactly, render-skipping counter and all; collecting generations into one long block there would be identical work with coarser pacing and a longer-held `bStepInProgress`, i.e. pure loss. **The loop also breaks out the moment `StepBatch()` reports it advanced only one generation**, for the same reason applied dynamically: `SupportsStepBatching()` is answered once per dispatch, but whether a batch actually fits is decided inside `StepBatch()` from the current AABB volume, which grows with the grid. Once that volume passes the batch ceiling the batch is trimmed to 1, and without the early break the loop would grind `StepsPerRender` single steps inside one dispatch — the same work as one multi-second block, holding `bStepInProgress` (which gates R and regeneration) throughout and interrupting the chunked reveal. Observed live at ~11M live cells: one such dispatch took 7.7 s. Correspondingly `LastDispatchGenerations` is written in `ApplyStepResult()` from what actually happened, not in `StepAsync()` from what was planned — otherwise a trimmed batch would make `Tick()` wait `StepsPerRender / Speed` for a single computed generation, slowing the simulation by exactly that factor. Correspondingly, `Tick()` paces dispatches at `LastDispatchGenerations / Speed` rather than `1 / Speed`, so `Speed` keeps meaning *generations* per second instead of silently becoming *dispatches* per second once batching engages.

When the background lambda finishes, it hands off to `AsyncTask(ENamedThreads::GameThread, ...)`, which calls `ApplyStepResult()` — swaps `Grid` and immediately clears `bStepInProgress` (deliberately at the *top* of the function, right after the swap, not at the end — its scope is narrowed to exactly "a background `Step()` is reading `*Grid`", nothing about rendering) before deciding whether/how to render (see `StepsPerRender` under Chunked rendering below); `Next()` and `GenerateState()` both check `bStepInProgress` and refuse (with a warning log) to run while a background step is outstanding — otherwise a manual click during Play could swap `Grid` out from under the background thread mid-read. The game-thread→background handoff captures `this` only as a `TWeakObjectPtr` for the completion callback (guards against the actor being destroyed — e.g. level unload — while a step is in flight; the background lambda itself never touches `this` at all, only the pre-snapshotted rule/grid pointers).

**Chunked rendering — spreads `AddInstances` across multiple frames for huge grids**: even with `StepAsync()` moving the simulation step off the game thread, `Renderer->Render()`'s own `AddInstances` call is still synchronous and still runs on the game thread — profiling showed it alone taking tens to hundreds of milliseconds once the grid grows past a few hundred thousand live cells, which is enough to stall the camera for a visible frame even though the step itself no longer does. `ApplyStepResult()` only takes this path for continuous Play (`StepAsync`'s completion), gated purely by `bEnableChunkedRender` — no automatic cell-count threshold; it's a manual on/off switch (Details panel or the **Z** hotkey, see `AGamePlayerController::OnToggleChunkedRender()` above) — `Next()`/`GenerateState()` always render the whole grid in one shot, since spreading a single deliberate manual action across frames would hurt responsiveness rather than help it. When chunking triggers, the shared `RenderCurrentGrid()` helper (used by both `ApplyStepResult()`'s normal path and the deferred hand-off below) calls `Renderer->BeginRender(*Grid, ChunkedRenderOrder, CameraLocation)` (builds the full `TArray<FTransform>` and clears the component once, but adds nothing yet) and sets `bChunkedRenderInProgress = true` — `bStepInProgress` is unaffected (already cleared, see `StepAsync()` above). `Tick()` then calls `AdvanceChunkedRender()` every frame — regardless of `bSimulationRunning`, so a reveal already in progress finishes even if `Stop()` is called mid-way — which calls `Renderer->AdvanceRenderChunk(ChunkedRenderCellsPerFrame)` to add the next slice of the pre-built transforms; once the whole array has been added, it clears `bChunkedRenderInProgress` and logs how many frames the reveal took. `FInstancedMeshCellGridRenderer::Render()` itself is implemented as `BeginRender(Grid, EChunkedRenderOrder::Sequential, FVector::ZeroVector)` (order is irrelevant for a one-shot render — everything lands in the same frame regardless) followed by one unbounded `AdvanceRenderChunk()` call, so the one-shot and chunked paths share the same transform-building code without duplication.

**`EChunkedRenderOrder` — which order live cells appear in across those frames** (`Automata/Rendering/ChunkedRenderOrder.h`, its own header like `ENeighborhood`): `AAutomataOrchestrator::ChunkedRenderOrder` picks it, rebuilt/read fresh on every `BeginRender()` call, no caching — same convention as `ComputeMethod`/`FCellularAutomatonRule`. `FInstancedMeshCellGridRenderer::BeginRender()` reorders the `TArray<FIntVector>` from `GetAliveCells()` (cheaper to permute than the built `FTransform`s) before building transforms, timed as `FRenderTimings::ReorderSeconds`: **`Sequential`** (default) — no-op, `GetAliveCells()`'s own order, which for `FDenseCellGrid` is chunk-by-chunk (`TMap<FIntVector, FChunk>` iteration order), so the reveal visibly fills one spatial blob at a time before moving to the next; **`SequentialReversed`** — `Algo::Reverse` of the same order; **`Shuffled`** — one `Algo::RandomShuffle` — each frame's slice becomes a uniform-random sample of the whole grid, so the overall silhouette is visible almost immediately and subsequent frames just increase density, rather than filling blob-by-blob; **`DistanceFromCameraNearFirst`**/**`DistanceFromCameraFarFirst`** — `Algo::Sort` by squared distance from `GamePC->PlayerCameraManager->GetCameraLocation()` (`FVector::ZeroVector` if `GamePC`/its camera manager isn't set yet), ascending or descending; **`FromCenterOutward`** — `Algo::Sort` by squared distance from the midpoint of the current alive-cell AABB (computed fresh from `AliveCells` each call, not from `FDenseCellGrid`'s internal chunk grid, so the renderer stays grid-agnostic) — reveal "grows" outward from the grid's own center regardless of camera position. Switchable live via the **X** hotkey (`AGamePlayerController::OnCycleChunkedRenderOrder()` → `CycleChunkedRenderOrder()`, cycles through the enum and wraps) or directly in the Details panel.

**`bWaitForChunkedRenderToFinish` — interrupt-and-restart vs. wait-for-completion when a new generation outruns the reveal**: by default (`false`), if a new generation finishes computing while the previous chunked reveal is still spreading across frames, `ApplyStepResult()` doesn't wait for it — it immediately calls `RenderCurrentGrid()` again, which rebuilds `PendingTransforms` from scratch via `BeginRender()` on the new `Grid`, so the undrawn tail of the previous reveal simply never reaches the screen (this is the **only** behavior that existed before this property was added, and remains the default). Setting it to `true` instead gates *stepping itself*, not rendering: in `Tick()`, `bBlockedByChunkedRender = bWaitForChunkedRenderToFinish && bChunkedRenderInProgress` is added to both the `bSimulationRunning` and `bFastStepActive` step-dispatch conditions, so the next `StepAsync()` (computing the next generation) simply doesn't fire while a reveal is still in progress — `TimeSinceLastStep` keeps accumulating meanwhile, so the step fires on the very next `Tick()` once `AdvanceChunkedRender()` (called unconditionally earlier in the same `Tick()`) finishes the reveal, no explicit hand-off flag needed. Because stepping is blocked at the source, `ApplyStepResult()`'s `if (bChunkedRenderInProgress)` interrupt branch is never actually reached in this mode — the reveal is always already finished by the time a new generation is ready to render. This deliberately gates *computing* the next generation, not just its render, matching "wait for the drawing to finish, then reset/draw the new state, and only then compute the next one." Switchable live via the **V** hotkey (`AGamePlayerController::OnToggleWaitForChunkedRenderToFinish()` → `SetWaitForChunkedRenderToFinish()`/`IsWaitingForChunkedRenderToFinish()`) or directly in the Details panel — unlike `ChunkedRenderCellsPerFrame`, not gated by `bEnableChunkedRender`'s `EditCondition`, so it stays visible as a pre-configurable default the same way `ChunkedRenderOrder` does.

**`StepsPerRender` — computing generations ahead of the display, without rendering every one**: at large cell counts, even chunked `AddInstances` costs real time, and showing every single generation isn't necessary — `StepsPerRender` (default `1` = render every generation, current behavior) lets `ApplyStepResult()` skip rendering for `StepsPerRender - 1` out of every `StepsPerRender` computed generations, only calling `RenderCurrentGrid()` once the counter (`StepsSinceLastRender`, reset in `GenerateState()`/`Start()`/`StartFastStep()` for a clean count on every fresh run) reaches the threshold. `ApplyStepResult()` takes how many generations its dispatch advanced and steps `StepsSinceLastRender` — as well as `GenerationCount` and the ghost-shape counter — **by that count rather than by one**, which is what makes the batched path (see `StepAsync()` above) need no special case at all: a dispatch that lands a full batch reaches the threshold through the very same condition and renders; skipped generations just log a "рендер пропущен (X/Y)" line and return immediately, so `Tick()` can dispatch the next `StepAsync()` right away (paced only by `Speed`, same as always) — this is exactly what narrowing `bStepInProgress`'s scope (see `StepAsync()` above) enables: computing ahead no longer waits on `bChunkedRenderInProgress`. This deliberately caps how far ahead the simulation can get to **at most one batch** past what's on screen: if the `StepsPerRender`-th generation finishes computing while the *previous* one's chunked reveal hasn't finished trickling in yet, `ApplyStepResult()` doesn't interrupt that reveal (which would abandon its progress and restart from scratch) — instead it sets `bRenderHandoffPending = true` and returns, and `Tick()`'s dispatch condition also checks `!bRenderHandoffPending`, so no further stepping happens until the hand-off completes. `AdvanceChunkedRender()` checks `bRenderHandoffPending` right after finishing a reveal and, if set, immediately calls `RenderCurrentGrid()` for the (by-then possibly even more current) `Grid` and clears the flag — at which point `Tick()` is free to start the next batch. `FinishChunkedRenderImmediately()` (`Stop()`'s helper, see above) does the same hand-off check before its own flush loop, so a pending generation is never left permanently unrendered just because Play was stopped mid-wait. `GenerateState()` ignores `StepsPerRender` entirely, and both it and `Next()` always render immediately and in full, ignoring `bEnableChunkedRender`'s spreading — but `Next()` *uses* `StepsPerRender` differently than Play does: rather than skipping renders between background steps, it computes all `StepsPerRender` generations in one background batch per press and renders only the last (see the orchestrator bullet above) — same net "generations per render" ratio, different mechanism.

**`StepBackward()` — one generation back, by recomputing rather than by remembering (Ctrl+Z)**: a cellular automaton has no inverse step at all — the rule is not a bijection, so a state can have many predecessors or none (Gardens of Eden), and "undo" cannot mean "apply the rule backwards". The two remaining options are storing history or replaying it, and this project deliberately does not store history: one generation at the scale this thing runs at is hundreds of megabytes, while the ingredients for a replay are already here — `InitialStateCells` (the same return point **R** uses) plus a deterministic rule. So `StepBackward()` re-seeds a fresh grid from `InitialStateCells` on the game thread (never touching `Grid`, so the current generation stays on screen throughout), snapshots rule/strategy/lattice/`ChunkSize` exactly like `Next()`, and runs the **same `StepBatch()` loop** for `GenerationCount - 1` generations in one background dispatch, rendering only the result. That is why the naive version is affordable at all: rendering is the dominant per-generation cost (that is the entire reason `StepsPerRender` exists), and a blind replay pays none of it — replaying a few hundred generations is markedly cheaper than living through the same few hundred on screen. The cost is nonetheless **linear in the generation number**, not constant, which is the one honest caveat: a checkpoint cache (one snapshot every K generations, replaying from it rather than from zero) is the obvious next step if held/repeated undo ever becomes the normal way to use it, and was deliberately not built first — the naive version is a dozen lines and answers the "is it fast enough?" question with a measurement instead of a guess.

Three details are load-bearing. **The run is stopped** (`Stop()`, not `Pause()` — the latter is about camera control in this project) before the replay: otherwise `Tick()`'s next `StepAsync()` would overwrite the rolled-back state immediately and the press would look like it did nothing. **`GenerationCount` is assigned, not decremented**, and the graph history loses only its tail via `GenerationHistory::TrimAfter()` rather than being wiped by `ResetGenerationCounter()` — a step back is not a fresh run, and the history *before* the rollback point remains true. **The deferred path is the same one R and N use** (`bStepBackwardPending`), but it matters more here: the replay itself holds `bStepInProgress` for its whole (long) duration, so a second press landing mid-flight is the common case rather than a rare race. It is a flag, not a counter — two quick presses roll back one generation, not two, because each queued press would cost its own full replay from zero. Both discharge points (`ApplyStepResult()` and `Next()`'s completion) check it **before** advancing `GenerationCount`, since the generation that dispatch just computed was never on screen; counting it first would make the rollback return exactly what is already in `Grid`.

**What it does *not* reproduce**: the replay uses the rule as it stands *now* (`BuildRule()` re-reads the Details panel every call, per the project-wide convention), and no history of rule edits is kept anywhere. Change the rule, the neighbourhood or `States` mid-run and Ctrl+Z shows not "the previous frame" but "what generation N-1 would have been had the new rule applied from the start". Recording past rule edits would mean introducing exactly the history this design exists to avoid, so this is accepted and documented rather than fixed.

**Manual edits are the half that cannot be recomputed — `CellEditJournal` (`Automata/Editing/`)**: everything above rests on the trajectory being reproducible from `InitialStateCells` plus a rule, and a hand edit breaks exactly that — no rule replays a deletion. So the project draws the line there: the deterministic half is replayed, the non-deterministic half is *stored*, and stored as a **delta** (which cells, plus their previous alive/age/decay state), never a grid snapshot — ten thousand deleted cells is ~160 KB. Age and decay are both kept because an undo returning a cell with age 0 flashes the wrong colour, and one dropping the decay phase changes what the *rule* does next. Each record carries the generation it was made on, and that tag is what keeps `StepBackward()` correct: the journal is a **script of the current trajectory**, so the replay re-seeds and then applies each record at its own generation, and manual edits survive a rollback with no snapshot kept anywhere. One consequence inside the replay loop: the batch is trimmed at the next journal record, because `StepBatch()` computes a whole batch internally and a generation swallowed by one has nowhere to take an edit — on stretches without edits the batch stays full, near an edit it collapses to a single step. After a successful rollback the journal is trimmed like the graph history (`CellEditJournal::TrimAfter()`), for a harder reason than tidiness: an edit made at a generation the trajectory no longer reaches would be replayed again on the next rollback. `ResetGenerationCounter()` clears the journal outright, being the one funnel of every "start over" path. Painting (Shift+Tab, see `docs/selection-and-baking.md`) writes into the same journal, one record per click — stroke-painting was built and removed, so a chain of hand-placed cells is a chain of separate undos rather than one.

**One Ctrl+Z over both undos — `UndoLastAction()`**: to the user it is one action, not a choice of machinery, so the split is made from what happened last. If the newest journal record sits on the *current* generation, nothing has stepped since it, and that edit is undone by its inverse delta — instant, no recompute. Otherwise the last event was a simulation step, and `StepBackward()` handles it. Undo, step, step therefore unwinds in the order it happened. Undone edits go to `EditRedoStack` (**Ctrl+Shift+Z**), which is a separate stack rather than an index into the journal, because the journal must keep describing exactly what is in the grid — a record left in place after being undone would be replayed by the next rollback. Any new action clears the redo stack, and here that is load-bearing rather than convention: a record carries the generation it belongs to, and after a step that generation is no longer where the grid is. There is no redo for a *step* — stepping forward is what **F** already does. The journal's ceiling (`EditJournalMaxCells`, 5M cells ≈ 100 MB) is counted in cells rather than records, since one deliberate action can touch a million cells; on overflow old records are **not** dropped, because a hole in the middle of a script would make the replay wrong silently. The journal is marked incomplete instead, `StepBackward()` refuses with a reason, and undoing edits keeps working.

**Correctness note on `GamePC`**: `AGamePlayerController* GamePC` is a `UPROPERTY(Transient)`, not a raw pointer — this matters specifically because of Live Coding. Reinstancing after a hot patch during an active PIE session only copies `UPROPERTY`-tagged fields from the old instance to the new one; a plain C++ member survives as uninitialized garbage (not `nullptr`), and `BeginPlay()` — the only place that populates `GamePC` — does not re-run on reinstancing. A raw-pointer `GamePC` therefore silently held garbage after any Live Coding patch made during PIE, and `Pause()`/`Resume()` dereferencing it segfaulted (`Access violation`) the next time either was called, crashing the whole Editor process. Fixed by making it a `UPROPERTY` (so reinstancing either preserves it correctly or resets it to `nullptr`) plus explicit null checks in `Pause()`/`Resume()` that log a warning and return instead of crashing when `GamePC` isn't set yet (e.g. before `BeginPlay`/outside PIE). Any other raw non-`UPROPERTY` `UObject*` member added to `AAutomataOrchestrator` (or any `UCLASS` in this project) in the future is a candidate for the same bug.

**One tail for both ways a generation lands — `CommitComputedGenerations()`.** `Next()` (manual **F**) and `ApplyStepResult()` (continuous Play) both finish a background computation the same way, and both used to spell it out separately: swap `Grid`, drop the selection, clear `bStepInProgress`, discharge whichever of R / N / Ctrl+Z was pressed mid-flight, check extinction, then advance the counters. The order in there is load-bearing — the pending flags are discharged **before** `GenerationCount` moves, because `StepBackward()` counts from it and the generation this dispatch just computed was never on screen — which is exactly why it should exist once rather than twice. It returns **false** when a deferred action or an auto-reseed has already taken over and rebuilt the grid, so the caller simply returns without rendering. Rendering deliberately stays outside it: Play still has to take the series snapshot and decide whether this generation is drawn at all, and the manual step always draws immediately and in full.

Unifying the two turned up one place they had quietly drifted apart: `LastGpuComputeUploadBytes` was recorded *after* the pending-flag discharge in `Next()` and *before* it in `ApplyStepResult()`, so a deferred R/N/Ctrl+Z landing on a manual step dropped the figure from the HUD. It now follows Play's order in both.

The Ghost Shape counter stayed out of that tail and became its own `AdvanceGhostShape()` instead, because the two callers run it at genuinely different points — after the series capture under Play, immediately before the render on a manual step. Folding it in would have removed the duplication by reordering the snapshot against the mesh rebuild, which is a behaviour change wearing a refactor's clothes.
