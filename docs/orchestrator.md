# Orchestrator — `Orchestration/AutomataOrchestrator.*`

Continuous play, the off-thread step, chunked rendering and `StepsPerRender`. Read before touching stepping, render pacing or anything that swaps `Grid`.

- **`AAutomataOrchestrator`** (`Orchestration/AutomataOrchestrator.*`) — the top-level conductor, placed in the level as an Actor. Root component is `CellsMeshHierarchical` (`UHierarchicalInstancedStaticMeshComponent`); `CellsMeshFlat` (`UInstancedStaticMeshComponent`) is attached as its child. Both are created unconditionally in the constructor and exist for the actor's whole life, though they no longer receive instances directly themselves — `CellMeshComponentType` (`ECellMeshComponentType::Instanced`/`HierarchicalInstanced`, default `HierarchicalInstanced`) now picks which of them actually receives instances (see `GetActiveCellsMeshComponent()` under `Automata/Rendering/` below); there is no separate scene-root or camera spline (that system was fully removed; `AGamePlayerController` no longer has `StartSplineMovement`/`StopSplineMovement`/spline-following `Tick`). Owns simulation parameters (`GridSize`, `ChunkSize`, `Seed`, `Speed`, `CameraSpeedMultiplier`, `CellMesh`/`CellMaterial`/`AgeColors`/`AgeColorMaxAge`/`DecayColors`/`CellSize`/`CellMeshComponentType`, `bEnableChunkedRender`/`ChunkedRenderCellsPerFrame`/`ChunkedRenderOrder`/`StepsPerRender`, `BirthCounts`, `SurvivalCounts`, `Neighborhood`) exposed as `CallInEditor` UFUNCTIONs (`Start/Pause/Resume/Stop/Next/Clear/GenerateState/NewSeed`) so designers can drive the sim from the Details panel. `BeginPlay` first wipes any instance state duplicated from the editor world (`ClearAllCellInstances()`/`ClearBakedMesh()`/`ClearGhostShape()` — PIE copies the placed actor *with* whatever instances a pre-PIE `GenerateState()`/`Next()` click left on its components, and the normal render path doesn't clear orphaned ones), then wires up the player controller, binds the cell renderer, calls `GenerateState()`, and finally shows the HUD via `InitializeHUD()`. That last call moved here **from `PostActorCreated()`** deliberately: that callback fires on any actor creation, including merely placing the actor in the editor outside PIE, and the HUD widget must never pop up outside a real game session — `BeginPlay()` is guaranteed PIE/game only. `NewSeed()` re-rolls `Seed` via `FMath::Rand()` and calls `GenerateState()`. A private `CreateGrid()` helper (always builds an `FDenseCellGrid` from `CellSize`/`ChunkSize` — see `Automata/Grid/` below) is shared by `GenerateState()`/`ResetToInitialState()`/`StartFromSelection()` (fresh grid) and `StepAsync()` (next-generation buffer) — `Next()`'s background loop is the one exception: it builds its intermediate generation buffers inside the background lambda from game-thread-snapshotted `CellSize`/`ChunkSize` copies, since `CreateGrid()` reads live UPROPERTYs a background thread must not touch (see `Next()` below). `GenerateState()`/`Next()`/`StepAsync()`→`ApplyStepResult()` all log generation-or-step and render timing (`FPlatformTime::Seconds()`) as an ad-hoc profiling baseline ahead of scaling to much larger cell counts. `Next()` builds a fresh `FCellularAutomatonRule` from `BirthCounts`/`SurvivalCounts`/`Neighborhood` every call (so Details-panel edits take effect immediately, no caching) and advances **`StepsPerRender` generations per call** (the same value the T/G hotkeys tune; at `1` it's the original single step), rendering only the final generation in one immediate shot via `RenderGridImmediate()` — intermediate generations never hit the screen, mirroring how continuous Play skips renders under `StepsPerRender`. The whole multi-generation loop runs on the thread pool exactly like `StepAsync()` (it used to be fully synchronous on the game thread, which froze the screen for the entire computation once multiplied by `StepsPerRender`): rule/strategy/`CellSize`/`ChunkSize` are snapshotted on the game thread before dispatch (intermediate generation buffers are built *in* the background lambda from the snapshotted values, constructing `FDenseCellGrid` directly rather than via `CreateGrid()`, which reads live UPROPERTYs), `bStepInProgress` guards the whole flight, and the completion hands off to the game thread to swap `Grid` and render — so the only remaining hitch on F is the render itself, same as Play. **Still stub**: `Clear`. Cell storage/rendering/simulation is delegated to the `Automata/` subsystem (below), not implemented inline.

Continuous play/stop: `Start()` (also acts as the "Play" entry point) generates a grid if none exists yet, resets the tick accumulator, sets `bSimulationRunning = true`, and calls `SetActorTickEnabled(true)`. `PrimaryActorTick.bCanEverTick = true` but `bStartWithTickEnabled = false` in the constructor, so the actor doesn't tick at all until `Start()` explicitly enables it. `Tick()` accumulates `DeltaTime` and, once it crosses `1/Speed` seconds (recomputed each tick, not cached, so editing `Speed` in the Details panel takes effect immediately), calls `StepAsync()` — **not** `Next()` — provided no background step is already in flight (`!bStepInProgress`) and no render hand-off is pending (`!bRenderHandoffPending`, see `StepsPerRender` below); if either is true, that tick is skipped rather than queued. `Stop()` clears `bSimulationRunning`, calls `FinishChunkedRenderImmediately()` (see Chunked rendering below — snaps any in-progress reveal, including a pending hand-off, straight to its final state instead of leaving it frozen once ticking stops), then disables ticking; it does **not** reset the grid (that's `Clear()`'s job, still a stub).

**`StepAsync()` — off the game thread, so continuous Play doesn't stall the camera/UI**: `Next()` (the manual `CallInEditor` button) originally stayed fully synchronous, but during continuous Play, that same synchronous cost was landing straight in `Tick()`, blocking the game thread (and therefore camera movement/input) for as long as the step took, which got severe at scale (multi-second stalls once the grid grew past hundreds of thousands of cells) — `StepAsync()` was the fix for Play, and `Next()` itself later moved to the same background-dispatch pattern too once it started computing `StepsPerRender` generations per press (see the orchestrator bullet above; the freeze that was tolerable for one step wasn't for ten). `StepAsync()` fixes this: on the game thread it first builds `FCellularAutomatonRule` from `BirthCounts`/`SurvivalCounts`/`Neighborhood`, a compute strategy via `CreateComputeStrategy()` (picks `FCpuComputeStrategy`/`FGpuComputeStrategy` per `ComputeMethod` — see `Automata/Simulation/` below), and a fresh `NextGridBuffer` via `CreateGrid()` (all three read Details-panel `UPROPERTY`s, so this snapshot has to happen before handing off — a background thread must never race a Details-panel edit), sets `bStepInProgress = true`, then dispatches `ComputeStrategy->Step(*Grid, *NextGridBuffer, AutomatonRule)` onto `Async(EAsyncExecution::ThreadPool, ...)` (`ComputeStrategy`, a `TUniquePtr`, is captured by move into the lambda exactly like `NextGridBuffer`). The CPU strategy's internal `ParallelFor` (see `Automata/Simulation/` below) still runs fine nested inside this — the calling thread is now a thread-pool worker instead of the game thread, so the game thread is free the whole time. **One dispatch is not necessarily one generation**: `StepAsync()` asks the freshly built strategy `SupportsStepBatching(Rule)` and, when it says yes (GPU, non-Generations rule), computes `StepsPerRender` generations inside that single background dispatch via the `StepBatch()` loop — the same loop and the same skip-`ComputeAges()`-when-`> 1` rule as `Next()`, holding the previous generation alive in a local `TUniquePtr` while the next is computed into a fresh buffer (built in the background from game-thread-snapshotted `CellSize`/`ChunkSize`, same as `Next()`). When it says no — the CPU strategy — `BatchGenerations` stays 1 and the previous rhythm is preserved exactly, render-skipping counter and all; collecting generations into one long block there would be identical work with coarser pacing and a longer-held `bStepInProgress`, i.e. pure loss. **The loop also breaks out the moment `StepBatch()` reports it advanced only one generation**, for the same reason applied dynamically: `SupportsStepBatching()` is answered once per dispatch, but whether a batch actually fits is decided inside `StepBatch()` from the current AABB volume, which grows with the grid. Once that volume passes the batch ceiling the batch is trimmed to 1, and without the early break the loop would grind `StepsPerRender` single steps inside one dispatch — the same work as one multi-second block, holding `bStepInProgress` (which gates R and regeneration) throughout and interrupting the chunked reveal. Observed live at ~11M live cells: one such dispatch took 7.7 s. Correspondingly `LastDispatchGenerations` is written in `ApplyStepResult()` from what actually happened, not in `StepAsync()` from what was planned — otherwise a trimmed batch would make `Tick()` wait `StepsPerRender / Speed` for a single computed generation, slowing the simulation by exactly that factor. Correspondingly, `Tick()` paces dispatches at `LastDispatchGenerations / Speed` rather than `1 / Speed`, so `Speed` keeps meaning *generations* per second instead of silently becoming *dispatches* per second once batching engages.

When the background lambda finishes, it hands off to `AsyncTask(ENamedThreads::GameThread, ...)`, which calls `ApplyStepResult()` — swaps `Grid` and immediately clears `bStepInProgress` (deliberately at the *top* of the function, right after the swap, not at the end — its scope is narrowed to exactly "a background `Step()` is reading `*Grid`", nothing about rendering) before deciding whether/how to render (see `StepsPerRender` under Chunked rendering below); `Next()` and `GenerateState()` both check `bStepInProgress` and refuse (with a warning log) to run while a background step is outstanding — otherwise a manual click during Play could swap `Grid` out from under the background thread mid-read. The game-thread→background handoff captures `this` only as a `TWeakObjectPtr` for the completion callback (guards against the actor being destroyed — e.g. level unload — while a step is in flight; the background lambda itself never touches `this` at all, only the pre-snapshotted rule/grid pointers).

**Chunked rendering — spreads `AddInstances` across multiple frames for huge grids**: even with `StepAsync()` moving the simulation step off the game thread, `Renderer->Render()`'s own `AddInstances` call is still synchronous and still runs on the game thread — profiling showed it alone taking tens to hundreds of milliseconds once the grid grows past a few hundred thousand live cells, which is enough to stall the camera for a visible frame even though the step itself no longer does. `ApplyStepResult()` only takes this path for continuous Play (`StepAsync`'s completion), gated purely by `bEnableChunkedRender` — no automatic cell-count threshold; it's a manual on/off switch (Details panel or the **Z** hotkey, see `AGamePlayerController::OnToggleChunkedRender()` above) — `Next()`/`GenerateState()` always render the whole grid in one shot, since spreading a single deliberate manual action across frames would hurt responsiveness rather than help it. When chunking triggers, the shared `RenderCurrentGrid()` helper (used by both `ApplyStepResult()`'s normal path and the deferred hand-off below) calls `Renderer->BeginRender(*Grid, ChunkedRenderOrder, CameraLocation)` (builds the full `TArray<FTransform>` and clears the component once, but adds nothing yet) and sets `bChunkedRenderInProgress = true` — `bStepInProgress` is unaffected (already cleared, see `StepAsync()` above). `Tick()` then calls `AdvanceChunkedRender()` every frame — regardless of `bSimulationRunning`, so a reveal already in progress finishes even if `Stop()` is called mid-way — which calls `Renderer->AdvanceRenderChunk(ChunkedRenderCellsPerFrame)` to add the next slice of the pre-built transforms; once the whole array has been added, it clears `bChunkedRenderInProgress` and logs how many frames the reveal took. `FInstancedMeshCellGridRenderer::Render()` itself is implemented as `BeginRender(Grid, EChunkedRenderOrder::Sequential, FVector::ZeroVector)` (order is irrelevant for a one-shot render — everything lands in the same frame regardless) followed by one unbounded `AdvanceRenderChunk()` call, so the one-shot and chunked paths share the same transform-building code without duplication.

**`EChunkedRenderOrder` — which order live cells appear in across those frames** (`Automata/Rendering/ChunkedRenderOrder.h`, its own header like `ENeighborhood`): `AAutomataOrchestrator::ChunkedRenderOrder` picks it, rebuilt/read fresh on every `BeginRender()` call, no caching — same convention as `ComputeMethod`/`FCellularAutomatonRule`. `FInstancedMeshCellGridRenderer::BeginRender()` reorders the `TArray<FIntVector>` from `GetAliveCells()` (cheaper to permute than the built `FTransform`s) before building transforms, timed as `FRenderTimings::ReorderSeconds`: **`Sequential`** (default) — no-op, `GetAliveCells()`'s own order, which for `FDenseCellGrid` is chunk-by-chunk (`TMap<FIntVector, FChunk>` iteration order), so the reveal visibly fills one spatial blob at a time before moving to the next; **`SequentialReversed`** — `Algo::Reverse` of the same order; **`Shuffled`** — one `Algo::RandomShuffle` — each frame's slice becomes a uniform-random sample of the whole grid, so the overall silhouette is visible almost immediately and subsequent frames just increase density, rather than filling blob-by-blob; **`DistanceFromCameraNearFirst`**/**`DistanceFromCameraFarFirst`** — `Algo::Sort` by squared distance from `GamePC->PlayerCameraManager->GetCameraLocation()` (`FVector::ZeroVector` if `GamePC`/its camera manager isn't set yet), ascending or descending; **`FromCenterOutward`** — `Algo::Sort` by squared distance from the midpoint of the current alive-cell AABB (computed fresh from `AliveCells` each call, not from `FDenseCellGrid`'s internal chunk grid, so the renderer stays grid-agnostic) — reveal "grows" outward from the grid's own center regardless of camera position. Switchable live via the **X** hotkey (`AGamePlayerController::OnCycleChunkedRenderOrder()` → `CycleChunkedRenderOrder()`, cycles through the enum and wraps) or directly in the Details panel.

**`bWaitForChunkedRenderToFinish` — interrupt-and-restart vs. wait-for-completion when a new generation outruns the reveal**: by default (`false`), if a new generation finishes computing while the previous chunked reveal is still spreading across frames, `ApplyStepResult()` doesn't wait for it — it immediately calls `RenderCurrentGrid()` again, which rebuilds `PendingTransforms` from scratch via `BeginRender()` on the new `Grid`, so the undrawn tail of the previous reveal simply never reaches the screen (this is the **only** behavior that existed before this property was added, and remains the default). Setting it to `true` instead gates *stepping itself*, not rendering: in `Tick()`, `bBlockedByChunkedRender = bWaitForChunkedRenderToFinish && bChunkedRenderInProgress` is added to both the `bSimulationRunning` and `bFastStepActive` step-dispatch conditions, so the next `StepAsync()` (computing the next generation) simply doesn't fire while a reveal is still in progress — `TimeSinceLastStep` keeps accumulating meanwhile, so the step fires on the very next `Tick()` once `AdvanceChunkedRender()` (called unconditionally earlier in the same `Tick()`) finishes the reveal, no explicit hand-off flag needed. Because stepping is blocked at the source, `ApplyStepResult()`'s `if (bChunkedRenderInProgress)` interrupt branch is never actually reached in this mode — the reveal is always already finished by the time a new generation is ready to render. This deliberately gates *computing* the next generation, not just its render, matching "wait for the drawing to finish, then reset/draw the new state, and only then compute the next one." Switchable live via the **V** hotkey (`AGamePlayerController::OnToggleWaitForChunkedRenderToFinish()` → `SetWaitForChunkedRenderToFinish()`/`IsWaitingForChunkedRenderToFinish()`) or directly in the Details panel — unlike `ChunkedRenderCellsPerFrame`, not gated by `bEnableChunkedRender`'s `EditCondition`, so it stays visible as a pre-configurable default the same way `ChunkedRenderOrder` does.

**`StepsPerRender` — computing generations ahead of the display, without rendering every one**: at large cell counts, even chunked `AddInstances` costs real time, and showing every single generation isn't necessary — `StepsPerRender` (default `1` = render every generation, current behavior) lets `ApplyStepResult()` skip rendering for `StepsPerRender - 1` out of every `StepsPerRender` computed generations, only calling `RenderCurrentGrid()` once the counter (`StepsSinceLastRender`, reset in `GenerateState()`/`Start()`/`StartFastStep()` for a clean count on every fresh run) reaches the threshold. `ApplyStepResult()` takes how many generations its dispatch advanced and steps `StepsSinceLastRender` — as well as `GenerationCount` and the ghost-shape counter — **by that count rather than by one**, which is what makes the batched path (see `StepAsync()` above) need no special case at all: a dispatch that lands a full batch reaches the threshold through the very same condition and renders; skipped generations just log a "рендер пропущен (X/Y)" line and return immediately, so `Tick()` can dispatch the next `StepAsync()` right away (paced only by `Speed`, same as always) — this is exactly what narrowing `bStepInProgress`'s scope (see `StepAsync()` above) enables: computing ahead no longer waits on `bChunkedRenderInProgress`. This deliberately caps how far ahead the simulation can get to **at most one batch** past what's on screen: if the `StepsPerRender`-th generation finishes computing while the *previous* one's chunked reveal hasn't finished trickling in yet, `ApplyStepResult()` doesn't interrupt that reveal (which would abandon its progress and restart from scratch) — instead it sets `bRenderHandoffPending = true` and returns, and `Tick()`'s dispatch condition also checks `!bRenderHandoffPending`, so no further stepping happens until the hand-off completes. `AdvanceChunkedRender()` checks `bRenderHandoffPending` right after finishing a reveal and, if set, immediately calls `RenderCurrentGrid()` for the (by-then possibly even more current) `Grid` and clears the flag — at which point `Tick()` is free to start the next batch. `FinishChunkedRenderImmediately()` (`Stop()`'s helper, see above) does the same hand-off check before its own flush loop, so a pending generation is never left permanently unrendered just because Play was stopped mid-wait. `GenerateState()` ignores `StepsPerRender` entirely, and both it and `Next()` always render immediately and in full, ignoring `bEnableChunkedRender`'s spreading — but `Next()` *uses* `StepsPerRender` differently than Play does: rather than skipping renders between background steps, it computes all `StepsPerRender` generations in one background batch per press and renders only the last (see the orchestrator bullet above) — same net "generations per render" ratio, different mechanism.

**Correctness note on `GamePC`**: `AGamePlayerController* GamePC` is a `UPROPERTY(Transient)`, not a raw pointer — this matters specifically because of Live Coding. Reinstancing after a hot patch during an active PIE session only copies `UPROPERTY`-tagged fields from the old instance to the new one; a plain C++ member survives as uninitialized garbage (not `nullptr`), and `BeginPlay()` — the only place that populates `GamePC` — does not re-run on reinstancing. A raw-pointer `GamePC` therefore silently held garbage after any Live Coding patch made during PIE, and `Pause()`/`Resume()` dereferencing it segfaulted (`Access violation`) the next time either was called, crashing the whole Editor process. Fixed by making it a `UPROPERTY` (so reinstancing either preserves it correctly or resets it to `nullptr`) plus explicit null checks in `Pause()`/`Resume()` that log a warning and return instead of crashing when `GamePC` isn't set yet (e.g. before `BeginPlay`/outside PIE). Any other raw non-`UPROPERTY` `UObject*` member added to `AAutomataOrchestrator` (or any `UCLASS` in this project) in the future is a candidate for the same bug.
