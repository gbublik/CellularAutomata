# Automation tests — what each one covers

Detail behind the test-suite line in CLAUDE.md's Build / run section. Read before adding, changing or deleting a test in `Source/CellularAutomata/Private/Tests/AutomataTests.cpp`.

Twelve tests, chosen for the places where a bug is both likely and invisible. Two cover slice capture (`Slice.Orientation` — the asymmetric-figure guard against mirroring and transposition described under `Automata/Capture/`; `Slice.Raster` — nearest-wins independent of input order, exact N×N blocks under scaling, budget refusal leaving no half-result, and empty input failing honestly rather than emitting a 1×1 file). Three cover the generators (`Generation.Determinism` — same seed, same set, and a *different* seed giving a different one, since a generator that ignores the seed passes the first check perfectly; `Generation.RandomBallParity` — the golden test that `GenerateRandom()`'s refactor didn't silently shift every previously saved seed; `Generation.LatticeNeighborUniformity` — that the neighbour counts the presets promise are the counts the geometry actually has). The other four: `Grid.NegativeCoords` (chunk math on negative coordinates — the floor-division trap flagged under `Automata/Grid/`, and generation is centred on the origin so negative coordinates are the norm, plus the "a re-created chunk must not inherit stale ages" guarantee), `Rules.RuleStringRoundTrip` (`Parse → Format → Parse`, range compression, every one of the 14 neighbourhood tokens surviving print-then-parse back into itself (a gap in the token table would otherwise fall through to its `M` fallback silently), and twelve malformed strings that must each be rejected *whole* with a non-empty error — including `M2` and `E2`, rejected rather than coerced), `Compute.CpuGpuParity` and `Compute.GpuBatchParity` (differential tests — they need no known-good answer, only that two implementations agree: CPU against GPU, and one batched dispatch against N single steps, comparing live cells, ages **and** decay stages). The last two are the automated form of the manual check the batching work was verified with, and they carry `EAutomationTestFlags::NonNullRHI` plus their own `GMaxRHIFeatureLevel` check so they report "skipped" rather than fail under `-nullrhi`. `Rules.NeighborhoodShells` checks the shell model itself rather than the 14 values one by one: that each shell is exactly one `d²` class with no strays from the 5×5×5 cube it is scanned from (`(2,1,0)` at `d²=5` is the one waiting to leak in), that every value equals the union of its own shells (by set algebra, since `6+8` and `12+2` both give 14 and counting alone would not notice classes swapped), that every value stays under the 26-offset ceiling, that `Moore` still returns its original offsets in the original order, that the parity properties the face-less sets exist for still hold, and that reach is 2 exactly where far axes are present. The twelfth, `GenerationHistory`, covers the sliding window behind the HUD graph (see `Ui/` below) — and it is the reason that logic was extracted out of the orchestrator into free functions at all: the traps in it (the last sample being edited *in place* rather than appended, the rendered value being carried forward, X mapped by generation value rather than by array index) are exactly the kind that need no actor, tick or render to exercise. Note the whole run costs an editor startup (tens of seconds) — there is no fast inner loop for UE automation tests. Deliberately not covered: anything requiring an actor, a tick or a render — that is where UE tests get expensive and brittle, and it is checked by hand in PIE instead.
