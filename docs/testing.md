# Automation tests — what each one covers

Detail behind the test-suite line in CLAUDE.md's Build / run section. Read before adding, changing or deleting a test in `Source/CellularAutomata/Private/Tests/AutomataTests.cpp`.

Twenty-six tests, chosen for the places where a bug is both likely and invisible. Three cover slice capture (`Slice.Orientation` — the asymmetric-figure guard against mirroring and transposition described under `Automata/Capture/`; `Slice.Raster` — nearest-wins independent of input order, exact N×N blocks under scaling, budget refusal leaving no half-result, and empty input failing honestly rather than emitting a 1×1 file; `Slice.Tile` — the mirrored tiling turning `[0 1 2 3]` into `[0 1 2 3 2 1]`, width `2W−2`, i.e. the column past the edge must be the *penultimate* one rather than a repeat of the edge, which would lay a double line along every seam — checked on a four-colour strip, since on a flat-coloured image a mirror looks correct even when it is not). Four cover the generators (`Generation.Determinism` — same seed, same set, and a *different* seed giving a different one, since a generator that ignores the seed passes the first check perfectly; `Generation.RandomBallParity` — the golden test that `GenerateRandom()`'s refactor didn't silently shift every previously saved seed; `Generation.LatticeNeighborUniformity` — that the neighbour counts the presets promise are the counts the geometry actually has; `Generation.ParityFilter` — that the parity filter **partitions** the set rather than cuts it, i.e. `Even ∪ Odd` equals the unfiltered result *as a set* and not as a count (several generators emit the same cell more than once — `RandomBall` reject-samples with collisions — so summing lengths would prove nothing), which is what catches the trap in `FCellEmitter::Emit()` where a parity rejection must return `true`, since `false` there means overflow and would truncate the whole generator at the first node of the wrong parity; plus the closure that makes the FCC mode a lattice at all — a grid seeded on even cells must stay even *forever* under `Edges`/`EdgesFarAxes`, with `Moore` included as the counter-check that must break it, or the assertion would be vacuous). The other four: `Grid.NegativeCoords` (chunk math on negative coordinates — the floor-division trap flagged under `Automata/Grid/`, and generation is centred on the origin so negative coordinates are the norm, plus the "a re-created chunk must not inherit stale ages" guarantee), `Rules.RuleStringRoundTrip` (`Parse → Format → Parse`, range compression, every one of the 14 neighbourhood tokens surviving print-then-parse back into itself (a gap in the token table would otherwise fall through to its `M` fallback silently), and twelve malformed strings that must each be rejected *whole* with a non-empty error — including `M2` and `E2`, rejected rather than coerced), `Compute.CpuGpuParity` and `Compute.GpuBatchParity` (differential tests — they need no known-good answer, only that two implementations agree: CPU against GPU, and one batched dispatch against N single steps, comparing live cells, ages **and** decay stages). The last two are the automated form of the manual check the batching work was verified with, and they carry `EAutomationTestFlags::NonNullRHI` plus their own `GMaxRHIFeatureLevel` check so they report "skipped" rather than fail under `-nullrhi`. `Rules.NeighborhoodShells` checks the shell model itself rather than the 14 values one by one: that each shell is exactly one `d²` class with no strays from the 5×5×5 cube it is scanned from (`(2,1,0)` at `d²=5` is the one waiting to leak in), that every value equals the union of its own shells (by set algebra, since `6+8` and `12+2` both give 14 and counting alone would not notice classes swapped), that every value stays under the 26-offset ceiling, that `Moore` still returns its original offsets in the original order, that the parity properties the face-less sets exist for still hold, and that reach is 2 exactly where far axes are present. Two cover the lattice: `Lattice.OrthogonalRoundTrip` — `WorldToGrid()` must be the *exact* inverse of `GridToWorld()` at any per-axis step including an unequal Z, which is precisely the hole that existed while four hand-written divisions by `CellSize` stood in place of an inverse mapping (see `docs/lattice-and-cell-shapes.md`), plus a point taken *inside* a cell rather than at its centre landing in that cell — what the DDA pick stands on — and `WorldBoundsToCellRange()` covering every cell whose centre is in the box, asserted as a **superset** because the range is deliberately conservative while a lost cell would be a hole in the cull box's edge; `Lattice.ElongatedDodecahedronFaces` — that the twelve offsets are the actual **faces of the Voronoi cell** under a 2× Z stretch (a face towards `V` exists exactly when the midpoint to `V` is nearer the origin than any other sublattice node), which pins down both the √2 threshold and the *absence* of a face towards `(0,0,±2)`, plus BCC closure (all three coordinates of one parity, tested with `&1` rather than `%2`, which yields −1 on negatives and would silently pass), the 26-offset shader ceiling, and reach 2 — the GPU batch halo is computed from it, and an understated one silently drops border cells. `Rendering.ColorRamp` sweeps all four colour spaces against both curves and asserts that a key stop returns the key itself within 1/255: that is the only thing that catches a broken there-and-back conversion, which otherwise shows up as a barely perceptible hue shift across the *whole* ramp and is indistinguishable from an intended colour. Alongside it: nothing outside `[0,1]` and no NaN (Catmull–Rom overshoots the key range by construction, and a NaN check must come first, since comparisons against NaN are all false), the degenerate inputs the settings panel relies on (an empty ramp is "material as-is", i.e. white; a single key gives itself at any `T`), and a guard that the middle of a red→blue ramp actually *differs* between LinearRgb and Oklab — without it an implementation that ignores the space setting entirely would pass everything else. Grey sits in the key set on purpose: it has no defined hue, and that is where a naive Oklch breaks (`atan2` of zero gives an arbitrary angle). The last, `GenerationHistory`, covers the sliding window behind the HUD graph (see `Ui/` below) — and it is the reason that logic was extracted out of the orchestrator into free functions at all: the traps in it (the last sample being edited *in place* rather than appended, the rendered value being carried forward, X mapped by generation value rather than by array index) are exactly the kind that need no actor, tick or render to exercise. The normalisation added on top of it is tested the same way and for the same reason: that `P(n)/n^d` really is flat on a set that grows as a clean power, that the fitted exponent comes out exactly 3 on `n³` and returns 0 rather than a NaN when there is nothing to fit, that generation 0 is dropped from *both* series at once (leaving them the same length) and takes the window's left edge with it, and that the axis segment never collapses to zero width — it is divided by. `TrimAfter()` (the rollback behind Ctrl+Z, see `StepBackward()` in `docs/orchestrator.md`) is tested here too, and what it guards is the *asymmetry*: the samples after the rollback point go, the ones before it stay — that is the whole difference from `ResetGenerationCounter()`, which clears the graph outright because it means "a new run", and getting it wrong would silently blank the history on every press. Plus the two ends: rolling back to generation 0 leaves one sample rather than an empty graph, and trimming above the window is a no-op (a press right after loading a file, where the counter is ahead of the history).

`Editing.EditJournal` covers the *other* half of Ctrl+Z — the manual edits, which no rule can recompute and which are therefore the one thing this project does store (as deltas, see `CellEditJournal`). Three properties, each of which fails invisibly rather than loudly: that undo restores a cell **whole** — age and decay phase included, since a returned cell with age 0 flashes the wrong colour and a lost decay phase changes the *rule's* subsequent behaviour, neither of which looks like a bug in the undo; that a record holds only the cells an edit actually touched, so the journal grows with the edit rather than with the marquee (dead cells inside the selection, and cells already alive when adding, are dropped); and that replaying a journal onto a fresh seed reproduces what the live edits produced — the property the whole "recompute forward through the edits" rollback rests on, checked by running both and comparing. The trim ends are checked the same way as the graph's: an edit exactly on the rollback point survives, one past it does not.

`Sonification.Curve` covers the measurement behind the audio (see `docs/sonification.md`) — free functions over a synthetic sample window, so no actor, tick, render or audio device is involved, which is exactly why the maths was extracted out of the component in the first place. Three of the twelve sections carry the weight. **The same exponential measured with holes punched in it must give the same slope to 1e-4**: that is the whole promise that the window lives by generation number rather than array index, and it is what makes the measurement survive `StepsPerRender`, GPU batching and the fast step — the very mechanisms that make the sample series irregular. **Two histories differing by a factor of 1000 in population must agree on slope, bend and oscillation**: the promise that sound describes the *shape* of a run and not the size of the grid, without which every rule on a big grid would sound the same. And the trap: **linear growth `50·n` must classify as `Growth`, not `Saturation`** — in log space `N = a·n` has slope `1/n`, positive, decaying, with negative bend, i.e. bit-for-bit the signature of a curve levelling off, and only the fitted growth exponent (exactly 1.0 for a clean power law, well below it for something running out of steam) tells them apart. A regression there would not fail loudly; it would just quietly make every linear run sound like it was dying. Around them: the slope of a doubling-every-five-generations run coming out as `ln2/5` (units, without which every threshold would be tuned against nothing), saturation, explosive growth, collapse and oscillation each landing in their own branch — oscillation in particular asserting that "pacing on the spot" and "standing still" are *different* sounds, since a boiling equilibrium and a dead one have the same slope and differ only in path length. Then the degenerate ends, which are where silent NaN lives: extinction must leave every field finite (one `ln(0)` would poison everything downstream and the sound would go quiet forever with nothing in the log), an empty or single-sample history must report "nothing to measure" rather than a measured zero growth (the same contract as `FitGrowthExponent()`), and a window whose samples all sit on **one** generation must not divide by zero — not a hypothetical, since `NoteRendered()` edits the last sample in place and the renderer fires on every camera move with the view slice on, so a paused window really does collapse to a single X. One section checks the sample floor: at a 256-generation stride a 64-generation window catches nothing at all, and it must widen backwards instead of reporting no data while the data is right there. The last one pins `SmoothTowards()` to its semigroup property — two steps of `Tau/2` equalling one of `Tau` — which is the formal statement that the sound does not depend on how the frame time happened to be sliced, and the reason it is `1 − exp(−Dt/Tau)` rather than a `Lerp`.

Note the whole run costs an editor startup (tens of seconds) — there is no fast inner loop for UE automation tests. Deliberately not covered: anything requiring an actor, a tick or a render — that is where UE tests get expensive and brittle, and it is checked by hand in PIE instead.

`Rendering.VisibilityFilter` is the newest, and it exists because the thing it covers used to be a **copy**. The three cuts that decide what reaches the screen — cull volume, view slice, age filter — were written out twice, once in `BuildCellRenderData()` and once in `ComputeVisibleCellsBounds()`, with the invariant between them held by a comment reading "change one of the three filters — change both places". That is the kind of invariant that goes first. Both now share `CellVisibility::FFilter` (`Automata/Rendering/CellVisibilityFilter.h`), and what the test pins down is the part that is easy to get subtly wrong rather than obviously wrong: that a *disabled* slice passes everything (its `Origin`/`Forward` are left at defaults, so a dot product against them answers nothing meaningful — the guard has to come first); that the depth window really is distance ± half thickness with **inclusive** bounds, which is what both original copies did (`Depth < Min || Depth > Max`) and what decides whether a cell on the exact edge of the slice flickers; that depth is measured *along the view direction* rather than as distance to the camera, checked by moving a point far sideways and requiring it to stay in the slice — with a length instead of a dot product it would drop out, and on screen that reads as a slice bowed into a sphere; that a disabled age filter is not the same thing as "age 0 selected", since 0 is a legitimate layer (cells just born) and confusing the two would hide the most visible layer every time the filter is cleared; and that the two filters are independent, because in the loop they are two separate `continue`s ordered by cost rather than by meaning. The predicates are `FORCEINLINE` in the header on purpose — they run per cell, i.e. millions of times a frame, and an exported function across a module boundary does not inline; the `.cpp` holds only the once-per-render assembly. Being a POD, `FFilter` needs no actor, tick or render to exercise, which is the whole reason the extraction took this shape.

`Input.HotkeyRegistry` guards the key table itself, and it is worth being precise about what makes it more than a spelling check. The table is indexed by `EHotkey` *directly* — `KeyFor()` looks up by the enum's integer value — so its length and order are correctness conditions, not formatting: a row forgotten while adding a hotkey shifts every key after it by one, which shows up as "half the layout moved", not as one missing binding. So the test asserts the row count equals `EHotkey::Count`, that row *i* really describes hotkey *i*, that no default key is `EKeys::Invalid` (a hotkey that silently does nothing), and that no two action names collide (two rows under one ini name are indistinguishable, and the second would quietly take the first's key). It also asserts the default layout does not collide with itself — skipping the pairs marked `bModifierGuarded`, which share a key on purpose (Ctrl+Z against bare Z), because a warning that always fires is one nobody reads — and then checks the checker, by feeding `FindConflicts()` a table where every key is the same and requiring it to notice; without that, the empty result above would prove nothing. `AgeFilter0..9` get their own assertion that they run consecutively and in order, since `InputKey()` reaches them by arithmetic (`AgeFilter0 + Digit`) rather than by name.

`Generation.LifePattern` guards the 2D→3D transfer (see `docs/generation.md`), and what it checks is **the arithmetic, not the coordinate tables** — those the eye checks the moment a glider flies. For every cell of every shipped pattern it counts Moore-8 neighbours in the flat pattern and Moore-26 in the extruded prism, and requires exactly `2N+1` where the cell is alive and `2N` where it is empty. That identity *is* the derivation of the `5,7/6` rule from B3/S23; if it fails anywhere, the numbers in the rule preset are simply wrong, and nothing else in the project would ever say so. Around it: the estimate must be exact (a fixed table times the layer count leaves nothing to estimate), there must be exactly two layers, and the layers must be *identical* — an extrusion is a copy, not a new figure. The Gosper gun gets its own section for the **threshold**: a cell above the prism sees only the neighbouring layer, so an empty cell with six 2D neighbours would start the gun growing upward instead of firing. The test finds the densest empty cell and logs the number — currently **4** against a threshold of 6, which is the whole answer to "will the gun work", available without running a single generation.

`Generation.StabilityWindow` covers the cheap trigger of the stasis detector (`FStabilityWindow`, see `docs/generation.md`), and what it mostly guards is the detector *not* firing early — the costs are asymmetric: a missed stasis wastes a few seconds of search, a false one throws away a seed that might have been the find. So: an immature window is never stable, even with every sample equal (two identical samples at the start of a run must not condemn a structure that hasn't begun); a single change inside the window clears stability until it scrolls off the end; and the tolerance is a *spread* rather than equality with the previous sample, since at `StepsPerRender > 1` an oscillator lands in successive samples on alternating phases and per-neighbour equality would catch none of them. Then `Clear()` must forget the samples but keep the capacity — every new seed goes through it, and the window has to mature again rather than declare stasis on its first sample — and a capacity below two is raised to two, because a one-sample window has no spread and would be stable always.

`Editing.Clipboard` covers copy/paste geometry (`CellClipboard`, see `docs/selection-and-baking.md`) — a module whose failures never throw and never log, they just put the pasted figure in the wrong place. The load-bearing assertion is that along the face normal the buffer is **pressed against** the surface rather than centred on it: an eleven-cell-tall figure pasted onto a floor must stand *on* it, and centring would bury five layers under it — checked from above, from below, and from a side face, that last one separately because a swapped axis looks entirely plausible. Around it: normalisation must move a piece cut a thousand cells from the origin to sit around zero while preserving its extents (it is a translation, not a rebuild); a zero normal means "nothing to press against", so the buffer centres on the point; `Place()` is a shift and nothing more; and the empty buffer answers honestly — `ComputeBounds()` returns false rather than inventing an extent. The 90° rotation is checked by four properties rather than by coordinates, on a figure deliberately asymmetric on all three axes (on a symmetric one a swapped axis or sign is invisible): four turns are an identity **bit for bit** — the point of quarter turns on a lattice, since any rounding would accumulate and the circle would not close; a turn and its reverse cancel, which is the only place a wrong sign in the reverse formula shows, as it has its own formula rather than being three forward turns; the bounds **swap** on the two axes crossing the rotation, which is what a mirror would not do; and a single turn must change *something*, or a do-nothing implementation would pass everything above. Then the creep guard: eight successive turns of an even-sided buffer must leave it centred on zero, since rotation about zero puts an even side's centre half a cell off and the drift would only become visible around the tenth press.

`Selection.PickFaceNormal` covers the entry-face normal the DDA pick now returns — what draw mode's "stick to the face you clicked" stands on (see `docs/selection-and-baking.md`). A wrong **sign** puts the new cell *inside* the structure, a wrong **axis** puts it beside where you aimed; neither throws, both are visible only as a cell appearing in the wrong place. So the sign is asserted not against a constant but by its consequence: the placed cell must be nearer the camera than the cell that was hit, from all six directions. The anti-vacuity case is the diagonal ray — every axial case would pass an implementation that summed the last two steps' normals, so a slanted ray must still yield a normal on exactly **one** axis, since there is no diagonal face to enter through. Two degenerate answers complete it: a ray starting *inside* the hit cell yields a **zero** normal (no entry face exists — a meaningful answer the caller must distinguish, or it would place a cell inside itself), and a miss clears the normal rather than leaving whatever the caller passed in.

`Generation.ArrayModifier` covers the Array modifier (`CellArrayModifier::Tile()`, Ctrl+D — see `docs/generation.md`). The source everywhere is two cells in a row, chosen because that is where the module's one real trap shows: a set's *size* is `Max − Min + 1`, so the flush step is 2 and not 1, and the off-by-one makes every copy overlap its neighbour by exactly one cell — invisible in a cell count, which is why the flush case asserts the six-cell contiguous run as a **set** rather than `Result.Num() == 6`. Around it: `Count = 1` on every axis must be an identity *including* the centring shift (otherwise a set would drift off the source for no reason on any axis not being multiplied); `ConstantOffset` must add on top of the relative step, which is the difference between "the copies fused into one body" and "they stand next to each other" as far as the rule is concerned; centring at an odd `Count` must put the array's centre exactly on the source's; and the estimate must be a genuine *upper* bound, checked on deliberately overlapping copies, since the refusal against `MaxGeneratedCells` happens before the grid is touched and an understated estimate would mean a wiped state instead of an honest refusal. The degenerate ends are the usual two: an empty source yields an empty result rather than a set of zeroes, and `Count ≤ 0` — reachable from Blueprint past the `ClampMin` — reads as 1, because "zero copies" would mean a silently erased scene.

`Persistence.CenteringOffset` covers the translation a `.casave` gets on the way out (`AutomatonStateSerializer::ComputeCenteringOffset()`, see `docs/persistence.md`). Two of its three sections carry weight, and only one of them is about centring. The obvious one — the AABB centre landing at the origin — is checked on a pattern deliberately placed thousands of cells away and asymmetric on every axis, because a sign error is invisible on a set already centred on zero. The one the test exists for is **parity**: the offset must be even on each axis, so that an FCC/BCC pattern (see `ECellParityFilter`) stays on its own sublattice. That failure is silent in the worst way — the file opens, the picture looks identical, and only the next reseed (N/Y) lands on the wrong sublattice and misses the structure entirely — so it is asserted twice over, once on the offset itself and once as the property that matters: sweeping the pattern's position through seven consecutive shifts, both the parity of the coordinate *sum* (`Even`/`Odd`) and the agreement of parities *between* coordinates (`SameParity`) must survive the move. The third section is the totality guard: an empty set yields a zero offset rather than indexing `Cells[0]`. It is unreachable through `WriteStateToFile()`, which refuses earlier, but the function is public.

The last part is the one that actually proves the feature works. `ResolveKeys()` returning the right keys means nothing while `DefaultInput.ini` merely repeats the code defaults — the config could be ignored entirely and every assertion would still pass. So the test reads `UInputSettings::GetActionMappings()` itself and requires that wherever a `CA_*` row exists there, the resolved key **is** that row's key rather than the compiled-in default; and if no `CA_*` row exists at all it says so as a warning instead of passing quietly. That was verified once by hand in the only way that settles it: `CA_ToggleGhostShape` was set to `F9` in the ini against a code default of `H`, and the test stayed green — which it could only do by having followed the config.
