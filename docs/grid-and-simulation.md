# Grid and simulation — `Automata/Grid/`, `Automata/Simulation/`

Cell storage, the 14 neighbourhoods and their four shells, rule-string parsing, and Generations decay. Read before adding a neighbourhood, a rule-string token or a storage backend.

- **`Automata/Grid/`** — `FCellGrid` (`CellGrid.h`, abstract, plain C++ not `UObject`): stores live cells addressed by integer `FIntVector` coordinates, decoupled from rendering. `GetAliveCells`/`SetAlive`/`Clear`/`Num` are pure virtual; `GridToWorld(FIntVector)` is **virtual with a default cubic-lattice implementation** (`Cell * CellSize`) — deliberately virtual so a future non-cubic topology (e.g. hex) can override just the coordinate-to-world math without touching storage or rendering. `FDenseCellGrid` (`DenseCellGrid.*`, chunked: space is divided into fixed-size cubic chunks — default `ChunkSize=16`, i.e. 4096 cells — each a packed `TBitArray`; chunks live in a sparse `TMap<FIntVector, FChunk>` and are lazily created on first live cell / pruned when they empty out, so memory scales with occupied volume, not a fixed upper bound) is the sole concrete implementation, unconditionally constructed by `CreateGrid()` from `CellSize`/`ChunkSize`. An earlier `FSparseCellGrid` (`TSet<FIntVector>`-backed) existed alongside it, selectable via an `AAutomataOrchestrator::GridStorageStrategy` enum property — both were removed to simplify the storage layer down to one implementation; if a sparse/scatter-friendly storage is ever needed again, reintroducing it as a second `FCellGrid` subclass is straightforward since the interface is already storage-strategy-agnostic everywhere else (`FCpuComputeStrategy`/`FGpuComputeStrategy`/`FInstancedMeshCellGridRenderer` only ever go through `GetAliveCells()`/`SetAlive()`/`GridToWorld()`). **Correctness note if touching `FDenseCellGrid`**: chunk-coordinate math needs real floor-division/positive-modulo helpers (defined file-local in `DenseCellGrid.cpp`) because cell coordinates routinely go negative (sphere-centered generation) and `FMath::DivideAndRoundDown` is *not* floor division for integers (it truncates toward zero). Chunk granularity is intentionally the unit future CPU/GPU per-chunk dispatch would parallelize over — not implemented yet. `FCellGrid` also declares `GetAge(FIntVector)`/`SetAge(FIntVector, uint8)` — a per-cell saturating byte counting how many consecutive generations that cell has survived (`0` = just born), used by the `AgeColors` ramp when colouring instances (see `Automata/Rendering/` below). `FDenseCellGrid::FChunk` stores this as a parallel `TArray<uint8> Ages` alongside `Bits`, indexed identically via `CellToLocalIndex()` — zero-initialized on lazy chunk creation and wiped wholesale (along with the rest of the chunk) when a chunk empties out and gets pruned, so a cell reborn later in a freshly-recreated chunk always starts at Age 0, never inheriting stale history. Age is deliberately **not** computed inside either compute strategy — `Automata/Simulation/CellAging.h/.cpp`'s `CellAging::ComputeAges(const FCellGrid* OldGrid, FCellGrid& NewGrid)` is a separate post-`Step()` pass, called from `Next()` and from `StepAsync()`'s background lambda right after `ComputeStrategy->Step(...)`, that diffs every alive cell in `NewGrid` against `OldGrid` (`Age = OldGrid->GetAge(Cell)+1` if it was already alive there, else `0`) purely through the public `FCellGrid` interface — this means `FCpuComputeStrategy`, `FGpuComputeStrategy`, and the `.usf` shader needed **zero changes** to support aging. `GenerateState()` needs no `ComputeAges()` call at all — a freshly created grid's chunks zero-init `Ages` on their own, so newly spawned cells are already Age 0 for free. Safe to fully parallelize (unlike the `SetAlive`/`WriteBack` sequential phase elsewhere) because `SetAge` only ever writes distinct bytes at distinct array indices, never touching the `TBitArray`/`AliveCount` that actually need serialized writes.

- **`Automata/Simulation/`** — `ENeighborhood` (`Neighborhood.h`, `UENUM`) — deliberately its own header rather than folded into `AutomataOrchestrator.h`, so the simulation subsystem owns its own type. It is **one concept, with no separate radius**: each of its 14 values names a set of *shells*, and the set fixes both which cells count as neighbours and how far the rule reaches.

**Four shells are the entire design space, and knowing that is what keeps a fifteenth value from being invented.** Every offset worth having falls into one of four classes, told apart by squared length: faces `d²=1` (6, ±1 on one axis), edges `d²=2` (12), corners `d²=3` (8), far axes `d²=4` (6, ±2 on one axis — "skip a cell"). Of the 15 non-empty subsets, **14 are enum values** — `VonNeumann` is faces, `Moore` is faces+edges+corners, `VonNeumann2` is faces+edges+far axes, and the rest are named for their contents. The one missing subset is all four at once: they total **32** against a shader array of **26**, and — the fact that settles it — *no subset sums to anything between 27 and 31*, so raising that array short of the mask rework would buy literally nothing. Everything at 32 or beyond (all four shells, the Euclidean radius-2 ball which is also exactly 32, Moore r=2 at 124, von Neumann r=3 at 62) hits the 32-bit `BirthMask`/`SurvivalMask` and needs them reworked first. The geometry itself lives in exactly one place, `GetNeighborhoodShellMask()`, which `BuildNeighborOffsets()` merely expands — so a new neighbourhood is one line there plus one row in the parser's token table.

**There used to be a separate `NeighborhoodRadius`, and removing it was a simplification, not a feature cut.** Radius > 1 only ever worked for von Neumann, and von Neumann radius 2 is *precisely* faces+edges+far axes — i.e. the whole mechanism served one set that the shells already express. Moore r=2 was expressible by radius but never fit, so it never worked either way. The removal also deleted a constraint the parser had been carrying: trailing digits were stripped as a radius, which forbade any token ending in a digit. Now names are compared whole, so `VN2` is simply a name. Saved files are migrated on load — a `.casave` written with `VonNeumann` + `NeighborhoodRadius=2` maps to `VonNeumann2`, since otherwise it would silently reload as plain von Neumann with 6 neighbours instead of 24; `FAutomatonSaveHeader::NeighborhoodRadius` survives as a read-only legacy field for exactly that.

**What the shapes are for.** `FacesEdges` is the geometric prize: `d² ≤ 2` is the exact midpoint between von Neumann's `d² ≤ 1` and Moore's `d² ≤ 3`, and it grows a **rhombic dodecahedral** front — the third classic polyhedron, which neither of the familiar two produces. The shell sets that omit faces earn their place structurally instead: `Edges` preserves the parity of `x+y+z`, so the lattice splits into **two** mutually invisible sublattices (these are the FCC nearest neighbours); `Corners` flips every coordinate's parity each step, splitting it into **four**; `FarAxes` preserves the parity of *each* coordinate, splitting it into **eight** — inside any one of them it is literally von Neumann on a lattice of twice the spacing. All of these render as sparse crystal rather than solid. Two identities are worth remembering because they orient the whole table: `EdgesFarAxes` is exactly the Manhattan shell `|d| = 2`, i.e. **`VonNeumann2` with its interior removed**, and `EdgesCornersFarAxes` has the same 26 offsets as `Moore` built from entirely different shells — a direct "26 against 26" comparison at equal cost.

**Reach comes from the offsets, never from a stored number — `GetNeighborExtent()`.** Sets containing far axes reach *two* cells while everything else reaches one, and the GPU batch halo is sized from reach: `StepBatch()` uses `Extent × NumSteps`. `FCellularAutomatonRule` therefore computes the extent as the largest component magnitude over the actual offset list. Deriving it from the geometry rather than storing it alongside is what makes any future neighbourhood correct for free, and the failure mode it guards is invisible — too small a halo silently drops border cells, with no crash and no log line. `Compute.GpuBatchParity`'s `FarAxes` case exists solely for this: it is the one case where reach (2) exceeds what a naive "one cell per generation" assumption would give.

**Cost is linear in the offset count and nothing else.** `Pack`/`Unpack`/`GetAliveCells` do not change with the neighbourhood at all (they are per live cell), and the CPU candidate buffer is `alive × (offsets+1) × 12` bytes, so a 24-offset set is *cheaper* than the 26-offset Moore this project runs by default. The only thing reach costs is batch length: at extent 2 the halo doubles, so `StepsPerRender` starts getting trimmed roughly twice as early. Not one line of the `.usf` has changed across any of this work.

**`RuleStringParser` (`Automata/Simulation/RuleStringParser.h/.cpp`, plain namespace like `CellAging`) — string notation as a convenience layer, not a replacement**: parses `"Survival/Birth/States/Neighborhood"` (e.g. `"0-6/1,3/2/VN"`, `"13-26/13-14,17-19/2/M"`) — the exact format used by williamyang98/3D-Cellular-Automata (itself following Softology): Survival/Birth are comma-separated lists whose elements are single counts or inclusive `x-y` ranges, States is the total cell-state count (`>= 2`), Neighborhood is a short or long name from the `NeighborhoodTokens` table (`VN`/`VonNeumann`, `M`/`Moore`, `VN2`/`VonNeumann2`, `E`/`Edges`, `C`/`Corners`, `FA`/`FarAxes`, `FE`/`FacesEdges`, `FC`, `FFA`, `EC`, `EFA`, `CFA`, `FCFA`, `ECFA`), case-insensitively. That one table serves parsing, printing *and* the error message, so the three cannot drift apart when a neighbourhood is added. Names are compared whole — `VN2` is a name, not "VN with a digit" — which is only possible because the separate radius is gone. The digit is taken by stripping trailing digits off the token rather than by a separator, so `VonNeumann` parses through the same code as `VN`; its absence means radius 1, and `FormatRuleString()` symmetrically omits the digit at radius 1 — that pairing is what keeps every previously written rule string, and all 14 `RulePresets` entries, parsing *and* printing byte-identically to before radius existed. This is **not** a reversal of the "no rule string" decision above — that was specifically about Conway notation breaking on two-digit neighbor counts; explicit `,`/`-` separators are unambiguous at any digit count. `ParseRuleString()` fills a result struct or fails with a human-readable error and touches nothing (never applies a rule half-way); `FormatRuleString()` is the inverse, re-compressing count lists into ranges (`1,2,3,7` → `1-3,7`). `AAutomataOrchestrator::RuleString` (`UPROPERTY`) plus `ApplyRuleString()`/`TryApplyRuleString()` are the only consumers — they overwrite `BirthCounts`/`SurvivalCounts`/`States`/`Neighborhood` **by field name, never positionally** (the string's field order is Survival-then-Birth, the opposite of those properties' declaration order — blind positional assignment would silently swap them). `GetActiveRuleString()` reports the *effective* rule by formatting those four properties, rather than echoing `RuleString`, which may be empty (rule built from the arrays in the Details panel) or stale (arrays hand-edited afterwards).

**`States` / Generations — multi-state decay**: `States == 2` (default) is the classic binary automaton and behaves bit-identically to how the project worked before this existed. `States > 2` enables "Generations": a cell that stops surviving doesn't die outright but decays through states `2, 3, ..., (States-1)` on its way to 0 (fully dead), and while decaying it is **birth-immune** — it can be neither revived nor killed, it just walks down at a fixed rate. Only state 1 (fully alive) counts as a live neighbor. Decay state is a **separate storage channel from `Age`** (see `FCellGrid::IsDecaying()`/`GetDecayState()`/`SetDecayState()`): `Age` is cosmetic, monotonic, and meaningful only for live cells; decay state affects the rule itself and is meaningful only for non-live ones. `FDenseCellGrid::FChunk` holds it as a third parallel `TArray<uint8> DecayStates` next to `Bits`/`Ages`, allocated **only** when the grid was constructed with decay enabled (`CreateGrid()` passes `States > 2`) — at `States == 2` it stays a default-empty `TArray` with no heap allocation at all, so the feature costs literally nothing in the common case. `ClampMax = 255` on `States` is not decorative: the state is a `uint8`.

Advancing decay is `CellDecay::AdvanceDecayStates(OldGrid, NextGrid, MaxStates)` (`Automata/Simulation/CellDecay.h/.cpp`) — a post-`Step()` pass alongside `CellAging::ComputeAges()`, working purely through the public `FCellGrid` interface so it doesn't care whether the generation was computed on CPU or GPU. Unlike `ComputeAges()` it is **not** parallelized: `SetAge()` is safe to call concurrently because the cell is already alive in the new grid (its chunk was created by the sequential write-back phase), whereas a decaying cell is typically *not* alive there and needs a lazy chunk creation — and `TMap::Add()` is not thread-safe even for disjoint keys. Both compute strategies needed only a narrow change for birth-immunity: the CPU strategy gained one short-circuit branch, and the GPU shader a second input bit-plane (`InputDecayBits`, "is decaying") gated by a `bDecayActive` uniform, bound to the same buffer as `InputBits` when inactive so no second allocation happens at `States == 2`. Rendering colours decay stages from their own `DecayColors` ramp (see `Automata/Rendering/` below). `States` round-trips through `.casave` as its own header field.
