# Rendering — `Automata/Rendering/`

The instanced renderer, distance culling, the cull volume, render presets, Ghost Shape and the F10 photograph. Read before changing what reaches `AddInstances`.

- **`Automata/Rendering/`** — `FCellGridRenderer` (`CellGridRenderer.h`, abstract, plain C++): `Render(const FCellGrid&, TArray<FCellRenderInstance>&&)` — *what* to draw is an explicit list of position+colour, not the grid itself (colour depends on age/decay, which is the orchestrator's policy, and an explicit list also covers drawing a subset without wrapping the grid); the grid stays in the signature only for `GetCellSize()`, still passed per-call rather than owned. `FInstancedMeshCellGridRenderer` (`InstancedMeshCellGridRenderer.*`) is the only concrete implementation: wraps a `UInstancedStaticMeshComponent*` (owned by the Actor, not this class), with `SetMesh`/`SetMaterial` setters called fresh before each `Render()` since those are designer-editable properties. Scales each instance so the mesh's actual bounding-box size matches `CellSize` (via `UStaticMesh::GetBounds()`), so grid cells tile evenly regardless of the assigned mesh's native dimensions. `AAutomataOrchestrator` holds exactly one (`CellsRenderer`) plus one for the selection overlay, via the **concrete** type, not the abstract base, since mesh/material setters aren't part of the abstract interface. **Perf-critical**: `Render()` builds a `TArray<FTransform>` for every alive cell and adds them in one batch via `UInstancedStaticMeshComponent::AddInstances(..., bUpdateNavigation=false)` rather than calling `AddInstance()` per cell — the per-call form rebuilds internal instance buffers on every invocation and showed catastrophic super-linear scaling under profiling (~1789x slower for only 54x more cells at ~45k cells). Both `CellsMeshFlat`/`CellsMeshHierarchical` also have collision disabled (`SetCollisionEnabled(ECollisionEnabled::NoCollision)` in the orchestrator's constructor) since automaton cells are purely visual — measured combined effect (batching + no collision) was a ~37x reduction in total render time at ~45k cells.

**`CellMeshScaleMultiplier` — how much larger than its cell the mesh is drawn** (default `1.0`, i.e. exactly cell-sized). It has to be a property rather than an authoring choice on the asset, because the renderer **normalises the mesh's own bounds away**: `InstanceScale = FVector(CellSize) / MeshBoundsSize`, so the world size is always `CellSize × ScaleMultiplier` no matter how the asset was modelled. It exists for the FCC mode (see `ParityFilter` under `Automata/Generation/`): on that sublattice neighbours sit `√2·CellSize` apart and the Voronoi cell is a **rhombic dodecahedron whose bounding box is exactly `2·CellSize`** — check by volume, a cube of side `S` plus six pyramids of base `S²` and height `S/2` gives `2S³`, matching the sublattice density of one point per two unit cells. So an RD mesh plus a multiplier of `2.0` tiles space with no gaps, while the default cube at `1.0` leaves the cells touching only along edges (still a correct lattice, just an airy-looking one). Applied in both render paths next to `SetMesh`/`SetMaterial`, so it takes effect on the next render like `CellSize` itself; the selection overlay keeps its own `SelectionScaleMultiplier`, deliberately separate since its `1.1` is about z-fighting against whatever size the cell happens to be.

**`CellBorderWidth` — the cell outline is *computed*, not painted, and that is what makes it survive distance.** The material draws a border on each face from the UV distance to the face edge (`d = min(u, 1-u, v, 1-v)`), so there is no mask texture at all. Two properties fall out that a painted mask cannot have: screen-space derivatives (`ddx`/`ddy`) keep the edge exactly one pixel wide at any distance with no mip chain and no shimmer, and the border **fades out** once a cell shrinks below it — otherwise the far field would flood with border colour instead of showing the age ramp, which is precisely how the painted version failed. `d` runs 0 at the edge to 0.5 at the face centre, so `0.04` is a border 8% of the way in.

The geometry cooperates exactly: on a **rhombus** all four sides are equal, so the perpendicular distance between *both* pairs of opposite sides is the same (`area / side` — measured 0.816497 on the actual asset), which means a constant UV inset yields a **constant world-space border width** on all four edges. The √2 diagonal ratio distorts a bitmap pattern but is irrelevant here, which is why the aspect-correct unwrap variant was not needed.

**The value reaches the material through a `UMaterialInstanceDynamic`** (`CellMaterialInstance`, `Transient` for the Live-Coding reason): parameter values on a plain `UMaterialInterface` are baked into the asset, so a HUD slider would have nothing to write to. `EnsureCellMaterialInstance()` creates it over `CellMaterial`, pushes the current parameters in, and returns what to hand a renderer — deliberately **one** function rather than a create/apply pair, since it has three call sites (both render paths plus the selection overlay) and a split would let one of them silently keep a stale width. It compares against `Parent`, not `GetBaseMaterial()`, so swapping `CellMaterial` for a different instance of the same base is noticed. `SetCellBorderWidth()` (`BlueprintCallable`, the `SetSpeed()` slider idiom) and `FHudStats::CellBorderWidth` complete the HUD path; **neither a re-render nor a new generation is needed**, because the value lives in the material's uniform buffer rather than in per-instance data — which is also why the Details-panel branch in `PostEditChangeProperty()` deliberately skips `RenderGridImmediate()`, since a slider drag would otherwise cost a full `AddInstances()` per mouse-move at millions of cells. A missing `BorderWidth` parameter is warned about once: `SetScalarParameterValue()` is a silent no-op otherwise, the same class of invisible failure as the missing `PerInstanceCustomData3Vector` node.

**`CellMeshComponentType` picks which of `CellsMeshFlat` (`UInstancedStaticMeshComponent`) and `CellsMeshHierarchical` (HISM) actually receives instances** — `FInstancedMeshCellGridRenderer` itself needed zero code changes to support either, since `AddInstances`/`ClearInstances`/`SetStaticMesh` are all `virtual` overrides on HISM (it *is-a* `UInstancedStaticMeshComponent`), so calling them through the base-class pointer already dispatches correctly regardless of which concrete class it points at. Both are `AAutomataOrchestrator`'s permanent `CreateDefaultSubobject`-created components (`CellsMeshHierarchical` the actor's root); `GetActiveCellsMeshComponent()` is the single place that decides which is active, and it is what `CellsRenderer` binds to (see below). The *other* one gets a cheap defensive `ClearInstances()` each render (`ClearInactiveCellsMeshComponent()`) — the active one is cleared by `BeginRender()` anyway, so clearing it there would wipe the render being drawn, whereas stale instances genuinely can survive on the inactive one after a type switch. **Both components are created unconditionally in the constructor and live for the actor's whole lifetime** rather than being destroyed/recreated: dynamically swapping which `UClass` a `CreateDefaultSubobject`-created component is at runtime isn't something Live Coding can safely hot-patch for an already-placed level actor (confirmed directly — after changing `CreateDefaultSubobject<UInstancedStaticMeshComponent>` to `CreateDefaultSubobject<UHierarchicalInstancedStaticMeshComponent>` for what was originally a single `CellsMesh` field, the existing placed actor's component pointer silently reinstanced to `null` — no crash, just a dangling reference — because the old object couldn't be safely upcast to the new class; a genuine editor restart was needed to get a clean instance). Runtime `NewObject()`-created components (`SelectionMeshComponent`, and the age-material pool that used to exist) never faced this hazard — they aren't default subobjects, so creating/destroying them at runtime is an ordinary, safe operation.

HISM builds an internal LOD cluster tree over the instances (async rebuild after `AddInstances`/`ClearInstances`, tracked via `bIsOutOfDate`/`BuildTreeIfOutdated`) enabling per-cluster occlusion and distance culling — the payoff scales with cell count (relevant at the 700k+ live-cell sizes seen once the sim runs for a while), but each full-grid `ClearInstances()` + re-`AddInstances()` per generation also means HISM rebuilds that cluster tree from scratch every step, which is extra work the plain (non-hierarchical) `UInstancedStaticMeshComponent` doesn't do — that comparison has now been run, and **the flat `Instanced` component wins outright — which is why it, not HISM, is `CellMeshComponentType`'s default**. Both settings were measured on the identical grid (same `Seed`, so the structure is bit-for-bit the same), rule `0-6/1,3/2/VN`, cull volume and distance culling both off:

| cells | FPS: ISM → HISM | `AddInstances`: ISM → HISM |
|---|---|---|
| 100,881 | 76.0 → 84.0 | 4.6 → 10.2 ms |
| 508,281 | 10.1 → 8.9 | 25.3 → 37.9 ms |
| 990,055 | 4.8 → 4.5 | 49.5 → 76.0 ms |

Insertion costs HISM 1.5–2.3× more at every size, far outside noise, and there is no FPS gain to pay for it (the 10–25% spread is within what camera placement alone could explain, so HISM cannot be said to *hurt* drawing — only to buy nothing). The cluster tree never gets a chance to help: the render does `ClearInstances()`+`AddInstances()` *every generation*, so the tree is rebuilt from scratch asynchronously and is usually still out of date when the next generation wipes it, meaning cluster culling never engages — and the structures these rules produce are dense and convex, with little inter-cluster occlusion to exploit anyway. HISM would become worth revisiting only if a mode appears where the grid stays unchanged for a long time (paused inspection, examining a bake), giving the tree time to finish. `FRenderTimings` now logs `GAverageFPS` alongside the phase breakdown precisely so this trade — insertion cost against draw cost — can be judged from one line instead of by feel.

**`CellCullStartDistance`/`CellCullEndDistance` — per-instance distance culling, deliberately not HLOD**: HLOD (Hierarchical LOD) bakes simplified proxy meshes for groups of *static* actors via an explicit "Build HLODs" step in the editor, then swaps a whole cluster for its proxy past a distance — it has no way to react to a grid that's fully cleared and rebuilt every simulation step (there's no static state to bake), so it never engages here no matter how it's configured on the level; that's the "HLOD doesn't seem to work" outcome the property was added to replace. `CellCullStartDistance`/`CellCullEndDistance` (`AAutomataOrchestrator`, `Automata|Cells`, both default `0.0f` = disabled — same as engine default) instead drive `UInstancedStaticMeshComponent::SetCullDistances()` directly — genuine per-instance runtime distance culling computed every frame from the current view, needing no baking and updating automatically as instances get replaced generation-to-generation. Applying the distances is factored into its own private helper, `ApplyCellCullDistances()`, called from `RenderCurrentGrid()`/`RenderGridImmediate()` on every render and from `SetCellCullingEnabled()` directly (rounded to `int32` via `FMath::RoundToInt`, clamped to non-negative) — applied to `CellsMeshFlat`/`CellsMeshHierarchical` *and* `SelectionMeshComponent`, regardless of which one `CellMeshComponentType` currently selects, so switching component types later doesn't leave a stale (or default/disabled) set of cull distances anywhere; `SetCullDistances()` itself is a no-op when values haven't changed, so the repeated call costs nothing once settled. `bEnableCellCulling` (default `true`) is a master on/off switch — while `false`, `ApplyCellCullDistances()` applies `(0, 0)` to all components instead of the configured distances, without touching `CellCullStartDistance`/`CellCullEndDistance` themselves, so toggling it for an A/B comparison never loses previously-tuned numbers; switchable live via the **B** hotkey (`AGamePlayerController::OnToggleCellCulling()` → `SetCellCullingEnabled()`/`IsCellCullingEnabled()`, no `CallInEditor` — same reasoning as `CycleChunkedRenderOrder()`/`SetWaitForChunkedRenderToFinish()` above, the checkbox is already directly editable) or the Details panel. **`SetCellCullingEnabled()` calls `ApplyCellCullDistances()` itself, immediately, rather than relying on the next render call** — an earlier version only applied cull distances as a side effect of rendering a newly-computed generation, so toggling `bEnableCellCulling` via the **B** hotkey while no generation was actively rendering (e.g. continuous Play paused, or between `Next()` calls) silently did nothing until the *next* render — `SetCullDistances()` itself updates the live `SceneProxy` on the Render Thread immediately and needs no `AddInstances()`/rebuild to take effect, so there was no actual reason to wait for a render; calling `ApplyCellCullDistances()` straight from the setter fixed the "have to regenerate a frame for the toggle to visibly take effect" symptom without needing to force any regeneration at all. **Two debugging aids added while chasing an initial "still doesn't cull no matter how far I fly" report**: (1) `ApplyCellCullDistances()` logs once whenever the applied `(Start, End)` actually changes (`"отсечение клеток по расстоянию включено/выключено"`), by comparing against `CellsMeshHierarchical->GetCullDistances()` before calling `SetCullDistances()` again; (2) while `CullEnd > 0`, a throttled (max once/second, via a local `static double LastCullDebugLogSeconds`) diagnostic line logs the camera location, the live-cell bounds center/radius (`ComputeAliveCellsBounds()`), the distance between them, the configured `(Start, End)`, and the *actual* `(Start, End)` read back from `CellsMeshHierarchical` right after `SetCullDistances()` — enough to directly compare "is the camera actually past the configured distance" against "did the value really stick on the component" without guessing. This diagnostic surfaced the actual root cause on this project: `r.ViewDistanceScale` (a Scalability-driven console variable, found via `r.ViewDistanceScale` with no argument to print its current value) was `10` instead of the expected default `1` — the engine multiplies `EndCullDistance` by this scale before comparing it to camera distance (`InstancedStaticMesh.cpp`'s `MaxDrawDistanceScale = GetCachedScalabilityCVars().ViewDistanceScale`), so a configured `20000` was actually enforcing a `200000`-unit (2 km) cutoff — nothing was broken, the fly-test distance just never reached the real threshold. Separately, disabling Nanite on the cell mesh (`NaniteSettings.bEnabled`) was tried and discarded — Nanite's renderer has no references to `EndCullDistance`/`InstanceCullDistance` at all (grepped `Renderer/Private/Nanite/`, zero hits) so it does bypass this legacy per-instance cull path, but turning Nanite off made rendering *worse* and introduced other bugs at this project's instance counts, so Nanite stayed enabled — the real fix was purely the `r.ViewDistanceScale` mismatch.

**`ARenderCullVolume` (`Automata/Rendering/RenderCullVolume.*`) — a placeable box that culls cells *before* they cost anything**: unlike `CellCullStartDistance`/`CellCullEndDistance`, which hide already-built instances after the fact and don't reduce the cost of building them, this cuts cells outside the box at the source — `BuildCellRenderData()` calls `FCellGrid::GetAliveCellsInBounds()` instead of `GetAliveCells()`, so the transforms are never built and `AddInstances()` never sees them (and `FDenseCellGrid` overrides that method chunk-aware, rejecting whole chunks at a time). The orchestrator finds the actor itself via `UGameplayStatics::GetActorOfClass()` (the same idiom as everywhere else in the project) — no manual Details-panel reference. It is moved and resized with the ordinary actor gizmo: there are no `Size`/`Location` properties, since Location *is* the actor transform and Size is the `BoundsBox` `UBoxComponent`'s `BoxExtent`. Deliberately **axis-aligned only** — rotating the actor does not tilt the culling box, `GetWorldBounds()` always builds an AABB from location plus scaled extent, the same simplicity choice as the marquee selection's "no depth bound". Because a programmatic `SetActorLocation()` doesn't trigger it, `PostEditMove(bFinished)`/`PostEditChangeProperty()` (editor-only) explicitly ask the orchestrator to re-render so dragging or retyping the bounds updates the view immediately; `MoveCullVolumeToSelection()` (**K**) calls `RefreshRenderCullVolume()` itself for the same reason. Master switch `bEnableRenderCullVolume` (default `true`, hotkey **C**); `SelectCellsInCullVolume()` (**L**) selects everything inside it.

**A hidden box does not cull** — `SetVolumeVisible()`/`IsVolumeVisible()` (hotkey **Ctrl+C**, `AGamePlayerController::OnToggleRenderCullVolumeVisibility()`) toggle the box's own geometry, and culling follows. Visibility and culling started out fully independent, which read badly on screen: an invisible crate that keeps cutting makes cells stop in mid-air for no visible reason. The invariant is enforced in exactly one place — `AAutomataOrchestrator::GetActiveCullVolume()`, which answers "is culling active right now" (actor present ∧ `bEnableRenderCullVolume` ∧ visible) and replaced the hand-written `bEnableRenderCullVolume ? EnsureRenderCullVolume() : nullptr` at all five of its call sites. **No second state is introduced**: `bEnableRenderCullVolume` is never overwritten, so showing the box again restores whatever **C** last set rather than force-enabling. Paths that want the box as a *spatial region* rather than as render culling (`SelectCellsInCullVolume()` on **L**, `MoveCullVolumeToSelection()` on **K**) deliberately keep calling `EnsureRenderCullVolume()` directly — the region exists whether or not it is currently cutting. Because visibility now changes what gets drawn, `SetVolumeVisible()` calls `NotifyOrchestratorToRefresh()` itself, same as `EndGizmoDrag()` — otherwise culled cells would return only at the next generation, and never while paused.

Ctrl is checked inside `OnToggleRenderCullVolume()` rather than mapped, since Enhanced Input can't require a modifier in a key mapping — the same idiom as Ctrl+S/Ctrl+O. Gizmo-handle visibility is the **conjunction** of selection mode and volume visibility: both `SetSelectionModeActive()` (Tab) and the Ctrl+C handler compose the two, so Tab can't pull handles out of a hidden box, and hiding mid-drag ends the drag first (same guard as leaving selection mode).

**`VolumeMaterial` — painting the box.** `UBoxComponent` draws wireframe edges only and takes no material at all, so a *filled* cube is a second component: `VolumeMesh` (`/Engine/BasicShapes/Cube`, a default subobject next to `BoundsBox`, collision and shadows off like every other purely visual component here), rescaled from `GetUnscaledBoxExtent() / 50` since the engine cube is 100 units. It stays hidden entirely while `VolumeMaterial` is unset — falling back to the default material would be worse than nothing, since an opaque cube would hide exactly the cells the culling exists to expose (the same conclusion `GhostShapeMaterial`/`BakedMeshMaterial` reached when their own fallback was dropped; a translucent material is what is expected). `ApplyVolumeVisuals()` is the single place that reconciles material, scale and visibility, called from `BeginPlay()` (the constructor is too early — `VolumeMaterial` isn't deserialized yet), from `PostEditChangeProperty()` (so typing a `BoxExtent` or assigning the material repaints immediately in-editor), and from `UpdateGizmoDrag()`'s scale branch every drag frame so the filled cube tracks the wireframe rather than lagging at its pre-drag size — which is why it compares the material before `SetMaterial()`, that call dirties the component's render state even when nothing changed.

**`RenderPresets` (`Automata/Rendering/RenderPresets.h/.cpp`, plain namespace + `FRenderPreset` `USTRUCT(BlueprintType)`) — whole quality profiles on F1–F4**, following `RulePresets` exactly (code-constant table, `BlueprintReadOnly` fields, `namespace RenderPresets { const TArray<FRenderPreset>& GetAll(); }`, plus `GetRenderPresets()`/`ApplyRenderPreset(int32)` on the orchestrator). Six profiles, of which four sit on F1–F4 and two belong to the F10 shot (see "The photograph" below — they have no key of their own, since outside a capture they are only slower): **Quality** (nothing disabled — also the way back), **Unlit** (differs from Quality in *exactly* the viewmode, so the two are comparable), **Balanced** (no Lumen, no shadows — neither from lights nor from the cells — no post-processing, no background, but full resolution and every cell still drawn), **Performance** (all of that plus 70% screen percentage and Ghost Shape, which without a cull volume replaces the per-cell render entirely — that, not the cvars, is where the time actually goes).

Two structural decisions carry the design. **Every preset sets every field and every cvar**: switching profiles can then never leave a tail from the previous one, so nothing has to be restored and no profile's result depends on which profile preceded it. That is why `FRenderCvars` (anonymous namespace in the .cpp) is a struct of named fields whose defaults *are* the Quality profile — the other three are written as differences from it, and the "same cvar names everywhere" invariant holds constructively instead of by eyeballing four lists. And **the whole preset is applied inside the orchestrator, including `VIEWMODE`** (routed through `RunRenderConsoleCommand()` → `GamePC->ConsoleCommand()`, since viewmode commands address a specific local player's viewport; `GEngine->Exec()` is the pre-`BeginPlay` fallback) — the controller's handler holds no console command of its own, so adding a fifth profile is a one-place change. `ApplyRenderPreset()` writes the cell fields directly rather than through their setters (each setter re-renders, and going through four of them would cost three or four full `RenderGridImmediate()` calls per keypress), then applies each thing once; `SetGhostShapeEnabled()` is the exception, called last through its setter because it is the one that changes *what* is drawn and its setter already does exactly the needed refresh. Deliberately **not** in any preset: `r.Nanite` (turning Nanite off on the cell mesh was already measured on this project and made rendering *worse* — see `CellCullStartDistance` above) and `bEnableChunkedRender` (Z stays independent; all four profiles would set it off anyway, so a field that never varies would be noise).

`ActiveRenderPresetIndex`/`bRenderPresetModified` (both `UPROPERTY(Transient)`, the usual Live-Coding-reinstancing reason) feed `FHudStats::RenderPresetName`/`RenderPresetIndex`/`bRenderPresetModified`. The modified flag is raised inside the setters the preset owns (`SetCellCullingEnabled()`, `SetGhostShapeEnabled()`, `SetCellShadowsEnabled()`, `SetBackgroundVisible()`) and cleared at the *end* of `ApplyRenderPreset()` — otherwise the HUD would keep naming a profile the screen no longer matches after one press of B or H.

**`bCellsCastShadows` / `SetCellShadowsEnabled()`** is its own switch rather than part of "shadow quality" in general: the shadow pass runs the same millions of instances again per cascade, so on this project it costs incomparably more than on an ordinary scene. `ApplyCellShadowSettings()` mirrors `ApplyCellCullDistances()` exactly — applied to *both* cell components plus `SelectionMeshComponent` (so a later `CellMeshComponentType` switch can't leave the other one stale), called from both render paths and immediately from the setter, since `SetCastShadow()` updates the scene proxy without needing a re-`AddInstances()`.

**`bShowBackground` / `SetBackgroundVisible()` — hide the sky, keep the light.** The naive version (hide `ASkyAtmosphere`) also kills the lighting, and that is a direct consequence of the level's setup rather than a bug: this level's `ASkyLight` has `bRealTimeCapture == true`, i.e. it rebuilds its ambient cubemap *from the sky* every frame. Remove the sky and there is nothing to rebuild from, so the ambient collapses along with the background — measured in PIE from a fixed camera, the blue and green cells disappeared entirely and the whole image fell back to the one warm directional light.

The fix is `USkyAtmosphereComponent::SetRenderInMainPass(false)`: it drops the sky from the basepass/transparency only, leaving the component in the scene for everything else — including the real-time sky capture. The camera stops seeing it; the capture keeps seeing it. Lights (`ASkyLight`/`ADirectionalLight`) are never touched at all. `AVolumetricCloud` gets the same treatment (via `FindComponentByClass`, since unlike `ASkyAtmosphere::GetComponent()` it exposes no public getter), while `AExponentialHeightFog` has no such flag and is simply hidden — verified in the same measurement to cost no light, the fog not being what feeds the capture.

**Rejected, and worth not retrying: freezing the capture** (`SetRealTimeCaptureEnabled(false)`) before hiding the sky. It reads like the obvious fix and it does not work, including with the hide deferred a frame via `SetTimerForNextTick`: that call does not rebuild the cubemap in place, it queues a recapture (`SetCaptureIsDirty()`) which still runs against the by-then-empty sky and freezes a *black* cubemap — i.e. exactly the lost light it was supposed to prevent. This was implemented, measured against `bRenderInMainPass` from an identical camera position, and removed.

**Ghost Shape — a chunk-granular silhouette that coexists with the live simulation**: marked experimental alongside Baking. Instead of one cube of geometry per cell, it builds one per occupied **chunk** (via `CellMeshBuilder::BuildFromCells()` over an `FChunkGridView`, reusing the exact face-culling mesh builder the bake uses), which is orders of magnitude cheaper. Unlike `BakeCellsToMesh()` it is **not** a one-way snapshot: `Grid` is never freed, the simulation keeps running, and the silhouette is rebuilt every `GhostShapeRefreshInterval` generations (default `10`, its own counter — `CellMeshBuilder::BuildFromCells()` is synchronous and single-threaded, so rebuilding every generation would be felt on the game thread). Two modes depending on whether a cull volume is active: **(1)** cull box active — the silhouette is built only from chunks *outside* it while the detailed per-cell render keeps drawing everything inside, so the ghost is pure addition, showing where the structure continues beyond the box; **(2)** no cull box (or disabled) — "outside" means "everywhere", the silhouette covers the whole grid and **replaces** the detailed render entirely (`ShouldGhostShapeReplaceDetailedRender()`). Mode 2 is where the feature actually saves time: at high live-cell counts the detailed path (collect + `AddInstances` per cell) is the expensive part, and often all that's wanted is the overall shape of how the structure is evolving. Off by default; **H** toggles it; `GhostShapeMaterial` has no fallback — unset means a warning plus the engine default material, exactly like `BakedMeshMaterial`.

**The photograph — `TakePhotoShot()` on F10, and the two profiles without an F-key**: F6/F7 rasterise the grid directly, bypassing the GPU, and give a flat image with no light or shadow — right for a mask, useless as a portrait. F10 is the other half: an ordinary engine render with all the lighting, at a resolution the window cannot hold. It stops the simulation (the frame has to hold still), applies a capture profile, redraws the grid whole, and issues `HighResShot`.

**`HighResShot` does not render in tiles.** It allocates a *single* render target of the requested size (`UnrealClient.cpp`: `DummyViewport->SizeX = GScreenshotResolutionX`), checked only against the RHI 2D texture limit. Video memory therefore grows with the **area** of the frame — 4K is ~8 Mpx, 8K ~33 — while the grid size barely matters. This contradicts the July high-quality-render research, which states the opposite and reasons from it about tile seams; that claim was taken on trust and cost a crash. The first Photo profile set `ScreenPercentage 200` to fight seams that cannot exist, turning 7680×4320 into 15360×8640 — 133 Mpx of GBuffer — and killed the editor on a scene of **82 thousand** live cells. `ValidatePhotoShotResolution()` now refuses past the texture limit and warns past 40 Mpx, and it runs **before any side effect**, so a refusal leaves simulation, cuts and profile untouched. The default is 4K, not 8K; raise it once 4K is proven on the card at hand.

**`PhotoShotDelayFrames` is not a pause either.** `r.HighResScreenshotDelay` makes the engine render the frame *at shot resolution* that many times over and keep the last, so the number is a direct multiplier on capture cost. It defaulted to 30 here — 7.5× the engine's own default of 4 — for no gain whatsoever. Now 4, which is also the threshold below which `TemporalAA` is force-disabled (`ShowFlags.cpp`). The loop is synchronous (`FlushRenderingCommands()` per iteration), so the window is frozen throughout; there is no progress to show and none is attempted.

**Two capture profiles, neither with an F-key** — `RenderPresets::GetPhotoPresetIndex(bLeanMemory)` looks them up **by name**, since positional arithmetic would break on any insertion. `Photo` differs from `Quality` in no cvar at all (with no tiles, TSR is safe and the shutter delay gives it still frames to converge on); it exists as its own entry because it also clears Ghost Shape and culling, and because the shot owns it and can tune it without disturbing the working profile. `Photo Lean` drops everything sized by the frame — Lumen, VSM, TSR history, bloom/DOF/SSAO/fog — but **keeps shadow quality high on purpose**: without VSM, shadows come from a fixed-size atlas that does not scale with the frame, and shadows are half the point of a portrait.

**What the shot does and does not touch.** It leaves alone everything set up for *looking* — cull volume (C), view slice (J), age filter (digits), hidden sky (U). The first version cleared the slice and the filter "so everything fits in frame", quietly discarding the setting the frame had been composed around. The profile owns quality plus the two accelerators that spoil a photograph; what is *in* the frame is the photographer's business. The background has to be saved and restored by hand around `ApplyRenderPreset()`, because a profile is required to set every field it owns and the table has no notion of an exception. Conversely the *tools* are hidden for the shot and restored after, unconditionally: the cull box, its gizmo handles and the selection highlight (`HideEditingVisualsForPhoto()`/`RestoreEditingVisualsAfterPhoto()`, the latter also on a failed shot — the screen must come back as it was found). That this is possible at all is the payoff from splitting the box's visibility from its culling: cells stay cut exactly as configured while the crate is out of frame.

**Completion is detected by frame counter, and that detail is load-bearing.** `HighResShot` returns *immediately* — it only raises a flag; the frame is drawn later, inside the viewport draw, blocking the game thread. There is no usable delegate: `UGameViewportClient::OnScreenshotCaptured()` looks right but subscribing to it **cancels writing the file** (`GameViewportClient.cpp`: *"If delegate subscribed, fire it instead of writing out a file to disk"*). So the hook is `Tick()` — but the tick of the *same* frame runs **before** the draw (order within a frame: input → actor tick → draw), so reporting from there put the gizmo handles back a moment before the shutter and they photographed faithfully. Waiting for `GFrameCounter` to move fixes both that and the duration, which was being measured a frame short. The completion line looks for the file **on disk** rather than assuming it appeared, since a shot that does not fit in memory fails silently.

**A photograph can only show what can be displayed** — the shot goes through the same `RenderGridImmediate()` and the same instances. A "fast-forward N generations before the shot" parameter was built and then removed for exactly this reason: a state too big for the screen is too big for the frame. Texture memory is logged at every shot (`RHIGetTextureMemoryStats()`), so `Photo` against `Photo Lean` is a comparison of numbers rather than impressions. The genuinely seam-free route to larger frames is Movie Render Queue, which tiles *with overlap* — blocked by MRQ rendering in the editor world while the structure lives in PIE.
