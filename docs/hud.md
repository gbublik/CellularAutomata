# HUD — `Ui/`

The C++/UMG split, the seven `FHud*Stats` summaries/`FCellRenderStats`, rule presets, and the generation graph widget. Read before adding anything the HUD must display.

- **`Ui/` — the HUD.** `FUiController` (`Ui/UiController.*`) is a plain (non-UObject) RAII-style helper, not an actor: it lazily creates a `UUserWidget` from a `TSubclassOf<UUserWidget>` set by the orchestrator (`HUDWidgetClass`) and exposes `ShowHUD/HideHUD/ToggleHUD`. Owned via `TUniquePtr` by `AAutomataOrchestrator`, driven from `BeginPlay()` (see that bullet for why not `PostActorCreated()`).

**A UMG widget never sees a keypress** — input arrives at `AGamePlayerController`, so anything the HUD should react to needs a bridge. **F5** (`OnToggleHudInfoPanel()` → `AAutomataOrchestrator::ToggleHudInfoPanel()`) is that bridge for hiding the info panel: it forwards to `UMainHudWidget::OnToggleInfoPanel()`, a `BlueprintImplementableEvent`. C++ deliberately does not know *what* gets hidden — one panel, several, or a cycle of "everything → compact → nothing" — because that is layout, and layout lives in UMG. The same shape is the right one for any future HUD key. `GetHudWidget()` (via the new `FUiController::GetWidget()`, a weak reference rather than the raw public `NewWidget` field) reaches the widget, and `ToggleHud()`/`IsHudVisible()` finally expose `FUiController::ToggleHUD()` — written long ago and, until now, called from nowhere at all.

**Split of responsibilities — C++ supplies data and actions, the visuals are built by hand in UMG**: `UMainHudWidget` (`Ui/MainHudWidget.*`) is a thin native shell whose only job is `GetOrchestrator()` — a lazily resolved, `IsValid()`-revalidated `GetActorOfClass()` lookup (the same idiom as `EnsureRenderCullVolume()`), deliberately *not* an editor-assigned reference, since a widget asset cannot hold a pointer to a specific level actor. The layout lives in a Blueprint subclass (`Content/HUD/WBP_MainHud`) assembled in the UMG Designer. Everything the widget needs is therefore exposed as `BlueprintPure`/`BlueprintCallable`/`BlueprintType` on the orchestrator; when the HUD needs something new, the change belongs in C++ as API, not as widget-construction code.

**Seven summaries, one per subsystem** (`Ui/HudStats.h`), each with its own `BlueprintPure` getter on the orchestrator: `GetSimulationStats()`, `GetHudRenderStats()`, `GetCutStats()`, `GetPerformanceStats()`, `GetCameraStats()`, `GetGeneratorStats()`, `GetSonificationStats()`. That is a **reversal** of the previous design and the reasoning is worth keeping, because the old argument was not wrong so much as outgrown: everything lived in one `FHudStats` precisely so the widget needed **one `Break` node** for the whole HUD, and settings sat beside measurements for the same reason. At fifty-odd fields that node no longer fits on screen, and every panel in the HUD drags a wire past forty pins belonging to other panels. There are about as many panels as there are structs here, and each reads its own.

What the split does *not* do is separate "measurement" from "setting" — the grouping is by topic, so `GenerationsPerSecond` still sits next to `SimulationSpeed` and `GenerationsPerDispatch` next to `StepsPerRender`. Deliberate: those pairs only mean anything read together (target vs. actual, asked-for vs. achieved), and splitting them by *kind* would have left nobody able to show the gap. Field names carried over unchanged, so the migration was a matter of re-pointing wires, not renaming pins.

The seven are filled by one `UpdateHudStats()`, which now runs **at most once per frame** (guarded on `GFrameCounter` via `LastHudStatsFrame`). With one node, rebuilding on every call was free; with seven getters a widget reading each from its own panel would pay seven full rebuilds a frame — including the rule `Printf` and the pawn walk for camera speed. The cost of the guard is one frame of lag on the counters *while the actor ticks* (`Tick()` snapshots at the top of the frame, a step can complete after it), which is invisible at frame rate; the case the per-getter rebuild exists for is untouched, since with the actor not ticking the first getter of the frame *is* the first pass. `ResetGenerationCounter()` clears the stamp, because starting a run over happens on pause too.

`FHudStats` and `GetHudStats()` are **gone**: they survived, deprecated, only until the WBP graphs were re-wired onto the seven summaries, and were then deleted in one commit together with `FillLegacyHudStats()` and `LastHudStats` — exactly the single deletion the compatibility layer was shaped for. The one-directional copy (`FillLegacyHudStats()` filled the old struct *from* the seven) is why the two could never drift while both existed.

**Data**: `USTRUCT(BlueprintType)` summaries, all computed once and read by everyone rather than recomputed per consumer (so a log line and the on-screen number can never disagree). `FCellRenderStats` (`GetLastRenderStats()`) — `RenderedCellCount`/`TotalCellCount` ("drawn/total", i.e. how much the cull volume is removing), `EstimatedUploadMB` (sized from `RenderedCellCount`, a single figure like a file size, not a before/after pair) and `BytesPerInstance`, filled by `BuildCellRenderData()`. Across the seven summaries above — `bIsComputing`/`bIsRendering` (the `bStepInProgress`/`bChunkedRenderInProgress` phases, which can overlap), `CurrentFPS` (`GAverageFPS`, not recomputed), `GenerationCount`, `GenerationsPerSecond` (recomputed on a one-second window, not per frame — sub-second sampling is visibly noisy at low `Speed`), `EstimatedGpuComputeUploadMB` (read from whatever the GPU strategy already packed, never a separate grid scan), plus `AliveCellCount` (`Grid->Num()`, O(1) — the chunks keep the count) and `SelectedCellCount`. The last two refresh every tick, so a Delete or a new selection shows up immediately rather than at the next generation. Three more mirror the live *settings* rather than measurements, so the HUD reads exactly what the hotkeys change instead of keeping its own copy: `SimulationSpeed` (`Speed`, +/-) and `StepsPerRender` (T/G), and `CameraSpeed` — read straight off the possessed pawn's `UFloatingPawnMovement::MaxSpeed` rather than derived from `CameraSpeedMultiplier`, since the controller has already multiplied it while Left Shift is held and the HUD should show the boosted figure. Note `SimulationSpeed` vs `GenerationsPerSecond` is target vs. actual: the gap between them is the readable sign that the sim is compute-bound rather than throttled by its setting. A **mode block** follows the same mirror rule, one field per hotkey — `bSimulationRunning`/`bFastStepActive` (Space, Shift+F), `bAutoReseedOnExtinction` plus its `AutoReseedCount` (Shift+N — the one mode carrying a number, since it is switched on and left to run and "which attempt is it on" is the only thing to ask from across the room), `bSelectionModeActive` (Tab, read off the controller), `ComputeMethod`, `bChunkedRenderEnabled`/`ChunkedRenderOrder`/`bWaitForChunkedRenderToFinish` (Z/X/V), `bCellCullingEnabled` (B), `bRenderCullVolumeEnabled`/`bRenderCullVolumeVisible` (C, Ctrl+Shift+C) and `bGhostShapeEnabled` (H), plus `bCellsCastShadows` and `bBackgroundVisible` (U) and the render-profile trio `RenderPresetName`/`RenderPresetIndex`/`bRenderPresetModified` (F1–F4 — see `RenderPresets` above; the last one is what lets the widget draw a "Performance\*" once a hotkey has changed something the profile owns). `RuleString` carries the rule the sim is actually running, as `Survival/Birth/States/Neighborhood` text — and it is the same distinction as `bRenderPresetModified`, one step further: it comes from `GetActiveRuleString()`, i.e. rebuilt from the live `SurvivalCounts`/`BirthCounts`/`States`/`Neighborhood`, never from the `RuleString` **`UPROPERTY`**, which is the *input* field and still holds whatever was last typed there — after a preset or a hand edit of the arrays it describes an automaton that is no longer being computed. It is rebuilt every tick rather than cached when a rule is applied, for the reason `BuildRule()` re-reads too: an array edited straight in the Details panel goes through no apply path there is anything to hook. Being a field in the simulation summary rather than a `BlueprintPure` call of its own keeps it beside the generation counters it describes, and keeps the once-per-frame rebuild in charge of when the `Printf` runs. Four of them are *effective* states rather than switches, and exist precisely because they can't be derived from the switches in the widget: `bCullVolumeActive` comes straight from `GetActiveCullVolume()` (which also requires the actor to be present in the level), and `bGhostShapeReplacesDetailedRender` from `ShouldGhostShapeReplaceDetailedRender()` — the mode that actually buys the speed. Reading them from the same functions the renderer uses is the point; a widget-side copy of those conditions could drift.

The other two, `bCellCullingActive` and `bViewSliceActive`, complete the trio of "is this actually cutting right now" flags behind the HUD's three cut indicators — **Culling** (B, distance), **Volume** (C, the box) and **Slab** (J, the view slice), i.e. the terminology split described under `Automata/Rendering/`: culling is what the renderer skips *after* the instances are built, the other two remove cells in `BuildCellRenderData()` before anything is built at all. All three lamps are wired to "cutting", never to "switched on", and `bCellCullingActive` is why: `bEnableCellCulling` defaults to **true** while both cull distances default to **0** (the engine's own "off"), so an indicator bound to that switch would be lit from the first second of every session while nothing whatsoever was being culled. `bViewSliceActive` adds the camera-availability half of the condition `BuildCellRenderData()` itself checks — the slice plane is defined by the camera, so without one there is nothing to cut with. The plain switches (`bCellCullingEnabled`/`bRenderCullVolumeEnabled`/`bViewSliceEnabled`) all survive alongside, so a widget wanting a third, dimmed "armed but inert" state can build it from a pair of fields with no C++ change. All seven `Last*Stats` members are `UPROPERTY(Transient)` for the usual Live-Coding-reinstancing reason (see `GamePC`), and so is `LastHudStatsFrame` — reinstancing garbage there could collide with the current frame number and hand the HUD one frame of somebody else's snapshot.

**Actions**: the simulation entry points were already `BlueprintCallable`; the HUD additions are `SetSpeed()`/`SetStepsPerRender()` (absolute setters for sliders, applying the same clamps as the `+`/`-` and T/G hotkeys rather than letting a slider write the `BlueprintReadWrite` property raw and reach 0), `TryApplyRuleString(In, out Error)` (same as `ApplyRuleString()` but takes the string as a parameter and hands the parse error *back* — a `UE_LOG` warning is invisible from UMG, and silently doing nothing on a button press is the worst option), and `GetActiveRuleString()`.

**`RulePresets` (`Automata/Simulation/RulePresets.h/.cpp`, plain namespace + `FRulePreset` `USTRUCT(BlueprintType)`)** — 13 ready-made rules transcribed verbatim from williamyang98/3D-Cellular-Automata's `system_entries.js`, in the source's own order and naming so a preset can be checked against the site one-to-one (this project's own finds are appended **after** that whole block, never inserted into it, precisely so that one-to-one numbering survives — currently one: **`Crystal Growth 1 (Moore)`**, `0-6/1,3/2/M`, which differs from the catalogued `Crystal Growth 1` in a single letter, the neighbourhood, and that is enough to change the growth geometry — under Moore the diagonals advance as fast as the axes, so the front is cubic and throws straight rays, where von Neumann's Manhattan metric gives an octahedral front with faces instead. Its core reads as a symmetric cross and is the strongest logo candidate so far) ("Builder 1"/"Builder 2" really are duplicates upstream; kept so the numbering matches). Each carries `Name`/`RuleString`/`SpawnRadius`/`Amount`; `GetRulePresets()` lists them and `ApplyRulePreset(Index, bApplySpawnSettings)` applies one **through `TryApplyRuleString()`**, so presets and hand-typed rules share exactly one application path instead of two that could drift. It deliberately does *not* regenerate the grid — applying a rule to an already-grown structure is sometimes exactly what's wanted, and "start fresh with this preset" is one more `GenerateState()` click. The upstream table specifies a fill *density*, which this project can't use directly (`Amount` is an absolute count and the `RandomBall` generator reject-samples **with collisions**, so `density × volume` systematically under-seeds); `Amount` is therefore derived with the coupon-collector estimate `N·ln(1/(1-p))`, `p` capped at 0.95 since full coverage by random draws is unreachable in principle. Two presets whose upstream radius is grid-relative get a concrete radius of 30, because `GridSize` doesn't affect generation in this project at all (it is saved and loaded, but generation seeds purely by `GenerationParams.Radius`).

**The generation graph — two lines over generation number, and the first time-series storage in the project**: everything else HUD-facing (`FRenderTimings`, `FCellRenderStats`, the seven `FHud*Stats`) is a snapshot of the last moment. A single instantaneous number cannot show what a run is actually judged by — where the rule accelerates, where it plateaus, where it collapses, and how much the cull volume is really taking off the renderer's plate — so `UGenerationGraphWidget` plots **total alive cells** against **rendered ("visible") cells**.

The two numbers arrive from different places at different rates, and that asymmetry is the whole design. Alive exists for every generation that reaches the game thread (`ApplyStepResult()`, right after `GenerationCount += Generations`); rendered exists only where `BuildCellRenderData()` actually ran. Four independent mechanisms punch holes in the second series — `StepsPerRender`, GPU batching (intermediate generations never exist on the game thread at all, and the batch is trimmed at runtime), series fast mode, and Ghost Shape replacing the detailed render — so the stride is not constant. Two consequences: samples are stored as **`(generation, value)` pairs** and X is mapped **by generation value, not by array index** (index mapping would compress and stretch the curve every time the batch size changed); and nothing may assume `rendered ≤ alive`, since under `States > 2` decaying cells are drawn but not counted alive.

`Automata`-style free functions in `Orchestration/GenerationHistory.h/.cpp` (namespace `GenerationHistory`, the `CellAging`/`CellSelection` idiom) own the window; `AAutomataOrchestrator` owns only the `UPROPERTY(Transient) TArray<FGenerationSample> GenerationSamples` (Transient for the usual Live-Coding-reinstancing reason — history cannot be recomputed on the next render, so reinstancing must not wipe it) and `GenerationHistoryCapacity` (512 **samples**, not generations). The member is named `Samples`, not `History`, because inside the class the latter would shadow the namespace.

Two write paths, deliberately asymmetric. `AppendGenerationSample()` sits beside the two `GenerationCount` increments (`ApplyStepResult()` and `Next()`'s completion) and **above** both render-skip returns, next to the series-capture and Ghost-Shape hooks and for the same reason: the alive line describes the simulation, not the screen. It carries the previous sample's rendered value forward, which is what makes the rendered line hold its last value as a step instead of dropping to zero. `NoteRenderedCells(int32)` is called from the four render points and **takes the count as a parameter rather than reading `LastRenderStats`** — `BuildCellRenderData()` has four callers, two of which (`BuildSliceCapture()`/`EstimateSliceCaptureSize()`) save and restore those stats, so "only the callers that leave fresh stats call me" is an unwritten contract a fifth caller would break silently. The parameter also lets the two Ghost-Shape branches record an honest **0**: zero detailed instances really do reach `AddInstances()` there, and watching the rendered line drop to the floor when Ghost Shape takes over is precisely the diagnostic the graph exists for. When the last sample is already about the current generation it is edited **in place** — load-bearing, not an optimisation: `RefreshRenderCullVolume()` fires from `Tick()` on every camera move while the view slice is on, and without in-place editing one flight of the camera would smear a single generation across hundreds of X positions. History is cleared in `ResetGenerationCounter()`, the one funnel for all five "start a run over" paths; `BakeCellsToMesh()` deliberately does **not** clear it, since a bake is "freeze and inspect" and the run that produced the sculpture is exactly what you want beside it (the visible consequence: `AliveCellCount` on the HUD drops to 0 while the graph keeps the curve).

**The widget is `UWidget` + `SLeafWidget`, not `UUserWidget` + `NativePaint`** — that was the first design and it is wrong for a reason worth recording: `SObjectWidget::OnPaint` paints **all** children first and only then calls `NativePaint` with a raised `LayerId`, so axis labels placed inside such a widget would sit *under* the graph and an opaque background would erase them outright, forcing axis text to be drawn from C++ via `MakeText` — which defeats the entire "layout lives in UMG" split. As a leaf widget it is an ordinary node of the tree: drop it in an `Overlay`, stack `TextBlock`s on top, and it appears directly in the palette (`GetPaletteCategory()` → "Automata", which **must** be `#if WITH_EDITOR` or non-editor builds fail to link) with no intermediate Widget Blueprint. Three more obligations that bite only later: `ComputeVolatility()` must return `true` (the data changes with no Slate invalidation whatsoever, so under `RetainerBox`/`InvalidationBox` or `Slate.EnableGlobalInvalidation 1` the graph would freeze on a cached image), `ReleaseSlateResources()` must reset the shared pointer, and colours must be multiplied by `InWidgetStyle.GetColorAndOpacityTint()` or the graph stays opaque while its parent panel fades. `MakeLines` takes its point array **by value** and in **local** coordinates. Y is scaled by the max of *both* series, pinned at 0, rounded to a nice 1/2/5×10^k ceiling with hysteresis (a raw per-frame max makes the whole curve breathe), and `bLogScaleY` exists mainly for the cull volume: with it on, rendered runs two or three orders of magnitude below alive and a linear axis lays that line flat on the floor.

**Normalisation — `P(n)/n^d` instead of the raw population** (`bNormalizePopulation` + `NormalizationExponent` on the widget, off by default). A growing figure's population goes as its volume, so the raw curve is an overgrown parabola that looks the same for *every* growing rule: the entire difference between rules is hidden inside the leading coefficient. Dividing it out leaves what it was hiding — whether the ratio settles on a constant (a solid body), drifts to zero (a fractal sponge), or oscillates with a period in `log₂ n`, which is the signature of exact self-similarity. The idea is lifted from the `U(n)/n²` plot in the Ulam–Warburton automaton article, where the ratio provably never converges: it oscillates forever between `0.9026116569…` and `4/3`, touching the ceiling exactly at `n = 2^k`. That last detail is the same phenomenon as this project's own observation that the clean picture from fractal rules falls on powers of two (see `docs/input-and-camera.md` on Shift+T/Shift+G).

The exponent is measured, not only assumed: `GenerationHistory::FitGrowthExponent()` is an ordinary least-squares slope of `log(alive)` on `log(n)` over the window, exposed as `GetFittedGrowthExponent()` for a UMG label and computed **whether or not normalisation is on**, since it is a result of the run rather than a detail of the plot. Typing the fitted number into `NormalizationExponent` lays the curve flat and turns the plot into a picture of the fluctuation around it. It fits against the **alive** series, never the rendered one — "visible" depends on the cull box and the filters, i.e. on where the camera is pointed, not on the rule. Three things it is not: it is not measured against the figure's radius but against the generation number, which is the same thing only while the front spreads at a constant speed (it cannot outrun the light cone, but it can stall, and then the ratio simply falls); it returns `0.0` for "nothing to measure" (fewer than two usable samples, or a dead grid), which a caller must not confuse with zero growth; and samples at generation 0 are dropped **everywhere** under normalisation, bounds included, since `n = 0` divides by zero — which is why the window's left edge can no longer be taken as the first element of the array.

Normalisation also forces a second Y-axis mode, and this is the part that would be tempting to skip. The population plot's floor **must** be zero or the curve lies about how many times something grew; the normalised plot's values live in a band like `[0.9, 1.33]`, and measured from zero that band is a straight line. So `ComputeNiceRange()` fits an axis segment to both window bounds, padded 10% and aligned to a nice `1/2/5×10^k` step — the alignment doubling as the hysteresis, since the segment then only moves when the data crosses a step boundary rather than on every tremor. Log scale and a raised floor are mutually exclusive by construction (one is for a range spanning orders of magnitude, the other for a narrow band), so `MapToPoints()` ignores `MinY` whenever `bLogScaleY` is on.

`AGameHud` (`Core/Hud/GameHud.*`, wired via `AAGameMode::HUDClass`) is separate and unrelated to UMG: a native `AHUD` subclass whose `DrawHUD()` paints the live marquee rectangle during a selection drag.

**The age-filter legend — `GetAgeFilterSwatches()` → `TArray<FAgeFilterSwatch>`.** Ten entries, one per digit-row key, each carrying the colour that age is actually drawn in, the key that toggles it, and whether it is visible right now. The widget lays them out as coloured squares and marks the filtered-out ones; that layout is UMG's half, this is the data.

It is a **legend**, and the distinction is the whole point: the colour comes from the same `SampleColorRamp(AgeColors, Age / AgeColorMaxAge)` the renderer uses, so the row can be read against the picture. A decorative even gradient would look better and mean nothing, because it would correspond to nothing on screen.

Three things fall out of that honesty. **The squares will look similar by default** — `AgeColorMaxAge` is 32, so ages 0–9 occupy only the first 28% of the ramp; that is not a bug but a true statement about what those cells look like, and the fix, if one is wanted, is a lower `AgeColorMaxAge` rather than a prettier legend. **The last square cannot be one colour**: its key covers age 9 *and everything older*, i.e. 9–255, nearly the whole ramp — hence `ColorEnd` alongside `Color` and the `bIncludesOlder` flag, so it can be drawn as a gradient instead of a lie. And **`KeyLabel` comes from `HotkeyRegistry` rather than being typed into the widget**, because the digit row is configurable now (and has already been shifted once — `1` is age 0, `0` is the tail), so a hardcoded caption would be wrong after the first rebind. That is what made `AGamePlayerController::KeyFor()` public.

Visibility is read from `BuildAgeFilterMask()` rather than re-derived from `AgeFilterValues`: the "and everything older" rule opens the range upward from the *oldest* selected age, and restating that condition here would have been a second copy with a first copy to drift from.

Why it earns a place at all, given that `ApplyAgeFilterChange()` already puts the filter on screen via `ShowStatusMessage()`: that message appears when the key is pressed and then fades. The HUD's `AliveCellCount` counts *living* cells while the screen shows only the filtered subset, so with a filter on, the number and the picture disagree and nothing persistent explains why. The neighbouring cuts already have exactly this — `bCullVolumeActive`, `bViewSliceActive` — and the age filter had nothing.

**`StepsPerRender` versus `GenerationsPerDispatch` — asked for against achieved.** The GPU strategy computes a batch in one round only while the AABB volume fits under its ceiling, and that volume grows with the structure. Once it stops fitting the batch is trimmed to a single generation, which the log reports as `поколений за круг: 1 из 3` — and the HUD used to show the requested 3 and say nothing about it. Worth seeing, because it is not a small performance detail: a dispatch in that state takes seconds rather than milliseconds, `Tick()` re-paces itself from this same number so that `Speed` keeps meaning generations per second rather than dispatches per second, and a collapsed batch is the early sign that outright CPU fallbacks (`bComputeFellBackToCpu`) are coming as the volume approaches the 32-bit indexing ceiling.

The assignment lives in `CommitComputedGenerations()` rather than `ApplyStepResult()`, ahead of every early return, so both step paths maintain it — it used to be set only on the Play path and would have shown a stale figure after a manual step. Note the two paths differ honestly here: `Next()` (**F**) keeps looping until the requested count is reached however many rounds that takes, so equality with `StepsPerRender` is normal there; a discrepancy is a continuous-run phenomenon, because that path deliberately breaks out as soon as a batch comes back trimmed.
