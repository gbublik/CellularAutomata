# HUD — `Ui/`

The C++/UMG split, `FHudStats`/`FCellRenderStats`, rule presets, and the generation graph widget. Read before adding anything the HUD must display.

- **`Ui/` — the HUD.** `FUiController` (`Ui/UiController.*`) is a plain (non-UObject) RAII-style helper, not an actor: it lazily creates a `UUserWidget` from a `TSubclassOf<UUserWidget>` set by the orchestrator (`HUDWidgetClass`) and exposes `ShowHUD/HideHUD/ToggleHUD`. Owned via `TUniquePtr` by `AAutomataOrchestrator`, driven from `BeginPlay()` (see that bullet for why not `PostActorCreated()`).

**A UMG widget never sees a keypress** — input arrives at `AGamePlayerController`, so anything the HUD should react to needs a bridge. **F5** (`OnToggleHudInfoPanel()` → `AAutomataOrchestrator::ToggleHudInfoPanel()`) is that bridge for hiding the info panel: it forwards to `UMainHudWidget::OnToggleInfoPanel()`, a `BlueprintImplementableEvent`. C++ deliberately does not know *what* gets hidden — one panel, several, or a cycle of "everything → compact → nothing" — because that is layout, and layout lives in UMG. The same shape is the right one for any future HUD key. `GetHudWidget()` (via the new `FUiController::GetWidget()`, a weak reference rather than the raw public `NewWidget` field) reaches the widget, and `ToggleHud()`/`IsHudVisible()` finally expose `FUiController::ToggleHUD()` — written long ago and, until now, called from nowhere at all.

**Split of responsibilities — C++ supplies data and actions, the visuals are built by hand in UMG**: `UMainHudWidget` (`Ui/MainHudWidget.*`) is a thin native shell whose only job is `GetOrchestrator()` — a lazily resolved, `IsValid()`-revalidated `GetActorOfClass()` lookup (the same idiom as `EnsureRenderCullVolume()`), deliberately *not* an editor-assigned reference, since a widget asset cannot hold a pointer to a specific level actor. The layout lives in a Blueprint subclass (`Content/HUD/WBP_MainHud`) assembled in the UMG Designer. Everything the widget needs is therefore exposed as `BlueprintPure`/`BlueprintCallable`/`BlueprintType` on the orchestrator; when the HUD needs something new, the change belongs in C++ as API, not as widget-construction code.

**Data**: two `USTRUCT(BlueprintType)` summaries, both computed once and read by everyone rather than recomputed per consumer (so a log line and the on-screen number can never disagree). `FCellRenderStats` (`GetLastRenderStats()`) — `RenderedCellCount`/`TotalCellCount` ("drawn/total", i.e. how much the cull volume is removing), `EstimatedUploadMB` (sized from `RenderedCellCount`, a single figure like a file size, not a before/after pair) and `BytesPerInstance`, filled by `BuildCellRenderData()`. `FHudStats` (`GetHudStats()`) — `bIsComputing`/`bIsRendering` (the `bStepInProgress`/`bChunkedRenderInProgress` phases, which can overlap), `CurrentFPS` (`GAverageFPS`, not recomputed), `GenerationCount`, `GenerationsPerSecond` (recomputed on a one-second window, not per frame — sub-second sampling is visibly noisy at low `Speed`), `EstimatedGpuComputeUploadMB` (read from whatever the GPU strategy already packed, never a separate grid scan), plus `AliveCellCount` (`Grid->Num()`, O(1) — the chunks keep the count) and `SelectedCellCount`. The last two refresh every tick, so a Delete or a new selection shows up immediately rather than at the next generation. Three more mirror the live *settings* rather than measurements, so the HUD reads exactly what the hotkeys change instead of keeping its own copy: `SimulationSpeed` (`Speed`, +/-) and `StepsPerRender` (T/G), and `CameraSpeed` — read straight off the possessed pawn's `UFloatingPawnMovement::MaxSpeed` rather than derived from `CameraSpeedMultiplier`, since the controller has already multiplied it while Left Shift is held and the HUD should show the boosted figure. Note `SimulationSpeed` vs `GenerationsPerSecond` is target vs. actual: the gap between them is the readable sign that the sim is compute-bound rather than throttled by its setting. A **mode block** follows the same mirror rule, one field per hotkey — `bSimulationRunning`/`bFastStepActive` (Space, Shift+F), `bSelectionModeActive` (Tab, read off the controller), `ComputeMethod`, `bChunkedRenderEnabled`/`ChunkedRenderOrder`/`bWaitForChunkedRenderToFinish` (Z/X/V), `bCellCullingEnabled` (B), `bRenderCullVolumeEnabled`/`bRenderCullVolumeVisible` (C, Ctrl+C) and `bGhostShapeEnabled` (H), plus `bCellsCastShadows` and `bBackgroundVisible` (U) and the render-profile trio `RenderPresetName`/`RenderPresetIndex`/`bRenderPresetModified` (F1–F4 — see `RenderPresets` above; the last one is what lets the widget draw a "Performance\*" once a hotkey has changed something the profile owns). Four of them are *effective* states rather than switches, and exist precisely because they can't be derived from the switches in the widget: `bCullVolumeActive` comes straight from `GetActiveCullVolume()` (which also requires the actor to be present in the level), and `bGhostShapeReplacesDetailedRender` from `ShouldGhostShapeReplaceDetailedRender()` — the mode that actually buys the speed. Reading them from the same functions the renderer uses is the point; a widget-side copy of those conditions could drift.

The other two, `bCellCullingActive` and `bViewSliceActive`, complete the trio of "is this actually cutting right now" flags behind the HUD's three cut indicators — **Culling** (B, distance), **Volume** (C, the box) and **Slab** (J, the view slice), i.e. the terminology split described under `Automata/Rendering/`: culling is what the renderer skips *after* the instances are built, the other two remove cells in `BuildCellRenderData()` before anything is built at all. All three lamps are wired to "cutting", never to "switched on", and `bCellCullingActive` is why: `bEnableCellCulling` defaults to **true** while both cull distances default to **0** (the engine's own "off"), so an indicator bound to that switch would be lit from the first second of every session while nothing whatsoever was being culled. `bViewSliceActive` adds the camera-availability half of the condition `BuildCellRenderData()` itself checks — the slice plane is defined by the camera, so without one there is nothing to cut with. The plain switches (`bCellCullingEnabled`/`bRenderCullVolumeEnabled`/`bViewSliceEnabled`) all survive alongside, so a widget wanting a third, dimmed "armed but inert" state can build it from a pair of fields with no C++ change. `LastHudStats` is a `UPROPERTY` for the usual Live-Coding-reinstancing reason (see `GamePC`).

**Actions**: the simulation entry points were already `BlueprintCallable`; the HUD additions are `SetSpeed()`/`SetStepsPerRender()` (absolute setters for sliders, applying the same clamps as the `+`/`-` and T/G hotkeys rather than letting a slider write the `BlueprintReadWrite` property raw and reach 0), `TryApplyRuleString(In, out Error)` (same as `ApplyRuleString()` but takes the string as a parameter and hands the parse error *back* — a `UE_LOG` warning is invisible from UMG, and silently doing nothing on a button press is the worst option), and `GetActiveRuleString()`.

**`RulePresets` (`Automata/Simulation/RulePresets.h/.cpp`, plain namespace + `FRulePreset` `USTRUCT(BlueprintType)`)** — 13 ready-made rules transcribed verbatim from williamyang98/3D-Cellular-Automata's `system_entries.js`, in the source's own order and naming so a preset can be checked against the site one-to-one (this project's own finds are appended **after** that whole block, never inserted into it, precisely so that one-to-one numbering survives — currently one: **`Crystal Growth 1 (Moore)`**, `0-6/1,3/2/M`, which differs from the catalogued `Crystal Growth 1` in a single letter, the neighbourhood, and that is enough to change the growth geometry — under Moore the diagonals advance as fast as the axes, so the front is cubic and throws straight rays, where von Neumann's Manhattan metric gives an octahedral front with faces instead. Its core reads as a symmetric cross and is the strongest logo candidate so far) ("Builder 1"/"Builder 2" really are duplicates upstream; kept so the numbering matches). Each carries `Name`/`RuleString`/`SpawnRadius`/`Amount`; `GetRulePresets()` lists them and `ApplyRulePreset(Index, bApplySpawnSettings)` applies one **through `TryApplyRuleString()`**, so presets and hand-typed rules share exactly one application path instead of two that could drift. It deliberately does *not* regenerate the grid — applying a rule to an already-grown structure is sometimes exactly what's wanted, and "start fresh with this preset" is one more `GenerateState()` click. The upstream table specifies a fill *density*, which this project can't use directly (`Amount` is an absolute count and the `RandomBall` generator reject-samples **with collisions**, so `density × volume` systematically under-seeds); `Amount` is therefore derived with the coupon-collector estimate `N·ln(1/(1-p))`, `p` capped at 0.95 since full coverage by random draws is unreachable in principle. Two presets whose upstream radius is grid-relative get a concrete radius of 30, because `GridSize` doesn't affect generation in this project at all (it is saved and loaded, but generation seeds purely by `GenerationParams.Radius`).

**The generation graph — two lines over generation number, and the first time-series storage in the project**: everything else HUD-facing (`FRenderTimings`, `FCellRenderStats`, `FHudStats`) is a snapshot of the last moment. A single instantaneous number cannot show what a run is actually judged by — where the rule accelerates, where it plateaus, where it collapses, and how much the cull volume is really taking off the renderer's plate — so `UGenerationGraphWidget` plots **total alive cells** against **rendered ("visible") cells**.

The two numbers arrive from different places at different rates, and that asymmetry is the whole design. Alive exists for every generation that reaches the game thread (`ApplyStepResult()`, right after `GenerationCount += Generations`); rendered exists only where `BuildCellRenderData()` actually ran. Four independent mechanisms punch holes in the second series — `StepsPerRender`, GPU batching (intermediate generations never exist on the game thread at all, and the batch is trimmed at runtime), series fast mode, and Ghost Shape replacing the detailed render — so the stride is not constant. Two consequences: samples are stored as **`(generation, value)` pairs** and X is mapped **by generation value, not by array index** (index mapping would compress and stretch the curve every time the batch size changed); and nothing may assume `rendered ≤ alive`, since under `States > 2` decaying cells are drawn but not counted alive.

`Automata`-style free functions in `Orchestration/GenerationHistory.h/.cpp` (namespace `GenerationHistory`, the `CellAging`/`CellSelection` idiom) own the window; `AAutomataOrchestrator` owns only the `UPROPERTY(Transient) TArray<FGenerationSample> GenerationSamples` (Transient for the `LastHudStats` reason — history cannot be recomputed on the next render, so Live-Coding reinstancing must not wipe it) and `GenerationHistoryCapacity` (512 **samples**, not generations). The member is named `Samples`, not `History`, because inside the class the latter would shadow the namespace.

Two write paths, deliberately asymmetric. `AppendGenerationSample()` sits beside the two `GenerationCount` increments (`ApplyStepResult()` and `Next()`'s completion) and **above** both render-skip returns, next to the series-capture and Ghost-Shape hooks and for the same reason: the alive line describes the simulation, not the screen. It carries the previous sample's rendered value forward, which is what makes the rendered line hold its last value as a step instead of dropping to zero. `NoteRenderedCells(int32)` is called from the four render points and **takes the count as a parameter rather than reading `LastRenderStats`** — `BuildCellRenderData()` has four callers, two of which (`BuildSliceCapture()`/`EstimateSliceCaptureSize()`) save and restore those stats, so "only the callers that leave fresh stats call me" is an unwritten contract a fifth caller would break silently. The parameter also lets the two Ghost-Shape branches record an honest **0**: zero detailed instances really do reach `AddInstances()` there, and watching the rendered line drop to the floor when Ghost Shape takes over is precisely the diagnostic the graph exists for. When the last sample is already about the current generation it is edited **in place** — load-bearing, not an optimisation: `RefreshRenderCullVolume()` fires from `Tick()` on every camera move while the view slice is on, and without in-place editing one flight of the camera would smear a single generation across hundreds of X positions. History is cleared in `ResetGenerationCounter()`, the one funnel for all five "start a run over" paths; `BakeCellsToMesh()` deliberately does **not** clear it, since a bake is "freeze and inspect" and the run that produced the sculpture is exactly what you want beside it (the visible consequence: `AliveCellCount` on the HUD drops to 0 while the graph keeps the curve).

**The widget is `UWidget` + `SLeafWidget`, not `UUserWidget` + `NativePaint`** — that was the first design and it is wrong for a reason worth recording: `SObjectWidget::OnPaint` paints **all** children first and only then calls `NativePaint` with a raised `LayerId`, so axis labels placed inside such a widget would sit *under* the graph and an opaque background would erase them outright, forcing axis text to be drawn from C++ via `MakeText` — which defeats the entire "layout lives in UMG" split. As a leaf widget it is an ordinary node of the tree: drop it in an `Overlay`, stack `TextBlock`s on top, and it appears directly in the palette (`GetPaletteCategory()` → "Automata", which **must** be `#if WITH_EDITOR` or non-editor builds fail to link) with no intermediate Widget Blueprint. Three more obligations that bite only later: `ComputeVolatility()` must return `true` (the data changes with no Slate invalidation whatsoever, so under `RetainerBox`/`InvalidationBox` or `Slate.EnableGlobalInvalidation 1` the graph would freeze on a cached image), `ReleaseSlateResources()` must reset the shared pointer, and colours must be multiplied by `InWidgetStyle.GetColorAndOpacityTint()` or the graph stays opaque while its parent panel fades. `MakeLines` takes its point array **by value** and in **local** coordinates. Y is scaled by the max of *both* series, pinned at 0, rounded to a nice 1/2/5×10^k ceiling with hysteresis (a raw per-frame max makes the whole curve breathe), and `bLogScaleY` exists mainly for the cull volume: with it on, rendered runs two or three orders of magnitude below alive and a linear axis lays that line flat on the floor.

`AGameHud` (`Core/Hud/GameHud.*`, wired via `AAGameMode::HUDClass`) is separate and unrelated to UMG: a native `AHUD` subclass whose `DrawHUD()` paints the live marquee rectangle during a selection drag.
