# Input and camera — `Core/PlayerController/`, `Core/CameraManager/`

Every hotkey, the NumPad camera layout, the orthographic projection and the headlight. Read before adding or rebinding a key, or touching camera framing.

- **`AGamePlayerController`** (`Core/PlayerController/GamePlayerController.*`) — owns the camera. No spline-following camera anymore (removed — see below); just toggles between gameplay input (`FInputModeGameOnly`, pawn input enabled) and UI input (`FInputModeGameAndUI`, cursor shown, pawn input disabled) via `SetCameraControlEnabled()`, and on `BeginPlay` sets FOV (viewmode is no longer forced here — see hotkeys below). `SetupInputComponent()` binds the project's testing hotkeys **from one table** — a `TArray<FHotkeyRow>` where each row carries an action name, its key or keys, and the handlers with their trigger events, walked once to create the `UInputAction`, map the keys and bind the handlers. It used to be three passes spread over a hundred and fifty lines (create every action, then map every key, then bind every handler), so answering "what does this key do" meant three lookups, and nothing but care kept the three in step — the render presets even carried a `static_assert` that the number of keys matched the number of actions, an invariant a table cannot express because it has nothing to drift against. Same shape as `RulePresets`/`RenderPresets`/`CapturePresets`: a constant table and one loop. The `UInputAction`s are still constructed at runtime via `NewObject` rather than saved as `.uasset` content — as assets the bindings would live in binary files invisible to `git diff`, and it would do nothing for the keys deliberately caught in raw `InputKey()` anyway.

**Which keys those are is configurable, and from one place for both halves — `HotkeyRegistry` (`Core/PlayerController/HotkeyRegistry.h`).** Every hotkey in the project is a value of `EHotkey`; a table pairs each with the name it is looked up by (`CA_*`) and the key it falls back to. `AGamePlayerController::KeyFor()` answers with the resolved key, and *both* the Enhanced Input table and every branch of `InputKey()` ask it rather than naming an `EKeys::` constant. Covering both halves is the whole point rather than thoroughness for its own sake: there are **more** keys in `InputKey()` than in Enhanced Input — 43 against 37 — and they are the most-pressed ones (Space, R, N, Y, P, the digits, the whole NumPad, F5–F7, F10), so a configuration scheme built on mappings alone would have covered the smaller and less important half of the board.

The source is the engine's own `UInputSettings::ActionMappings` — `UPROPERTY(config, EditAnywhere)`, so the keys sit as text in `Config/DefaultInput.ini` (visible in `git diff`) and are editable in **Project Settings → Input → Bindings** with no code and no rebuild. It is taken purely as a *data source*: handler dispatch is still ours, and the legacy binding path is not used. Defaults stay in code, so an empty or absent config is the default layout rather than no controls at all. Conflicts are logged rather than trusted to care — a key assigned twice produces neither a compile error nor a refusal, just two things happening at once — and pairs that share a key deliberately (Ctrl+Z against bare Z) are marked `bModifierGuarded` so the warning stays meaningful. Re-reading the config mid-session is deliberately not supported: the `UInputAction`s are already bound by then, so half the layout would move and half would not; an edit takes effect on the next PIE run. `W`/`A`/`S`/`D`/`Q`/`E` are the one thing left out on purpose — they are the pawn's movement keys, bound in `RebindPawnVerticalMovement()`, and a second copy here could drift from what actually flies the camera. Guarded by `Input.HotkeyRegistry` — see `docs/testing.md`. Every handler resolves the orchestrator through the cached `FindOrchestrator()` (except the camera-only ones); it was forty-seven copies of a `UGameplayStatics::GetActorOfClass` call, each correct — a keypress is rare, the cost is irrelevant — and each a place to edit if finding the orchestrator ever changes. All keys are mapped on one shared `SimulationMappingContext` — all except **Space**: **Space** (`OnToggleSimulation()`, originally **P** — moved once the key had proven to be the one pressed most often, freed by dropping Space from the pawn's vertical-movement axis, see `RebindPawnVerticalMovement()` below) calls `Start()`/`Stop()` depending on `IsSimulationRunning()`, and is deliberately **not** routed through Enhanced Input at all — it's caught in an `InputKey()` override on the controller, which fires immediately per raw OS key message (`WM_KEYDOWN`, `IE_Pressed` only, so no repeat-on-hold). Enhanced Input evaluates its triggers once per `Tick` by sampling the key's current down/up *level*, so under heavy frame lag (large `AddInstances`/HISM cluster-tree rebuilds at high cell counts) a quick press-and-release of the pause key could land entirely inside one long frame gap and never register as a transition — the pause got harder to catch the worse the lag became, which defeated the whole point of a pause key; `InputKey()` sees every press regardless of frame length. The other hotkeys stay on Enhanced Input — they're either less lag-critical or hold-style bindings that genuinely want per-tick evaluation; **F** (`OnFastStepPressed()`/`OnFastStepReleased()`, bound to `ETriggerEvent::Started`/`Completed`) — a bare press (no Shift) calls `Next()` once, which now advances **`StepsPerRender` generations per press** (the same value tuned via T/G), computed off the game thread, rendering only the final one (see `Next()` under the orchestrator bullet below); if Shift is down at the moment F is pressed (checked via `IsInputKeyDown(EKeys::LeftShift)`, not a separate Enhanced Input binding), it instead calls `AAutomataOrchestrator::StartFastStep()` — a **hold** mode, independent of `bSimulationRunning` and mutually exclusive with it (`Start()` refuses while `IsFastStepActive()`, and `StartFastStep()` refuses while Play is running), that paces steps by `Speed` exactly like continuous Play via the same `bFastStepActive` branch in `Tick()` (ahead of the `bSimulationRunning` branch, sharing `TimeSinceLastStep`/`StepAsync()`/chunked-render with zero duplicated logic) — and stops the instant F is released (`OnFastStepReleased()` calls `StopFastStep()` only if `IsFastStepActive()`). Bound to `Started`/`Completed` rather than `Triggered` specifically so a bare hold of F doesn't repeat `Next()` every frame (that was the pre-Shift-hold-mode behavior and confused continuous auto-stepping with a single step). **R** (`OnResetSimulation()`) calls `ResetToInitialState()` — rebuilds the grid from `InitialStateCells` (ages reset to 0), the shared "initial pattern" populated by whichever of `StartFromSelection()` (Enter), `LoadStateFromFile()` (Ctrl+O) or `GenerateState()` itself ran most recently (see the `InitialStateCells`/`ResetToInitialState()` paragraph below for the full picture), so an isolated glider/oscillator, a loaded save, or just the last random spawn can all be replayed from their exact starting shape. Deliberately *not* gated on `IsSimulationRunning()` since both paths guard their own race with `bStepInProgress`. **R is caught in the same raw `InputKey()` override as Space, not through Enhanced Input** — for exactly the reason described there (a quick press-and-release landing inside one long frame gap is never seen by Enhanced Input's per-tick level sampling, and R is pressed precisely when the sim is lagging hardest), and it goes through a *deferred* path on top: when a background step is in flight, `ResetToInitialState()` sets `bResetToInitialStatePending` and returns instead of refusing, and `ApplyStepResult()`/`Next()`'s completion performs the reset once the `Grid` race is over. Those were two independent bugs with one shared symptom ("R doesn't always work") — the input-sampling one and the silently-dropped-during-a-step one — fixed separately; **F1**–**F4** (`OnApplyRenderPreset0()`…`OnApplyRenderPreset3()`, each a thin wrapper over `OnApplyRenderPreset(int32)`) apply a whole **render preset** via `AAutomataOrchestrator::ApplyRenderPreset(Index)` — see `RenderPresets` under `Automata/Rendering/` below. These replaced a bare Lit/Unlit pair that sat on the same two keys: `VIEWMODE LIT`/`VIEWMODE UNLIT` are equivalent in cost here, so two keys were spent on a choice that changed nothing about speed. Viewmode is now one field of a preset alongside shadows, culling, background and a list of engine cvars. **U** (`OnToggleBackground()`) flips `SetBackgroundVisible()`/`IsBackgroundVisible()` — hide the sky/fog without losing the light (see that method below), and **Shift+U** (same handler, modifier checked in code) instead toggles the **headlight** — see `SetHeadlightEnabled()` under `Core/PlayerController/` below; separate from the presets because hiding the background is wanted on top of `Quality` too; **Vertical camera movement is rebound away from the engine defaults** (`RebindPawnVerticalMovement()`): stock `ADefaultPawn` binds its up/down axis to six keys, two of which are spoken for here — `LeftControl` fired on every Ctrl+S/Ctrl+Shift+S/Ctrl+O/Ctrl+C, and bare `C` on the cull toggle, so the camera sank at exactly the moment one looks at what changed. The two cannot be removed individually: they live in the private static `UPlayerInput::EngineDefinedAxisMappings`, which exposes only a const getter. So the engine binding is dropped from the pawn's `InputComponent` whole and replaced with an own axis on the same `ADefaultPawn::MoveUp_World`, leaving **E up and Q down** — the engine set minus the two collisions, minus Space. Space left that axis for a different reason than the other two: it wasn't in conflict with anything, it was simply the third key on one action (E already lifts) and the most valuable key on the board, while Play/Pause — the most-pressed hotkey in the project — sat on P, where the hand does not rest. Vertical movement lost a duplicate; the pause gained a thumb. It runs from `Tick()`, once per pawn (compared against `VerticalMovementBoundPawn`), because the pawn's `InputComponent` is created later than both `SetupInputComponent()` and `AcknowledgePossession()` — see `ClientRestart_Implementation`, where acknowledge precedes `DispatchRestart()`. **Left Shift** (held) — `OnSpeedBoostStarted()`/`OnSpeedBoostEnded()` (bound to `Started`/`Completed`) scale the possessed `ADefaultPawn`'s `UFloatingPawnMovement::MaxSpeed` by `AAutomataOrchestrator::CameraSpeedMultiplier` for faster flying while held, restoring the original speed on release — `BaseFlySpeed` caches that original value on first press (guarded by `<= 0.0f` so a stray repeated `Started` can't cache an already-boosted speed). `CameraSpeedMultiplier` lives on the orchestrator rather than the controller/pawn so a designer tunes it from the same Details panel as the rest of the simulation; **Z** (`OnToggleChunkedRender()`) flips `AAutomataOrchestrator::bEnableChunkedRender` via `SetChunkedRenderEnabled()`/`IsChunkedRenderEnabled()` — there's no automatic cell-count threshold for chunked rendering (an earlier `ChunkedRenderCellThreshold` property was removed), it's purely a manual on/off toggle now. **Ctrl+Z** (`OnUndoLastAction()` → `AAutomataOrchestrator::UndoLastAction()`) is a *different* action on the same key — **undo whatever happened last**, and it covers two mechanisms behind one key because to the user it is one action rather than a choice of machinery. If the newest journal record was made on the *current* generation, nothing has stepped since, so that manual edit is undone — an inverse delta straight onto the grid, instant. Otherwise the last thing that happened was a simulation step, and *it* is undone: the grid is re-seeded from `InitialStateCells` and run forward to `GenerationCount - 1` in one background dispatch, no intermediate generation rendered, replaying the edit journal at the generations where the edits were made (see `StepBackward()` and `CellEditJournal` in `docs/orchestrator.md` — why a state history is not the mechanism for generations while a delta journal *is* for edits, and the caveat about editing the rule mid-run). **Ctrl+Shift+Z** (`OnRedoEdit()` → `RedoLastEdit()`) puts an undone *edit* back; there is deliberately no redo for a step, since stepping forward is what **F** already does. Caught in the raw `InputKey()` override like Space/R/N/Y — a modifier cannot be expressed in an Enhanced Input mapping, and this is the same lag-critical class of key — while bare **Z** stays on Enhanced Input, so `OnToggleChunkedRender()` opens with a Ctrl check and returns (the Ctrl+S idiom, in the other direction: here the *bare* handler is the one that has to exclude the modifier). Bound to `IE_Pressed` only, never `IE_Repeat`, and that is load-bearing rather than stylistic: undoing a step costs a full replay from generation 0, so auto-repeat on a held key would sum every generation number below the current one — quadratic. Shift is checked inside the same block rather than mapped, the usual reason. **X** (`OnCycleChunkedRenderOrder()`) advances `AAutomataOrchestrator::ChunkedRenderOrder` to the next `EChunkedRenderOrder` value by calling `CycleChunkedRenderOrder()` (wraps back to `Sequential` after the last value) — see `EChunkedRenderOrder` under Chunked rendering below for what each order looks like; **V** (`OnToggleWaitForChunkedRenderToFinish()`) flips `AAutomataOrchestrator::bWaitForChunkedRenderToFinish` via `SetWaitForChunkedRenderToFinish()`/`IsWaitingForChunkedRenderToFinish()` — see `bWaitForChunkedRenderToFinish` under Chunked rendering below for the two interrupt-vs-wait behaviors this switches between; **B** (`OnToggleCellCulling()`) flips `AAutomataOrchestrator::bEnableCellCulling` via `SetCellCullingEnabled()`/`IsCellCullingEnabled()` — see `bEnableCellCulling` under `CellCullStartDistance`/`CellCullEndDistance` below; **C** (`OnToggleRenderCullVolume()`) flips `bEnableRenderCullVolume`, and **Ctrl+C** (same handler, modifier checked in code) flips the box's own visibility instead via `OnToggleRenderCullVolumeVisibility()` — see `ARenderCullVolume` under `Automata/Rendering/` below; **H** (`OnToggleGhostShape()`) flips `bEnableGhostShape` via `SetGhostShapeEnabled()`/`IsGhostShapeEnabled()` — see the Ghost Shape paragraph there too; **N** (`OnNewSeed()`) calls `AAutomataOrchestrator::NewSeed()` — re-rolls `Seed` and re-seeds the grid, i.e. the "show me a different one" counterpart to **R**, which replays the *same* `InitialStateCells` pattern. **Shift+N** (`SetAutoReseedOnExtinction()`, modifier checked in the handler as everywhere else) turns that press into a mode instead: while it is on, a generation that leaves the grid empty re-rolls the seed by itself and the automaton keeps running — a brute-force search for a seed that survives, since extinction is the usual fate of a random pattern and hunting for a live one by hand was "Space, watch, everything goes dark, N, Space" on repeat. Switching it on also **starts the run** if it is stopped — nothing goes extinct while nothing is being computed — and re-rolls at once if the grid is already dead; switching it off leaves the run going. See `bAutoReseedOnExtinction` in `docs/generation.md`. **Caught in the same raw `InputKey()` override as Space and R, not through Enhanced Input, and deferred through `bNewSeedPending` the way R is through `bResetToInitialStatePending`** — it had exactly the same two independent sources of dropped presses as R did (per-tick Enhanced Input level sampling missing a short press inside one long lagged frame, plus a silent refusal while a background step holds `Grid`), and for the same reason: a re-roll is pressed precisely when the grid has grown big and ugly, i.e. when the lag is worst. The two pending flags are mutually exclusive (each clears the other), since N and R want incompatible things from the same `Grid` — last press wins rather than whichever flag happens to be checked first. `Seed` is deliberately re-rolled only at the moment the deferred re-seed actually runs, not when the flag is raised, so repeated presses during one long step burn one seed rather than several unseen ones; **Y** (`OnGenerateState()`) builds the initial state with the currently selected geometric generator (`AAutomataOrchestrator::GenerateState()`), **Shift+Y** cycles to the next generator type without building (`CycleStateGeneratorType()` — see `Automata/Generation/` below), and **Ctrl+Y** logs a live-neighbour histogram of the *current* structure (`AnalyzeLiveStructure()`, same section) — the modifier is checked inside the handler, as with every other Ctrl combination here. Caught in the same raw `InputKey()` override as Space/R/N for the same reason — the key is pressed exactly when the picture is disappointing and the grid has already grown, i.e. when the lag is worst — with Shift checked inside the handler, since Enhanced Input cannot require a modifier in a key mapping (the Ctrl+S/Ctrl+C idiom). Note **J** was the obvious letter and is already taken (`ToggleViewSliceAction`); `Y` was the only free letter left; **F6** (`OnCaptureTextureSlice()`) writes the current view out as a PNG slice, **Shift+F6** through a save dialog, and **F7** (`OnToggleSeriesCapture()`) records a whole series of frames as the simulation runs — see `Automata/Capture/` below; **F10** (`OnTakePhotoShot()`) takes the beauty shot instead — a real engine render at a resolution the window cannot hold, see "The photograph" under `Automata/Rendering/`. F10 specifically because the engine's own `DebugExecBindings` claim F1–F5, F9 and F11, F8 ejects from the pawn in PIE, and F6/F7 are already ours; **P** (`OnToggleSonification()`) switches the **sonification** on and off (`SetSonificationEnabled()`/`IsSonificationEnabled()`), and **Shift+P** (same handler, modifier checked in code as everywhere else) cycles the tuning preset instead — see `docs/sonification.md`. P is the one honestly free letter on the board: it came free when Play/Pause moved to Space (see the Space paragraph above), and nothing has claimed it since — every other letter of the alphabet is spoken for, which is why Ghost Shape had to reuse H and the neighbour histogram had to go on Ctrl+Y. The preset ride on Shift rather than a key of its own for the same reason, and because a mute *is* bare P — putting one action on two keys is the duplication that dropping Space from the vertical axis already fixed once. Shift deliberately does **not** touch the on/off state: presets are compared by ear, mid-run, and silencing the thing being judged in order to switch it would defeat the comparison. Caught in the raw `InputKey()` override alongside F5/F10, `IE_Pressed` only — these are one-shot toggles with nothing to gain from repeat-on-hold, and a modifier cannot be expressed in an Enhanced Input mapping anyway; **K** (`OnMoveCullVolumeToSelection()`) teleports the cull volume onto the current selection (`MoveCullVolumeToSelection()`) and **L** (`OnSelectCellsInCullVolume()`) selects every alive cell inside it (`SelectCellsInCullVolume()`, with the same Shift/Ctrl combine modifiers as a marquee drag) — the two together make the cull box usable without the viewport gizmo: select a cell, K to bring the box there, L to grab everything it now contains; **=/NumPad+** and **-/NumPad-** (`OnIncreaseSpeed()`/`OnDecreaseSpeed()`, both bound to `Triggered`, so holding repeats — at the auto-repeat rate, see `ShouldFireRepeat()` below) call `AAutomataOrchestrator::AdjustSpeed(±SpeedAdjustStep)` to nudge `Speed` up/down by a fixed `0.5` step — or `±SpeedAdjustStepFast` (`5.0`) with **Shift** held, since fifty half-steps to cross the range is the same complaint that put Shift+T/Shift+G on powers of two, and a ten-fold multiplier is enough here because the `Speed` scale is linear rather than exponential. Unlike Shift+T/Shift+G, Shift does **not** route to a separate handler: the coarse step is the same operation, only bigger, so it is one `IsShiftHeld()` inside the existing handler (Enhanced Input cannot require a modifier in a key mapping — the Ctrl+S idiom). Clamped to `[0.1, 100.0]` inside `AdjustSpeed()` itself — deliberately wider than `Speed`'s own `UIMax = "10.0"` metadata, since that only caps the Details-panel slider, not a hard `ClampMax`; **Home** (`OnFrameAllCells()`) resolves the orchestrator and delegates to the public `AGamePlayerController::FrameAllCells(AAutomataOrchestrator*)`. It is a public method rather than a private handler because `ResetToInitialState()` used to call it through `GamePC` at the end of every R press — that auto-framing was **removed** (R now only rebuilds the pattern and leaves the camera exactly where it was, since being yanked to a framing distance on every reset fought with flying around a structure), so today the only caller is the explicit Home press. `FrameAllCells()` moves the possessed pawn along its *current* view direction (viewing angle unchanged, only distance) so the whole live-cell set fits in frame — `AAutomataOrchestrator::ComputeAliveCellsBounds()` scans `GetAliveCells()` once for a world-space AABB (via `GridToWorld()` on the min/max cell coordinates, expanded by half a `CellSize` since `GridToWorld()` gives cell *centers*) and returns its center and bounding-sphere radius (`FrameAllCells()` itself returns `false` and does nothing if the grid is empty/uninitialized or the pawn/camera aren't ready yet); it then computes `Distance = Radius / sin(FOV/2)` (the exact distance at which a sphere of that radius exactly fills the frustum half-angle, using `PlayerCameraManager->GetFOVAngle()`), multiplies by a small `FramingPadding` (`1.1`) so cells don't touch the frame edge, and sets the pawn's location to `Center - CameraRotation.Vector() * Distance` via `PlayerCameraManager->GetCameraRotation()`; **T**/**G** (`OnIncreaseStepsPerRender()`/`OnDecreaseStepsPerRender()`, bound to `Triggered` like `+`/`-` for Speed, so holding repeats at the same auto-repeat rate) call `AAutomataOrchestrator::AdjustStepsPerRender(±1)` to nudge `StepsPerRender` (see `StepsPerRender` under Chunked rendering below), clamped to `[1, MaxStepsPerRender]` inside `SetStepsPerRender()`, which `AdjustStepsPerRender()` now routes through. **Shift+T/Shift+G** step to the next/previous **power of two** instead (`OnDoubleStepsPerRender()`/`OnHalveStepsPerRender()` → `ScaleStepsPerRender(bool)`): a step of one never reaches the interesting values, since typing 256 from the keyboard is either 255 presses or catching it on auto-repeat, where overshooting is easier than landing (observed — an intended 256 came out as 254). Powers of two are what matter here: the clean picture from fractal rules falls on 2^k, and the batching ceiling in `FGpuComputeStrategy` is governed by a halo equal to the batch size. It steps to the next *power*, not simply doubling, so that one press off an uneven value lands on 2^k rather than preserving the unevenness (254 → 256, not 508). These are bound to `Started` while the ±1 pair stays on `Triggered` — a doubling that repeated every frame of a hold would hit the ceiling in a fraction of a second — and each of the four handlers checks Shift itself, since Enhanced Input cannot require a modifier in a key mapping (same idiom as Shift+F, Ctrl+S, Ctrl+C). `MaxStepsPerRender` (4096) exists only because of that doubling: without a ceiling it would overflow `int32` within a dozen presses; batching is trimmed long before it (originally mapped to `[`/`]` but rebound by hand during testing — see `SetupInputComponent()` for the current mapping). **Digits 0–9** (`OnSetAgeFilter(int32)`) filter the view down to a single cell age, and **Shift+digit** adds that age to the ones already shown or removes it if it is already there — see `AgeFilterValues` under `Automata/Rendering/` below; the whole **NumPad** positions the camera (axial views, isometric, orthographic toggle, ortho zoom, framing) — see `AGameCameraManager` below; both are caught in the raw `InputKey()` override rather than Enhanced Input, for a reason unrelated to Space/R/N's lag problem: ten-plus keys of one kind would be ten-plus `UInputAction`s for one lookup table. **Tab** (`OnToggleSelectionMode()`, originally C but rebound by hand during testing) toggles **one shared mouse-interaction mode** covering both cell selection (see the dedicated section below, after the cell-colour section) and HUD interaction — a separate H hotkey for "show the cursor so I can click the HUD" existed briefly and was folded into Tab, since both wanted the exact same state (`SetCameraControlEnabled(false)`: camera stopped, cursor shown, controller input still live) and having two keys toggling one thing independently could leave it half-on. **Any flight key leaves the mode too** — W/A/S/D/Q/E on `IE_Pressed`, handled in the same raw `InputKey()` override: pawn input is disabled inside the mode, so those keys used to do *nothing at all*, and they get pressed exactly when the selection or the cull box is finished with and one wants to fly on — the Tab that had to come first was pure ceremony. The press is not consumed (movement axes are polled from key state each frame, so a key already held starts moving the instant the mode drops, with no second press). **Ctrl is excluded** so that Ctrl+S — save, on a bare `S` mapping — cannot eject from the mode as a side effect; Shift is not, since Shift+W is the same movement, only faster. H was later reused for Ghost Shape. While active, **left mouse button** drag-selects a screen-space rectangle of cells (**Shift**+drag adds to the existing selection, **Ctrl**+drag removes from it — see `ESelectionCombineMode` in that section), **I** (`OnInvertSelection()`) inverts the selection against the alive-cell set, **Delete** (`OnDeleteSelectedCells()`) kills the selected cells in place without resetting the simulation, and **Enter** (`OnExtractSelection()`) launches the current selection as a fresh starting state; **M** (`OnBakeCellsToMesh()`) bakes the current state (or the selection, if one exists) into a single hollow mesh and unloads the cells from memory — see the Baking paragraph below; **S**/**O** (`OnSaveOrSaveAs()`/`OnLoadState()`) — Ctrl+S/Ctrl+Shift+S save/save-as, Ctrl+O loads, to/from a `.casave` file (see the `Automata/Persistence/` bullet below for the format and semantics) — mapped on the raw `S`/`O` keys *without* a modifier (Enhanced Input has no way to require Ctrl directly in a key mapping), so the handlers themselves check `IsInputKeyDown(EKeys::LeftControl/RightControl)` and silently return if Ctrl isn't held (bare `S` still drives `ADefaultPawn` camera movement, unaffected), then branch on Shift to pick `SaveState()` (Ctrl+S) vs `SaveStateAs()` (Ctrl+Shift+S). **Why hotkeys and not just the `CallInEditor` buttons**: clicking a `CallInEditor` button in the Details panel during PIE is unreliable — if the World Outliner still has the non-PIE (persistent-level) copy of the actor selected rather than its PIE-world duplicate, the click invokes the function on the frozen editor-world instance, whose `Tick()` never runs (`AActor::TickActor` early-returns when `TickType == LEVELTICK_ViewportsOnly`, which is how the engine ticks actors outside PIE) — so e.g. continuous Play silently never begins, with no error. Hotkeys sidestep this entirely since key input always arrives via the currently-possessing (PIE-world) `PlayerController`. Requires the `EnhancedInput` module (see below).
- **`AGameCameraManager`** (`Core/CameraManager/GameCameraManager.*`) — everything it adds to `APlayerCameraManager` is a switchable **orthographic projection** (NumPad 5): without perspective distortion the structure reads like a drawing, and together with the axial numpad views that is exactly how a DCC viewport is used to examine a shape. `AGamePlayerController`'s constructor points `PlayerCameraManagerClass` at it — the constructor and not `BeginPlay()`, since `APlayerController` spawns the manager in `PostInitializeComponents()`, i.e. earlier. **Why a camera-manager subclass and not a `UCameraComponent` on the pawn**: the pawn is a stock `ADefaultPawn`, which has no camera component at all (the view comes from `GetActorEyesViewPoint()`), and the projection mode lives in an `FMinimalViewInfo` that the manager rebuilds *every frame* — writing `ProjectionMode` into `PlayerCameraManager->ViewTarget.POV` from outside is overwritten by the next `DoUpdateCamera()`. `UpdateViewTarget()` is the one virtual hook where the view is already computed but not yet submitted to the renderer, and it runs for both the current and the incoming (blending) view target, so the projection doesn't flicker when the target changes. Two properties of the ortho view are deliberate: `bAutoCalculateOrthoPlanes` is turned **off** (it derives the clip planes from a view-target distance this project never sets, which would make the clipping unpredictable), and the visible slab is **symmetric around the camera** — `OrthoNearClipPlane` is *negative* — because ortho gets switched on while the camera is often *inside* the structure, and with a near plane of 0 everything behind the camera would simply vanish, which reads as a bug rather than as a change of projection (DCC ortho views behave the same way). The depth range is a finite `1000000` units rather than `UE_OLD_WORLD_MAX`: linear ortho depth over that range still resolves ~0.1 units in a float, a thousandth of a cell, so cube faces don't z-fight. `OrthoWidth` is stored here but *fitted* by the controller — the radius of the live cells is the orchestrator's knowledge, not the camera's. State fields are `UPROPERTY(Transient)` for the usual Live-Coding-reinstancing reason (see `GamePC` below), so a hot patch mid-PIE doesn't silently drop back to perspective.

**Hold-repeat is throttled — `AGamePlayerController::ShouldFireRepeat(FHotkeyRepeatState&)`.** `ETriggerEvent::Triggered` fires *every frame* while a key is down, so `+`/`-` and `T`/`G` moved `Speed` and `StepsPerRender` at 60–120 changes per second: the value hit its clamp before the finger came off, and landing on a chosen number meant tapping, never holding. The four handlers now pass through one shared throttle — the first press always fires, then nothing for `HotkeyRepeatDelay` (0.4 s), then one change per `HotkeyRepeatInterval` (0.15 s). Ordinary keyboard auto-repeat, in other words. `T`/`G` needed it more than `+`/`-` did: their step is an integer `1` and cannot be made smaller, so the repeat rate was the only knob left (`Shift+T`/`Shift+G`, the power-of-two jumps, are on `Started` and were never affected).

It is driven by **timestamps rather than a second binding on `Started`**, and that is the non-obvious part. Binding `Started` for the first press and `Triggered` for repeats looks cleaner but depends on the order in which Enhanced Input dispatches the two on the frame of the press — both fire on that frame, and if `Triggered` were dispatched first the press would count twice. Instead each key keeps its own `FHotkeyRepeatState` (per *key*, not per pair: one state shared by `+` and `-` would confuse holding one with tapping the other) and the handler asks how long ago it was last called. A gap wider than `HotkeyRepeatFreshPressGap` (0.25 s) means the key was released and pressed again — fire at once, restart the delay. The gap is longer than a frame but shorter than the delay, so on a badly lagging frame (millions of cells — the normal case here) a hold decays into a chain of "fresh presses", i.e. back to one step per frame; harmless, because at that point the frame rate is single digits anyway. The state fields are plain members, not `UPROPERTY`s, against the project's usual rule: after Live Coding reinstancing they hold garbage, but the worst garbage produces is one extra or one skipped press, after which all three timestamps are rewritten.

**NumPad — camera positioning.** Home frames along the current angle; this is the same thing from a chosen side. **4**/**6** — left/right, **8**/**2** — top/bottom, **1**/**3** — front/back (project axes are X forward, Y right, Z up, so "left view" is a gaze along +Y; the layout is geometric, like a DCC viewport), **7** — isometric, the only angle that shows three axes at once, i.e. the volume the axial views specifically hide, **9** — the same angle from the opposite side (the current view direction negated, not another fixed axis, since the angle may well have been set with the mouse), **0** — the same framing as Home (on the numpad because the hand is already there), **5** — ortho on/off, ***** / **/** — ortho zoom, **.** — frame the current *selection* instead of the whole grid (the pair to K/L: select an interesting piece, then fly to it without hunting for it by eye). **Requires NumLock on**: without it Windows sends `Left`/`Up`/`Home`/`Delete` from these keys — the very codes that move the cull volume. Not a conflict (they are different `FKey`s), but it is exactly why the numpad looks dead without NumLock.

All framing goes through one `AGamePlayerController::FrameBounds(Center, Radius, ViewDirection, bApplyRotation)` — Home keeps the current angle (`bApplyRotation = false`), the axial views also set the control rotation. Pitch is clamped to the camera manager's own `ViewPitchMin`/`ViewPitchMax` **before** the position is computed, and the position then uses the *clamped* direction: a top view is exactly -90°, which the manager trims to -89.9 on the first mouse move anyway, and standing the camera straight overhead while aiming 0.1° off walks the frame centre further off the bigger the structure gets. In orthographic mode the same call fits `OrthoWidth` instead of leaning on distance (distance does not affect an ortho picture at all), via `ComputeOrthoWidthForRadius()` — which fits the **smaller** side of the frame, since `OrthoWidth` is a *width* and the height follows from the aspect ratio, so on a wide screen (and it practically always is) the diameter has to be laid into the height or the grid gets cut off top and bottom. Toggling ortho on fits the width immediately, for the same reason: at the default width (or one left over from a differently-sized structure) the first press would show either one cell filling the screen or nothing at all, and that reads as a broken feature.

**A hand-picked ortho zoom survives a change of view.** `ScaleOrthoWidth()` (the `*` / `/` keys) marks the width as user-chosen (`HasUserOrthoWidth()`), and framing skips its own fit while that mark is set. Without it, switching to an axial view threw the zoom away — the numpad views go through the same framing code as Home, and that code *has* to set the ortho width or it would do nothing whatsoever in ortho, so picking a scale and walking around the structure by axis were mutually exclusive. Only explicit "fit this in frame" requests clear the mark: Home/Shift+Home, NumPad 0, NumPad . and enabling ortho; a change of view is not a request to fit, it is a request to look from elsewhere. The mark is raised in `ScaleOrthoWidth()` rather than in `SetOrthoWidth()` because automatic fitting goes through the setter too — counting that as "the user chose this" would let the first framing block every later one. Enabling ortho deliberately drops a zoom left from a previous session: the structure may have grown by an order of magnitude since, and the stale width would show exactly the emptiness that the initial fit exists to prevent.

**Shift+Home / Shift+\<numpad view\> frame only what is currently visible** — `AAutomataOrchestrator::ComputeVisibleCellsBounds()`, which mirrors the same three filters `BuildCellRenderData()` applies to alive cells: the cull volume (`GetActiveCullVolume()`), the age filter (`AgeFilter`/`bAgeFilterIncludesOlder`), the view slice (`bEnableViewSlice`). Plain Home still frames the whole structure, and the two are genuinely different requests: with the cull box cutting most of the grid away, framing the entire (mostly invisible) structure left the visible fragment tiny in the middle of an otherwise empty shot. The filtering is **duplicated** rather than calling `BuildCellRenderData()` — that one also colours cells and updates the view-slice refresh bookkeeping (`LastViewSliceCameraLocation`/...), none of which framing needs — so a change to one of the three filters has to be made in *both* places. It is not `const` (unlike `ComputeAliveCellsBounds()`) because `GetActiveCullVolume()` lazily caches the actor, the same reason `BuildCellRenderData()` isn't. Decaying cells are deliberately left out of the count: a framing sphere needs no per-decaying-cell accuracy and its radius already carries slack. `ComputeSelectedCellsBounds()` (NumPad .) is the third caller of the shared `ComputeCellsBounds(Cells, ...)` that the Ritter-sphere body was extracted into, and it filters the selection down to still-alive cells first (a selection outlives simulation steps).

`FHudStats::bOrthographicCamera` mirrors the projection off the controller (`IsOrthographicCamera()`), exactly like `bSelectionModeActive` — projection is camera state, not automaton state. And `AAutomataOrchestrator::ShowStatusMessage()`/`EStatusMessageKey` moved from private to **public** with a `StatusKey_Camera` added: the camera hotkeys live on the controller but have to report into the same on-screen channel, and a second `AddOnScreenDebugMessage()` call site would fork the convention — the engine's message keys are global, so lifetime, colour and key numbering must stay in one place or messages start overwriting each other.

**Status messages now go into the HUD, not over it.** The engine's on-screen channel draws its lines from a hardcoded 45 pixels down (`UnrealEngine.cpp`, `MessageStartY` — neither a setting nor a cvar), i.e. straight across the HUD's own top bar, and the bar cannot simply move down because several messages stack (45 plus 20 per line). `ShowStatusMessage()` therefore offers the message to `UMainHudWidget::OnStatusMessage(FText, int32 Key)` — a `BlueprintImplementableEvent`, same bridge shape as F5's `OnToggleInfoPanel()` — and only falls back to `AddOnScreenDebugMessage()` when the HUD cannot take it. Position, styling and lifetime become layout, which is where they belong; the three hardcoded seconds were presentation all along. That this was a one-place change is exactly the property described above: that call was the only `AddOnScreenDebugMessage()` in the project. The fallback checks whether the event is **implemented**, not merely whether a widget exists — an unimplemented `BlueprintImplementableEvent` is a silent no-op, so without the check the messages would have vanished outright the moment this shipped; a stub with no Blueprint implementation still has the native class as its `UFunction` owner, so a non-native owner is the signal that the graph has taken over.

**The headlight (Shift+U) — a lamp carried by the camera**, `AGamePlayerController::SetHeadlightEnabled()`/`IsHeadlightEnabled()`, off by default. It was briefly flipped to on-by-default and put back within the session: the scene's own light reads better on a whole structure, and the lamp is wanted point-wise, when going *inside* one. It exists for one case the level's lighting cannot serve: flying *inside* the structure. From outside, the directional light shapes the figure; inside a dense lattice only the faces it happened to reach through are visible, and the rest is a dark cave. A lamp at the camera lights whatever you are actually next to.

**The light hangs on the possessed pawn, not on the controller, and that is load-bearing rather than stylistic.** `AController` marks itself hidden in its constructor (`SetHidden(true)`), and `ULightComponent::CreateRenderState_Concurrent()` only adds a light to the scene when `ShouldRender()` — which folds in the owner's hidden flag — is true. Parented to the controller it would silently never light anything, with nothing in the log: exactly the failure mode `CellMaterial`'s missing `PerInstanceCustomData3Vector` node has. On the pawn it also follows the camera for free, so there is no per-frame position update. `EnsureHeadlight()` creates it lazily on the first switch-on (the default session never pays for it) and re-creates it if the pawn changes; switching off only calls `SetVisibility(false)`, since the lamp is flicked back and forth and re-registering a light in the scene is not free.

Three deliberate settings at creation. **Inverse-squared falloff is off** (`LightFalloffExponent = 4`, unitless intensity) so that `HeadlightIntensity` and `HeadlightRadius` are independent knobs — with inverse-squared, changing how far the light reaches also changes how bright it is, and inside a structure both get retuned constantly. **`SourceRadius = 0`**, since the source sits exactly at the eye. And **shadows default off** (`bHeadlightCastsShadows`): a shadow-casting point light is a cubemap, i.e. six more passes over the same millions of instances — the same cost argument that gave `bCellsCastShadows` its own switch. All four settings live on `AAutomataOrchestrator` (`Automata|Camera`, next to `CameraSpeedMultiplier`, for the reason recorded there) and are re-read every frame while the lamp burns, so a slider drag is visible immediately; that per-frame read is also the only reason the controller caches the orchestrator (`FindOrchestrator()`, the `FindCullVolume()` idiom) instead of resolving it per press like every hotkey does.

**Shift+U rather than its own key, because there is no own key left** — every letter of the alphabet is spoken for (see the hotkey list above). Of the taken ones U is the only one about light and background, which makes the pair read as one thought: *U* removes the scene's light, *Shift+U* brings your own. The modifier is checked inside `OnToggleBackground()`, the usual "Enhanced Input cannot require a modifier in a key mapping" idiom. Note the lamp is invisible under **F2 (Unlit)** — that viewmode ignores lighting entirely — and `FHudStats::bHeadlightEnabled` mirrors the state off the controller, exactly like `bSelectionModeActive`/`bOrthographicCamera`.
