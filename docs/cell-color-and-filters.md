# Cell colour and view filters

The per-instance colour ramps, the age filter, `FCellRenderInstance`, and the measured cost of chunked rendering. Read before touching colour or per-instance data.

**Cell color is per-instance data, not a material — one `CellMaterial`, a keyframe ramp, and `PerInstanceCustomData`**: cells used to be coloured by an `AgeMaterials` array (`TArray<UMaterialInterface*>`, ordered oldest→youngest, `MaterialIndex = N-1-min(Age, N-1)`). Because ISM/HISM applies a material per **component**, N materials meant N runtime components, a bucketing pass per generation, N `AddInstances` calls and N HISM cluster-tree rebuilds. That whole structure is gone. Now:

- **`CellMaterial`** (`UMaterialInterface*`) — the single base material for every cell of every age, and the only mandatory one (`GenerateState()`/`Next()`/`StepAsync()` refuse with a warning if it's unset, exactly like the pre-existing `!CellMesh` check; the render paths repeat the guard defensively, since it could be cleared in the Details panel between a background step's dispatch and its completion). It **must** contain a `PerInstanceCustomData3Vector` node (`DataIndex = 0`) feeding Base Color/Emissive. This is the one hard failure mode worth knowing: the engine derives `bHasPerInstanceCustomData` from the material itself (`MakeInstanceDataFlags(...)`, `InstancedStaticMesh.cpp:309`) and binds `GDummyFloatBuffer` when it's false (`:457`) — a material without that node renders every cell one flat colour with **nothing in the log**. Giving the node a loud `ConstDefaultValue` (magenta) makes "custom data never arrived" distinguishable from "the colour really is black".
- **`AgeColors`** (`TArray<FLinearColor>`) — keyframes **smoothly interpolated**, not bucketed. Ordered `[0]` = age 0 (just born) → `[Last]` = oldest: the **reverse** of `AgeMaterials`. Empty is deliberately *not* an error (unlike a missing `CellMaterial`) — it yields white, i.e. "whatever the material looks like on its own", which is the normal state right after assigning a material and before authoring a ramp; refusing to render there would recreate exactly the "why is nothing showing" confusion. One element = flat colour.
- **`AgeColorMaxAge`** (default 32) — the age at which the last keyframe is reached (`t = clamp(Age / AgeColorMaxAge, 0, 1)`). Deliberately decoupled from `AgeColors.Num()`: keyframe count is the ramp's *resolution*, this is its *duration*. Under `AgeMaterials` these were the same number, so "a smooth gradient, but over 4 generations" was unexpressible.
- **`DecayColors`** — a separate ramp for Generations decay states (`2 .. States-1`), empty = fall back to `AgeColors`. Previously decaying cells shared the age buckets and were pixel-identical to live ones, which hid the most interesting part of Generations rules. Note the fallback is *approximately*, not bit-identically, the old look: the old formula reused the age bucket index, the new one stretches the decay range across the whole ramp.
- **`ColorRampSpace` / `ColorRampCurve`** — *how* the ramp is interpolated, as two **orthogonal** switches: the space decides where the straight line between two keys runs, the curve decides how you travel along the keys, and they combine freely. Both apply to `AgeColors` and `DecayColors` alike, since this is a property of the interpolation rather than of a particular key set. Spaces: `LinearRgb` (the historical default — physically correct light mixing, but the line cuts through the RGB cube's interior so midpoints lose saturation, and steps read unevenly), `Srgb` (what a paint program does, so it matches what whoever drew the ramp expected), `Oklab` (perceptually uniform, Ottosson 2020 — no muddy midpoints, equal `t` steps give equal *perceived* difference; chosen over CIELAB, which OKLab was specifically designed to fix for its blue-region hue shift), and `Oklch` (the polar form — hue travels along the *arc*, always the short way, so saturation holds up instead of sagging through grey). Curves: `Linear` (piecewise, so the derivative jumps at **every** key — with three or more keys that shows as a visible seam exactly where a key sits) and `CatmullRom` (smooth, passes through all keys, endpoints handled by duplicating the outer keys). Defaults are the historical pair, so no existing ramp changes appearance silently.

The math lives in `Automata/Rendering/ColorRamp.h/.cpp` as free functions (namespace `ColorRamp`, the `CellAging`/`GenerationHistory` idiom) rather than on the orchestrator, precisely so it is testable without an actor, a tick or a render — `AAutomataOrchestrator::SampleColorRamp()` is now a two-line wrapper. **Cost is genuinely irrelevant here and that is the point**: this runs 256 times per render building the LUT, never per cell, so cube roots and splines alike are free against millions of instances — the choice can be made on looks alone. Three traps are handled and worth not re-discovering: `FMath::Pow` of a negative is `NaN`, so every transfer function is sign-preserving (a Catmull-Rom overshoot legitimately produces negatives); Catmull-Rom overshoot means the result **must** be clamped, or out-of-gamut colours reach `ToFColor()`; and under `Oklch` a grey or black key has **no defined hue** (`atan2` of zero returns an arbitrary angle), so such keys inherit their neighbour's hue instead of yanking the ramp in a random direction. `Rendering.ColorRamp` covers all eight space×curve combinations, and its load-bearing assertion is that **the keys reproduce themselves exactly at their own positions** — that is the one check that catches a round-trip conversion bug, which otherwise shows up as a barely-visible hue shift across the whole ramp that no one can distinguish from the intended colour. It also asserts that `LinearRgb` and `Oklab` *disagree* at the midpoint, since a version that silently ignored the setting would pass everything else.

- **`SelectionColor`** replaces the former `SelectionMaterial` — the highlight now draws with the same `CellMaterial` and differs only in its custom-data colour (`SelectionScaleMultiplier = 1.1` and the dedicated `SelectionMeshComponent` are unchanged). That multiplier is **relative** — `RenderSelectionOverlay()` applies it *on top of* `CellMeshScaleMultiplier`, not instead of it. While the latter was always 1 the distinction was invisible; on a lattice cell that needs a scale of 2 (rhombic dodecahedron, truncated octahedron) an absolute 1.1 drew the highlight at **half the cell's size**, entirely swallowed inside it — selection worked, it simply could not be seen.

Colours are `FColor` (not `FLinearColor`) inside `FCellRenderInstance` for size, and the conversion is **`ToFColor(bSRGB=false)`** — `PerInstanceCustomData` is a raw float the material never sRGB-decodes, so the quantisation must be linear; `bSRGB=true` silently washes the whole ramp out with nothing in the log. HDR brightness belongs on a scalar `Intensity` parameter on a Material Instance, not in the byte. As with `AgeMaterials` before it, the ramp applies identically in continuous Play (`StepAsync()` → `ApplyStepResult()` → `RenderCurrentGrid()`, chunked-render-aware) and in the manual step/spawn path (`Next()`/`GenerateState()` → `RenderGridImmediate()`, one-shot) — "this cell is young" shouldn't depend on how it got drawn.

**One renderer, not a pool.** `AgeMeshComponents`/`AgeRenderers`/`RebuildAgeMeshComponents()` are deleted; there is a single `TUniquePtr<FInstancedMeshCellGridRenderer> CellsRenderer` bound to `GetActiveCellsMeshComponent()`. `CellsMeshFlat`/`CellsMeshHierarchical` — the two permanent `CreateDefaultSubobject` components that had been reduced to attach-parents — receive instances again, which is what they existed for. `EnsureCellsRenderer()` replaces all three phases of the old rebuild with one condition (`!CellsRenderer || CellsRenderer->GetComponent() != Target`), covering first call, a `CellMeshComponentType` switch, and a Live-Coding-nulled `TUniquePtr` alike; on a rebind it clears the *previous* component so a type switch doesn't leave two overlapping grids. The old `AgeMeshComponents`-is-a-`UPROPERTY` dance is unnecessary now: the components are default subobjects that always survive reinstancing, and the plain `TUniquePtr` being nulled is exactly what the first half of that condition catches.

Two consequences at the call sites: `ApplyCellCullDistances()` no longer loops a pool (both permanent components plus `SelectionMeshComponent` already cover everything), and the defensive `ClearInstances()` in the render paths flipped from the **active** component to the **inactive** one (`ClearInactiveCellsMeshComponent()`) — the active one is now the render target and `BeginRender()` clears it every frame, so clearing it there would have the render wipe itself, while stale instances can only survive on the component `CellMeshComponentType` no longer selects. `ClearAllCellInstances()`'s orphan sweep needed no logic change and now doubles as the migration cleanup: with the legitimate set down to three components, every leftover runtime-created age component is an orphan it destroys on the first `BeginPlay`.

**`BuildCellRenderData()`** (replacing `BuildAgeBuckets()`) is the shared collection step for both render paths: one pass producing a single `TArray<FCellRenderInstance>` — live cells coloured from a 256-entry age LUT, plus (when `States > 2`) decaying cells from their own LUT. The LUTs are built once per render rather than per cell: at millions of cells a lerp per cell is millions of wasted lerps, while the table is 1 KB. Cull-volume filtering (`GetAliveCellsInBounds()`/`GetDecayingCellsInBounds()`) is unchanged and still happens before anything is built. It also fixes a long-standing undercount: `LastRenderStats.RenderedCellCount` used to be `AliveCells.Num()` written *after* decaying cells had been added to the buckets, so under Generations both it and `EstimatedUploadMB` were low by exactly the decaying-cell count. It now counts the array actually handed to the renderer — which means it can legitimately exceed `TotalCellCount` (`Grid->Num()` counts only live cells).

**`AgeFilterValues` — the view cut down to chosen age layers (digit keys)**: an **empty list** (the default) draws everything, and each entry keeps cells of exactly that age. A bare digit **0–9** selects that one age (the same digit again clears the filter); **Shift+digit** *adds* an age to what is already shown, or removes it if it is already there — remove the last one and the filter switches itself off, since "nothing selected" and "show everything" are one state, not two. Age is how many consecutive generations a cell has survived, so under rules where nothing ever dies (`0-6/1,3/2`) "age N" is precisely the concentric layer born N generations ago — an octahedron face under von Neumann, a cube face under Moore. That makes this layer-by-layer dissection, concentric, complementing the flat view slice.

**A set rather than a single age, because the interesting thing is the *combination* of layers**: where the growth front (age 0) sits relative to the old core is only visible with both on screen at once, and one-layer-at-a-time cannot show it. It started as a single `int32 AgeFilter` with `-1` for "off"; the list replaced it, and `TArray<int32>` edited in the Details panel is the same idiom as `BirthCounts`/`SurvivalCounts`. Order and duplicates carry no meaning — `ApplyAgeFilterChange()` canonicalises the list (sorted, deduplicated, clamped) so that a hand-typed panel entry behaves like a keypress and so that Shift+digit reliably finds an age already in the set. `GetAgeFilter()` survives for callers that want a single layer, but now answers only when exactly one is selected; `GetAgeFilterValues()`/`IsAgeFilterActive()` are the full picture.

**Off is the empty list, not age `0`** (as it was `-1`, not `0`, before). Age 0 is the just-born cells — the first colour of the ramp and the growth front, the single most interesting layer. The first version used zero as "off", which made that layer unreachable altogether and left the digits looking shifted by one against the colours; that was noticed immediately.

**The last digit is the deliberate exception: 9 means "age 9 and older"** (`bAgeFilterIncludesOlder`). There are ten digits and 256 ages, so without it every cell older than nine generations — the tail of the ramp, usually the largest part of the structure — was reachable by no digit at all. It is its own flag rather than a special case for 9 inside the comparison, because `AgeFilterValues` is also edited from the Details panel, where 9 is an age like 42 and has to mean exactly itself; and there is deliberately **no** "is anything older?" condition, since when nothing is, `>= 9` equals `== 9` and the flag changes nothing. **The flag belongs to the digit that raised it and leaves with it**: `ToggleAgeFilterValue()` clears it when Shift+9 removes the nine, so the tail can never stay switched on by itself — which would read as "the key did nothing".

The filter is expanded into a **256-entry mask** (`BuildAgeFilterMask()`) **before** the render loop, so the per-cell cost is one table read with no scan of the selected list across millions of cells. It was an `[AgeFilterMin, AgeFilterMax]` range while the filter was a single age; a range cannot express an arbitrary set of layers, and the mask is no more expensive per cell than the two comparisons it replaced. `SetAgeFilter(NewAgeFilter, bIncludeOlder)` (single age, `-1` clears) and `ToggleAgeFilterValue(Age, bIncludeOlder)` (add/remove) both set age and flag in one call — two calls would mean an intermediate state (right age, stale flag), each re-rendering the grid, i.e. a double render per keypress — and both clear the flag whenever the filter itself goes off, since it is meaningless there.

Decaying cells (Generations) are hidden **entirely** while any age filter is active: their age is undefined — decay is a separate state channel, not an age (`FCellGrid::IsDecaying()`) — and assigning them one would be a lie.

One UE 5.7 trap this ran into, worth knowing before touching any log line here: `ApplyAgeFilterChange()` (the shared tail of both setters) builds its log and on-screen strings with `if`/`else` *before* calling `Printf`, rather than picking a format string with a ternary. The format string is `consteval`-checked (`TCheckedFormatString`) and must be a literal, so `Printf(bFlag ? TEXT("a %d") : TEXT("b %d"), X)` does not compile at all.

`FCellRenderInstance` (`Automata/Rendering/CellRenderInstance.h`) is `{ FVector3f Position; FColor Color; }`, exactly 16 bytes. **`Position` is already world-space**, and that is load-bearing twice over: `AdvanceRenderChunk()` spans frames while `ApplyStepResult()` swaps `Grid` underneath it, so no grid reference may be held between `BeginRender()` and the last chunk — and it let `PendingTransforms` be **deleted outright**. `BeginRender()` used to materialise one `FTransform` per live cell up front and hold them for the whole reveal; `sizeof(FTransform)` is 80 bytes under LWC, i.e. ~560 MB at 7M cells against 112 MB now, with the transform construction moved into `AdvanceRenderChunk()` where it spreads across the reveal instead of spiking on one frame. Secondary win: the `DistanceFromCamera*`/`FromCenterOutward` comparators stop calling the **virtual** `GridToWorld()` twice per comparison.

Per chunk, `AdvanceRenderChunk()` builds that slice's transforms and a flat `TArray<float>` of RGB, calls `AddInstances()`, then one range `SetCustomData(First, First + Count - 1, Data, bMarkRenderStateDirty=false)`. **`MarkRenderStateDirty()` is deliberately never called**: `SetCustomData` already marks the changed instances through `PrimitiveInstanceDataManager` (`CustomDataChanged` → `MarkComponentRenderInstancesDirty()` → `MarkRenderInstancesDirty()`, latched by `bComponentMarkedDirty`), which is the cheap incremental path, whereas `MarkRenderStateDirty()` destroys and recreates the whole scene proxy — once per chunk slice that would be catastrophic. There is no visible zero-colour frame either, since `AddInstances` and `SetCustomData` land in the same game-thread call and the gather is deferred to end-of-frame. Passing `bMarkRenderStateDirty=true` would additionally call `Modify()` (an undo-transaction write, per generation, at millions of instances). `SetNumCustomDataFloats(3)` is called **after** `ClearInstances()`, not before — it sizes and zeroes the buffer from the *current* instance count, so calling it on a still-full component allocates a large array `ClearInstances()` immediately discards; it early-outs when unchanged, so it's free after the first call.

`FFilteredCellGridView` survives but is no longer part of the render path — its only remaining consumer is the DDA ray-pick in `CellSelection::PickCellAlongRay()`. `AdvanceChunkedRender()`/`FinishChunkedRenderImmediately()` now drive one renderer, and `PerBucketBudget = max(1, ChunkedRenderCellsPerFrame / NumBuckets)` is gone: the full `ChunkedRenderCellsPerFrame` goes to it.

**Chunked rendering multiplies total render cost — it does not merely spread a fixed amount of work.** This was measured, not reasoned: `FRenderTimings` collected six per-phase timers that nothing ever printed (`GetLastRenderTimings()` had no callers), so the parameter had only ever been tuned by watching for stutter. With the breakdown logged (`RenderTimings[chunked|oneshot|immediate]`, see `LogRenderTimings()` in `AutomataOrchestrator.cpp`), the same ~622k live cells on the flat `Instanced` component cost **35.97 ms in one `AddInstances` call, 78.63 ms across 7 (budget 100k), and 179.23 ms across 31 (budget 20k)** — a 5× penalty for the finest slicing. Each `AddInstances()` call evidently does work proportional to the instances already present, so N calls of B instances lose badly to one call of N·B. Two consequences worth keeping straight:

- **The apparent superlinearity in render cost is an artifact of chunking, not of instance count.** Cost per cell in the one-shot path is a flat ~0.058 µs and scales linearly; under chunking it climbed 0.169 → 0.440 µs/cell between 168k and 990k purely because a fixed budget means more calls as the grid grows. An earlier reading of that curve blamed HISM's LOD cluster-tree rebuild — wrong twice over, since the run was on `Instanced`, which builds no tree at all.
- **Chunking still does what it claims** (it caps the per-frame spike), but on large grids the trade is bad: one 36 ms hitch beats forty 5 ms frames totalling 200 ms. Hence `ChunkedRenderCellsPerFrame`'s default was raised 20000 → 100000 — not to encourage chunking, but so that pressing **Z** costs 2× instead of 5×. `AddInstances` is ~97% of render time either way; `CustomData` (per-instance colour) is ~1% and `Reorder` is exactly 0 under `Sequential`, so neither is worth optimizing.

Known cost characteristics (not yet profiled in this project at multi-million-cell scale, see the `CandidateBuild`/`ParallelFor`/`WriteBack` breakdown above for comparison): `CellAging::ComputeAges()` adds roughly one more full alive-cell pass per generation (order of a few percent of total step time, fully parallel, no serialized phase); the render side now has a single cell component, so the former per-material overhead (one component each, and for HISM one LOD cluster-tree rebuild each) is gone — what remains is one cluster-tree rebuild on every `ClearInstances()`+`AddInstances()` (see above) — plus 12 bytes/instance of per-instance colour upload and an O(N) `CustomDataChanged` marking loop per chunk slice (timed separately as `FRenderTimings::CustomDataSeconds`). That last one has since been measured and is a non-issue: **per-instance colour is ~1% of render time** (4.77 ms of 435 ms at 990k cells), against `AddInstances`'s ~97%. Unmeasured at multi-million-cell scale — profile before assuming.
